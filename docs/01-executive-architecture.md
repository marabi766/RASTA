# ۰۱ — Executive Architecture

> معماری اجرایی رستا در یک سند. اگر فقط یک فایل از این پوشه خوانده شود، همین باشد.

---

## ۱٫۱ مسئله معماری

سند محصول یک واقعیت را روشن می‌کند: **مسئله، کمبود ماشین‌آلات نیست.** مسئله نبود نظام
مدیریت دارایی، نبود ارتباط مستقیم کاربر با ارائه‌دهنده خدمت، و نبود مدل اقتصادی روشن است.

از این، سه الزام معماری بیرون می‌آید که همه‌چیز دیگر تابع آن است:

| الزام کسب‌وکار                                   | پیامد معماری                                                        |
| ------------------------------------------------ | ------------------------------------------------------------------- |
| دارایی باید «پرونده الکترونیکی» پایدار داشته باشد | **Asset-Centric** — دارایی Aggregate مرکزی است، نه ضمیمه‌ای بر کاربر |
| هیچ لایه واسطه اجباری میان کاربر و پلتفرم         | مدل مجوزدهی نباید زنجیره تأیید نهادی را کد کند؛ موافقت‌ها Configurable |
| ارزش اقتصادی باید اندازه‌گیری و تسویه شود         | **دفتر کل دوطرفه و تغییرناپذیر** از روز اول، نه یک ستون `balance`    |
| مسیر ۳۲۸ دهیاری → ملی → Marketplace عمومی         | **Multi-Tenant و Organization-Agnostic** از روز اول                  |
| پلتفرم مرجع حقوقی جدید نمی‌سازد                   | حکمرانی **داده پیکربندی** است، نه کد                                 |

---

## ۱٫۲ اصول حاکم

### ۱. Asset-Centric

مدل مفهومی پایه — و ترتیب آن معنادار است:

```
Organization
 └─ User / Role
     └─ Asset  ◄── موجودیت مرکزی
         ├─ Driver / Operator
         ├─ Usage
         ├─ Maintenance
         ├─ Insurance
         ├─ Orders          (کالا و خدمت مصرف‌شده روی این دارایی)
         ├─ Projects        (عملیاتی که این دارایی در آن به کار رفته)
         └─ Transactions    (اثر مالی همه موارد بالا)
```

**CONSTRAINT.** `AssetId` هویت دیجیتال پایدار دارایی است و **هرگز** به یزد، دهیاری، یا سازمان
مالک وابسته نیست. مالکیت یک **رابطه** است که تغییر می‌کند؛ هویت نیست.
یک بیل مکانیکی که از دهیاری الف به شهرداری ب منتقل می‌شود، همان `AST_01J...` را نگه می‌دارد
و کل تاریخچه‌اش همراهش می‌آید.

پیامد فنی: هیچ شناسه دامنه‌ای شامل کد استان، کد سازمان یا شمارنده محلی نیست.
شناسه‌ها **ULID با پیشوند نوع** هستند (`AST_01JBQ8...`) — مرتب‌شدنی بر حسب زمان، بدون هماهنگی
مرکزی تولیدشدنی، و خوانا در Log.

### ۲. Organization-Agnostic

سیستم نمی‌داند «دهیاری» چیست. می‌داند `Organization` چیست و `OrganizationType` دارد:

```
DEHYARI · MUNICIPALITY · UNION · COMPANY · GOVERNMENT
PRIVATE · NATIONAL_ORGANIZATION · COOPERATIVE
```

سلسله‌مراتب هم Configurable است و به‌صورت درخت با `parentOrganizationId` مدل می‌شود:

```
Country → Province → County → Municipality/Village → Organization → Unit
```

**چرا این‌قدر مهم است؟** چون سند محصول صریحاً مسیر «شهرداری‌ها → مقیاس ملی» را ترسیم می‌کند.
اگر امروز `village_id` در جدول‌ها بنشیند، فردا مهاجرت آن یک بازنویسی است، نه یک Migration.

### ۳. Multi-Tenant by Default

**CONSTRAINT.** هیچ Query‌ای بدون `organizationId` به داده نمی‌رسد. جداسازی در شش لایه:

| لایه          | مکانیزم                                                                 |
| ------------- | ----------------------------------------------------------------------- |
| API           | `org_id` از JWT استخراج و در `RequestContext` قرار می‌گیرد               |
| Application   | `TenantGuard` هر درخواست را در برابر عضویت کاربر بررسی می‌کند            |
| Database      | هر جدول مستأجرمحور ستون `organization_id` دارد؛ Repository آن را تزریق می‌کند |
| Authorization | مجوز در سطح **Object** بررسی می‌شود، نه فقط Endpoint (دفاع در برابر BOLA) |
| Cache         | هر کلید Redis با `org:{id}:` پیشوند می‌گیرد                              |
| Events        | Envelope رویداد `tenantId` دارد؛ Consumer آن را اعمال می‌کند             |

**MVP → PRODUCTION.** در MVP جداسازی در لایه Application تضمین می‌شود (Repository پایه که
Scope را اجباری می‌کند + تست جداسازی برای هر سرویس). در Production، **PostgreSQL Row-Level
Security** به‌عنوان لایه دوم دفاعی افزوده می‌شود تا یک Query فراموش‌شده هم نتواند داده لو دهد.
دلیل تعویق: RLS با Prisma نیازمند مدیریت `SET LOCAL` در هر Transaction است و در MVP
پیچیدگی بیش از فایده می‌آورد — اما ستون‌ها و Indexها از امروز طوری چیده شده‌اند که افزودن
Policy یک Migration باشد، نه بازطراحی.

### ۴. Database Ownership per Service

**CONSTRAINT.** هیچ جدول مشترکی وجود ندارد. هیچ سرویسی پایگاه داده سرویس دیگر را نمی‌خواند.

**MVP → PRODUCTION.** در MVP همه پایگاه‌های داده روی **یک Cluster PostgreSQL** اجرا می‌شوند
(۱۶ Database منطقی، هر کدام با نقش و اعتبارنامه اختصاصی). مالکیت **منطقی** از روز اول
کامل است؛ جداسازی **فیزیکی** یک تصمیم استقرار است، نه یک تصمیم معماری — و چون هیچ کدی به
Cross-Database Join وابسته نیست، جدا کردن Cluster بعداً تغییر Connection String است.

### ۵. Event-Driven با تضمین تحویل

رویدادها **هرگز** مستقیماً از Service Method منتشر نمی‌شوند. الگو **Transactional Outbox** است:

```
┌── یک Transaction پایگاه داده ─────────────┐
│  1. تغییر وضعیت Aggregate                  │
│  2. درج ردیف در جدول outbox                │
└────────────────────────────────────────────┘
                  │  (Commit)
                  ▼
        Outbox Relay (Poller)
                  ▼
              Kafka Topic
                  ▼
      Consumer (Idempotent، با کلید eventId)
```

**چرا؟** بدون Outbox، «ذخیره در DB» و «انتشار در Kafka» دو عمل غیراتمیک‌اند. یک Crash میان
آن دو یا رویداد گمشده تولید می‌کند (سفارش ثبت شد، کارمزد هرگز محاسبه نشد) یا رویداد شبح
(کارمزد محاسبه شد، سفارش Rollback شد). در یک پلتفرم مالی هیچ‌کدام قابل قبول نیست.

### ۶. Financial Integrity

**CONSTRAINT.** `Wallet ≠ Ledger`.

- **Ledger** مرجع حقیقت است: دوطرفه، تغییرناپذیر، قابل حسابرسی. اصلاح فقط با Reversal Entry.
- **Wallet** نمای عملیاتی است: موجودی در دسترس، موجودی معلق، Hold/Release.

هیچ موجودی کیف پولی بدون ورودی متناظر در دفتر کل تغییر نمی‌کند. مجموع بدهکار هر Journal
همیشه برابر مجموع بستانکار آن است — و یک تست این را در هر اجرا اثبات می‌کند.

### ۷. Configurable Governance

**CONSTRAINT (از سند محصول).** پلتفرم «هیچ اختیار یا مرجع تصمیم‌گیری تازه‌ای ایجاد نمی‌کند».

پیامد: مرجع موافقت، سطوح اختیار، ماهیت حقوقی هر فرآیند (مناقصه رسمی / استعلام / درخواست
پیشنهاد)، وزن معیارهای ارزیابی، و نرخ کارمزد — **همه داده پیکربندی‌اند**، نه کد.
Hard-Code کردن هر یک از این‌ها نقض سند محصول است.

### ۸. Security by Design

هر Endpoint پیش‌فرض بسته است. هیچ Feature‌ای «فقط برای Demo» از Auth، اعتبارسنجی،
Tenant Isolation یا Audit عبور نمی‌کند. این در `AGENTS.md` قاعده الزام‌آور است.

### انحراف‌های آگاهانه از Stack پیشنهادی اولیه

دو مورد با ثبت ADR تغییر کرده‌اند:

1. **API Gateway: NestJS به‌جای Kong/APISIX** (ADR-009).
   Gateway رستا باید کاری کند که یک Gateway عمومی نمی‌تواند: حل `activeOrganizationId`
   از عضویت‌های کاربر، و اعمال Scope مستأجر پیش از مسیریابی. پیاده‌سازی این در Plugin
   Lua/Go برای Kong، منطق دامنه را به لایه زیرساخت می‌برد — جایی که تست و نگهداری‌اش سخت است.
   **مسیر Production:** Kong/APISIX به‌عنوان **Edge Gateway** (TLS، WAF، Rate Limit سراسری)
   جلوی این Gateway می‌نشیند؛ دو نقش مکمل، نه رقیب.

2. **wallet/ledger/payment/commission/reward → یک `economic-service`** (ADR-013).
   این پنج، یک مرز تراکنشی مشترک دارند: یک سفارش تکمیل‌شده باید در **یک تراکنش** کیف پول را
   کاهش دهد، ورودی دفتر کل بزند و کارمزد را ثبت کند. تقسیم آن‌ها به پنج سرویس یعنی جایگزینی
   یک تراکنش ACID با یک Saga پنج‌مرحله‌ای — پیچیدگی و ریسک ناسازگاری مالی، بدون فایده مقیاس‌پذیری.
   داخل سرویس، پنج ماژول با Schema و Topic جدا هستند؛ استخراج `ledger` (نخستین نامزد)
   یک تغییر مسیریابی است، نه بازنویسی.

## ۱٫۵ سه منطق اقتصادی در معماری

سند محصول سه مسیر ایجاد ارزش تعریف می‌کند. هر سه باید **قابل محاسبه از داده واقعی** باشند،
نه ادعای گزارشی:

| منطق                | منبع داده معماری                                                     | سرویس مسئول محاسبه       |
| ------------------- | -------------------------------------------------------------------- | ------------------------ |
| **کاهش هزینه**      | قیمت واحد خرید در برابر خط مبنا؛ اثر تجمیع تقاضا                     | `analytics` از رویدادهای `procurement` + `marketplace` |
| **اجتناب از هزینه** | نسبت تعمیر پیشگیرانه به اضطراری؛ توقف اجتناب‌شده                     | `analytics` از رویدادهای `maintenance` |
| **افزایش درآمد**    | مجموع کارمزد تراکنش‌های تکمیل‌شده                                    | `economic` (Commission Ledger) |

**ASSUMPTION.** سند محصول تصریح می‌کند اندازه‌گیری کمی این‌ها مشروط به **ایجاد خط مبنا در
سال نخست** است. معماری، **ثبت و محاسبه** را فراهم می‌کند؛ **ادعای عدد** نمی‌کند. جدول
`baseline_metric` در `analytics-service` از روز اول وجود دارد و تا پر نشدن، KPIهای وابسته
با وضعیت `INSUFFICIENT_BASELINE` برگردانده می‌شوند — نه با صفر و نه با تخمین.

| مورد                          | وضعیت                                                                 |

| اتصال بانکی / درگاه پرداخت    | **ساخته نمی‌شود.** `MockPaymentProvider` پشت `PaymentProvider` Interface |
| نگهداری واقعی وجوه            | **ساخته نمی‌شود.** مشروط به الزامات بانکی و مقرراتی (سند محصول)         |
| IoT / Telematics              | فاز ۳. مدل داده `UsageRecord` منبع را ثبت می‌کند تا ورود خودکار بعداً ممکن باشد |

| امضای دیجیتال قراردادها        | فاز ۲. **OPEN QUESTION** — نیازمند تعیین مرجع گواهی                     |
| مناقصه رسمی با اثر حقوقی      | **CONSTRAINT.** پلتفرم ابزار دیجیتالی‌سازی است؛ ماهیت حقوقی را کارفرما تعیین می‌کند |

## ۱٫۷ نقشه تصمیم‌های بنیادین

| تصمیم                                       | جایگزین رد شده                        | دلیل رد                                                        |
| ------------------------------------------- | -------------------------------------- | -------------------------------------------------------------- |
| Microservices از روز اول                    | Modular Monolith، تقسیم بعدی           | مرز داده‌ای در Monolith عملاً هرگز رعایت نمی‌شود؛ اصلاح بعدی گران‌تر است |
| ۱۶ سرویس (نه ۲۲)                            | یک سرویس به‌ازای هر Domain سند اولیه   | Over-Engineering؛ سرویس‌های با مرز تراکنشی مشترک ادغام شده‌اند   |
| Transactional Outbox                        | انتشار مستقیم از Service               | تضمین اتمیک بودن تغییر وضعیت و انتشار رویداد                     |
| دفتر کل دوطرفه از MVP                       | ستون `balance` ساده، دفتر کل بعداً     | مهاجرت داده مالی موجود به دفتر کل، عملاً غیرممکن است             |
| ULID با پیشوند                              | UUIDv4، شمارنده صحیح                   | ULID مرتب‌شدنی است (Index بهتر) و پیشوند در Log خوانا است        |
| `bigint` در واحد فرعی                       | `decimal`، `float`                     | `float` برای پول اشتباه است؛ `bigint` سریع‌تر و دقیق است         |
| Prisma به‌ازای هر سرویس                     | TypeORM، یک Schema مشترک               | Schema مشترک همان Shared Database است با ظاهر دیگر              |
