# ۰۶ — API Architecture

> API-First. قرارداد پیش از پیاده‌سازی نوشته می‌شود، و پیاده‌سازی در برابر قرارداد تست می‌شود.

---

## ۶٫۱ اصول

| اصل                     | معنا                                                               |
| ----------------------- | ------------------------------------------------------------------ |
| **Contract First**      | OpenAPI پیش از کد؛ Schemaها از `@rasta/contracts` می‌آیند          |
| **Uniform**             | همه سرویس‌ها یک قرارداد دارند: صفحه‌بندی، خطا، فیلتر، Header       |
| **Closed by Default**   | هر Endpoint نیازمند احراز هویت است مگر با `@Public()` صریح و مستند |
| **Explicit Versioning** | نسخه در مسیر (`/v1/...`)؛ تغییر شکننده = نسخه جدید                 |
| **Idempotent Writes**   | هر عمل غیر ایمن با اثر جانبی، `Idempotency-Key` می‌پذیرد           |
| **Traceable**           | هر پاسخ `X-Correlation-Id` و `X-Trace-Id` برمی‌گرداند              |

## ۶٫۲ توپولوژی

```
Client (web/admin/PWA)
   │  HTTPS + Bearer JWT
   ▼
API Gateway  :3000     ◄── تنها نقطه ورود بیرونی
   │  • اعتبارسنجی JWT با JWKS
   │  • حل activeOrganizationId از عضویت
   │  • RBAC سطح مسیر
   │  • Rate Limit (به‌ازای مستأجر و به‌ازای کاربر)
   │  • CORS · Secure Headers
   │  • تولید/انتشار Correlation ID
   │  • Cache پاسخ Idempotency
   │  • Circuit Breaker
   ▼
Domain Services  :31xx    ◄── فقط از شبکه داخلی؛ NetworkPolicy می‌بندد
   • توکن داخلی سرویس‌به‌سرویس را اعتبارسنجی می‌کنند
   • هرگز مستقیم از اینترنت در دسترس نیستند
```

**مسیر عمومی:** `https://api.rasta.example/v1/assets`
**مسیر داخلی:** `http://asset-service:3103/internal/v1/assets` (نیازمند توکن داخلی)

## ۶٫۳ قرارداد Header

### درخواست

| Header              | الزام            | شرح                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| ------------------- | ---------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `Authorization`     | اجباری           | `Bearer <JWT>`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `X-Correlation-Id`  | اختیاری          | اگر نیاید، Gateway ULID تولید می‌کند. از فراخوان بیرونی (توکن کاربر — مستقیم یا از راه Gateway —، درخواست ناشناس، relay) فقط دقیقاً شناسه‌ای پذیرفته می‌شود که پلتفرم می‌سازد: یک ULID یا یک UUID تنها، بی هیچ برچسبی پیش یا پس از آن. فراخوان سرویس‌به‌سرویس احرازشده (توکن داخلی `SERVICE` بدون Bearer) شناسهٔ خود را نگه می‌دارد اگر حداکثر ۱۲۸ نویسه و از `[A-Za-z0-9_.:-]` باشد، تا زنجیرهٔ پیش از این قاعده (مثل `corr-1` سفارشی که Temporal از سر می‌گیرد) نشکند. هر مقدار دیگر نادیده گرفته می‌شود، ULID تازه جایش می‌نشیند و خودش در Log نمی‌آید (S-09) |
| `X-Organization-Id` | شرطی             | برای کاربر چندعضویتی، انتخاب مستأجر فعال؛ **در برابر عضویت اعتبارسنجی می‌شود**                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   |
| `Idempotency-Key`   | اجباری برای بعضی | روی `POST` مالی و عملیات ایجادکننده اثر بیرونی؛ اجباری در سرویس روی `POST /v1/assets` (#169) و روی `POST /v1/assets/{id}/insurance-policies` و `POST /v1/assets/{id}/inspections` (EXP-002، برش ۶)؛ اختیاری و رعایت‌شده روی `POST /v1/maintenance-requests` (#157)                                                                                                                                                                                                                                                                                               |
| `If-Match`          | اختیاری          | ETag برای قفل خوش‌بینانه در `PATCH`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              |
| `Accept-Language`   | اختیاری          | `fa-IR` (پیش‌فرض) یا `en`                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                        |

**`Idempotency-Key` روی `POST /v1/maintenance-requests`** ([#157](https://github.com/marabi766/RASTA/issues/157)): اختیاری؛
اگر بیاید، maintenance-service رعایتش می‌کند — همان کلید و همان بدنه از همان کاربر، `201` اصلی را بازپخش می‌کند و کار را
دوباره ثبت نمی‌کند (حتی اگر درخواست اول از آن پس بسته شده باشد)، بدنهٔ دیگر یا کاربر دیگر `409 IDEMPOTENCY_KEY_REUSED`، و
درخواست هم‌زمان با همان کلید تا ۵ ثانیه منتظر می‌ماند و همان `201` را می‌گیرد — اگر درخواست اول بیش از این طول بکشد،
تکراری `409 CONFLICT` با `Retry-After: 1` می‌گیرد (نه خطای فرم: پورتال آن را «در حال پردازش است، کمی بعد دوباره ببینید»
نشان می‌دهد و همان ارسال را پس از انتظار دوباره پیشنهاد می‌کند، که پاسخ درخواست اول را می‌گیرد). بررسی Claim، ثبت درخواست،
Outbox و ذخیرهٔ پاسخ **یک تراکنش‌اند** (دور ۱ بازبینی #171): ایجادی که Claim آن منقضی و دوباره گرفته شده، چیزی Commit
نمی‌کند، و شکست ذخیرهٔ پاسخ چیزی نیمه‌کاره نمی‌گذارد. برداشتن Claim منقضی‌ای که درخواستی هنوز قفلش را نگه داشته هم
بیش از همان ۵ ثانیه منتظر نمی‌ماند: پس از آن `409 CONFLICT` با `Retry-After: 1` (#194). Hash درخواست هر کلید بدنه را، هر
نامی داشته باشد (حتی `__proto__`)، دربر می‌گیرد. کلیدها مال مستأجرند (همان کلید در دو سازمان، دو درخواست) و
`MAINTENANCE_IDEMPOTENCY_TTL_HOURS` (پیش‌فرض ۲۴) از لحظهٔ پاسخ نگه داشته می‌شوند. بی کلید، رفتار پیشین.

**`Idempotency-Key` روی `POST /v1/assets`** ([#169](https://github.com/marabi766/RASTA/issues/169)): **اجباری، در خودِ
asset-service** — نه فقط در Gateway، که برای پیشوند `assets` کلید نمی‌خواهد. نبودن یا خالی بودنش `400 VALIDATION_FAILED`
با `code: required`، و کلید خارج از ۸ تا ۲۵۵ نویسه همان ۴۰۰ با `code: invalid` است؛ در هر دو هیچ چیز ثبت نمی‌شود. نقش
فراخوان (`ORGANIZATION_ADMIN`، `FLEET_MANAGER`، `UNION_ADMIN`) **پیش از هر بازپخش** بررسی می‌شود. Hash درخواست، بدنه و
کاربر را با هم می‌بندد: همان کلید + همان بدنه از همان کاربر = همان `201` اول (همان شناسهٔ دارایی) بی هیچ دارایی یا
رویداد `ASSET_CREATED` تازه؛ بدنهٔ دیگر یا کاربر دیگر = `409 IDEMPOTENCY_KEY_REUSED` بی هیچ اثری از پاسخ ذخیره‌شده؛
تکراری هم‌زمان روی قفل ردیف Claim درخواست اول منتظر می‌ماند (حداکثر ۵ ثانیه) و همان `201` را می‌گیرد، وگرنه `409 CONFLICT`
با `Retry-After: 1`؛ هر انتظار سمت Claim — از جمله برداشتن Claim اجاره‌گذشته‌ای که صاحبش هنوز قفلش را دارد — به باقی‌ماندهٔ همین ۵ ثانیه محدود است. **رزرو کلید (Claim) پیش از کار، در تراکنش کوتاه خودش Commit می‌شود**؛ سپس تراکنش کار، ردیف Claim را با توکنش قفل می‌کند و **پاسخ تکمیل‌شده همراه با خود دارایی و ردیف Outbox در همان یک تراکنش Commit می‌شود** — یا هیچ‌کدام. هر Claim توکن حصار خودش را دارد. Claim «در
جریان» یک اجارهٔ کوتاه است (`ASSET_IDEMPOTENCY_CLAIM_LEASE_SECONDS`، پیش‌فرض ۱۲۰، ۳۰ تا ۳۶۰۰، در راه‌اندازی اعتبارسنجی
می‌شود) و پاسخ تکمیل‌شده `ASSET_IDEMPOTENCY_TTL_HOURS` (پیش‌فرض ۲۴، ۱ تا ۱۶۸) نگه داشته می‌شود: پس از اجاره، تلاش مجدد
Claim رهاشده را با توکن تازه برمی‌دارد و تکمیل دیرهنگام صاحب قبلی با توکن رد می‌شود. کلیدها مال مستأجرند (`organization_id`
ستون نخست کلید اصلی): مستأجر B کلید مستأجر A را بازپخش نمی‌کند، دارایی خودش را ثبت می‌کند.

**`Idempotency-Key` روی `POST /v1/assets/{id}/insurance-policies`، `POST /v1/assets/{id}/inspections` و `POST /v1/assets/{id}/documents`** (EXP-002، برش ۶ و ۷؛ سومی بازپخش «ارجاع مدرک» است نه خودِ فایل — فایل هرگز از asset-service نمی‌گذرد):
**اجباری، در خودِ asset-service**، با **همان سازوکار** `POST /v1/assets` (`IdempotencyStore`؛ سازوکار دومی نیست؛ برای مدرک، همان ارجاع `documentId` + `kind` + عنوان است که در Hash می‌آید، پس همان کلید با `documentId` دیگر `409 IDEMPOTENCY_KEY_REUSED` است) — نبودن یا
خالی بودن یا خارج از ۸ تا ۲۵۵ نویسه `400 VALIDATION_FAILED` با مسیر جزئیات `Idempotency-Key` و هیچ چیز ثبت نمی‌شود. نقش
فراخوان (`ORGANIZATION_ADMIN`، `FLEET_MANAGER`، `UNION_ADMIN`) پیش از هر بازپخش بررسی می‌شود. Hash درخواست **شناسهٔ دارایی
مسیر**، بدنه و کاربر را می‌بندد: همان کلید + همان بدنه + همان دارایی + همان کاربر = همان `201` اول (همان شناسهٔ رکورد) بی
هیچ ردیف، رویداد (`INSURANCE_RECORDED` / `INSPECTION_RECORDED` / `ASSET_DOCUMENT_ATTACHED`) یا ورودی تاریخچهٔ تازه؛ بدنهٔ دیگر، دارایی دیگر یا کاربر
دیگر = `409 IDEMPOTENCY_KEY_REUSED`؛ تکراری هم‌زمان تا ۵ ثانیه منتظر می‌ماند و همان `201` را می‌گیرد، وگرنه `409 CONFLICT` با
`Retry-After: 1`. Claim پیش از کار Commit می‌شود؛ سپس **رکورد، ردیف Outbox، ورودی تاریخچه و پاسخ تکمیل‌شده یک تراکنش‌اند**
(Claim را نخستین دستور تراکنش قفل می‌کند و پاسخ آخرین دستور آن است). کلیدها مال مستأجرند. پاسخ‌های رد‌شده (۴۰۴، ۴۲۲، ۴۰۹
یکتایی) Claim را آزاد می‌کنند تا ارسال اصلاح‌شده با همان کلید اجرا شود. دارایی مستأجر دیگر برای خواندن و هر دو نوشتن `404`
است، دقیقاً مثل شناسهٔ ناموجود. پورتال شناسهٔ ارسال بسته به نشست را همان کلید می‌فرستد (docs/16).

**بازپخش در asset-service دوباره مجوز می‌گیرد** (بازبینی #206 دور ۱؛ هر چهار مسیر بالا، `POST /v1/assets` هم): پیش از
بازگرداندن هر پاسخ تکمیل‌شده، `IdempotencyStore` بررسی «هنوز می‌تواند ببیند»ِ همان مسیر (`ReplayGuard`) را اجرا می‌کند —
همان قاعدهٔ خواندن تازه، با وضعیت امروز: دارایی هنوز مال سازمان فراخوان است. دارایی‌ای که در عمر کلید به سازمان دیگری
منتقل شده، برای بازپخش همان کاربر `404 NOT_FOUND` است، دقیقاً مثل دارایی ناموجود، بی هیچ چیز از بدنهٔ ذخیره‌شده و بی هیچ
نوشتن یا رویداد؛ بازپخش درون همان مستأجر همان `201` ذخیره‌شده است.

**پیوست مدرک، مالکیت سند را از document-service می‌پرسد** (بازبینی #225 دور ۱): پیش از نوشتن ارجاع، asset-service
`GET /v1/documents/{id}` را با توکن سرویس و سازمان **دارایی** می‌خواند (`DOCUMENT_SERVICE_URL`،
`ASSET_DOCUMENT_LOOKUP_TIMEOUT_MS` پیش‌فرض ۳۰۰۰). سندی که نیست، مال سازمان دیگر است، حذف‌شده است یا برای دارایی دیگری ثبت
شده، همان `404 NOT_FOUND`ِ سند ناموجود است (بی نشانه‌ای که این‌ها را از هم جدا کند) و Claim آزاد می‌شود؛ document-service
در دسترس نباشد یا پاسخش خوانا نباشد `503` است (بسته‌بسته، Claim آزاد، هیچ ارجاع تأییدنشده‌ای نوشته نمی‌شود). **انتقال
دارایی:** ارجاع‌ها همراه دارایی به سازمان جدید می‌روند، ولی document-service مالک سند را همان سازمان قبلی نگه می‌دارد؛ پس
پیوست تازهٔ همان سند از سوی مالک جدید `404` می‌شود. این رفتار موجود است و این‌جا بازطراحی نشده.

**`Idempotency-Key` روی `POST /v1/fleet/availability`** (EXP-002، برش ۷): **اجباری، در خودِ fleet-service**، با نسخهٔ محلیِ همان
سازوکار (`IdempotencyStore`؛ جدول `idempotency_key` با Migration قابل بازگشت `20261005120000_fleet_availability_idempotency`؛
`FLEET_IDEMPOTENCY_TTL_HOURS` پیش‌فرض ۲۴ و `FLEET_IDEMPOTENCY_CLAIM_LEASE_SECONDS` پیش‌فرض ۱۲۰). دلیل: هر اعلام، اعلامِ پیشینِ
همان دارایی را **جایگزین** می‌کند، پس ارسال دوبارهٔ یک درخواست قدیمی (پاسخ گمشده، تلاش مجدد مرورگر) می‌توانست اعلامِ تازه‌تر را
بی‌صدا باطل کند. Hash درخواست بدنه (شامل `assetId`) و کاربر را می‌بندد؛ بازپخش همان `201` اول است (همان شناسهٔ پنجره، بی رویداد
`AVAILABILITY_CHANGED` تازه) و **اعلام تازه‌تر را جایگزین نمی‌کند**؛ بدنه/کاربر دیگر `409 IDEMPOTENCY_KEY_REUSED`؛ نبودن یا
نامعتبر بودن کلید `400`. بازپخش پیش از پاسخ دوباره مجوز می‌گیرد (`ReplayGuard`: دارایی هنوز مال سازمان فراخوان است، وگرنه
`404` مثل دارایی ناموجود). **ابطال کلید ندارد**: وضعیت‌محور است و بازپخش آن `409 INVALID_STATE_TRANSITION` («پیش‌تر باطل شده») است نه
اثر دوم. دارایی/پنجرهٔ مستأجر دیگر برای هر چهار مسیر (اعلام، فهرست، ابطال، بازپخش) `404` یکسان با ناموجود است.

**یک اعلام زنده برای هر دارایی** (بازبینی #225 دور ۱): اعلام‌ها در تراکنش با قفل همان دارایی (`lockAssetRef`، قفلی که مصرف‌کنندهٔ
`ASSET_TRANSFERRED` هم می‌گیرد) پشت‌سرهم اجرا می‌شوند و مالک دارایی زیر همان قفل دوباره خوانده می‌شود؛ پایگاه داده هم با
ایندکس یکتای جزئی و مستأجر-پیش `ux_availability_window_live` (`organization_id, asset_id` وقتی `revoked_at IS NULL`؛ Migration
`20261005130000_availability_window_one_live`، با رد پیش‌بررسی اگر دادهٔ موجود دو اعلام زنده دارد) دومی را می‌پذیرد نه.
**انتقال دارایی:** وقتی fleet رویداد `ASSET_TRANSFERRED` را اعمال می‌کند، هر اعلام زندهٔ سازمان قبلی که در `transferredAt` یا
پس از آن ثبت شده با `revoked_by = SYSTEM` و `revoke_reason = ASSET_TRANSFERRED` باطل و با `AVAILABILITY_CHANGED` (زیر مستأجر
قبلی، علت = رویداد انتقال) اعلام می‌شود؛ پس از آن، اعلام و بازپخش سازمان قبلی `404` است. **باقیماندهٔ شناخته‌شده:** میان
Commit انتقال در asset-service و اعمال رویداد در fleet، رونوشت هنوز مالک قبلی را نشان می‌دهد؛ اعلام یا بازپخش ذخیره‌شدهٔ او
در این فاصله پذیرفته می‌شود (fleet وابستگی همگام به asset-service ندارد) و با اعمال رویداد باطل می‌شود. اعلام زودتر از
`transferredAt` همچنان در تاریخچهٔ سازمان قبلی است و مالک جدید هرگز آن را نمی‌بیند. اختلاف ساعت دو سرویس، مرز را به همان
اندازه جابه‌جا می‌کند.

**CONSTRAINT.** `X-Organization-Id` **هرگز** بدون بررسی پذیرفته نمی‌شود، و این
روی هر دو مسیر صادق است:

- **توکن کاربر** — Gateway و سرویس بررسی می‌کنند کاربر عضویت فعال در آن سازمان
  دارد، وگرنه `TENANT_MISMATCH` (۴۰۳) — ADR-011.
- **توکن سرویس** — Header باید با Claim امضاشده `org_id` برابر باشد، وگرنه
  `SERVICE_TENANT_CONTEXT_INVALID` (۴۰۳) — ADR-035، § ۶٫۱۲.

این نقطه دقیقاً همان جایی است که یک اشتباه به Tenant Escape تبدیل می‌شود.

## ۶٫۴ Versioning

| نوع تغییر                    | شکننده؟ | اقدام                                                                 |
| ---------------------------- | ------- | --------------------------------------------------------------------- |
| افزودن فیلد اختیاری به پاسخ  | ❌      | همان نسخه                                                             |
| افزودن Endpoint جدید         | ❌      | همان نسخه                                                             |
| افزودن پارامتر Query اختیاری | ❌      | همان نسخه                                                             |

## ۶٫۵ صفحه‌بندی

**پیش‌فرض: صفحه‌بندی مبتنی بر Cursor.**

```http
GET /v1/assets?limit=25&cursor=eyJpZCI6IkFTVF8wMUpCUTh...
```

```json
{
  "items": [ ... ],
  "nextCursor": "eyJpZCI6IkFTVF8wMUpCUTla...",
  "hasMore": true
}
```

**چرا Cursor و نه Offset؟** با Offset، اگر بین دو صفحه رکوردی درج یا حذف شود، ردیف‌ها
جا می‌افتند یا تکرار می‌شوند. برای فهرست ورودی‌های دفتر کل یا سوابق حسابرسی این پذیرفتنی نیست.

**استثنا: Offset فقط جایی که تعداد کل خودش هدف است** (جدول‌های مدیریتی، داشبورد):

```http
GET /v1/orders?page=2&pageSize=50
```

```json
{ "items": [...], "page": 2, "pageSize": 50, "totalItems": 1247, "totalPages": 25 }
```

`limit` پیش‌فرض ۲۵، حداکثر ۲۰۰. مقدار بالاتر → `VALIDATION_FAILED`، نه بریدن بی‌صدا.

**Cursor فقط ردیفی از همان فهرست است.** سرویس پیش از صفحه‌بندی، Cursor را با **همان**
دامنهٔ فهرست درخواست‌شده پیدا می‌کند — همان مستأجر، همان فیلتر طرف معامله، همان نما — و
صفحه را به‌صورت Keyset از `(زمان، id)` همان ردیف می‌خواند. Cursorی که ردیف این فهرست
نیست — وجود ندارد، مال سازمان دیگری است، یا ردیف خود فراخوان از نمای دیگر است (پرداختی
در برابر دریافتی، حساب دیگر) — در هر سه حالت **یک پاسخ یکسان** می‌گیرد:
`400 VALIDATION_FAILED` با `details: [{ path: "cursor", message: "cursor is not a row of this list" }]`،
بی‌آنکه مقدار ارسالی در پیام یا جزئیات بازتاب یابد. سپردن خام Cursor به `cursor: { id }`
در Prisma ممنوع است: Prisma ردیف Cursor را با زیرپرسشی پیدا می‌کند که نه `where` فهرست
به آن می‌رسد و نه Tenant Guard، پس پاسخ فهرست (ردیف‌های قدیمی‌تر یا هیچ) وجود ردیفِ
مستأجر دیگر را فاش می‌کرد، درحالی‌که `GET /{id}` همان ردیف را پشت ۴۰۴ یکسان پنهان
می‌کند (بازبینی Codex روی PR #249). فیلترهای باریک‌کننده مثل `status` شرط Cursor
نیستند، چون وضعیت ردیف میان دو صفحه عوض می‌شود. پیاده‌سازی مرجع:
`services/economic-service/src/shared/cursor.ts`.

## ۶٫۶ فیلتر و مرتب‌سازی

```http
GET /v1/assets
    ?status=ACTIVE,IDLE                 # چندمقداری با کاما
    &assetType=EXCAVATOR
    &createdAt[gte]=2026-01-01T00:00:00Z
    &createdAt[lt]=2026-07-01T00:00:00Z
    &q=گریدر                             # جست‌وجوی متن آزاد
    &sortBy=createdAt&sortDir=desc
```

عملگرها: `[eq] [ne] [gt] [gte] [lt] [lte] [in] [contains]`

**CONSTRAINT.** `sortBy` فقط فیلدهای **Index‌شده** را می‌پذیرد. فهرست مجاز به‌ازای هر
Endpoint در Schema اعلام می‌شود. مرتب‌سازی آزاد روی ستون بدون Index، یک بردار DoS است.

## ۶٫۷ مدل خطا

**یک شکل، در همه سرویس‌ها:**

```json
{
  "code": "VALIDATION_FAILED",
  "message": "درخواست معتبر نیست.",
  "details": [{ "path": "items[0].quantity", "message": "باید بزرگ‌تر از صفر باشد", "code": "min" }],
  "correlationId": "01JBQ8Z4K7M2N5P8R1T3V6X9Y2",
  "traceId": "4bf92f3577b34da6a3ce929d0e0e4736",
  "timestamp": "2026-08-26T10:15:30.123Z",
  "path": "/v1/orders"
}
```

**قاعده.** کلاینت روی `code` شاخه می‌زند، نه روی `message` (بومی‌سازی‌شده و متغیر) و
نه صرفاً روی کد وضعیت HTTP (بیش از حد درشت).

**S-09 در پاسخ خطا.** `details` فقط واقعیت‌های Schema را دارد، نه ورودی کاربر (`ZodValidationPipe`، `toErrorDetails`):
پیام `invalid_enum_value` فقط گزینه‌های مجاز را می‌گوید (بی «received»)، `unrecognized_keys` فقط تعداد کلیدهای اضافه را، و
بخشی از `path` که کلاینت انتخاب کرده (کلید `z.record` یا `.catchall()`) `*` می‌شود. پیام نوشتهٔ Schema (`refine`،
`errorMap`، پیام Regex) باید متن ثابت باشد: **نویسندهٔ Schema هرگز مقدار ورودی را در پیام سفارشی نمی‌گذارد** — نه با
`refine((v) => ({ message: … }))`، نه با `ctx.data` در `errorMap`، نه با `addIssue` در `superRefine`. پشتیبان فقط تکرار مقدارِ زیر
مسیر همان Issue را، از سه نویسه به بالا، می‌گیرد و پیام را با پیام ثابت همان کد عوض می‌کند؛ مقدار میدان دیگر یا ورودی کوتاه‌تر را
نمی‌گیرد. پاسخ هر 5xx پیام عمومی است — پیام خطای ناشناخته، `HttpException` 5xx یا `RastaError` با وضعیت ۵۰۰ به بالا (وضعیت و
`code` می‌مانند) هرگز به کلاینت نمی‌رسد، مگر با انتخاب صریح `RastaError.internalClientSafe` برای جمله‌ای ثابت و بی‌ورودی که
کلاینت برای اقدام لازم دارد (مثلاً «امن است دوباره بفرستی»)؛ این انتخاب از پرچم خوانده می‌شود، هرگز از محتوای پیام — و آن پیام
فقط در Log
سرور، پاک‌سازی‌شده و حداکثر ۲۰۰ نویسه (`safeLogText`) ثبت می‌شود. درخواستی که Nest نتواند بخواند (بدنهٔ JSON نامعتبر، کدگذاری
درصدی نادرست در مسیر) `400 VALIDATION_FAILED` با متن ثابت می‌گیرد («The request body is not valid JSON» یا «The request could
not be read»)؛ متن Parser که بایت‌های کلاینت را نقل می‌کند نه به پاسخ می‌رسد نه به Log.

**`path` فقط مسیر است.** `path` پاکت خطا و `path` خط Log همان خطا مسیر درخواست‌اند **بی Query و بی Fragment**
(`/v1/x?cursor=…` ← `/v1/x`)؛ مقدار Query دادهٔ کلاینت است (Cursor، عبارت جست‌وجو) و S-09 بازتابش را در پیام خطا و Log
نمی‌پذیرد. `RequestContextMiddleware` همین را در زمینهٔ درخواست ثبت می‌کند (`requestPath`) و `AllExceptionsFilter` دوباره
اعمالش می‌کند. پاسخ 404 خود Nest برای مسیری که Route ندارد همان شکل `Cannot <METHOD> <path>` را دارد — کلاینت‌ها 404 مسیر
را از 404 رکورد با همین متن جدا می‌کنند — اما متن Nest نگه داشته نمی‌شود: Filter آن را از Method و `requestPath` خود درخواست
از نو می‌سازد، پس Query با هر شکل Method (`M-SEARCH`) یا Target نمی‌ماند. Gateway خطای 4xx و 5xx Upstream را **بازسازی**
می‌کند، نه عبور: فقط میدان‌های پاکت پلتفرم (`code`، `message`، `details[].{path,message,code}`، `correlationId`، `traceId`،
`timestamp`، `path`) می‌روند و هر میدان دیگر (`url`، `error.path`، `stack`) می‌افتد؛ `path` کوتاه می‌شود و متن 404 مسیر از
Method و مسیر درخواست Forwardشده از نو نوشته می‌شود. بدنهٔ 4xxی که پاکت پلتفرم نیست (HTML، متن، JSON ناقص یا شکل دیگر، خالی)
با پاکتی ثابت جایگزین می‌شود («The request was refused»، `code` از Status) و فقط شکلش (Status، Content-Type، طول) Log
می‌شود. مسیریابی و خود Query دست نمی‌خورند: Query بی‌تغییر به سرویس مالک می‌رسد.

**Span ردیابی هم Query ندارد.** Instrumentationهای HTTP، چه ورودی چه خروجی (`http`، undici یعنی `fetch`، NestJS)، Query را در
`url.query` و درون `url.full` ثبت می‌کنند. Query دادهٔ کلاینت است (Cursor، عبارت جست‌وجو، توکن در URL بازگشت) و S-09 رسیدنش به
Backend ردیابی را هم نمی‌پذیرد. `RedactingSpanProcessor` در `initTelemetry` (`@rasta/observability`) هنگام نوشتن هر مقدار،
`url.full`، `http.url` و `http.target` را تا پیش از `?` یا `#` کوتاه می‌کند، گذرواژهٔ user-info آن‌ها را برمی‌دارد و آن‌ها را
هم به همان سقف زیر می‌برد، و `url.query` را برمی‌دارد. Instrumentationها
خطا را هم ثبت می‌کنند و متن خطا همان را تکرار می‌کند — Parser JSON در Express بدنهٔ ردشده را نقل می‌کند — پس هر رشتهٔ دیگر
Span هم پاک‌سازی می‌شود: Attributeها، Attributeهای هر Event (`exception.message`، `exception.stacktrace`) و هر Link، و پیام
Status. در متن، هر جا URL یا مسیری (`scheme://…` یا `/…`) باشد، همه‌چیز از نخستین `?` یا `#` تا نخستین فاصلهٔ سفید یا پایان
متن به `?[REDACTED]` یا `#[REDACTED]` بدل می‌شود. نویسه‌های خود Query خوانده نمی‌شوند: آپستروف، گیومه، کروشه یا هر خط دیگری
پایان Query حساب نمی‌شود، و پاک‌کردن بیش از اندازه بر نشت ترجیح دارد. Query بی‌مسیر هم همین‌طور است: `?` چسبیده به واژه
(`cb?…`) یا `?` با `=`/`&` در ادامه. `?`ای که پس از آن فاصله یا پایان متن می‌آید (پرسش در نثر، Placeholder در SQL) دست
نمی‌خورد. منبع نقل‌شده در خطای `JSON.parse` به `"[REDACTED]"` بدل می‌شود، هر چند خط که باشد (با هر نویسهٔ پایان خط)، و
تا آخرین `is not valid JSON` یکجا. اعتبارنامه‌هایی هم که `scrubMessage` در `@rasta/logging` از Log می‌گیرد گرفته می‌شوند:
گذرواژه در `scheme://user:password@` و توکن `Bearer`/`Basic`. این دو در متن دست‌نخورده پیدا می‌شوند، پیش از آنکه قاعدهٔ JSON یا
Query نشانه‌شان (`@`، واژهٔ `Bearer`) را ببرد، و هر چه هر قاعده بگیرد گرفته می‌شود. این پاک‌سازی برای هر Span، نمونه‌برداری‌شده یا نه، و پیش از هر احراز هویتی روی سرصفحه‌های
درخواست اجرا می‌شود؛ پس همهٔ قاعده‌ها پیمایش خطی‌اند (`indexOf` و پیمایش رو به جلو، بی هیچ عبارت باقاعده‌ای که Backtrack
کند یا به عقب بنگرد) و متنی بلندتر از ۴۰۹۶ نویسه (`REDACT_TEXT_MAX`) پیش از پاک‌سازی به همین اندازه بریده و با
`…[TRUNCATED]` نشان‌دار می‌شود. در متن بریده، هر قاعده در محل برش بسته عمل می‌کند: از نخستین گیومه همه‌چیز می‌رود، چون
پایان `is not valid JSON` ممکن است پس از برش بوده باشد، و هر `?` در آخرین تکهٔ بی‌فاصله Query حساب می‌شود، چون `=` یا `&`
آن ممکن است بریده شده باشد، و `://`ای که user-infoاش تا محل برش ادامه دارد (بی `@`، `/` یا فاصله) از پس از `://` تا برش
گرفته می‌شود، چون `@` آن ممکن است پس از برش بوده باشد (توکن `Bearer` تا هر جا که آمده باشد گرفته می‌شود). سقف بر خواندن است؛
نوشته کمی بزرگ‌تر می‌شود، چون جایگزین می‌تواند از آنچه جایش می‌نشیند بلندتر باشد (`?=` ← `?[REDACTED]`). متن آزاد `key=value`
بی `?` (مثل DSN به شکل `host=… password=…`) را هیچ‌یک از این قاعده‌ها، و نه `scrubMessage`، در هیچ طولی نمی‌شناسد. پاک‌سازی هنگام نوشتن هر مقدار در Span است، **پیش از** آنکه SDK آن را به
`attributeValueLengthLimit` کوتاه کند، زیرا کوتاه‌شدن ممکن است همان پایان `is not valid JSON` را ببرد و بدنه را نگه دارد.
Attributeها و Linkهایی که Span با آن‌ها آغاز می‌شود را SDK پیش از هر Span Processor ذخیره و کوتاه می‌کند. این‌ها از سرصفحه‌های
درخواست می‌آیند: `server.address` (از `Host`/`Forwarded`/`X-Forwarded-Host`)، `client.address` (از
`X-Forwarded-For`/`Forwarded`)، `url.path` و `url.full` در Span ‏NestJS. پس `RedactingSampler` آن‌ها را در `shouldSample` پاک
می‌کند، که SDK پیش از ساختن Span صدا می‌زند، و تصمیم نمونه‌برداری همچنان با `RastaSampler` است. `User-Agent`
(`user_agent.original`) اصلاً ثبت نمی‌شود: متن آزاد کلاینت است تا سقف ۱۶ کیلوبایت سرصفحه، و ردیابی چیزی از آن لازم ندارد.
نام Span، نام Event، `url.path` و `http.route` (الگوی Route) دست نمی‌خورند. انتخاب Exporter همان است که بود: پردازشگرهای صادرکننده را همان دو
تابعی می‌سازند که `NodeSDK` خودش می‌خواند (`OTEL_TRACES_EXPORTER`، پروتکل OTLP، `OTEL_BSP_*`، `none` یعنی بی‌Tracer Provider) و
پاک‌ساز فقط جلوی آن‌ها می‌ایستد. Log همبسته با Trace (pino ← OTel Logs) هم دادهٔ کلاینت از درخواست ندارد: `path` بی‌Query
است (بالا)؛ متن خطایی که Filter ثبت می‌کند — پیام خطا، پیام هر Cause و `internalContext.originalMessage` — از `safeLogText`
می‌گذرد که همین `redactText` را پیش از یک‌خطی‌کردن و کوتاه‌کردن اعمال می‌کند (نشانی OAuth در پیام خطا فقط تا مسیر می‌ماند)، و
Frameهای Stack با خود پیام خطا از آن جدا می‌شوند (`stackFrames`): وقتی Stack با سطری که به همان پیام ختم می‌شود آغاز شود و
بقیه‌اش `at …` باشد و گیومه نداشته باشد، Frameها جدا از پیام پاک‌سازی می‌شوند و پیام بلند گیومه‌دار دیگر Frameها را با خود
نمی‌برد؛ وگرنه کل Stack یکجا پاک‌سازی می‌شود، چون سطری از بدنهٔ نقل‌شده می‌تواند شکل `at …` داشته باشد (`exception.stacktrace`
در Span هم همین‌طور)؛ و Correlation Id
همان است که قاعدهٔ `X-Correlation-Id` (§ ۶٫۳) پذیرفته — `access_token=…` پذیرفته نمی‌شود و ULID تازه جایش را می‌گیرد. تست‌ها
با Instrumentationهای واقعی و Exporter درون‌حافظه:

- `packages/observability/src/url-redaction.spec.ts`: Span، با و بی `OTEL_ATTRIBUTE_VALUE_LENGTH_LIMIT=40`، از جمله
  `X-Forwarded-Host` به شکل خطای Parser و سرصفحه‌ها و مسیر ۱۵٬۰۰۰ نویسه‌ای؛ برابری با دو عبارت باقاعدهٔ پیشین روی متن‌های
  تصادفی؛ اعتبارنامه‌ها، از جمله وقتی `?`، `#`، `=` یا `"` در گذرواژه است؛ رازی که برش از میانش می‌گذرد (رشتهٔ اتصال،
  `password=`/`token=`، بدنهٔ نقل‌شده، توکن `Bearer`)؛ متن‌های تصادفی که در هر محل برش ممکن بریده می‌شوند و هیچ تکه‌ای از
  رازی که متن کامل از دست می‌داد نگه نمی‌دارند؛ و متن‌های ۱۶٬۳۸۴ نویسه‌ای در برابر بدترین حالت هر قاعده، با سقف زمان (کمینهٔ
  سه بار)، نسبت هزینهٔ ۱۶k به ۴k (زمان CPU) و شمار خواندن هر نویسه.
- `exporter-selection.spec.ts`: مقایسه با کد پیشین در هر ترکیب محیط.
- `packages/nest-common/src/middleware/request-path-logs.spec.ts`: Log و Span در سطح debug و info و با حد ۴۰، شامل:
  - 404 خود Nest؛
  - خطای OAuth با Cause، در هر سه شکل `Error`، `RastaError.internal` و `BadGatewayException`، با Query دارای آپستروف،
    Fragment، گیومه/کروشه/یونیکد و URL در پایان متن؛
  - نثر پرسشی که دست نمی‌خورد؛
  - بدنهٔ JSON چندخطی؛
  - خطا با Cause که رازش (رشتهٔ اتصال، توکن `Bearer`، `password=`، بدنهٔ نقل‌شده) از سقف می‌گذرد: بریده، بی هیچ تکه از راز،
    با Frameهای Stack؛
  - 403 با `x-correlation-id: access_token=…`.

**دلیل بستهٔ امتناع در `details`.** امتناعی که دلیلش یکی از فهرستی بسته است، آن دلیل را در `details[].code` می‌آورد.
`code` سطح بالا (`FORBIDDEN`، `CONFLICT`، `BUSINESS_RULE_VIOLATION` …) و `message` همان می‌مانند. کلاینت اول روی `code` و سپس روی `details[].code`
شاخه می‌زند و هرگز `message` را تجزیه نمی‌کند. `path` می‌گوید دلیل از کجاست: میدان (`status` در asset)، منبع (`registration` در identity)
یا حوزهٔ قاعده (`publication`، `bid`، `opening`، `evaluation`، `award`، `approval`، `cancellation` در construction، #227). `message` هر ورودی متن ثابت است.
در `details` فقط کد بسته می‌آید، نه شناسه، نه متن آزاد، نه `internalContext`. امتناع بی‌دلیل بسته `details` ندارد: نه آرایهٔ خالی، نه ورودی ناقص.
فهرست بستهٔ هر مسیر در OpenAPI همان سرویس آمده است.

**`internalContext` چه می‌تواند داشته باشد.** این زمینه هرگز به کلاینت نمی‌رسد و برای تشخیص اپراتور در Log سرور است؛ پس
**شناسه و مبلغ** مجاز است — شناسهٔ رکورد و مستأجر، Endpoint، موجودی درخواستی و موجود کیف پول (`{walletId, requested,
available}`)، گذار وضعیت — اما **هرگز**: اعتبارنامه یا کلید (توکن، گذرواژه، `Idempotency-Key` یا هر چیز مشتق از آن)، **دادهٔ
شخصی** (نام، ایمیل، تلفن، کد ملی، نشانی) یا **متن آزاد کلاینت** (دلیل، یادداشت، بدنهٔ خام). چیزی آن را پاک‌سازی نمی‌کند؛
همان‌طور که نوشته شده ثبت می‌شود و مسئولیتش با نویسنده است (توضیح `RastaError.internalContext`). متنی که کلاینت
نوشته — Header ‏`X-Organization-Id` بیرون از عضویت‌ها، شناسهٔ متن آزادی که سازمانی نیافت، مقدار تکراری میدانی یکتا — نه در
پیام می‌آید نه در `internalContext`: برای Header فقط طولش (`unmatchedHeader`، `headerLength`)، و برای برخورد یکتایی
(`label`، `sku`، `title`) فقط نام میدان (`field`) ثبت می‌شود. پیام jose برای Token ردشده هم ثبت نمی‌شود، فقط کدش (`joseCode`).

**بدنه‌ای که سرویس نمی‌خواند.** بدنهٔ بزرگ‌تر از سقف (`entity.too.large` در body-parser) `413 PAYLOAD_TOO_LARGE` و
Charset یا Content-Encoding پشتیبانی‌نشده (`charset.unsupported`، `encoding.unsupported`) `415 UNSUPPORTED_MEDIA_TYPE`
می‌گیرد، هر دو با متن ثابت؛ پیام body-parser که مقدار فرستاده‌شده را نام می‌برد به پاسخ و Log نمی‌رسد.

حالت اکنون `422 ACTOR_IDENTITY_UNKNOWN` است — همان کدی که هر جدایی وظایفِ اثبات‌ناپذیر در پلتفرم برمی‌گرداند (`docs/09` § ۹٫۳).

هیچ رویدادی نیست.

دیگر نیست. `404` و `403` برای منبع متعلق به مستأجر دیگر **هر دو `404` برمی‌گردانند** —
تا وجود یا نبود منبع لو نرود.

## ۶٫۸ Idempotency

**اجباری روی:** ایجاد سفارش · تراکنش · شارژ کیف پول · تسویه · ثبت پیشنهاد · تأیید صورت‌وضعیت
· هر عملی با اثر مالی یا اثر بیرونی برگشت‌ناپذیر.

```http
POST /v1/orders
Idempotency-Key: 01JBQ8Z4K7M2N5P8R1T3V6X9Y2
```

| حالت                          | پاسخ                                  |
| ----------------------------- | ------------------------------------- |
| کلید جدید                     | اجرا، ذخیره پاسخ، بازگشت ۲۰۱          |
| کلید تکراری + همان بدنه       | پاسخ ذخیره‌شده، **بدون اجرای دوباره** |
| کلید تکراری + بدنه متفاوت     | `409 IDEMPOTENCY_KEY_REUSED`          |
| کلید در حال پردازش            | `409 CONFLICT` + `Retry-After: 1`     |
| بدون کلید روی Endpoint اجباری | `400 VALIDATION_FAILED`               |

**شکستِ آزادکردنِ Claim روی مسیر شکست (contract-service، #231 دور ۵).** وقتی کار فرمان شکست می‌خورد
(مثلاً ثبت ردپای رد شدن ممکن نیست و پاسخ `503 UPSTREAM_UNAVAILABLE` است)، Claim آزاد می‌شود تا همان
درخواست دوباره بیاید. اگر خودِ آزادکردن هم شکست بخورد (همان پایگاه دادهٔ ناپایدار)، **پاسخ همان `503`
اصلی می‌ماند** و خطای آزادکردن جایگزین آن نمی‌شود؛ خطای آزادکردن فقط در Log می‌آید (بی کلید و بی
مقدار). Claim تا پایان اجاره‌اش (`CONTRACT_IDEMPOTENCY_CLAIM_LEASE_SECONDS`، پیش‌فرض ۱۲۰ ثانیه) می‌ماند و
تا آن‌گاه تکرار با همان کلید `409 CONFLICT` + `Retry-After: 1` است؛ پس از آن تکرار Claim را با توکن تازه
برمی‌دارد و کار دوباره اجرا می‌شود. هیچ حالتی کار را دوبار اجرا نمی‌کند: تراکنش کار با توکن Claim
قفل و تکمیل می‌شود.

نگهداشت کلید: **۲۴ ساعت**. تطبیق بدنه با SHA-256 بدنه نرمال‌شده (کلیدهای مرتب، فضای خالی حذف).

**ثبت پیشنهاد مناقصه (`POST /v1/tenders/{id}/bids`، ممیزی construction، F4).** کلید **در خودِ construction-service اجباری** است
(نبودن ⇒ `400 VALIDATION_FAILED` با مسیر `Idempotency-Key` و کد `required`؛ فراخوانی مستقیم هم)؛ کلید از آنِ سازمان پیشنهاددهنده است،
درخواست = شناسهٔ مناقصه + بدنه، و پاسخ (رسید) در همان تراکنشِ پیشنهاد، رسید و Outbox ثبت می‌شود؛ هر شکست کلید را آزاد می‌کند. **استثنای
Hash:** بدنه قیمت است، پس Hash ذخیره‌شدهٔ آن SHA-256 بی‌کلید نیست — که از روی پشتیبان با حدس قیمت بازسازی‌پذیر بود (ADR-066 § ۱) — بلکه
HMAC-SHA256 با کلیدی مشتق (HKDF) از KEK جاریِ مناقصه‌ها است (`hmac-v1:<kekId>:<salt>:<mac>`)، که پس از چرخش KEK هم تا وقتی KEK قدیم نگه داشته
شود شناخته می‌شود. **قابل مقایسه میان دو ادعا نیست** (دور اول Codex روی #250، R1): ادعا پیش از سنجش صلاحیت، یکتایی و پنجره ثبت می‌شود، پس
Hash یکسانِ دو بدنهٔ یکسان به خوانندهٔ پایگاه داده‌ای که حساب پیمانکار هم دارد اجازه می‌داد قیمتِ حدس‌زده‌ای را با ثبت نامزدها تأیید کند. از این رو
سازمان و کاربرِ پیشنهاددهنده درون MAC‌اند و هر ادعا `salt` تصادفیِ خودش را دارد که با آن ذخیره می‌شود؛ تکرار با همان `salt` سنجیده می‌شود.
نتیجه: همان کلید از کاربر دیگرِ همان سازمان درخواست دیگری است (`409 IDEMPOTENCY_KEY_REUSED`)، مثل ارزیاب در ثبت امتیاز. ثبت امتیاز (`POST /v1/tenders/{id}/bids/{bidId}/scores`، F5) کلید اختیاری را رعایت می‌کند و ارزیاب جزء درخواست است.

**`Retry-After` دقیقاً چه زمانی فرستاده می‌شود.** فقط روی ۴۰۹ کلید در حال پردازش
(`CONFLICT`)، با مقدار `1`، در economic، marketplace و construction؛ نه روی
`IDEMPOTENCY_KEY_REUSED`، چون صبر آن را حل نمی‌کند. مدت انتظار فقط Header است و
در بدنه خطا نمی‌آید. سرویس آن را با فیلد نوع‌دار `RastaError.retryAfterSeconds`
می‌گوید و `AllExceptionsFilter` فقط از همین فیلد Header می‌سازد: عدد صحیح (رو به
بالا گرد می‌شود)، محدود به ۱ تا ۳۶۰۰ ثانیه؛ مقداری که عدد متناهی نباشد اصلاً فرستاده
نمی‌شود. هیچ چیز از `internalContext` — که فقط در Log سرور می‌ماند (§ ۶٫۷) —
هرگز Header نمی‌شود. Gateway این Header را مانند بقیهٔ Headerهای پاسخ سرویس
عبور می‌دهد و در CORS در `exposedHeaders` است تا اسکریپت مرورگر بتواند آن را بخواند.

**امتناع نهایی (فقط economic، فقط با اعلام Endpoint).** در economic هر خطای کار، کلید را آزاد می‌کند و فقط
پاسخ موفق بازپخش می‌شود — عمداً: تسویه‌ای که به‌دلیل کمبود موجودی رد شد باید پس از شارژ با همان کلید دوباره
اجرا شود. استثنا فهرستی بسته است که خودِ Endpoint اعلام می‌کند (`terminalRefusals`)؛ هر نام در آن یک کد خطا و
یک پیام ثابتِ نوشتهٔ نویسنده دارد، و Store فقط وضعیت HTTP و **نام بستهٔ امتناع** را ذخیره می‌کند، نه پیام
خطا، نه `internalContext` و نه متنی از کلاینت (S-09). همان کلید با همان بدنه همان امتناع (۴۲۲) را بازپخش می‌کند، بی
اجرای دوباره، بی نگه‌داشت تازه و بی رویداد تازه؛ همان کلید با بدنهٔ دیگر مانند همیشه `409 IDEMPOTENCY_KEY_REUSED`
است. نگهداشت، گرفتن کلید و Hash بدنه همان است که بود. فقط یک Endpoint اعلام کرده است:

| Endpoint                               | امتناع‌های نهایی                                                                                                          | چرا نهایی است                                                                                                                                                                                                    |
| -------------------------------------- | ------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `POST /v1/payment-intents/{id}/refund` | `REFUND_DECLINED` (ارائه‌دهنده بازپرداخت را رد کرد)، `REFUND_DECLINED_EARLIER` (رد پیشین؛ مبلغ نگه‌داشته‌شده اکنون برگشت) | ارائه‌دهنده همان کلید یگانهٔ تلاش بازپرداخت (`<key>:refund`) را با همان رد پاسخ می‌دهد (ADR-064)، پس با همان کلید و بدنه هرگز موفق نمی‌شود. بازپخش به‌جای نگه‌داشت دوباره، همان امتناع ثبت‌شده را می‌دهد (#210). |

هرچه ممکن است بعداً موفق شود **آزاد می‌شود، نه ثبت**: کمبود موجودی (`INSUFFICIENT_BALANCE`، با شارژ)، وابستگی
در دسترس‌نبودنی، هر ۵xx، بازپرداخت ناتمام یا نامعلوم، کیف پول غیرفعال، و رد ارائه‌دهنده‌ای که برگرداندن مبلغ
نگه‌داشته‌شده‌اش هنوز معلق است (`REFUND_DECLINED_RELEASE_PENDING`: بازتلاش با همان کلید همان است که مبلغ را
برمی‌گرداند). ثبت امتناع اگر شکست بخورد، کلید مانند هر خطای دیگر آزاد می‌شود.

**شکستِ پس از Commit، کلید را آزاد نمی‌کند (economic، docs/23 D-054).** پاسخ — یا ردِ نهاییِ اعلام‌شده — در
همان تراکنشِ اثر ثبت می‌شود، از ردیف‌هایی که همان تراکنش نوشته؛ پس اثر و کلیدِ کامل‌شده با هم Commit می‌شوند یا
هیچ‌کدام. اگر ثبت شکست بخورد، اثر برمی‌گردد و کلید آزاد می‌شود. هر شکستِ پس از Commit — خواندن، ساختن پاسخ، اتصالی
که پس از COMMIT قطع شد — به فراخوان می‌رسد، ولی کلید `COMPLETED` است و تکرار با همان کلید همان پاسخ را بازپخش
می‌کند، نه اینکه در برابر وضعیتِ جلو رفته سنجیده شود. کاری که بی ثبت پاسخ برگردد (خطای برنامه‌نویسی) کلید را «در
حال پردازش» نگه می‌دارد: تکرار تا انقضای کلید `409 CONFLICT` + `Retry-After` می‌گیرد، نه اجرای دوباره.

**پاسخ ثبت‌شده فقط به کنشگرش، و فقط تا وقتی هنوز به شیء دسترسی دارد (economic، docs/23 D-054، دور ۲).** هر رکورد
Hash ـِ کنشگری را که کلید را گرفت نگه می‌دارد (issuer و subject ـِ تأییدشده، یا سرویس فراخواننده)؛ همان کلید از
کنشگر دیگرِ همان سازمان `409 IDEMPOTENCY_KEY_REUSED` است، بی هیچ اثری از پاسخ ذخیره‌شده. پیش از بازپخشِ هر پاسخ یا
امتناع ثبت‌شده، بررسی‌های دسترسی شیءِ همان Endpoint دوباره اجرا می‌شوند — بی اجرای دوبارهٔ گذار — و کسی که دسترسی‌اش
رفته همان `404 NOT_FOUND` (یا `403`) ـِ درخواست تازه را می‌گیرد. هر رزرو توکن تصادفیِ خودش را دارد و فقط با آن کامل یا
آزاد می‌شود: درخواستی که ادعایش منقضی و جایگزین شده، ادعای جایگزین را نه کامل می‌کند نه آزاد (`409 CONFLICT` +
`Retry-After`، و اثرش برمی‌گردد).

**ثبت پاسخ در همان تراکنش دامنه (construction، contract و marketplace).** پاسخ آخرین دستورِ تراکنشِ خودِ کار
است و فقط ردیفِ `IN_PROGRESS`ِ همین Claim (با توکنش) را کامل می‌کند؛ پس تغییر و کلیدِ کامل‌شده‌اش با هم Commit
می‌شوند یا هیچ‌کدام. اگر ثبت پاسخ شکست بخورد، کل کار برمی‌گردد — در marketplace یعنی نه سفارش، نه رویداد، نه
موجودیِ رزروشده — و Claim آزاد می‌شود تا تکرار با همان کلید یک بار اجرا شود؛ دیگر هیچ `5xx`ای برای سفارشی که
وجود دارد برنمی‌گردد. Claimی که زیر کار منقضی و دوباره گرفته شده باشد در ثبت پاسخ رد می‌شود (`409 CONFLICT` +
`Retry-After: 1`) و کار Commit نمی‌شود. در marketplace هیچ Endpointی پاسخ را پس از Commit ثبت نمی‌کند (#253).
در marketplace، یک کلید در هر سازمان **حداکثر یک سفارش** می‌سازد (`uq_order_org_idempotency_key`)، حتی
پس از انقضا یا از دست رفتن رکورد کلید؛ سفارش دوم با همان کلید `409 CONFLICT`
است، بدون `Retry-After`، چون صبر آن را حل نمی‌کند.

**marketplace: شکستِ آزادکردن و اجارهٔ Claim (#253 دور ۲).** همان قاعدهٔ contract-service: وقتی کار شکست می‌خورد
و آزادکردنِ Claim هم شکست می‌خورد (پایگاه داده در دسترس نیست)، **پاسخ همان خطای اصلیِ کار است** و خطای آزادکردن
فقط در Log ساخت‌یافته می‌آید (Endpoint، کلاس و کد خطا؛ بی کلید، بی توکن، بی بدنه). Claimِ «در جریان» فقط یک اجاره
است (`MARKETPLACE_IDEMPOTENCY_CLAIM_LEASE_SECONDS`، پیش‌فرض ۶۰ ثانیه، ۳۰ تا ۳۶۰۰ و کوتاه‌تر از نگهداشت؛ مقدار
بیرون از بازه راه‌اندازی را متوقف می‌کند)، نه نگهداشتِ ۲۴ ساعتهٔ پاسخ: تا پایان اجاره تکرار همان درخواست
`409 CONFLICT` + `Retry-After: 1` است و پس از آن تکرار، Claimِ منقضی را — فقط اگر هنوز منقضی باشد — برمی‌دارد و با
توکن تازه یک بار اجرا می‌شود. صاحب قبلی اگر دیر برسد، تکمیلش با توکنش هیچ ردیفی نمی‌یابد (`409 CONFLICT` +
`Retry-After: 1`) و کارش Commit نمی‌شود؛ آزادکردنش هم چیزی از جانشین برنمی‌دارد. کاری که بی ثبت پاسخ برگردد (خطای
برنامه‌نویسی) Claimش را تا پایان نگهداشت نگه می‌دارد، نه تا پایان اجاره، تا اجرای دومی رخ ندهد.

**Hash بدنه هر کلید را دربر می‌گیرد** — هر نامی داشته باشد، حتی `__proto__` — پس دو بدنهٔ متفاوت هرگز یکی
شمرده نمی‌شوند (#194). در construction، برداشتن کلید منقضی‌ای که تراکنش دامنه‌ای هنوز قفلش را نگه داشته حداکثر
۵ ثانیه منتظر می‌ماند و سپس `409 CONFLICT` + `Retry-After: 1` است، نه انتظار بی‌پایان.

**شناسهٔ منبع جزء هویت درخواست است.** کلید زیر الگوی مسیر ذخیره می‌شود
(`POST /v1/orders/:id/cancel`)، پس روی مسیری که بر یک منبع مشخص عمل می‌کند،
شناسهٔ آن منبع همراه بدنه هش می‌شود. همان کلید و همان بدنه روی منبعی دیگر
`409 IDEMPOTENCY_KEY_REUSED` است، نه بازپخش.

**بازپخش هیچ اثری جز بازگرداندن پاسخ ذخیره‌شده ندارد.** در بازپخش هیچ بررسی
مجوز یا گذار وضعیتی اجرا نمی‌شود (استثنا: asset-service پیش از بازپخش دیدن دارایی
را دوباره بررسی می‌کند، § ۶٫۳؛ marketplace بررسی خواندن و مالکیتِ هدف را، پایین‌تر)، پس هر کاری که کنترلر پس از اجرا انجام
می‌دهد — مانند Signal به Saga — فقط وقتی انجام می‌شود که فرمان در همین
درخواست واقعاً اجرا شده باشد.

**بازپخش در marketplace به فراخوان بسته است و دوباره مجوز می‌گیرد (#253 دور ۲).** Hash درخواست، فراخوانِ
احرازشده را هم دربر می‌گیرد (نوع احراز، شناسهٔ کاربر، و برای توکن سرویس نام سرویس): همان کلید و همان بدنه و همان هدف
از کاربر دیگری در همان سازمان `409 IDEMPOTENCY_KEY_REUSED` است، نه بازپخش — حتی وقتی کلید هنوز در جریان است.
پیش از برگرداندن پاسخ ذخیره‌شده، بررسیِ **کنونیِ** خواندن و مالکیتِ هدفِ آن پاسخ دوباره اجرا می‌شود، بی هیچ نوشتن
و بی هیچ بررسی گذار وضعیت: سفارش‌ها — دیده‌شدنِ سفارش (`404` برای غریبه، مانند `GET /v1/orders/{id}`) و بررسی طرفِ
همان فرمان (`403`)؛ `POST /v1/offers` و `PATCH /v1/offers/{id}` — همان `assertOfferOwner` که ویرایش اجرا می‌کند
(`403` برای نقش، `404` برای پیشنهاد سازمان دیگر)؛ `POST /v1/products` — قاعدهٔ خواندن `GET /v1/products/{id}`
(`404` برای محصول غیرفعال). فراخوانی که از آن پس نقش یا مالکیت را از دست داده، همان پاسخِ Endpointِ زنده را می‌گیرد،
نه بدنهٔ ذخیره‌شده. **اثر استقرار:** پاسخ‌هایی که پیش از این تغییر ذخیره شده‌اند Hash بی‌فراخوان دارند؛ تکرار آن‌ها
پس از استقرار و تا انقضای نگهداشت `409 IDEMPOTENCY_KEY_REUSED` است، نه بازپخش (سفارش دوم را
`uq_order_org_idempotency_key` در هر حال رد می‌کند). دو توکنِ یک شخص با دو شناسهٔ کاربر (`platformUserId`) دو
فراخوان شمرده می‌شوند — سمت محافظه‌کار: امتناع، نه بازپخش.

**قاعدهٔ سخت‌گیرانه‌ترِ بدنه، بازپخشِ بدنه‌ای را که اکنون رد می‌کند هم رد می‌کند.** اعتبارسنجی بدنه پیش از
جست‌وجوی پاسخ ذخیره‌شده اجرا می‌شود؛ پس درخواستی که پیش از سخت‌ترشدن یک قاعده پذیرفته شد، اگر با همان کلید و همان
بدنه در ۲۴ ساعت نگهداشت تکرار شود، اکنون `400 VALIDATION_FAILED` می‌گیرد، نه پاسخ ذخیره‌شده (#220: نویسه‌های
`Bidi_Control` در ثبت دارایی، ثبت بازرسی فنی و ثبت قطعهٔ ارجاع تعمیر). پیش از تولید، بدون تغییر کد پذیرفته شده است.

**پاسخ بازپخش‌شده پاسخ تاریخی است، نه وضعیت امروز.** همان کلید همان پاسخ را
می‌گیرد، و لایهٔ Idempotency عمداً وضعیت منبع را دوباره نمی‌خواند (تصمیم مدیر
پروژه، بازبینی دور ۲ #143). پس شارژ کیف پولی که `CAPTURED` شد و بازپرداختش سپس
ناتمام ماند، با همان کلید هنوز `CAPTURED` بازپخش می‌شود. وضعیت امروز را
`GET /v1/payment-intents/{id}` می‌گوید: `status` همراه `failureReason`، که یکی
از علامت‌های بازپرداخت ناتمام ADR-064 را نشان می‌دهد — `REFUND_REQUESTED`،
`REFUND_UNKNOWN`، `REFUNDED_NOT_REVERSED` یا `REFUND_DECLINED_RELEASE_PENDING`.
فراخوانی که باید بداند پول کجاست، Intent را می‌خواند، نه بازپخش را.

**بازپرداخت از کیف پول `FROZEN`** با `422 BUSINESS_RULE_VIOLATION` رد می‌شود، پیش از هر Hold یا فراخوانی Provider؛ از کیف
پول منجمد پولی بیرون نمی‌رود و Intent پس از فعال‌شدن دوبارهٔ کیف پول بازپرداخت‌پذیر می‌ماند (تصمیم مدیر پروژه، ADR-064).

## ۶٫۹ Rate Limiting

| محدوده              | حد پیش‌فرض    | پنجره    |
| ------------------- | ------------- | -------- |
| به‌ازای کاربر       | ۳۰۰ درخواست   | ۱ دقیقه  |
| به‌ازای مستأجر      | ۳٬۰۰۰ درخواست | ۱ دقیقه  |
| به‌ازای IP (ناشناس) | ۶۰ درخواست    | ۱ دقیقه  |
| ورود / بازیابی رمز  | ۵ تلاش        | ۱۵ دقیقه |
| آپلود سند           | ۲۰ فایل       | ۱ ساعت   |
| جست‌وجو             | ۶۰ درخواست    | ۱ دقیقه  |

الگوریتم: **Sliding Window** روی Redis. همه حدود **پیکربندی‌پذیر**اند.

**کلید حد ناشناس (L1-03).** حد «به‌ازای IP» روی نشانی واقعی کاربر می‌نشیند، نه نشانی Ingress. Gateway
`X-Forwarded-For` را فقط از Hopهایی می‌پذیرد که در `GATEWAY_TRUSTED_PROXIES` نام برده شده‌اند (نشانی، بازهٔ CIDR یا
`loopback`/`linklocal`/`uniquelocal`)؛ «اعتماد به همه»، شمارش Hop و بازهٔ `/0` (`0.0.0.0/0`، `::/0`) پذیرفته نمی‌شوند، چون
هر سه سرآیندی را باور می‌کنند که خودِ Client نوشته. پیش‌فرض خالی است — هیچ Hopی مورد اعتماد نیست. **این فهرست فقط نشانی‌های
Proxy است، هرگز بازه‌ای که Client هم در آن باشد:** هر نشانی درون فهرست می‌تواند نشانی Client را اعلام کند، پس Clientی که
نشانی خودش در بازهٔ مورد اعتماد بیفتد، سطل حد نرخ خودش را انتخاب می‌کند.

**مسیر متعارف (L1-04).** مسیری که Segment نقطه‌ای (`.`، `..` یا شکل کدشدهٔ آن‌ها مثل `%2e%2e`) یا Backslash دارد، **پیش از
انتخاب Route** با `400 VALIDATION_FAILED` رد می‌شود. دلیل: Gateway حد نرخ، فیلتر نقش و الزام `Idempotency-Key` را از Route
مسیر خام انتخاب می‌کند، ولی `fetch` هنگام ارسال Segmentهای نقطه‌ای را حذف می‌کند؛ بدون این بررسی
`/v1/users/../audit-corrections` با قواعد `users` سنجیده و به `audit-corrections` تحویل داده می‌شد.

**خطای ۵xx بالادست (L1-06).** پاسخ ۵xx‌ای که Envelope خطای پلتفرم نیست (صفحهٔ HTML، Stack Trace، JSON دلخواه یا بدنهٔ خالی)
به Client بازتابانده نمی‌شود؛ Gateway به‌جایش `503 UPSTREAM_UNAVAILABLE` می‌دهد و فقط وضعیت، نوع محتوا و طول بدنه را Log
می‌کند، نه خودِ بدنه را (S-09). Gateway همیشه با سریال‌سازی JSON خودش پاسخ می‌دهد، پس `Content-Type` بالادست منتقل نمی‌شود.

### قرارداد یکنواخت CRUD

**ویرایش دارایی و نسخهٔ موردانتظار (`expectedVersion`).** `PATCH /v1/assets/{id}`
بدنه‌ای می‌پذیرد که فیلد **اجباری** `expectedVersion` دارد: همان `version` که خواندن
دارایی برگردانده است (فیلد تازهٔ پاسخ، عدد صحیح JSON و ≥ ۱؛ رشته، `true`، `null` و
صفر پذیرفته نیستند). بدنه‌ای که آن را نگوید `400 VALIDATION_FAILED` می‌گیرد و چیزی
نوشته نمی‌شود: فراخوانی که نمی‌داند ویرایشش بر کدام نسخه بنا شده، نمی‌داند چه چیزی را
بازنویسی می‌کند، و بی‌آن هر مشتری مستقیمِ API می‌توانست تغییر دیگری را بی‌صدا
برگرداند. به‌روزرسانی فقط روی همان نسخه اعمال می‌شود؛ اگر دارایی از آن زمان تغییر
کرده باشد پاسخ `409 OPTIMISTIC_LOCK_FAILED` است و **هیچ چیز نوشته نمی‌شود**
(مقایسه و نوشتن در یک عبارت `UPDATE … WHERE version = ?` انجام می‌شود، نه فقط پس از
خواندن، پس از رقابت میان خواندن و نوشتن هم بازنده چیزی نمی‌نویسد). فقط فیلدهایی
نوشته و در `ASSET_UPDATED.changedFields` گزارش می‌شوند که مقدارشان با مقدار
ذخیره‌شده فرق دارد؛ ویرایشی که چیزی را تغییر نمی‌دهد چیزی نمی‌نویسد، رویدادی منتشر
نمی‌کند و دارایی را همان‌طور که هست برمی‌گرداند (نسخهٔ کهنه حتی برای چنین ویرایشی
`409` است). دارایی سازمان دیگر، با هر نسخه‌ای که فرستاده شود، `404` است نه `403`.
این تغییر برای فراخوان‌های بی‌نسخه سازگار با گذشته نیست: تنها فراخوان درون‌مخزن
(پورتال) همیشه نسخه را می‌فرستد. این سازوکار Idempotency نیست (§ ۶٫۸): ثبت دارایی
کلید را ذخیره می‌کند (#193)، ولی ویرایش و دستورهای چرخهٔ حیات نه: گارد آن‌ها همین نسخه است.

**دستورهای چرخهٔ حیات و نسخهٔ موردانتظار.** `POST /v1/assets/{id}/activate`،
`POST /v1/assets/{id}/status` و `POST /v1/assets/{id}/decommission` نیز فیلد **اجباری**
`expectedVersion` دارند، با همان معنا و همان قاعدهٔ `PATCH`: بدنه‌ای که آن را نگوید
`400 VALIDATION_FAILED` است و نسخهٔ کهنه `409 OPTIMISTIC_LOCK_FAILED` با نوشتنِ هیچ‌چیز و
انتشارِ هیچ رویداد. `POST …/status` با `status: ACTIVE` از `REGISTERED` `422 INVALID_STATE_TRANSITION` است: فعال‌سازی فقط با `…/activate` انجام می‌شود، که کامل بودن پرونده را می‌سنجد، و مسیر وضعیت راه دور زدن آن نیست. نسخه **پیش از** بررسی گذار سنجیده می‌شود و در خودِ `UPDATE … WHERE
status = ? AND version = ?` دوباره نگه داشته می‌شود؛ پس دستوری که یک بار اعمال شده و
دوباره می‌رسد (فرم دوبار فرستاده‌شده، تلاش مجدد پس از پاسخ گم‌شده) همیشه `409` می‌گیرد، نه
`422`ی که بسته به وضعیت تازه معنای دیگری دارد، و نه اعمال دوم — حتی اگر دارایی در این میان
به وضعیت نخست برگشته باشد (`ACTIVE ← IDLE ← ACTIVE` و سپس همان فرم `ACTIVE ← IDLE`).
این **قفل خوش‌بینانه است، نه Idempotency**: دستور تکراریِ بازخوانی‌شده پاسخ نخست را
بازنمی‌گرداند، رد می‌شود. گذارهایی که رویداد سرویس دیگر (تخصیص، تعمیر) انجام می‌دهد
نسخه ندارند و فقط با وضعیت سنجیده می‌شوند.

**کار باز در سرویس دیگر (Q-94، تصمیم موقت).** دارایی در `ASSIGNED` (تخصیص باز در `fleet-service`) یا
`IN_MAINTENANCE` (ارجاع تعمیر باز در `maintenance-service`) را هیچ کاربری با `…/status` به `OUT_OF_SERVICE`
نمی‌برد و با `…/decommission` اسقاط نمی‌کند (و `…/activate` هم از آن‌ها ممکن نیست): پاسخ
`409 INVALID_STATE_TRANSITION` است با `details: [{ "path": "status", "code": "OPEN_ASSIGNMENT" | "OPEN_MAINTENANCE",
"message": … }]`؛ کد، بستهٔ بسته و بخشی از قرارداد است و مشتری می‌تواند بی‌خواندن جمله به آن تکیه کند. نسخه همچنان
**پیش از** این بررسی سنجیده می‌شود (نسخهٔ کهنه `409 OPTIMISTIC_LOCK_FAILED` است). راه آزادسازی: سرویس صاحب کار
کارش را می‌بندد و رویداد پایان آن وضعیت را به `ACTIVE` برمی‌گرداند. گذارهای رویدادی تغییری نکردند.

**وضعیتِ خودِ دارایی کافی نیست؛ صاحبان کار پرسیده می‌شوند.** پیش از هر گذار **به** `OUT_OF_SERVICE` (`…/status`) یا
`DECOMMISSIONED` (`…/decommission`) `asset-service` از `fleet-service` و `maintenance-service` می‌پرسد — همان
کلاینت و همان نقاط پایان داخلی `transfer-clearance` که انتقال مالکیت به کار می‌برد (ADR-062) — آیا تخصیص باز یا
درخواست/ارجاع تعمیر باز هست، حتی وقتی وضعیت دارایی چیزی نشان نمی‌دهد (تعمیرِ آغازشده روی دارایی `OUT_OF_SERVICE`؛
تخصیصی که هنوز رویدادش نرسیده). همه باید «روشن» بگویند: کار باز ← همان `409` با `details[].code` برابر
`OPEN_ASSIGNMENT` و/یا `OPEN_MAINTENANCE` (هر دو، اگر هر دو باز باشند)؛ صاحب کار در دسترس نیست یا کند است ←
`503` / `504` و **هیچ‌چیز نوشته نمی‌شود** (بسته می‌ماند، هرگز «روشن» نیست). **اگر یک صاحب کار کار باز گزارش کند و دیگری
در دسترس نباشد، «در دسترس نیست» (`503`/`504`) پیش می‌افتد، نه `409 OPEN_*`:** فراخوان تصویر کامل را نمی‌داند و باید
پاسخ «بعداً دوباره تلاش کنید» را بگیرد، نه یک «مسدود به‌سبب کار باز» قطعی (پورتال همین را می‌گوید). نسخه همچنان پیش از این پرسش سنجیده
می‌شود (نسخهٔ کهنه `409 OPTIMISTIC_LOCK_FAILED` است و از هیچ سرویسی چیزی پرسیده نمی‌شود). گذارهای `ACTIVE` و
`IDLE` و گذارهای رویدادی پرسشی ندارند. ریسک باقی‌ماندهٔ فاصلهٔ رویداد پس از Commit در Q-94 ثبت شده است.

دارایی سازمان دیگر، با هر نسخه، `404` است نه `403`. این تغییر برای فراخوان‌های بی‌نسخه سازگار با گذشته نیست؛ تنها فراخوان درون‌مخزن
(پورتال) و آزمون‌های E2E همیشه نسخه را می‌فرستند.

**انحراف از طرح اولیه — ثبت‌شده در ADR-026.** نسخه پیشین این بخش مسیرهای
`/v1/assets/{id}/usage` و `/v1/assets/{id}/assignments` را نوشته بود. `api-gateway`
پیاده‌شده مسیر را از **نخستین قطعه مسیر** حل می‌کند (ADR-009: Gateway بدون دانش
دامنه)، پس هرچه زیر `assets/` باشد به `asset-service` می‌رود. منابع ناوگان به
Prefix های خودشان منتقل شدند و `assetId` یک **فیلد بدنه** است. این علاوه بر رفع
مسیریابی، صادقانه‌تر هم هست: تخصیص و کارکرد به ناوگان تعلق دارند، نه به دارایی.

**قواعد مشترک این سرویس:**

| مورد              | رفتار                                                                                                                        |
| ----------------- | ---------------------------------------------------------------------------------------------------------------------------- |

**پنج نکته که در فهرست بالا پیدا نیست:**

- **بدنه `POST /v1/orders` هیچ فیلد قیمتی ندارد و `.strict()` است.** قیمتی که
  کلاینت بفرستد `400 VALIDATION_FAILED` می‌گیرد — نادیده گرفتنش بی‌صدا بود و به
  کلاینتی که فکر می‌کند قیمت می‌گذارد نمی‌گفت که نمی‌گذارد (ADR-037 § ۵).
- **`sort` مقدار `RATING` نمی‌پذیرد.** امتیاز تأمین‌کننده نزد `supplier-service`
  است که وجود ندارد؛ پذیرفتن و مرتب کردن بر چیز دیگر، دروغ گفتن درباره نتیجه
  است (ADR-042 § ۲).
- **مسیرهای گذار وضعیت `200` برمی‌گردانند، نه `201`.** پیش‌فرض Nest برای `POST`
  اینجا دو بار نادرست بود: چیزی ساخته نمی‌شود، و وضعیت ثبت‌شده برای بازپخش
  Idempotent هم `200` است — پس Retry با کدی متفاوت از فراخوان اول پاسخ می‌گرفت.
  فقط ثبت سفارش و ثبت ارزیابی `201`اند.
- **`note` در بدنهٔ `POST /v1/orders` فعلاً فقط خالی پذیرفته می‌شود (Q-110، تصمیم موقت).** سفارش جایی برای
  نگه‌داشتن یادداشت ندارد — نه ستون، نه فیلد رویداد — و اینکه یادداشت خریدار کجا برود پرسشی باز است. یادداشت
  غیرخالی `400 VALIDATION_FAILED` روی `note` می‌گیرد و هیچ سفارشی ثبت نمی‌شود؛ پیش از این پذیرفته و بی‌صدا دور
  ریخته می‌شد. یادداشت خالی (پس از Trim) مانند نبودنش پذیرفته است.
- **`note` در بدنهٔ `POST /v1/orders/{id}/confirm-receipt` فعلاً فقط خالی پذیرفته می‌شود (Q-110، تصمیم موقت).**
  تأیید دریافت فقط کیستی و زمان تأیید را نگه می‌دارد — نه ستونی برای یادداشت، نه فیلدی در `ORDER_RECEIPT_CONFIRMED`.
  یادداشت غیرخالی `400 VALIDATION_FAILED` روی `note` می‌گیرد و سفارش تأیید نمی‌شود؛ پیش از این پذیرفته و بی‌صدا دور
  ریخته می‌شد. یادداشت خالی (پس از Trim) مانند نبودنش پذیرفته است.

> **وضعیت پیاده‌سازی (RUN-005 PR ۱، 2026-10-16، marketplace-service):** `POST /v1/orders/{id}/returns`، `GET /v1/returns/{id}`
> و `POST /v1/returns/{id}/decisions` (`AUTHORIZE`\|`REJECT`، فقط تأمین‌کنندهٔ همان سفارش) ساخته شده‌اند، به‌اضافهٔ دو مسیر که
> فهرست بالا ندارد: `GET /v1/returns` (درخواست‌های خود سازمان) و `POST /v1/returns/{id}/cancellation` (لغو توسط خریدار). ادعای
> ضمانت هنوز **NOT_IMPLEMENTED** است. هیچ مسیر Refund وجود ندارد.
>
> **RUN-005 PR ۲ (inventory-service):** `POST /v1/return-shipments` (همان مسیر برنامه‌ریزی‌شده) به‌اضافهٔ

> `/v1/returns`: آن پیشوند در Gateway از آنِ marketplace است. دو فرمان جدا: `POST …/{id}/inspection` و `POST …/{id}/resolution`
> (بدنهٔ دوم: `dispositions[]`؛ مجاز بودن هر نتیجه پیکربندی و بی‌پیش‌فرض است، Q-133). هیچ‌کدام موجودی یا Refund را تغییر نمی‌دهند.
>
> **مالکیت و مرز لغو (Codex r1 روی #336؛ D-058، Q-133 (۵، ۹)):** `POST /v1/return-shipments` پیش از هر نوشتن درخواست را از
> marketplace می‌خواند و ارسالش را رزرو می‌کند؛ دو مسیر داخلی marketplace (پیشوند `/v1/internal/` که Gateway به هیچ‌جا نمی‌برد، فقط
> توکن `SERVICE` ـِ `inventory-service` امضاشده برای تأمین‌کننده، طرح `internalToken`): `GET /v1/internal/returns/{id}` و
> `POST /v1/internal/returns/{id}/dispatch-reservation`. ناهم‌خوانی‌ها `422 BUSINESS_RULE_VIOLATION` با دلیل بسته
> (`RETURN_REQUEST_NOT_AUTHORIZED`، `RETURN_REQUEST_MISMATCH`، `RETURN_LINES_MISMATCH`)، درخواستِ تأمین‌کنندهٔ دیگر `404`، marketplace
> در دسترس‌ناپذیر `503`/`504`. نمای درخواست `dispatchReservedAt` دارد و `POST /v1/returns/{id}/cancellation` پس از آن
> `422` با `RETURN_DISPATCH_RESERVED` است.

همهٔ مسیرهای نوشتنی به Tenant Scope، مجوز سطح Object، Audit و در صورت اثر تکرارپذیر به
`Idempotency-Key` نیاز دارند. نمایش مسیر برنامه‌ریزی‌شده به‌عنوان API موجود ممنوع است.

**سه نکته که از فهرست بالا پیدا نیست:**

- **هیچ Endpoint ی Journal دلخواه Post نمی‌کند.** یک Journal همیشه رکورد چیزی
  است که اتفاق افتاده؛ Endpoint ای که Journal دلخواه بپذیرد یعنی جابه‌جایی
  مانده بدون هیچ واقعیت کسب‌وکاری پشتش — همان چیزی که یک دفتر کل برای غیرممکن
  کردنش وجود دارد.
- **هیچ Endpoint ی حساب نمی‌سازد.** نمودار حساب‌ها از `AccountPurpose` مشتق
  می‌شود و در نخستین استفاده ساخته می‌شود.
- **نقش `AUDITOR` هیچ‌کدام از این‌ها را نمی‌بیند** — نه در جدول مسیریابی
  Gateway، نه در `@Roles` هیچ Controller ی، و `assertNotAuditor()` هم بار سوم
  ردش می‌کند. یک قاعده به این اندازه مهم نباید به درست ماندن یک فایل وابسته باشد.

## ۶٫۱۲ ارتباط سرویس‌به‌سرویس

**همزمان (REST)** — فقط وقتی پاسخ **همین حالا** برای تصمیم لازم است:

```
POST /internal/v1/...
X-Internal-Token: <signed service token>
X-Correlation-Id: <propagated>
X-Organization-Id: <optional; must MATCH the token's signed org_id>
```

**CONSTRAINT (ADR-035).** تنانت یک فراخوان سرویسی از Claim امضاشده `org_id`
داخل توکن می‌آید، **نه از Header**. Header می‌تواند بیاید و برای Log و
همبستگی مفید است، اما فقط اجازه دارد با امضا **موافقت** کند:

| حالت                                   | نتیجه                                    |
| -------------------------------------- | ---------------------------------------- |
| `org_id` امضاشده، بدون Header          | پذیرفته — تنانت از امضا                  |
| `org_id` امضاشده + Header هم‌خوان      | پذیرفته                                  |
| `org_id` امضاشده + Header ناهم‌خوان    | **`403 SERVICE_TENANT_CONTEXT_INVALID`** |
| بدون `org_id`، روی عملیات مستأجر-محدود | **`403 SERVICE_TENANT_CONTEXT_INVALID`** |
| بدون `org_id`، روی عملیات غیرمستأجری   | پذیرفته، مشروط به `@AllowService`        |

هیچ Fallback به Header وجود ندارد. توکن `RELAY` هرگز `@AllowService` را ارضا
نمی‌کند و `org_id` روی آن نادیده گرفته می‌شود.

قواعد:

| قاعده           | مقدار                                                            |
| --------------- | ---------------------------------------------------------------- |
| Timeout         | ۳ ثانیه پیش‌فرض؛ ۱۰ ثانیه برای عملیات سنگین                      |
| Retry           | حداکثر ۲ بار، فقط روی خطای گذرا، با Exponential Backoff + Jitter |
| Circuit Breaker | باز شدن پس از ۵ خطای متوالی؛ نیمه‌باز پس از ۳۰ ثانیه             |
| Fallback        | Replica مرجع محلی، یا `UPSTREAM_UNAVAILABLE` صریح                |

**`Retry-After` روی Circuit باز.** وقتی Circuit Breaker Gateway باز است، درخواست بدون
تماس با سرویس با `503 UPSTREAM_UNAVAILABLE` رد می‌شود و `Retry-After` مدت باقی‌ماندهٔ
باز بودن Circuit را می‌گوید: ثانیهٔ صحیح، رو به بالا گرد، محدود به ۱ تا ۳۶۰۰. مقدار از
فیلد نوع‌دار `RastaError.retryAfterSeconds` می‌آید، نه از `internalContext`.

**ناهمزمان (Kafka)** — پیش‌فرض. اگر ارتباطی می‌تواند رویداد باشد، رویداد است.

**CONSTRAINT.** فراخوانی REST همزمان **هرگز** در مسیر بحرانی یک عمل مالی قرار نمی‌گیرد.
تسویه با رویداد و Saga انجام می‌شود، نه با زنجیره فراخوانی همزمان.
