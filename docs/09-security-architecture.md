# ۰۹ — Security Architecture

> Security by Design. هر Endpoint پیش‌فرض بسته است. هیچ Feature‌ای «فقط برای Demo» از
> احراز هویت، مجوزدهی، اعتبارسنجی یا حسابرسی عبور نمی‌کند.
>
> **این سند از عبارت‌هایی مانند «Military Grade Security» یا «۱۰۰٪ امن» استفاده نمی‌کند.**
> امنیت با **کنترل‌های مشخص و قابل تست** توصیف می‌شود، نه با صفت.

## ۹٫۱ مدل اعتماد

```
┌──── ناحیه غیرقابل اعتماد ───────────────────────────────────┐
│  مرورگر کاربر · اپلیکیشن موبایل · شبکه عمومی               │
└────────────────────────┬────────────────────────────────────┘
                         │ TLS 1.3
┌────────────────────────▼────────────────────────────────────┐
│  Edge:  Ingress + WAF + Rate Limit سراسری                   │  ◄── Production
└────────────────────────┬────────────────────────────────────┘
                         │
┌────────────────────────▼────────────────────────────────────┐
│  API Gateway  ── مرز اعتماد                                 │
│  اعتبارسنجی JWT · حل مستأجر · RBAC · Rate Limit             │
└────────────────────────┬────────────────────────────────────┘
                         │ توکن داخلی (mTLS در Production)
┌────────────────────────▼────────────────────────────────────┐
│  Domain Services ── ناحیه Zero Trust                        │
│  هیچ سرویسی به فراخواننده اعتماد ضمنی ندارد                 │
│  هر سرویس مجدداً احراز هویت و مجوزدهی می‌کند                │
└────────────────────────┬────────────────────────────────────┘
                         │ TLS + اعتبارنامه اختصاصی
┌────────────────────────▼────────────────────────────────────┐
│  Data: PostgreSQL (نقش به‌ازای سرویس) · Redis · Kafka · S3   │
└─────────────────────────────────────────────────────────────┘
```

**CONSTRAINT — Zero Trust.** یک سرویس **هرگز** فرض نمی‌کند «چون درخواست از شبکه داخلی آمده،
معتبر است». هر سرویس:

1. توکن داخلی را اعتبارسنجی می‌کند (امضا، انقضا، صادرکننده، سرویس مبدأ، سرویس مقصد).
2. `organizationId` را از **Claim امضاشده `org_id`** می‌گیرد — نه از Header — و
   **دوباره** بر آن Scope می‌گذارد (ADR-035).
3. مجوزدهی سطح Object را **مستقل از Gateway** بررسی می‌کند، و برای فراخوان
   سرویسی هم همان بررسی را انجام می‌دهد: توکنی که برای سازمان A امضا شده،
   رکورد سازمان B را نمی‌بیند و تغییر نمی‌دهد.

**CONSTRAINT — Header مرجع نیست (ADR-035).** یک Header امضا ندارد؛ هر چیزی که
بتواند به سرویس برسد می‌تواند بنویسدش. `X-Organization-Id` روی مسیر سرویسی فقط
اجازه دارد با Claim امضاشده موافقت کند. ناهم‌خوانی → `403
SERVICE_TENANT_CONTEXT_INVALID`. نبودِ Claim روی عملیات مستأجر-محدود → همان
`403`، **هرگز `500`**. توکن `RELAY` هرگز `@AllowService` را ارضا نمی‌کند.

## ۹٫۲ احراز هویت

### جریان کاربر (OIDC Authorization Code + PKCE)

```
مرورگر → Keycloak (ورود، MFA اختیاری) → Authorization Code
       → تبادل با PKCE Verifier → Access Token (JWT) + Refresh Token
       → API Gateway: اعتبارسنجی امضا با JWKS
```

| پارامتر           | مقدار                                                            |
| ----------------- | ---------------------------------------------------------------- |
| الگوریتم          | RS256 (کلید نامتقارن؛ Gateway کلید خصوصی ندارد)                  |
| عمر Access Token  | ۱۵ دقیقه                                                         |
| عمر Refresh Token | ۳۰ روز؛ **چرخشی**، استفاده مجدد ممنوع (`refreshTokenMaxReuse=0`) |
| بی‌کاری Session   | ۳۰ دقیقه                                                         |
| بررسی اجباری      | `iss` · `aud` (`rasta-api`) · `exp` · `nbf` · امضا               |
| Cache کلید JWKS   | ۱ ساعت؛ ابطال فوری در صورت خطای اعتبارسنجی                       |

**CONSTRAINT.** توکن **هرگز** در `localStorage` نگهداری نمی‌شود (بردار XSS).
Refresh Token در Cookie با `HttpOnly`, `Secure`, `SameSite=Strict` است.
Access Token فقط در حافظه Frontend.

### Claimهای توکن

```jsonc
{
  "sub": "USR_01JBQ8...",
  "iss": "https://auth.rasta.example/realms/rasta",
  "aud": "rasta-api",
  "exp": 1756200000,
  "org_id": "ORG_01JBQ8...", // مستأجر فعال
  "org_ids": ["ORG_...", "ORG_..."], // همه عضویت‌ها
  "realm_access": { "roles": ["ORGANIZATION_ADMIN", "FLEET_MANAGER"] },
  "preferred_username": "dehyari.admin",
}
```

### سیاست رمز عبور و MFA

| کنترل       | تنظیم                                            |
| ----------- | ------------------------------------------------ |
| طول         | حداقل ۱۲ کاراکتر                                 |
| پیچیدگی     | حرف بزرگ + حرف کوچک + رقم + نویسه ویژه           |
| تاریخچه     | ۳ رمز آخر قابل استفاده مجدد نیست                 |
| Hash        | Argon2                                           |
| Brute-Force | قفل ۱۵ دقیقه پس از ۵ تلاش ناموفق                 |
| **MFA**     | **معماری آماده** — TOTP در Keycloak پیکربندی شده |

**MVP → PRODUCTION.** در MVP، MFA پیکربندی‌شده اما اجباری نیست.
در Production، **اجباری** برای `SYSTEM_ADMIN`، `UNION_ADMIN` و هر کاربر با دسترسی مالی.
این یک تغییر پیکربندی Keycloak است، نه تغییر کد.

### ارتباط سرویس‌به‌سرویس

**MVP:** JWT کوتاه‌عمر (۵ دقیقه) امضاشده با کلید مشترک، حاوی سرویس مبدأ و مقصد.
هر سرویس صادرکننده، مقصد و انقضا را بررسی می‌کند.

**PRODUCTION:** **mTLS** با گواهی کوتاه‌عمر به‌ازای هر Workload (SPIFFE/SPIRE یا Service
Mesh). هویت از گواهی می‌آید، نه از یک راز مشترک — که خودش یک نقطه شکست است.
→ ADR-020

#### دو نوع ترافیک داخلی — Claim `purpose`

یک توکن داخلی می‌تواند دو چیز کاملاً متفاوت بگوید، و تا 2026-08-27 هر دو یک
شکل داشتند. این ابهام یک باگ واقعی ساخت: تنها Endpoint عمومی پلتفرم از راه
Gateway پاسخ `403` می‌داد (D-007). حالا Claim `purpose` آن دو را جدا می‌کند:

| `purpose`     | چه کسی صادر می‌کند                      | معنایش                                                                  | چه چیزی درباره‌اش تصمیم می‌گیرد             |
| ------------- | --------------------------------------- | ----------------------------------------------------------------------- | ------------------------------------------- |
| **`RELAY`**   | فقط `api-gateway` — و **همیشه** همین را | «من درخواست کسی دیگر را Forward می‌کنم». اثبات Hop است، نه هویت بازیگر. | `@Public()` — درست مثل یک تماس گمنام مستقیم |
| **`SERVICE`** | هر سرویس، وقتی از طرف خودش تماس می‌گیرد | «من، سرویس A، دارم سرویس B را صدا می‌زنم»                               | `@AllowService(...)` — نبودش یعنی `403`     |

**قواعد الزام‌آور:**

1. توکن `RELAY` **هرگز** `@AllowService` را ارضا نمی‌کند — حتی روی
   Endpoint ای که هم `@Public` و هم `@AllowService` داشته باشد.
2. `api-gateway` هرگز توکن `SERVICE` صادر نمی‌کند. Gateway یک Filter است،
   نه یک Authority (ADR-020) — پس نباید بتواند توکنی با اقتدار سرویس
   بسازد.
3. توکن داخلی **همیشه** اعتبارسنجی می‌شود، حتی روی Endpoint عمومی. یک
   توکن داخلی جعلی روی `POST /v1/registration-requests` پاسخ
   `401 TOKEN_INVALID` می‌گیرد، نه عبور.
4. توکن بدون Claim `purpose` به‌عنوان `SERVICE` خوانده می‌شود —
   سخت‌گیرانه‌ترین قرائت، و سازگار با هر توکنی که پیش از این تغییر صادر
   شده بود.

**چرا این ترتیب، و نه صرفاً «اول `@Public` را چک کن»:** جابه‌جا کردن ترتیب
بررسی هم باگ را رفع می‌کرد، اما دو چیز را از دست می‌داد — `@AllowService`
روی یک Endpoint عمومی بی‌صدا بی‌اثر می‌شد، و توکن داخلی روی مسیر عمومی
اصلاً اعتبارسنجی نمی‌شد. راه‌حل فعلی هر دو را نگه می‌دارد.

پیاده‌سازی: `packages/nest-common/src/auth/token-verifier.ts` و
`packages/nest-common/src/guards/auth.guard.ts`.

## ۹٫۳ مجوزدهی

### RBAC — لایه اول

| نقش                  | محدوده       | مجوزهای کلیدی                                                      |
| -------------------- | ------------ | ------------------------------------------------------------------ |
| `SYSTEM_ADMIN`       | Platform     | همه (شامل پیکربندی سیستم)                                          |
| `UNION_ADMIN`        | Platform     | عملیات پلتفرم، Marketplace، موتور اقتصادی                          |
| `ORGANIZATION_ADMIN` | Organization | همه در سازمان خود؛ مدیریت کاربران سازمان                           |
| `FLEET_MANAGER`      | Organization | `asset:*` · `fleet:*` · `maintenance:*`                            |
| `OPERATOR`           | Organization | `usage:create` · `maintenance:create` — **فقط دارایی تخصیص‌یافته** |
| `DRIVER`             | Organization | `usage:create` — **فقط دارایی تخصیص‌یافته**                        |
| `PROCUREMENT_USER`   | Organization | `order:*` · `demand:*` · `rfq:read`                                |
| `SUPPLIER`           | Supplier Org | `offer:*` · `order:read,fulfill` — **فقط سفارش‌های خود**           |
| `WORKSHOP`           | Supplier Org | `repair-order:*` — **فقط ارجاع‌شده به خود**                        |
| `CONTRACTOR`         | Supplier Org | `tender:read` · `bid:create` · `statement:create`                  |
| `AUDITOR`            | Province     | **فقط `analytics:read` تجمیعی** — بدون داده سطح ردیف               |

**CONSTRAINT (از سند محصول).** نقش `AUDITOR` (استانداری) دسترسی «تجمیعی و بدون دسترسی به
جزئیات تراکنش‌های فردی» دارد. این در کد یعنی: `AUDITOR` هیچ مجوزی روی `economic-service`،
`marketplace-service` یا هر Endpoint سطح ردیف ندارد — فقط `analytics-service`.

**اجرا و تأیید زنده در `economic-service` (2026-08-29).** سه لایه، به‌عمد:

1. جدول مسیریابی Gateway هیچ Prefix اقتصادی‌ای به `AUDITOR` نمی‌دهد
   (تست: `routes.spec.ts`).
2. هیچ `@Roles` در هیچ Controller اقتصادی نام `AUDITOR` را ندارد.
3. `assertNotAuditor()` در `access.ts` حتی اگر هر دوی بالا ویرایش شوند ردش
   می‌کند.

زنده گرفته شد با توکن واقعی Keycloak: `GET /v1/wallets/me` → `403
INSUFFICIENT_ROLE`، `GET /v1/transactions` → `403`، `GET
/v1/ledger/trial-balance` → `403 FORBIDDEN`.

و خواندن میان‌مستأجری همان‌جا **۴۰۴** گرفت، نه ۴۰۳: `GET /v1/wallets/{id}`
برای کیف پول سازمان دیگر → `404 NOT_FOUND`، تا وجود رکورد فاش نشود.

**وضعیت واقعی دو قاعده این جدول در `maintenance-service` (2026-08-28).** هر دو
**باریک‌تر** از آنچه نوشته شده پیاده شده‌اند، نه تقریبی از آن، و هر دو در ADR-029
با پرسش باز ثبت شده‌اند:

| قاعده جدول                                                | پیاده‌شده                                                                                                                         |
| --------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------- |
| `OPERATOR` → `maintenance:create`، فقط دارایی تخصیص‌یافته | اپراتور در **سازمان خودش** خرابی ثبت می‌کند و فقط گزارش‌های **خودش** را می‌خواند. هیچ ارجاع، شروع، پایان، هزینه یا تأییدی. (Q-24) |
| `WORKSHOP` → `repair-order:*`، فقط ارجاع‌شده به خود       | **پیاده نشد.** نقش `WORKSHOP` در همان باریک‌سازی می‌افتد و هیچ نمی‌بیند — امن به‌صورت پیش‌فرض. (Q-25)                             |

دلیل باریک‌سازی اول، یک انتخاب میان دو شکست است: «دارایی تخصیص‌یافته» واقعیتی نزد
`fleet-service` است که این سرویس امروز نمی‌تواند به‌شکل قابل‌تطبیق با یک توکن
به‌دستش بیاورد، و هر Replica ای از آن در نهایت سازگار است — یعنی اپراتوری که دو
ثانیه پیش دستگاه را تحویل گرفته، اجازه گزارش خرابی نمی‌گیرد. **رد کردن یک گزارش
خرابی به‌خاطر Replica کهنه، بدتر از مزاحمتی است که این قاعده جلویش را می‌گیرد.**

دلیل دومی ساده‌تر است: خدمت‌رسانی به تعمیرگاه یعنی خواندن ردیف‌هایی در تنانت دیگر —
مدلی که این پلتفرم ندارد و **نباید به‌طور تصادفی به‌دست بیاورد**.

### ABAC / سطح Object — لایه دوم (بحرانی‌ترین)

RBAC می‌گوید «این نقش می‌تواند دارایی بخواند». ABAC می‌گوید «**این** دارایی را نه».

```
   درخواست
      │
      ▼
 ۱. توکن معتبر؟                    ── نه ──► 401 UNAUTHENTICATED
      │ بله
      ▼
 ۲. نقش مجوز این عمل را دارد؟      ── نه ──► 403 INSUFFICIENT_ROLE
      │ بله
      ▼
 ۳. کاربر عضو org_id درخواست است؟  ── نه ──► 403 TENANT_MISMATCH
      │ بله
      ▼
 ۴. منبع متعلق به همین org است؟    ── نه ──► 404 NOT_FOUND  ◄── نه 403!
      │ بله
      ▼
 ۵. قواعد ویژه منبع (تخصیص، طرف قرارداد، مهلت مناقصه)
      │
      ▼
    اجازه
```

**چرا مرحله ۴ `404` برمی‌گرداند و نه `403`؟** چون `403` وجود منبع را تأیید می‌کند.
یک مهاجم می‌تواند با شمارش شناسه‌ها بفهمد چه دارایی‌هایی در سازمان‌های دیگر وجود دارند.
`404` این نشتی را می‌بندد.

**قواعد سطح Object نمونه:**

| منبع                 | قاعده اضافی                                                         |
| -------------------- | ------------------------------------------------------------------- |
| `Asset`              | `ownerOrganizationId = ctx.organizationId`                          |
| `Asset` (نقش DRIVER) | علاوه بر بالا: تخصیص فعال به این راننده                             |
| `Order`              | `buyerOrgId = ctx.org` **یا** `supplierOrgId = ctx.org`             |
| `RepairOrder`        | `workshopOrgId = ctx.org` **یا** مالک دارایی                        |
| `Bid`                | نویسنده پیشنهاد **یا** (کارفرمای مناقصه **و** وضعیت ≥ `EVALUATION`) |
| `Contract`           | یکی از `contract_party`                                             |
| `Wallet`             | `organizationId = ctx.org` — بدون استثنا                            |
| `LedgerEntry`        | `organizationId = ctx.org` — بدون استثنا                            |

### Tenant Isolation — دفاع در عمق

| لایه            | مکانیزم                                                | تست                              |
| --------------- | ------------------------------------------------------ | -------------------------------- |
| Gateway         | اعتبارسنجی `X-Organization-Id` در برابر `org_ids` توکن | تست API                          |
| Context         | `AsyncLocalStorage` — `organizationId` غیرقابل تغییر   | تست واحد                         |
| Repository پایه | هر Query خودکار `organizationId` می‌گیرد               | **تست جداسازی به‌ازای هر سرویس** |
| Cache           | هر کلید پیشوند `org:{id}:` دارد                        | تست قاعده‌محور در CI             |
| Event           | Consumer `tenantId` را از Envelope اعمال می‌کند        | تست یکپارچگی                     |
| Database (Prod) | **Row-Level Security** به‌عنوان لایه آخر               | تست یکپارچگی                     |

**تست اجباری به‌ازای هر سرویس:**

```
مستأجر A منبعی می‌سازد → مستأجر B تلاش می‌کند بخواند/تغییر دهد/حذف کند
→ باید 404 بگیرد (نه 403، نه 200)
```

بدون این تست، هیچ Featureای Done نیست.

## ۹٫۴ حفاظت ورودی

| تهدید                   | کنترل                                                                                                                        |
| ----------------------- | ---------------------------------------------------------------------------------------------------------------------------- |
| **SQL Injection**       | Prisma با Query پارامتری. `$queryRaw` فقط با Template Tag و بازبینی؛ الحاق رشته‌ای SQL در ESLint ممنوع                       |
| **XSS**                 | React به‌صورت پیش‌فرض Escape می‌کند. `dangerouslySetInnerHTML` ممنوع. CSP سخت‌گیرانه                                         |
| **CSRF**                | توکن Bearer (نه Cookie Session) برای API. Refresh Cookie با `SameSite=Strict`. Endpointهای مبتنی بر Cookie نیازمند توکن CSRF |
| **Mass Assignment**     | DTOهای Zod صریح. `.strict()` روی هر Schema ورودی — فیلد ناشناخته = خطا                                                       |
| **Path Traversal**      | مسیر فایل هرگز از ورودی کاربر ساخته نمی‌شود؛ کلید S3 از ULID سرور تولید می‌شود                                               |
| **SSRF**                | بدون واکشی URL دلخواه. Webhookها فهرست سفید دارند                                                                            |
| **XXE**                 | پارس XML وجود ندارد                                                                                                          |
| **Prototype Pollution** | Zod به‌جای `Object.assign` روی ورودی خام؛ `__proto__` رد می‌شود                                                              |
| **ReDoS**               | الگوهای Regex بازبینی‌شده؛ محدودیت طول ورودی پیش از تطبیق                                                                    |
| **آپلود بدخواه**        | بررسی Magic Number (نه پسوند) · محدودیت اندازه · S3 جدا · هرگز اجرا نمی‌شود · اسکن بدافزار                                   |

## ۹٫۵ رمزنگاری

| داده                           | در حالت سکون                           | در حال انتقال |
| ------------------------------ | -------------------------------------- | ------------- |
| رمز عبور                       | Argon2 (Keycloak)                      | TLS 1.3       |
| **پیشنهاد مناقصه پیش از مهلت** | **AES-256-GCM با کلید به‌ازای مناقصه** | TLS 1.3       |
| مدارک هویتی (کد ملی و …)       | `pgcrypto` سطح ستون                    | TLS 1.3       |
| اسناد (S3)                     | SSE-S3 / SSE-KMS                       | TLS 1.3       |
| Backup                         | رمزنگاری‌شده پیش از انتقال             | TLS 1.3       |
| کل پایگاه داده                 | رمزنگاری در سطح دیسک (Production)      | TLS 1.3       |

هیچ سرویسی نیست — نه حتی اپراتور پلتفرم. این مستقیماً از الزام سند محصول برای شفافیت و
رهگیری‌پذیری فرآیند مناقصه می‌آید.

**CONSTRAINT:**

```
🚫 هیچ Secret واقعی در Repository — هرگز، حتی موقت
🚫 هیچ Secret در Log، پیام خطا یا Payload رویداد

✅ فقط .env.example با مقادیر آشکارا ساختگی
```

اگر Secret نشت کرد → Runbook: [`runbooks/secret-leak.md`](runbooks/secret-leak.md).
اولین گام همیشه **چرخش**، نه پاک کردن تاریخچه Git.

## ۹٫۸ حسابرسی

هر عمل تغییردهنده وضعیت یک `AuditEvent` تولید می‌کند:

```jsonc
{
  "id": "AUD_01JBQ8...",
  "occurredAt": "2026-08-26T10:15:30.123Z",
  "actor": { "type": "USER", "id": "USR_...", "roles": ["FLEET_MANAGER"] },
  "organizationId": "ORG_...",
  "action": "asset.decommission",
  "resourceType": "Asset",
  "resourceId": "AST_...",
  "outcome": "SUCCESS",
  "changes": { "status": { "from": "ACTIVE", "to": "DECOMMISSIONED" } },
  "reason": "پایان عمر مفید",
  "source": { "ip": "10.0.1.42", "userAgent": "...", "service": "asset-service" },
  "correlationId": "01JBQ8...",
}
```

**همیشه حسابرسی می‌شود:** ورود/خروج · تغییر نقش و عضویت · هر تغییر مالی · هر موافقت ·
انتشار مناقصه و ثبت پیشنهاد · انتقال و اسقاط دارایی · تغییر پیکربندی · دسترسی به داده حساس ·
هر ۴۰۳ (تلاش ناموفق دسترسی).

**CONSTRAINT.** `audit_event` **فقط الحاقی** است — بدون API نوشتن (فقط از Kafka)، بدون
UPDATE، بدون DELETE. در Production زنجیره Hash برای اثبات دست‌نخوردگی افزوده می‌شود.

## ۹٫۹ امنیت در CI/CD

| مرحله                | ابزار                      | سیاست شکست               |
| -------------------- | -------------------------- | ------------------------ |
