## ۱۰٫۱ سه منطق اقتصادی

سند محصول سه مسیر ایجاد ارزش تعریف می‌کند. هر سه باید **از داده واقعی محاسبه‌شدنی** باشند:

| منطق                | تعریف سند محصول                        | منبع داده                                     | مالک محاسبه |
| ------------------- | -------------------------------------- | --------------------------------------------- | ----------- |
| **کاهش هزینه**      | تجمیع تقاضا، کارایی عملیاتی            | قیمت واحد در برابر خط مبنا؛ اثر تجمیع         | `analytics` |

این یک تصمیم صداقت است، نه یک محدودیت فنی.

## ۱۰٫۲ چرا یک سرویس با پنج ماژول

**تصمیم (ADR-013).** `wallet` · `ledger` · `payment` · `commission` · `reward` در یک
`economic-service` با مرزبندی داخلی کامل قرار می‌گیرند.

**دلیل.** تکمیل یک سفارش باید **در یک تراکنش ACID**:

1. Hold کیف پول خریدار را آزاد کند
2. کیف پول تأمین‌کننده را افزایش دهد
3. Journal دفتر کل را Post کند (متوازن)
4. کارمزد را ثبت کند
5. پاداش را اعطا کند

تقسیم این به پنج سرویس یعنی جایگزینی یک تراکنش با یک Saga پنج‌مرحله‌ای که هر مرحله‌اش
می‌تواند شکست بخورد و نیازمند جبران مالی باشد. این **ریسک ناسازگاری مالی** می‌آورد بدون آنکه
مسئله مقیاسی حل کند — هیچ‌کدام از این پنج، پروفایل بار متفاوتی ندارند.

**مرزبندی داخلی (اجباری):**

```
services/economic-service/src/
├── wallet/       ماژول Nest جدا · Schema جدا · بدون Join به ledger
├── ledger/       ماژول Nest جدا · فقط الحاقی
├── payment/      Abstraction ارائه‌دهنده
├── commission/   موتور Rule-Based
├── reward/       موتور Rule-Based
└── shared/       فقط Value Objectهای مالی
```

ماژول‌ها از راه **Interface داخلی** با هم حرف می‌زنند، نه با Join مستقیم به جدول یکدیگر.
استخراج `ledger` (نخستین نامزد، وقتی حجم ورودی از ۱۰ میلیون در ماه بگذرد) یک تغییر
مسیریابی است، نه بازنویسی.

## ۱۰٫۳ Wallet ≠ Ledger

**CONSTRAINT — بنیادی‌ترین قاعده این دامنه:**

| بُعد       | Ledger (دفتر کل)             | Wallet (کیف پول)              |
| ---------- | ---------------------------- | ----------------------------- |
| نقش        | **مرجع حقیقت مالی**          | نمای عملیاتی                  |
| تغییرپذیری | **تغییرناپذیر** — فقط الحاقی | قابل تغییر (با قفل)           |
| اصلاح      | فقط با **Reversal Entry**    | با ورودی جدید دفتر کل         |
| ساختار     | دوطرفه (بدهکار/بستانکار)     | مانده ساده                    |
| پرسش       | «چه اتفاقی افتاد و چرا؟»     | «الان چقدر می‌توانم خرج کنم؟» |
| حسابرسی    | کامل، دائمی                  | مشتق‌شده                      |

**Invariant — با اصلاح ADR-034:**

> **این بند و Journal بند ۱۰٫۴ در نسخه اولیه با هم سازگار نبودند.** اگر Journal
> ثبت Hold حساب کیف پول را بدهکار کند، `ledgerBalance` کم می‌شود _و_
> `pendingBalance` زیاد می‌شود، و `availableBalance` منفی درمی‌آید برای کیف پولی
> که هیچ اشتباهی در آن رخ نداده — مبلغ دو بار شمرده می‌شود. تحلیل کامل و تصمیم
> در **ADR-034**.

پیاده‌سازی: هر سازمان **دو** حساب `LIABILITY` دارد — `LIAB-<ORG>-WALLET` برای
آنچه می‌تواند خرج کند و `LIAB-<ORG>-ESCROW` برای آنچه تعهد شده — و امانت
به‌ازای هر سازمان است، نه یک حساب تجمیعی پلتفرم:

```
wallet.availableBalance = مانده طبیعی LIAB-<ORG>-WALLET
wallet.pendingBalance   = مانده طبیعی LIAB-<ORG>-ESCROW   ( = Σ holdهای فعال )
wallet.ledgerBalance    = availableBalance + pendingBalance

⇒ availableBalance = ledgerBalance − pendingBalance      ✓ (همان رابطه اصلی)
```

هر سه **کاملاً مشتق از دفتر کل**اند، و رابطه بالا در پایگاه داده به‌صورت
`ck_wallet_balances` تحمیل می‌شود — یعنی Invariant این سند یک محدودیت
غیرقابل دور زدن است، نه یک قاعده کد.

**و هر سه در هر تغییر از دفتر کل بازمحاسبه می‌شوند، نه افزایش تدریجی.** افزایش
تدریجی یک Read-Modify-Write است و زیر همروندی یک به‌روزرسانی گم می‌شود — همان
باگی که فاز نگهداری با مجموع هزینه گرفت (ADR-028).

هیچ موجودی کیف پولی بدون ورودی متناظر در دفتر کل تغییر نمی‌کند. یک Workflow روزانه
(`LedgerBalanceAuditWorkflow`) این تطابق را بررسی می‌کند؛ انحراف = هشدار بحرانی.

## ۱۰٫۴ مدل دفتر کل

### نمودار حساب‌ها

| نوع حساب    | نمونه                                    | ماهیت طبیعی |
| ----------- | ---------------------------------------- | ----------- |
| `ASSET`     | موجودی کیف پول کاربر (از دید پلتفرم)     | بدهکار      |
| `LIABILITY` | بدهی پلتفرم به کاربر بابت موجودی کیف پول | بستانکار    |
| `REVENUE`   | درآمد کارمزد پلتفرم                      | بستانکار    |
| `EXPENSE`   | هزینه پاداش پرداختی                      | بدهکار      |
| `EQUITY`    | حقوق صاحبان                              | بستانکار    |

کد حساب: `<TYPE>-<ORG>-<PURPOSE>` — مثلاً `LIAB-ORG_01JBQ8-WALLET`.

### مثال کامل: تکمیل یک سفارش

سفارش ۱۰٬۰۰۰٬۰۰۰ ریال · کارمزد ۲٪ (۲۰۰ Basis Point) = ۲۰۰٬۰۰۰ ریال

**۱) ثبت سفارش — Hold وجه:**

```
Journal: FUNDS_HELD (TXN_01JBQ8...)
  بدهکار   LIAB-BUYER-WALLET          10,000,000    (از مانده قابل خرج خارج شد)
  بستانکار LIAB-BUYER-ESCROW          10,000,000    (به امانت خود خریدار رفت)
                                      ─────────────
  توازن: 10,000,000 = 10,000,000  ✓
```

> حساب امانت **مال خریدار** است، نه پلتفرم (ADR-034). وجه در امانت هنوز مال
> اوست؛ فقط تعهد شده. این همان چیزی است که `pendingBalance` را یک مانده واقعی
> دفتر کل می‌کند به‌جای یک `SUM` روی جدول Hold.

**۲) تأیید دریافت — تسویه و کارمزد:**

```
Journal: SETTLEMENT (TXN_01JBQ8...)
  بدهکار   LIAB-BUYER-ESCROW          10,000,000
  بستانکار LIAB-SUPPLIER-WALLET        9,800,000    (خالص به تأمین‌کننده)
  بستانکار REV-PLATFORM-COMMISSION       200,000    (درآمد کارمزد)
                                      ─────────────
  توازن: 10,000,000 = 10,000,000  ✓
```

> **بدون قاعده کارمزد فعال، خط سوم اصلاً نوشته نمی‌شود** و Journal دو خطی است.
> یک ورودی صفر، `CHECK (amount_minor > 0)` را می‌شکند و چیزی هم نمی‌گوید؛
> «هیچ قاعده‌ای مطابقت نکرد» روی ردیف `commission` ثبت می‌شود، که جای درستش
> برای یک حسابرس است.

**۳) اعطای پاداش (از سهم اتحادیه از کارمزد — مطابق سند محصول):**

```
Journal: REWARD_GRANT (RWD_01JBQ8...)
  بدهکار   EXP-PLATFORM-REWARD            20,000
  بستانکار LIAB-BUYER-WALLET               20,000    (اعتبار به کیف پول کاربر)
                                      ─────────────
  توازن: 20,000 = 20,000  ✓
```

**۴) اصلاح (اگر لازم شد) — هرگز UPDATE:**

```
Journal: REVERSAL (reverses_id = <journal اصلی>)
  ← دقیقاً همان ورودی‌ها با جهت معکوس
  ← سپس Journal صحیح جدید Post می‌شود
```

### تضمین‌های پایگاه داده

```sql
-- ۱. تغییرناپذیری — Trigger، نه فقط قرارداد کد
CREATE TRIGGER trg_ledger_entry_immutable
  BEFORE UPDATE OR DELETE ON ledger_entry
  FOR EACH ROW EXECUTE FUNCTION reject_ledger_mutation();

-- ۲. مبلغ همیشه مثبت؛ جهت در ستون direction است
CHECK (amount_minor > 0)

-- ۳. توازن — بررسی در Domain + حسابرسی روزانه
SELECT journal_id FROM ledger_entry
GROUP BY journal_id, currency
HAVING SUM(CASE WHEN direction='DEBIT' THEN amount_minor ELSE -amount_minor END) <> 0;
```

## ۱۰٫۵ چرخه Hold / Release

مستقیماً از الزام سند محصول: تسویه **پس از تأیید دریافت توسط کاربر**.

```
ORDER_CREATED
     │
     ▼
 placeHold(orderAmount)
     │  availableBalance −= amount
     │  pendingBalance   += amount
     │  Journal: ORDER_HOLD
     ▼
 ┌───────────────────────────────────────┐
 │  وجه در امانت (Escrow)               │
 └───┬─────────────────┬─────────────┬───┘
     │ تأیید دریافت    │ لغو        │ اعتراض
     ▼                 ▼             ▼
 releaseAndSettle  refundHold   HOLD می‌ماند
  ├ تأمین‌کننده +  ├ خریدار +    └ تا رفع اختلاف
  ├ کارمزد →      └ Journal:       (بدون حرکت خودکار)
  │  درآمد          ORDER_REFUND
  └ Journal:
    ORDER_SETTLEMENT
```

**CONSTRAINT.** اعتراض ثبت‌شده = **توقف کامل تسویه**. هیچ حرکت خودکاری تا رفع اختلاف
انجام نمی‌شود. سند محصول این را «امکان ثبت اعتراض پیش از آزادسازی کامل تسویه» می‌نامد.

### همزمانی

```sql
BEGIN;
SELECT * FROM wallet WHERE id = $1 FOR UPDATE;   -- قفل ردیف
-- بررسی availableBalance ≥ amount
-- درج hold، Post کردن journal، به‌روزرسانی wallet
COMMIT;
```

~~قفل Redis به‌عنوان لایه دوم برای عملیات چندکیف‌پولی (تسویه بین دو سازمان).~~
**جایگزین شد (ADR-031):** ترتیب قطعی قفل‌گیری بر حسب `wallet.id` صعودی. هر دو
کیف پول در یک پایگاه داده‌اند، پس قفل ردیف از یک قفل بیرونی قوی‌تر است — و
یک قفل Redis که زیر تراکنش باز منقضی شود، دو نویسنده هم‌زمان می‌سازد که پایگاه
داده نمی‌سازد.

تست همزمانی اجباری: ۱۰۰ برداشت موازی از یک کیف پول → دقیقاً به تعداد موجودی
موفق. **اجرا شد و سبز است** (`test/wallet-concurrency.int-spec.ts`)، همراه با
ده تسویه معکوس هم‌زمان میان یک جفت سازمان که Deadlock نمی‌سازند.

## ۱۰٫۶ Abstraction پرداخت

```typescript
interface PaymentProvider {
  readonly name: string;
  authorize(req: AuthorizeRequest): Promise<AuthorizeResult>;
  capture(req: CaptureRequest): Promise<CaptureResult>;
  refund(req: RefundRequest): Promise<RefundResult>;
  getStatus(providerRef: string): Promise<PaymentStatus>;
}
```

| پیاده‌سازی            | محیط                | رفتار                                                  |
| --------------------- | ------------------- | ------------------------------------------------------ |
| `MockPaymentProvider` | local · test · demo | موفقیت قطعی؛ شکست قابل تحریک برای تست؛ تأخیر شبیه‌سازی |
| `<PSP>Provider`       | Production          | **ساخته نشده.** نیازمند تصمیم و مجوز — OPEN QUESTION   |

**وضعیت واقعی (2026-08-29).** پیاده‌سازی شده. شکست **قابل تحریک از درخواست**
است (`instrument: "fail:<CODE>"`, `fail-capture:<CODE>`, `fail-refund:<CODE>`)،
نه تصادفی — یک ارائه‌دهنده که یک تماس از بیست را تصادفی رد کند، Suite تست را
غیرقابل‌اعتماد می‌کند و چیزی را ثابت نمی‌کند. تأخیر شبیه‌سازی هم **ثابت** است، نه
تصادفی. `simulated: true` روی هر ردیف، هر رویداد و هر پاسخ API می‌آید، و
`GET /v1/wallets/provider` آن را صریحاً اعلام می‌کند.

**CONSTRAINT:**

```
🚫 هیچ ادعایی درباره اتصال بانکی واقعی — در کد، UI، مستند یا Demo
🚫 هیچ منطق مالی وابسته به یک PSP خاص
✅ Domain Core فقط Interface را می‌شناسد
✅ افزودن PSP واقعی = یک کلاس جدید + یک رکورد پیکربندی
✅ UI صریحاً «حالت نمایشی» را نشان می‌دهد وقتی Provider، Mock است
```

**PaymentIntent** الگوی مرکزی است: هر پرداخت یک `PaymentIntent` با `Idempotency-Key` دارد
که چرخه `CREATED → AUTHORIZED → CAPTURED | FAILED | REFUNDED` را طی می‌کند. این تضمین
می‌کند تعویض Provider، مدل دامنه را دست نمی‌زند.

## ۱۰٫۷ موتور کارمزد

**CONSTRAINT (از سند محصول).** «تعیین درصد دقیق کارمزد در هر نوع تراکنش، ساختگی و پیشینی
نیست و باید پس از بررسی هزینه واقعی … و الزامات قانونی تعیین شود.»

بنابراین: **هیچ نرخی Hard-Code نمی‌شود و هیچ نرخ پیش‌فرض تجاری در Seed نیست.**

```
commission_rule
  id, organizationId (NULL = سراسری), transactionType,
  rateBasisPoints,        -- عدد صحیح؛ ۲۵۰ = ۲٫۵٪
  minAmountMinor, maxAmountMinor,   -- کف و سقف
  validFrom, validTo,     -- نسخه‌دار در زمان
  status, createdBy
```

انواع تراکنش: `MARKETPLACE_ORDER` · `MAINTENANCE_SERVICE` · `LOGISTICS` ·
`CONSTRUCTION_STATEMENT` · `PROCUREMENT_ORDER`

**قواعد موتور:**

| قاعده                                                  | چرا                                                    |
| ------------------------------------------------------ | ------------------------------------------------------ |
| نرخ بر حسب **Basis Point** صحیح، نه درصد اعشاری        | «۲٫۵٪» باید دقیقاً ۲۵۰ باشد، نه ۰٫۰۲۴۹۹۹۹۹۹۹۹۹۹۹۹۹۸    |
| گرد کردن **نیم به بالا** روی مقدار مطلق                | قاعده ثابت و مستند؛ بدون خطای انباشته                  |
| قاعده **نسخه‌دار در زمان**                             | تراکنش قدیمی باید با نرخ زمان خودش قابل بازمحاسبه باشد |
| قاعده اختصاصی سازمان بر قاعده سراسری اولویت دارد       | امکان توافق‌های خاص بدون شاخه‌بندی کد                  |
| تغییر نرخ نیازمند `SYSTEM_ADMIN` و در Audit ثبت می‌شود | سند محصول: تغییر از راه کارگروه راهبری تصویب می‌شود    |
| **بدون نرخ فعال = بدون کارمزد** (نه خطا، نه پیش‌فرض)   | صریح‌تر از حدس زدن                                     |

## ۱۰٫۸ موتور پاداش

زنجیره طراحی از سند محصول:

```
رفتار مطلوب → امتیاز → سطح/مزیت → پاداش → مشارکت بیشتر → داده بهتر → ارزش اقتصادی
```

```
reward_rule
  id, organizationId (NULL = سراسری),
  triggerEvent,           -- USAGE_RECORDED, MAINTENANCE_COMPLETED, REVIEW_SUBMITTED, ...
  condition,              -- JSON: مثلاً «ثبت در ۲۴ ساعت اول»
  points,
  periodCap,              -- سقف در هر دوره — کنترل ضدتقلب
  periodType,             -- DAY | WEEK | MONTH
  validFrom, validTo, status
```

رفتارهای امتیازآور (از سند محصول): ثبت به‌موقع اطلاعات · ثبت منظم کارکرد · انجام سرویس در
موعد · ثبت دقیق مصرف · پرداخت به‌موقع · کاهش لغو سفارش · ثبت بازخورد و ارزیابی.

**منبع تأمین پاداش (نقل سند):** «از سهم تعریف‌شده اتحادیه از کارمزد دریافتی».
بنابراین هر `REWARD_GRANTED` **پولی‌شده** یک Journal با بدهکار
`EXP-PLATFORM-REWARD` می‌زند — پاداش یک هزینه واقعی ثبت‌شده است، نه یک عدد
نمایشی.

> **اصلاح — ADR-033.** «هر `REWARD_GRANTED` یک Journal می‌زند» با Q-09 سازگار
> نیست: نرخ تبدیل امتیاز به اعتبار هنوز تصمیم‌گیری نشده، و یک نرخ پیش‌فرض یعنی
> اختراع یک عدد تجاری (ADR-023). پیاده‌سازی: `reward_rule.creditPerPointMinor`
> **اختیاری و بدون پیش‌فرض** است. با آن خالی، پاداش فقط امتیاز است و **هیچ
> Journal نمی‌زند** — یک ورودی صفر `CHECK (amount_minor > 0)` را می‌شکند و
> چیزی هم نمی‌گوید. با آن پر، Journal دقیقاً همان شکل مثال سوم بند ۱۰٫۴ است.
> رویداد `monetised` را حمل می‌کند تا مصرف‌کننده مجبور نباشد از یک صفر حدس
> بزند، و `ck_reward_monetisation` نمی‌گذارد این پرچم دروغ بگوید.

**سطح و نشان:** `RewardLevel` بر مبنای امتیاز انباشته. مزایا (اولویت پشتیبانی، دسترسی
زودتر به ظرفیت محدود) **پیکربندی‌اند**.

**CONSTRAINT — Cashback.** سند محصول Cashback را «در صورت امکان و پس از بررسی مقرراتی»
مشروط کرده است. بنابراین `RewardType.CASHBACK` پشت **Feature Flag با پیش‌فرض خاموش** است.

**قید طراحی (نقل سند).** «از الگوهای کودکانه یا سرگرمی‌محور پرهیز کند.»
پیامد UI: بدون انیمیشن جشن، بدون Confetti. شاخص حرفه‌ای.

## ۱۰٫۱۰ الگوی تسویه

> **وضعیت واقعی (2026-08-29) — ADR-031.** تسویه **یک تراکنش ACID** است، نه یک
> Workflow در Temporal. دلیلش خودِ CONSTRAINT پایین همین بند است: مراحل ۳ و ۴
> در یک تراکنش پایگاه داده‌اند و پس از مرحله ۳ هیچ جبران خودکاری وجود ندارد —
> یعنی هسته این فرآیند اصلاً Saga نیست، و Temporal برای چیزی که جبران ندارد
> هماهنگی اضافه نمی‌کند. ترتیب واقعی، در یک `BEGIN … COMMIT`:
>
> ```
>   قفل ردیف تراکنش                       ← یک تسویه، نه دو
>   بررسی ماشین حالت                      ← هرگز از DISPUTED
>   قفل هر دو کیف پول، به ترتیب صعودی id  ← Deadlock ساختاراً غیرممکن
>   محاسبه کارمزد با نرخ زمانِ تراکنش      ← نه نرخ امروز
>   Post کردن یک Journal متوازن
>   بستن Hold (بدون Journal دوم)
>   بازمحاسبه هر دو مانده از دفتر کل
>   ثبت کارمزد و تسویه، و انتقال به SETTLED
>   نوشتن SETTLEMENT_COMPLETED در Outbox
> ```
>
> **Redis در هیچ مسیر مالی استفاده نمی‌شود** (انحراف آگاهانه از بند ۱۰٫۵):
> هر دو کیف پول در یک پایگاه داده‌اند، پس قفل ردیف از یک قفل بیرونیِ
> منقضی‌شدنی قوی‌تر است، و ترتیب قطعی `wallet.id` جای قفل توزیع‌شده را
> می‌گیرد. تسویه شکست‌خورده وجه را در Hold نگه می‌دارد؛ هیچ بازگشت خودکاری.
> مرحله ۵ (پاداش) بیرون تراکنش است و هرگز تسویه را Rollback نمی‌کند.

```
ORDER_RECEIPT_CONFIRMED
        │
        ▼
SettlementWorkflow (Temporal، صف rasta-settlement) — تصمیم معماری، هنوز اجرا نشده
  ۱. Activity: بارگذاری تراکنش و اعتبارسنجی وضعیت
  ۲. Activity: محاسبه کارمزد از CommissionRule فعال در زمان تراکنش
  ۳. Activity: Post کردن Journal تسویه (اتمیک، متوازن)
  ۴. Activity: به‌روزرسانی کیف پول‌ها (تحت قفل)
  ۵. Activity: ارزیابی و اعطای پاداش
  ۶. Activity: انتشار SETTLEMENT_COMPLETED
```

**CONSTRAINT.** مراحل ۳ و ۴ در **یک تراکنش پایگاه داده**اند. اگر ۵ شکست بخورد، تسویه
معتبر می‌ماند و پاداش جداگانه Retry می‌شود — پاداش هرگز تسویه را Rollback نمی‌کند.

**بدون جبران خودکار پس از مرحله ۳.** اگر تسویه شکست بخورد، وجه در Hold می‌ماند و هشدار
انسانی صادر می‌شود. برگرداندن خودکار پول ریسک بزرگ‌تری از مشکل اصلی است.

## ۱۰٫۱۲ تست‌های اجباری یکپارچگی مالی

هیچ تغییری در `economic-service` بدون سبز بودن این‌ها Merge نمی‌شود.
**همه سبزند (2026-08-29)** — روی PostgreSQL و Kafka واقعی، بدون Mock:

| تست                         | ادعا                                                                    | کجا                                                       |
| --------------------------- | ----------------------------------------------------------------------- | --------------------------------------------------------- |
| **توازن Journal**           | هر Journal: `Σ debit = Σ credit` بر حسب هر ارز                          | `financial-consistency` + `trg_journal_balanced` معوق     |
| **تغییرناپذیری دفتر کل**    | UPDATE و DELETE روی `ledger_entry` خطا می‌دهند                          | `ledger-immutability` — از **SQL خام**، نه از لایه Domain |
| **صحت Reversal**            | معکوس کردن یک Journal، مانده حساب‌ها را به دقیقاً وضعیت قبل برمی‌گرداند | `financial-consistency`                                   |
| **تطابق کیف پول و دفتر کل** | `wallet.ledgerBalance = Σ(ledger_entry)` برای هر کیف پول                | `financial-consistency` + `wallet-concurrency`            |
| **Idempotency**             | ثبت دو باره یک تراکنش با یک کلید → یک اثر، یک پاسخ                      | `idempotency` — اثر روی دفتر کل بررسی می‌شود، نه فقط پاسخ |
| **همزمانی**                 | ۱۰۰ برداشت موازی → دقیقاً به تعداد موجودی موفق؛ هرگز مانده منفی         | `wallet-concurrency`                                      |
| **صحت کارمزد**              | نرخ زمان تراکنش اعمال می‌شود، نه نرخ فعلی                               | `commission/rule-engine.spec`                             |
| **سقف پاداش**               | `periodCap` هرگز نقض نمی‌شود، حتی با رویدادهای موازی                    | `reward-cap` — بیست محرک هم‌زمان                          |
| **Tenant Isolation**        | سازمان A هرگز کیف پول یا دفتر کل سازمان B را نمی‌بیند                   | `tenant-isolation`                                        |
| **ترتیب تسویه**             | تسویه بدون تأیید دریافت غیرممکن است                                     | `financial-consistency` + ماشین حالت (یال وجود ندارد)     |
| **توقف با اعتراض**          | اعتراض ثبت‌شده → هیچ حرکت مالی خودکار                                   | `financial-consistency`                                   |
| **اتمیک بودن تسویه**        | شکست میانی → نه Journal، نه تغییر مانده، نه کارمزد؛ وجه در Hold می‌ماند | `settlement-atomicity` (افزوده — ADR-031)                 |
| **Outbox**                  | تغییری که Rollback شود هرگز رویدادی منتشر نمی‌کند                       | `outbox` (افزوده — ADR-021)                               |
