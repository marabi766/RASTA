# ۱۶ — UI Architecture

> Next.js · React · TypeScript · Tailwind. **RTL و فارسی‌محور از پایه، نه به‌عنوان وصله.**
> هدف: Demo بسیار حرفه‌ای، بدون ایجاد بدهی UI که بعداً نیاز به بازنویسی گسترده داشته باشد.

## ۱۶٫۱ Stack

| لایه          | انتخاب                       | دلیل                                                  |
| ------------- | ---------------------------- | ----------------------------------------------------- |
| Framework     | Next.js 15 (App Router)      | SSR برای داشبورد سنگین، Streaming، Route Handler، PWA |
| UI            | React 19 + TypeScript strict | Server Component، مدل داده یکسان با Backend           |
| Styling       | Tailwind CSS v4              | **Logical Property بومی** → RTL بدون شاخه‌بندی کد     |
| Component     | Radix UI Primitives          | دسترس‌پذیر و بدون Style؛ ما ظاهر را کنترل می‌کنیم     |
| فرم           | React Hook Form + Zod        | **همان Schemaهای `@rasta/contracts`** — یک منبع حقیقت |
| داده سمت سرور | TanStack Query               | Cache، Retry، به‌روزرسانی خوش‌بینانه                  |
| نمودار        | Recharts                     | سبک، سازگار با SSR، قابل تم‌بندی                      |
| جدول          | TanStack Table               | مرتب‌سازی، فیلتر و صفحه‌بندی سمت سرور                 |
| آیکون         | Lucide React                 | ثابت، Tree-shakeable                                  |
| تقویم         | `date-fns-jalali`            | تبدیل هجری شمسی **فقط در لایه ارائه**                 |
| احراز هویت    | جریان سمت سرور (ADR-059)     | Authorization Code + PKCE، **در سرور نه در مرورگر**   |

> **این ردیف در 2026-09-21 عوض شد، و دلیلش یک تناقض در همین سند بود.**
> `§ ۱۶٫۱۱` می‌گوید Refresh Token باید در Cookie با `HttpOnly` بنشیند، و یک کتابخانهٔ جاوااسکریپتِ مرورگر —
> که `oidc-client-ts` است — نمی‌تواند چنین Cookie ای بنویسد؛ معنای `HttpOnly` دقیقاً همین است. پس دو بند با هم
> شدنی نبودند. `ADR-059` این را یک‌بار بست: جریان در **Route Handler های Next.js** اجرا می‌شود، هیچ توکنی به
> جاوااسکریپت مرورگر نمی‌رسد، و هر دو بند `§ ۱۶٫۱۱` واقعاً برآورده می‌شوند به‌جای نیمی از آن‌ها.

**CONSTRAINT.** Zod Schema از `@rasta/contracts` می‌آید. یک تعریف: هم اعتبارسنجی فرم،
هم اعتبارسنجی سرور، هم نوع TypeScript، هم مستند OpenAPI. اگر فرم و API از هم واگرا شوند،
Build می‌شکند.

**فرم‌های Server Action — `<select>` با `key`.** React مقدار `defaultValue` یک `<select>` را فقط هنگام Mount می‌خواند و
Reset فرم پس از هر Action همان انتخابِ Mount را برمی‌گرداند؛ پس انتخابِ فرمی که رد شد و مقدارهای شخص را پس داد خالی می‌شد.
هر `<select>` که پیش‌فرضش از وضعیت برگشتی Action می‌آید، `key={values.x}` هم‌نام `defaultValue={values.x}` را می‌گیرد (پیش از
`{...control}`)؛ ورودی متنی، `textarea`، چک‌باکس و رادیو نیازی ندارند. محافظ: `apps/web/src/app/select-reset.spec.tsx`.

## ۱۶٫۳ RTL و فارسی‌محوری

این بخش **الزام معماری** است، نه سلیقه.

```html
<html lang="fa" dir="rtl"></html>
```

| قاعده                                           | چرا                                            |
| ----------------------------------------------- | ---------------------------------------------- |
| **همیشه** Logical Property                      | `ms-4` نه `ml-4`؛ `text-start` نه `text-left`  |
| هرگز `left`/`right` فیزیکی در چیدمان            | در RTL معکوس نمی‌شوند                          |
| آیکون‌های جهت‌دار در RTL آینه می‌شوند           | فلش «بعدی» به چپ اشاره می‌کند                  |
| **اعداد در داده و API همیشه لاتین**             | تبدیل به فارسی فقط در لحظه رندر                |
| **تاریخ در پایگاه داده و API همیشه میلادی/UTC** | تبدیل به هجری شمسی فقط در لحظه رندر            |
| نیم‌فاصله (ZWNJ) در متن فارسی رابط              | «می‌شود» نه «می شود»                           |
| نویسه‌های استاندارد فارسی                       | «ی» و «ک» فارسی، نه عربی                       |
| جهت‌دهی صحیح متن دوزبانه                        | شناسه‌های لاتین داخل متن فارسی با `dir="auto"` |

**متن آزاد و پیام‌های فارسی.** یک تعریف واحد برای «متن نمایشی» (توضیح، یادداشت، عنوان، دلیل) هست:
`displayText` / `DISPLAY_TEXT_PATTERN` در `packages/contracts/src/common/text.ts`؛ همه‌ی سرویس‌ها و پورتال همان را
وارد می‌کنند و نسخه‌ی محلی ندارند (آزمون `display-text-sites.spec.ts` این را نگه می‌دارد). علامت‌های «،» «؛» «؟»
و `? ! ; % " … –` مجازند؛ کشیده (U+0640)، ZWJ، فاصله‌ی صفر‌عرض (غیر از نیم‌فاصله)، کنترل‌ها
و همه‌ی کنترل‌های جهت‌دهی (`Bidi_Control`) ردند. فاصله‌ی سفید همان `\s` پیشین است (تب، خط جدید، BOM و
جداکننده‌های خط/بند هم می‌گذرند) تا مقدار ذخیره‌شده‌ی پیش از این قاعده بی‌تغییر دوباره ارسال شود؛ سخت‌گیرتر
کردن آن پیشنهاد جدا است و باید نخست مقدارهای ذخیره‌شده را یکدست کند. نام شخص و نام سازمان عمداً محدودترند (نام
سازمان فقط «،» را افزون دارد) و فاصله‌ی سفیدشان نیز همان `\s` پیشین است. هیچ جمله‌ی انگلیسی سرویس به کاربر نشان داده نمی‌شود: `mapProblemToFields` جمله‌ی شناخته‌شده را
فارسی می‌کند، و برای ناشناخته جمله‌ی عمومی فارسی (یا `fallback` همان فرم) را می‌گوید و فقط یک رکورد تشخیصی
پاک‌سازی‌شده (وضعیت، کد، مسیر فیلد، طول و هش کوتاه — بدون متن) در لاگ سرور می‌نویسد (S-09). اعتبارسنجی
محلی پورتال هم یک مرز دارد، `apps/web/src/lib/form-issues.ts`: جمله‌ای که نویسنده‌ی طرح به فارسی نوشته همان را
نشان می‌دهد، و جمله‌ی پیش‌فرض Zod به جمله‌ی فارسی دقیق (با حد) یا یک جمله‌ی عمومی تبدیل می‌شود؛ آزمون
`form-issues.spec.ts` هر خواندن دیگرِ `ZodError.issues` را رد می‌کند. دلیل ثبت‌شده‌ی تراکنش فقط اگر یکی از
دلیل‌های ماشینی شناخته‌شده باشد ترجمه می‌شود و هر دلیل دیگر همان‌طور که نوشته شده نمایش داده می‌شود. کدهای
نقش/وضعیت/نوع هرگز خام نمایش داده نمی‌شوند؛ هر صفحه از نقشه‌ی برچسب فارسی همان واژگان می‌گذرد.

**فونت:** Vazirmatn (متغیر) برای فارسی، `ui-monospace` برای شناسه و کد.
بارگذاری محلی با `next/font` — بدون CDN خارجی (کنترل CSP و کارایی).

**تست RTL اجباری.** هر Component در هر دو جهت Snapshot می‌شود. یک Component که فقط در
LTR درست است، در این پروژه شکسته است.

## ۱۶٫۴ Design System

### Design Token

```css
:root {
  /* ---- رنگ‌های برند ---- */
  --color-primary-50 … --color-primary-950;   /* سبز-فیروزه‌ای: هویت رستا */
  --color-neutral-50 … --color-neutral-950;

  /* ---- رنگ‌های معنایی ---- */
  --color-success: …;   /* فعال، تأییدشده، تحویل‌شده */
  --color-warning: …;   /* سررسید نزدیک، در انتظار تأیید */
  --color-danger:  …;   /* خرابی، رد شده، منقضی */
  --color-info:    …;   /* اطلاع‌رسانی */

  /* ---- سطح ---- */
  --surface-base / --surface-raised / --surface-overlay / --surface-sunken;

  /* ---- تایپوگرافی (مقیاس ۱٫۲۵ از پایه ۱rem) ---- */
  --text-xs: 0.75rem; --text-sm: 0.875rem; --text-base: 1rem;
  --text-lg: 1.25rem; --text-xl: 1.5625rem; --text-2xl: 1.953rem; --text-3xl: 2.441rem;
  --leading-tight / --leading-normal / --leading-relaxed;

  /* ---- فاصله (پایه ۴px) ---- */
  --space-1: 0.25rem … --space-16: 4rem;

  /* ---- شعاع، سایه، انیمیشن ---- */
  --radius-sm … --radius-full;
  --shadow-sm … --shadow-lg;
  --duration-fast: 150ms; --duration-normal: 250ms;
  --ease-out: cubic-bezier(0.16, 1, 0.3, 1);
}
```

**قاعده.** هیچ رنگ، فاصله یا اندازه‌ای در Component به‌صورت Hard-Code نوشته نمی‌شود.
همه از Token. این تفاوت میان «Design System» و «مجموعه‌ای از Componentها» است.

**Dark Mode.** Tokenها بازتعریف می‌شوند، یک‌بار برای ترجیح سیستم‌عامل
(`prefers-color-scheme: dark`، مگر آنکه سند صراحتاً `data-theme="light"` بخواهد) و
یک‌بار برای انتخاب صریح سند (`[data-theme="dark"]`). هیچ Component شاخه روشن/تیره ندارد.

**Token های هدف‌محور.** رَمپ یک پالت است، نه یک تصمیم. اینکه دکمه اصلی کدام پله را
بردارد در هر تم فرق می‌کند، چون پله‌ای که در تم روشن متن سفید را با نسبت ۴٫۵:۱ نگه
می‌دارد در تم تیره خوانا نیست. پس `--color-accent`، `--color-accent-hover`،
`--color-accent-text` و `--color-accent-on-surface` این انتخاب را یک‌بار و در جایی که
تم معلوم است انجام می‌دهند. به همین ترتیب `--color-border` جداکننده تزیینی است و
`--color-border-strong` مرز یک کنترل، که معیار ۱٫۴٫۱۱ برای آن ۳:۱ می‌خواهد.

**اندازه‌گیری، نه ادعا.** همه جفت‌های مجاز در `apps/web/src/design-contrast.spec.ts`
در هر دو تم محاسبه می‌شوند؛ جفتی که به AA نرسد، Build را می‌شکند.

## ۱۶٫۵ الگوهای کلیدی

### StatusBadge — زبان بصری وضعیت

هر وضعیت در پلتفرم یک رنگ و یک نماد ثابت دارد، در همه صفحات:

| وضعیت                                                                                 | رنگ     |
| ------------------------------------------------------------------------------------- | ------- |
| `ACTIVE` · `APPROVED` · `COMPLETED` · `SETTLED` · `ASSIGNED` · `SIGNED` · `EFFECTIVE` | success |
| `PENDING_APPROVAL` · `BID_OPEN` · `IN_PROGRESS` · `PROPOSED`                          | warning |
| `REJECTED` · `CANCELLED` · `FAILED` · `OUT_OF_SERVICE` · `DECOMMISSIONED`             | danger  |
| `DRAFT` · `IDLE` · `REGISTERED`                                                       | neutral |
| `IN_MAINTENANCE` · `EVALUATION`                                                       | info    |

> **سه وضعیت در 2026-09-21 افزوده شد (`EXP-002`).** `ASSIGNED`، `REGISTERED` و `DECOMMISSIONED` وضعیت‌های واقعی
> `asset-service` بودند و این جدول نامشان نبرده بود، پس هر سه به رنگ پیش‌فرض `neutral` می‌افتادند. برای دوتاشان
> آن رنگ غلط بود: یک دستگاهِ تخصیص‌یافته در حال کار است، و یک دستگاهِ از رده خارج برای همیشه رفته — و کسی که
> فهرست را برای پیدا کردن دستگاهِ قابل استفاده می‌خواند، این دو را نباید کنار «بیکار» ببیند.

> **`SIGNED`، `PROPOSED` و `EFFECTIVE` افزوده شد (`EXP-004`، برش قراردادها).** `contract-service` این سه وضعیت
> را برای قرارداد (`SIGNED`) و الحاقیه (`PROPOSED`، `EFFECTIVE`) دارد و این جدول نامشان نبرده بود. `SIGNED` و
> `EFFECTIVE` به رنگ موفق‌اند — قرارداد در جریان و الحاقیهٔ لازم‌الاجرا، هر دو حالت خوب پایدارند، مثل `APPROVED`؛
> `PROPOSED` به رنگ هشدار — الحاقیه‌ای که هنوز امضای یک یا هر دو طرف را ندارد، چیزی است که خوانندهٔ فهرست باید
> متوجه‌اش شود.

### WorkflowStepper — گردش‌کار قابل مشاهده

مناقصه، سفارش و صورت‌وضعیت همگی State Machine دارند. کاربر باید **همیشه بداند کجاست و
مرحله بعد چیست**:

```
ثبت نیاز ✓ ── اسناد ✓ ── موافقت ✓ ── انتشار ● ── پیشنهاد ○ ── ارزیابی ○ ── قرارداد ○
                                       ↑ اینجا
```

با نمایش مسئول هر مرحله و مهلت آن. این مستقیماً الزام «شفافیت و ثبت کامل سوابق» سند محصول است.

### MoneyField و نمایش پول

```
ذخیره/API:  "10000000"  (رشته، ریال)
نمایش:      ۱۰٬۰۰۰٬۰۰۰ ریال   (رقم فارسی، جداکننده هزارگان)
ورودی:      کاربر «۱۰٬۰۰۰٬۰۰۰» یا «10000000» می‌نویسد → نرمال به bigint
```

هرگز `parseFloat`. هرگز اعشار شناور. تبدیل رقم فارسی/عربی به لاتین در نرمال‌سازی ورودی.

### DateField

نمایش و ورودی هجری شمسی؛ ذخیره و ارسال ISO-8601 UTC. تقویم با ناوبری فارسی و نام ماه‌های
شمسی. نمایش دوگانه در Tooltip برای رفع ابهام.

> `WEB_PROJECT_ROLES` (پیش‌فرض `ORGANIZATION_ADMIN`) و `WEB_PROJECT_READER_ROLES` (پیش‌فرض: هیچ‌کس)؛
> `AUDITOR` هرگز، و نام‌بردنش در این دو تنظیم راه‌اندازی پورتال را متوقف می‌کند. این دو تنظیم **آینهٔ**

> `CONSTRUCTION_PROJECT_ROLES`، `canWriteProjects`) یا `SYSTEM_ADMIN` دارد؛ فرم تصمیم فقط وقتی کشیده می‌شود که مرحله `PENDING` باشد و

> موافقت پذیرفته نمی‌شود (`422`) و صفحه همین را به‌عنوان یک وضعیت می‌گوید («سیاست موافقت فعالی نیست؛ سامانه بسته است»، با

> **سمت کارفرما** (`GET /v1/tenders`، `/v1/tenders/{id}`، `/v1/tenders/{id}/criteria`) مناقصه‌های سازمان فعال را نشان می‌دهد؛ مناقصهٔ
> سازمان دیگر `404` است و مثل شناسهٔ ناموجود نمایش داده می‌شود. **سمت پیمانکار** (`GET /v1/open-tenders` و `/{id}`، درِ جلویی
> مناقصه‌های منتشرشدهٔ عمومی یا دعوت‌شده، هرگز مناقصهٔ خودش) با نقش `CONTRACTOR` است و معیارهای منجمدشده را همراه دارد. پیوند جزئیات
> سمت پیمانکار `?view=open` دارد؛ نشانی بدون آن، در سمت کارفرما باز می‌شود (یا سمت پیمانکار برای کسی که فقط پیمانکار است).
> پیوند «مناقصه‌ها» برای کسی نمایش داده می‌شود که یکی از دو سمت را دارد: سمت کارفرما با **همان** `WEB_PROJECT_ROLES` و
> `WEB_PROJECT_READER_ROLES` (سرویس خواندن مناقصه را با همان نقش‌های پیکربندی‌شدهٔ پروژه مجاز می‌کند، پس تنظیم تازه‌ای لازم نیست) و `SYSTEM_ADMIN`
> همیشه؛ سمت پیمانکار با `CONTRACTOR` که در سرویس ثابت است و پیکربندی ندارد. `AUDITOR` در هر دو سمت **هرگز**، و `SYSTEM_ADMIN` همراه
> `CONTRACTOR` سمت پیمانکار را ندارد — همان‌طور که سرویس هر وقت این نقش‌ها حاضر باشند رد می‌کند. نقشی که هیچ‌کدام نیست و نشانی را می‌زند،
> پاسخ خود سرویس را می‌گیرد (پورتال در را به او نشان نمی‌دهد ولی نمی‌بندد). **هیچ‌چیز دربارهٔ پیشنهاد دیگران خوانده یا نشان داده نمی‌شود**:
> نه محتوای پیشنهاد، نه هویت پیشنهاددهنده، نه تعداد؛ از مسیرهای `…/bids` فقط پیشنهادِ خودِ سازمان پیمانکار (یادداشت بعد) خوانده
> می‌شود و هیچ مسیر `…/evaluation`، `…/award` یا `…/invitations` فراخوانی نمی‌شود (ADR-066). انتشار و گشایش (سمت کارفرما) در یادداشت
> «سمت کارفرما» آمده‌اند؛ ارزیابی و واگذاری برش بعدی‌اند. هر زمان نمایشی (بازهٔ پذیرش، انتشار) باید
> لحظهٔ UTC معتبر باشد، وگرنه پاسخ «نامعتبر» است و متن ثابت نشان داده می‌شود؛ متن خطای سرویس هیچ‌جا بازتاب نمی‌یابد.

> **پیشنهاد پیمانکار روی `/tenders/[id]?view=open` (`EXP-004`، CON-002).** زیر مناقصه، بخش «پیشنهاد سازمان شما» رسیدِ
> پیشنهادِ **خودِ** سازمان را از `GET /v1/tenders/{id}/bids/mine` نشان می‌دهد — وضعیت، نسخه، زمان دریافت، زمان پس‌گرفتن و رسید
> (سرِ زنجیرهٔ رسیدهای مناقصه) — و **هرگز محتوا**: پیش از گشایش هیچ‌کس، خودِ پیشنهاددهنده هم، آن را نمی‌خواند (ADR-066 § ۴).
> سرویس هر خواندنِ این مسیر را، پذیرفته یا ردشده، در همان تراکنش ممیزی می‌کند، پس پورتال فقط برای فراخوانی آن را می‌پرسد که
> سرویس به‌عنوان پیشنهاددهنده می‌پذیرد. مناقصه‌ای که دیگر پشت درِ پیمانکار نیست (بسته، گشوده، واگذارشده) همچنان پیشنهادِ خودِ
> سازمان را روی همین صفحه نشان می‌دهد. **فرم‌ها فقط جایی که سرویس می‌پذیرد:** نمای پیمانکار فهرست اقدام‌های مجاز ندارد، پس
> `server/tender-bids.ts` بررسی‌های `assertCanBid` و `BidService.decide` را از Token تکرار می‌کند و `tender-bids.contract.spec.ts`
> آن‌ها را به کد سرویس سنجاق می‌کند — `CONTRACTOR` در سازمانِ فعال، نه `SYSTEM_ADMIN` و نه `AUDITOR` (هر وقت حاضر باشند)؛
> مناقصه‌ای که درِ پیمانکار نشان می‌دهد (منتشرشده، از سازمان دیگر، عمومی یا دعوت‌شده — دعوت را سرویس تصمیم می‌گیرد)؛ بازهٔ
> `[bidOpeningAt, bidClosingAt)`؛ سپس **ثبت** فقط وقتی سازمان پیشنهادی ندارد و **جایگزینی** و **انصراف** فقط برای پیشنهاد `SUBMITTED`.
> بازه را پورتال با ساعت خودش فقط برای انتخاب فرم می‌سنجد؛ سرویس پس از قفل مناقصه با ساعت پایگاه داده دوباره می‌سنجد و فرمی که
> نزدیک مرز کشیده شده با `BID_WINDOW_CLOSED`/`BID_WINDOW_NOT_OPEN` و متن ثابت رد می‌شود. **صلاحیت پیمانکاری** (CONTRACTING،
> بدون تعلیق) را construction-service همان لحظه از supplier-service می‌پرسد و پورتال آن را بازسازی نمی‌کند: ردش (`BIDDER_NOT_ELIGIBLE`)
> و هر دلیل بستهٔ دیگرِ `BID_REFUSALS` با متن فارسی ثابت گفته می‌شود، هرگز با متن سرویس. محتوای فرم بدنهٔ `bidContentSchema` است:
> مبلغ به ریال، **رشتهٔ دهدهی، هرگز `number`**، پاسخ هر معیار (اختیاری؛ پاسخ خالی فرستاده نمی‌شود) و یادداشت؛ متن فقط Trim می‌شود و
> هیچ نویسه‌ای بازنویسی نمی‌شود، چون همان بایت‌ها مهر و موم می‌شوند. **کلید و مُهر:** هر فرم شناسهٔ ارسال (`Idempotency-Key`؛ دروازه
> روی هر فرمان ناامن `/v1/tenders` لازمش دارد و ثبت با آن بازپخش می‌شود) و مُهر امضاشدهٔ خودش را دارد (`server/bid-replay.ts`، مهلت =
> `WEB_CONSTRUCTION_IDEMPOTENCY_TTL_HOURS` (حداکثر ۱ و نه بیشتر از `CONSTRUCTION_IDEMPOTENCY_TTL_HOURS`) منهای `WEB_CONSTRUCTION_REPLAY_MARGIN_SECONDS`)؛
> شناسهٔ پیشنهاد و `expectedRevision` از مُهر می‌آیند، نه از فرم. **ارسالِ تأییدنشده** الگوی صورت‌وضعیت‌هاست با یک تفاوت که
> مهر و موم تعیین می‌کند: `lib/unresolved-bid.ts` فقط **این‌که** فرمانی فرستاده شد را نگه می‌دارد (فرمان، شناسهٔ ارسال، کد پیگیری،
> زمان) و **هیچ مبلغ، پاسخ یا یادداشتی** در مرورگر ذخیره نمی‌شود. در همان صفحه «ارسال دوباره» همان محتوا را از حافظهٔ صفحه با همان
> کلید می‌فرستد — جز **جایگزینی و انصراف**، که نتیجهٔ نامعلومشان از همان ابتدا فقط‌نمایش است، چون ارسال دوباره روی پیشنهاد آن‌طور
> که در آن لحظه است عمل می‌کند و ممکن است از صفحهٔ دیگری تغییر کرده باشد (بازبینی PR 345)؛ پس از تازه‌شدن صفحه رکورد فقط‌نمایش است، کنار رسیدی که صفحه خوانده، تا شخص آن را کنار بگذارد. این امن است چون هیچ
> فرمان پیشنهادی با کلید تازه دو بار اثر نمی‌کند: هر سازمان یک پیشنهاد دارد (`409 ALREADY_EXISTS`) و جایگزینی و انصراف نسخهٔ
> خوانده‌شده را دارند (`409 OPTIMISTIC_LOCK_FAILED`). سه فرم یک مناقصه **یک جایگاه** دارند، مثل فرم‌های یک صورت‌وضعیت.

> **سمت کارفرما روی `/tenders/[id]?view=own` (`EXP-004`، CON-002): انتشار، بستن، گشایش.** نمای کارفرما فهرست اقدام‌های مجاز ندارد،
> پس `server/tender-owner.ts` بررسی‌های سرویس را از Token تکرار می‌کند و `tender-owner.contract.spec.ts` آن‌ها را به کد سرویس سنجاق
> می‌کند. **انتشار** (`POST …/publish`، `@RequirePlatformUserId`): نویسندگان `SYSTEM_ADMIN` و `CONSTRUCTION_PROJECT_ROLES`
> (`WEB_PROJECT_ROLES`)، نه `AUDITOR`؛ فقط روی پیش‌نویس و فقط وقتی آخرین درخواست انتشار (`GET …/approvals?workflowKey=tender.publication&limit=1`)
> برای **همین نسخهٔ** مناقصه در انتظار نیست؛ درخواست در انتظارِ نسخهٔ پیشین جلوی درخواست تازه را نمی‌گیرد، چون درگاه موافقت آن را
> پایان می‌دهد و از نو می‌پرسد (`TenderApprovalGate.resolve`). بار نخست سرویس دور موافقت را باز می‌کند (`202`)؛ پس از موافقت همان فرم، با همان نسخهٔ مناقصه، انتشار را اجرا
> می‌کند (`200`). نسخه از مُهر امضاشده می‌آید (`server/tender-owner-replay.ts`)، پس فرمی که پیش از تغییر مناقصه کشیده شده با `409`
> (`APPROVAL_STALE` یا `OPTIMISTIC_LOCK_FAILED`) رد می‌شود. هر دلیل `PUBLICATION_REFUSALS` با متن فارسی ثابت گفته می‌شود، همه با هم.
> **تصمیم** (`POST /v1/approvals/{id}/decision`): فقط برای مرحلهٔ `PENDING`ِ درخواست `PENDING`ِ همین نسخه (تصمیم روی درخواستِ
> نسخهٔ پیشین آن را `STALE` پایان می‌دهد)، سازمانِ مرحله با نقشِ دقیقِ آن (بی‌جایگزین)، نه `AUDITOR`. **موافقت هرگز برای کسی که
> درخواست داده** (`assertDistinctActors`، که سرویس فقط بر `GRANT` اعمال می‌کند؛ شناسه = `rasta_uid`، وگرنه `sub`) — او یادداشت
> تفکیک وظایف می‌بیند و اگر مرجعِ همان مرحله باشد، **ردکردن** درخواست خودش برایش عرضه می‌شود. ردکردن دلیل ۸ تا ۵۰۰ نویسه لازم دارد؛ نسخهٔ مرحله از مُهر می‌آید. عضویت زنده را identity-service
> می‌گوید و پورتال آن را بازسازی نمی‌کند؛ `403` بی‌دلیلِ بسته با جملهٔ ثابتِ هر فرمان گفته می‌شود. **بستن** فرم ندارد: سرویس مناقصه
> را خودش در پایان مهلت می‌بندد (`TenderCloseSweeper`)، پس پس از مهلت فقط همین گفته می‌شود. **گشایش دو نفره** (Q-91): پیشنهاد،
> گشایش (نفر دوم) و پس‌گرفتن پیشنهاد (`POST …/open-bids/proposal`، `…/open-bids`، `…/open-bids/proposal/withdraw`؛ دو تای نخست
> بی‌بدنه، پس‌گرفتن با نام پیشنهاد: `{proposedAt}` — وظیفهٔ ۰۶۰) فقط
> روی مناقصهٔ `CLOSED` و فقط برای گشاینده‌ها: `CONSTRUCTION_TENDER_OPEN_ROLES` (`WEB_TENDER_OPEN_ROLES`)، وگرنه نقش‌های پروژه، و
> هرگز `SYSTEM_ADMIN`، `CONTRACTOR` یا `AUDITOR`. فرم **پس‌گرفتن** فقط وقتی کشیده می‌شود که `GET …/bids` پیشنهادی برقرار
> (`proposal`) نشان دهد، و `proposedAt` همان پیشنهاد در مُهرِ امضاشدهٔ فرم بسته می‌شود: بدنه فقط از مُهر ساخته می‌شود، در هر
> ارسالِ همان فرم همان است و هنگام ارسال پیشنهاد دوباره خوانده نمی‌شود (بازبینی PR-350 r1، F1)؛ پیشنهاد دیگری که از آن پس
> برقرار شده `409 PROPOSAL_SUPERSEDED` است، با جملهٔ ثابت. **گشاینده‌ای که مناقصه را نمی‌خواند** (نقش گشایشِ پیکربندی‌شده‌ای که نقش خوانندهٔ
> پروژه نیست؛ `GET /v1/tenders/{id}` با `assertCanRead` است و گشایش و `GET …/bids` فقط با `assertCanOpenBids`) صفحه‌ای جدا می‌بیند:
> فقط `GET …/bids` خوانده می‌شود — مناقصهٔ سازمان دیگر یا ناموجود همان `404` است — و تا گشوده‌نشدن، سه فرم گشایش؛ وضعیت مناقصه را
> نمی‌خواند، پس گشایشِ مناقصهٔ بسته‌نشده را سرویس با `NOT_CLOSED` و متن ثابت رد می‌کند. نمای مناقصه نمی‌گوید پیشنهاد گشایشی ثبت شده یا نه، پس هر سه عرضه می‌شوند و سرویس
> کار نابجا را با دلیل بستهٔ `OPENING_REFUSALS` و متن ثابت رد می‌کند (`SECOND_PERSON_REQUIRED` = تفکیک وظایف؛ تعارض منافع `403`).
> سرویس فقط وقتی می‌گشاید که audit-service همهٔ رسیدها را داشته باشد؛ تا آن وقت `503` است و فرم آن را «تأییدنشده» می‌گوید؛ شخص
> وضعیت را می‌بیند، آن را کنار می‌گذارد و از فرمی تازه دوباره می‌گشاید (یا همان درخواست را دوباره می‌فرستد؛ پایین‌تر). **پیشنهادها** (`GET …/bids`، هر خواندن ممیزی می‌شود) فقط برای گشاینده و پس از
> پیش‌نویس خوانده می‌شوند: پیش از گشایش فقط شمار و زمان‌ها، پس از آن هر پیشنهاد با مبلغ (رشتهٔ دهدهی، قالب‌بندی فقط در نمایش)،
> پاسخ‌ها و یادداشت — همان‌قدر که سرویس برمی‌گرداند. **ارسالِ تأییدنشده** الگوی پیشنهادهاست: `lib/unresolved-tender-command.ts`
> (روی `lib/unresolved-marker.ts`، که `lib/unresolved-bid.ts` هم اکنون رویش است) فقط این‌که فرمانی فرستاده شد را نگه می‌دارد، یک
> جایگاه برای هر مناقصه، و هیچ دلیل ردی ذخیره نمی‌شود. construction-service از #350 نتیجهٔ **انتشار، پیشنهاد گشایش، گشایش و پس‌گرفتن پیشنهاد** (و واگذاری، پایین‌تر) را به
> `Idempotency-Key` نگه می‌دارد: ارسال دوبارهٔ همان درخواست با همان کلید و همان بدنه پاسخ نخست را برمی‌گرداند، وضعیت مناقصه درون
> کار سنجیده می‌شود و درخواست به فرستنده‌اش بسته است. پس نتیجهٔ نامعلومِ این‌ها، **در همان صفحه**، با «ارسال دوبارهٔ همین
> درخواست» دوباره فرستاده می‌شود (`REPEATABLE_OWNER_COMMANDS`): همان کلید و بدنه‌ای که مُهر امضاشده می‌بندد (پس‌گرفتن، `proposedAt`
> امضاشدهٔ خودش را) — هرگز از وضعیت کنونی صفحه ساخته نمی‌شود. پاسخ ارسال دوباره ممکن است پاسخ تاریخیِ ارسال نخست باشد (مثلاً ۲۰۲
> دوری که از آن پس رد شده)؛ متن ثابتش می‌گوید وضعیت کنونی از خوانده‌های همین صفحه می‌آید، و `409 IDEMPOTENCY_KEY_REUSED` و
> `409 PROPOSAL_SUPERSEDED` هم متن ثابت دارند. پس از تازه‌شدن صفحه رکورد فقط‌نمایش می‌ماند. تصمیم‌های موافقت
> (`POST /approvals/:id/decision`) نتیجه‌ای به کلید نگه نمی‌دارند و از همان ابتدا **فقط‌نمایش**‌اند، چون ارسال دوبارهٔ آن‌ها درخواستی
> تازه روی مرحله آن‌طور که در آن لحظه است می‌بود: فرمانی که مقایسه‌وتعویضِ `expectedVersion` را دارد پس از هر تغییری، از جمله ارسال
> نخست، رد می‌شود و این دربارهٔ ارسال نخست چیزی نمی‌گوید.

> **ارزیابی و واگذاری روی همان صفحه (`EXP-004`، CON-002 PR 9–11، ADR-067، Q-84، Q-88..Q-93).** `server/tender-evaluation.ts`
> بررسی‌های سرویس را تکرار می‌کند و `tender-evaluation.contract.spec.ts` آن‌ها را به کد سرویس سنجاق می‌کند؛ فرمان‌ها از همان اکشن،
> مُهر و جایگاهِ فرمان‌های کارفرما می‌گذرند. **ماتریس** (`GET …/evaluation`) فقط برای ارزیاب و فقط پس از گشایش خوانده می‌شود:
> `CONSTRUCTION_TENDER_EVALUATE_ROLES` (`WEB_TENDER_EVALUATE_ROLES`)، وگرنه نقش‌های پروژه، و هرگز `SYSTEM_ADMIN`، `CONTRACTOR` یا
> `AUDITOR`؛ هر خواندن برای هر پیشنهاد ممیزی می‌شود و سرویس عضو سازمانِ پیشنهاددهنده (`CONFLICT_OF_INTEREST`) و — با
> `EVALUATOR_NOT_TENDER_AUTHOR` — سازندهٔ مناقصه را رد می‌کند؛ پس ماتریسی که خوانده شد خودش نشان می‌دهد این شخص از همهٔ بررسی‌هایی که
> فرمان ارزیاب پیش از قاعده‌های خودش می‌کند گذشته است. روی مناقصهٔ `EVALUATING`: **تصمیم** (`POST …/bids/{bidId}/qualification`) دربارهٔ
> پیشنهادِ گشوده و بی‌تصمیم — واجد شرایط، یا فاقد شرایط با یکی از دلیل‌های بسته و شرح تا ۲۰۰۰ نویسه — و نه برای کسی که از آن پیشنهاد
> کنار رفته (`RECUSED`)؛ **امتیاز** (`POST …/bids/{bidId}/scores`) برای پیشنهاد واجد شرایط، اگر این شخص ارزیاب آن است یا جا برای ارزیاب
> تازه هست (ارزیاب‌های کنارنرفته کمتر از `maxEvaluators`)، هر معیار بسته به نسخهٔ خانهٔ خودِ او که صفحه خوانده (`expectedRevision`، در
> مُهر)؛ امتیاز به‌صورت امتیاز × ۱۰۰ و عدد صحیح می‌رود، از ورودیِ دهدهی تا دو رقم اعشار با رقم فارسی یا لاتین، و معیار قبول/رد فقط صفر یا
> بیشینه است؛ **تکمیل** (`POST …/evaluate`) فقط وقتی ماتریس `ready` است — همان پاسخی که `evaluate` می‌دهد. جمع وزنی
> (`Σ weightBp × score`، رشتهٔ عدد صحیح) فقط در نمایش به امتیاز دهدهی با رقم فارسی تبدیل می‌شود، هرگز از راه عدد اعشاری؛ رتبهٔ مشترک
> برنده‌ای نمی‌سازد. **واگذاری** (`POST …/award`) روی مناقصهٔ `EVALUATED` برای واگذارنده: `CONSTRUCTION_TENDER_AWARD_ROLES`
> (`WEB_TENDER_AWARD_ROLES`) با همان استثناها؛ با `AWARDER_NOT_EVALUATOR` (`CONSTRUCTION_COI_RULES` ← `WEB_TENDER_COI_RULES`، پیش‌فرض
> روشن) به کسی که در ماتریس تصمیم گرفته، امتیاز داده یا کنار رفته، یا ارزیابی را کامل کرده (`statusChangedBy`ِ مناقصهٔ ارزیابی‌شده، که
> فقط «آیا خودِ اوست» از آن نگه داشته می‌شود) عرضه نمی‌شود. یک فرم برای هر پیشنهاد واجد شرایطِ رتبه‌دار؛ هر انتخابی جز تنها رتبهٔ نخست
> دلیل نوشته لازم دارد (`JUSTIFICATION_REQUIRED`). **واگذاری بی‌ماتریس** (PR 346 بازبینی ۱، یافتهٔ ۲): شایستگی واگذاری از همان چیزی
> تصمیم گرفته می‌شود که مسیر واگذاری لازم دارد (`assertCanAward`)، نه از خواندن ماتریس؛ واگذارنده‌ای که ماتریس برایش خوانده نمی‌شود
> (نقش‌های جدای ارزیاب و واگذارنده، یا `EVALUATOR_NOT_TENDER_AUTHOR`) برای هر پیشنهاد گشوده و `QUALIFIED` از نمای گشاینده
> (`GET …/bids`) فرمی بی‌رتبه می‌گیرد که دلیل را اختیاری می‌گذارد و می‌گوید سرویس رتبه و نقش او در ارزیابی را می‌سنجد
> (`AWARD_MATRIX_UNREAD`)؛ اگر خواندنی که از آنِ اوست شکست بخورد فرمی نیست و صفحه می‌گوید کمی بعد (`AWARD_BIDS_UNREAD`)؛ و واگذارنده‌ای
> که نه گشاینده است و نه ارزیاب (بازبینی ۲، یافتهٔ ۱) بخش واگذاری را با متن ثابتی می‌بیند که می‌گوید در این نسخه آغاز واگذاری به خواندن
> ماتریس یا فهرست پیشنهادها نیاز دارد (`AWARD_CANDIDATES_UNREADABLE`)، چون construction-service خواندنی از نامزدها با مجوز واگذاری ندارد
> (`GET …/award` فقط واگذاریِ ثبت‌شده است و تا واگذاری `404`) و پورتال آن را نمی‌سازد. اجرای موافقت‌شده هیچ ماتریس یا فهرستی لازم ندارد. بار نخست دور موافقت `tender.award` باز می‌شود (`202`)؛ درخواستِ در انتظار جلوی فرم‌ها را
> نمی‌گیرد، چون انتخاب دیگری آن را پایان می‌دهد و از نو می‌پرسد؛ پس از موافقت روی همین نسخه فقط **اجرای** همان انتخاب عرضه می‌شود، با
> پیشنهاد و دلیلی که از مرحلهٔ موافقت (`GET /v1/approvals/{id}`) خوانده و در مُهر بسته شده — چون فرمانی که اجرا می‌شود باید همان موافقت‌شده
> باشد (`TenderApprovalGate.covers`). **تصمیم دربارهٔ واگذاری** برای مرجعِ مرحلهٔ `PENDING`، نه با نقش‌های مستثنای سمت پیشنهاد
> (`assertMayDecideAward`)؛ خواندن مرحله همان قاعده‌های تصمیم را دارد، پس `403`ِ آن (مثلاً `APPROVER_IS_EVALUATOR`) یعنی تصمیم هم پذیرفته
> نمی‌شود و فرم عرضه نمی‌شود؛ موافقت هرگز برای کسی که درخواست داده. **مرجعِ سازمانی دیگر** (یافتهٔ ۳): سیاست موافقت می‌تواند نقشی از هر
> سازمانی را نام ببرد، و آن مرجع مناقصه را نمی‌خواند (`GET /v1/tenders/{id}` از آنِ مالک است و برای دیگران `404` می‌ماند). وقتی خواندن
> مناقصه `404` یا `403` است، صفحه مرحله‌های همین مناقصه را از صندوق مرجع (`GET /v1/approvals?status=PENDING`، صفحه‌به‌صفحه تا ۵ صفحهٔ
> ۲۰۰تایی) پیدا می‌کند، هر کدام را جدا می‌خواند (`GET /v1/approvals/{id}`، با قاعده‌های تصمیم) و فقط عنوان پروژه، مرحله، درخواست و — برای
> واگذاری — پیشنهادی را که مرحله نام می‌برد با فرم‌های تصمیم نشان می‌دهد (`server/tender-authority.ts`، `AuthoritySections.tsx`)؛ اگر
> مرحله‌ای نباشد، همان نبودنِ خواندن مناقصه، مگر تأییدِ تصمیمی که همین نشست همین لحظه روی همین مناقصه گرفته. همین راه پس از ردِ
> خواندن‌های سمت پیشنهاد هم پیموده می‌شود (بازبینی ۲، یافتهٔ ۲): مرجعی که نقشش گشاینده یا ارزیاب هم هست و `GET …/bids` یا ماتریسش `404`
> است. صندوقی بلندتر از ۵ صفحه هرگز «پیدا نشد» نیست (یافتهٔ ۳): صفحه هشدار می‌دهد و پیوند «ادامهٔ جست‌وجو» با نشانگر خود سرویس
> (`?inbox=`، فقط نویسه‌های چاپی، تا ۵۱۲) پنج صفحهٔ بعد را می‌خواند، و پیوند «از آغاز» به ابتدا برمی‌گرداند؛ متن آن نه می‌گوید شما مرجع
> این مناقصه‌اید و نه چیزی از خودِ مناقصه، پس برای هر شناسه‌ای یکسان است. **کنار خواندنِ موفقِ سمت پیشنهاد هم** (بازبینی ۳، یافتهٔ ۱)
> صندوق خوانده می‌شود: گشاینده یا ارزیابی که سیاست موافقت او را مرجع مرحله‌ای از همین مناقصه نام برده، تصمیم آن را در بخش «موافقت‌های شما
> در این مناقصه» کنار فرم‌های گشایش و ارزیابی می‌بیند؛ خواندن ماتریس کسی را شریک ارزیابی نمی‌کند، و اگر واقعاً شریک بوده، سرویس خواندن
> مرحله را رد می‌کند و صفحه همان را می‌گوید. **صفحهٔ ناخوانده‌ای از صندوق** (یافتهٔ ۲) جست‌وجو را همان‌جا نگه می‌دارد: مرحله‌هایی که تا آنجا
> پیدا شد نشان داده می‌شوند، خطای ویژهٔ صندوق با کد پیگیری و پیوند «تلاش دوباره» از نشانگر همان صفحه می‌آید، و «پیدا نشد» فقط پس از
> جست‌وجویی است که از آغاز تا پایان همهٔ صفحه‌هایش خوانده شده؛ فقط ردِ صفحهٔ نخست (صندوقی که از آنِ این شخص نیست، مثلاً `AUDITOR`) همان
> نبودن است. **فرمانِ گم‌پاسخ کنار نبودن** (بازبینی ۴): اگر تصمیمِ مرجع دربارهٔ آخرین مرحلهٔ در انتظارش ثبت شده ولی پاسخش نرسیده باشد،
> پس از تازه‌کردن صندوق خالی است و صفحه همان نبودن است؛ نشانِ ثبت‌نشدهٔ همین نشست در این مرورگر و پیوند «کنار بگذار» کنار آن می‌ماند. این
> نشان فقط در مرورگر و پس از خواندن انبارهٔ نشست کشیده می‌شود، پس صفحهٔ سرور برای مناقصهٔ موجود و ناموجود یکی است. پس از واگذاری، `GET …/award` برای واگذارنده برنده، مبلغ او (رشتهٔ
> دهدهی)، رتبه و دلیل را نشان می‌دهد. **نتیجهٔ نامعلوم** (یافتهٔ ۴، همان حکم #345): **امتیاز و واگذاری** دوباره فرستاده می‌شوند، چون سرویس
> نتیجه‌شان را به کلید نگه می‌دارد (`IdempotencyStore.run`؛ واگذاری از #350، با دور رد‌شده‌ای که از آن پس بسته شده هم، بی‌دور تازه؛ اجرای واگذاریِ موافقت‌شده هم، چون `binding` امضاشده‌اش در مقدارهای برگشتی می‌ماند و ارسال دوباره همان کلید و بدنه را می‌سازد) و هر خانهٔ امتیاز
> مقایسه‌وتعویض است (`REPEATABLE_OWNER_COMMANDS`)؛ تصمیم دربارهٔ پیشنهاد، تکمیل ارزیابی و تصمیم‌های موافقت
> نتیجه‌ای به کلید نگه نمی‌دارند و **فقط‌نمایش**‌اند: تکرارِ
> تکمیل ماتریسی را که کسی در این میان تغییر داده منجمد می‌کند. **مُهر
> فشرده** (یافتهٔ ۱): مُهر امضاشده معیارهای امتیاز و دلیل واگذاری را در خود ندارد، فقط شناسه‌ها و چکیدهٔ SHA-256 بدنهٔ بسته‌شده را؛ خودِ
> بدنه (JSON) در فیلد پنهان `binding` کنار مُهر می‌آید، و اکشن آن را فقط وقتی می‌پذیرد که چکیده‌اش همان باشد و با طرح سخت‌گیر (تا ۵۰
> معیار، دلیل تا ۲۰۰۰ نویسه) بخواند؛ پس مُهر هر فرمِ معتبر زیر سقف ۴۰۹۶ نویسهٔ `verifyPayload` می‌ماند. ارزیابی که نقش خوانندهٔ پروژه
> ندارد، مثل گشاینده، صفحه‌ای جدا با ماتریس می‌بیند. پیمانکار چیزی تازه نمی‌بیند: فقط وضعیت پیشنهاد خودش (`…/bids/mine`)، نه امتیاز و نه
> پیشنهاد دیگران. **در این برش نیست:** کناره‌گیری ارزیاب (نمایش داده می‌شود، فرم ندارد)، لغو مناقصهٔ بی‌پیشنهادِ واجد شرایط
> (`tender.cancellation`)، و نتیجهٔ ارزیابی پیشنهادِ خودِ پیمانکار (`…/bids/mine/opened`). **کمبودهای API:** واگذارنده‌ای که نقش ارزیابی
> ندارد پیشنهادهای رتبه‌دار را از هیچ خواندنی نمی‌گیرد (ماتریس با `assertCanEvaluate` است)، پس فرمش بی‌رتبه است و اگر گشاینده هم نباشد
> فرمی ندارد (خواندنی از نامزدهای واگذاری با `assertCanAward` لازم است)؛ صندوق موافقت (`inboxQuerySchema`) پالایه‌ای برای مناقصه ندارد و
> مسیری برای مرحله‌های یک مناقصه برای مرجعِ آن نیست (`GET …/tenders/{id}/approvals` از آنِ مالک است)، پس مرجعی با بیش از ۱۰۰۰ مرحلهٔ در
> انتظار باید صفحه‌به‌صفحه ادامه دهد؛ ماتریس
> نمی‌گوید چه کسی ارزیابی را کامل کرد و این از `statusChangedBy`ِ مناقصه گرفته می‌شود؛ و یکی‌بودنِ دو شناسهٔ کاربری را (هویت پایدار) فقط
> سرویس می‌داند و با متن ثابت رد می‌کند.

> **قراردادها، فقط‌خواندنی (`EXP-004`، برش ۴).** `/contracts` و `/contracts/[id]` یک در دارند، نه دو: `GET /v1/contracts`
> و `GET /v1/contracts/{id}` خود همان قرارداد را برای هر دو طرف جواب می‌دهند — کارفرما (سازمان مالک مناقصه) یا پیمانکارِ
> برنده (ADR-068 § ۷) — پس برخلاف مناقصه‌ها نشانی `?view=` لازم نیست. صفحهٔ جزئیات وضعیت، طرفین، مبلغ (`amountMinor`،
> `amendmentsTotalMinor`، `currentAmountMinor`)، امضاها (`employerSignedAt`/`contractorSignedAt`/`authorityReviewRequired`؛
> همه روی خودِ قرارداد، بدون مسیر امضای جدا)، الحاقیه‌ها (`GET …/amendments`) و Milestoneها (`GET …/milestones`) را
> نشان می‌دهد؛ هر دو زیرمنبع جدا خوانده می‌شوند و شکست هرکدام قرارداد را پنهان نمی‌کند، مثل معیارهای مناقصه. سازمان دیگر
> یا قرارداد ناموجود هر دو `404`اند و با یک متن نمایش داده می‌شوند (S-03). صورت‌وضعیت‌های قرارداد زیر همین صفحه‌اند
> (یادداشت بعد). پیوند «قراردادها» برای کسی نمایش داده می‌شود که یکی از دو سمت را دارد:
> سمت کارفرما با `WEB_CONTRACT_READER_ROLES` (آینهٔ `CONTRACT_READER_ROLES`، پیش‌فرض `ORGANIZATION_ADMIN`؛ تنظیم تازه و
> جدا از `WEB_PROJECT_ROLES`، چون contract-service یک نقش «خوانندهٔ اضافه» جدا مثل construction-service ندارد) و
> `SYSTEM_ADMIN` همیشه؛ سمت پیمانکار با `CONTRACTOR` که در سرویس ثابت است و پیکربندی ندارد، دقیقاً مثل سمت پیمانکار
> مناقصه‌ها. `AUDITOR` در هر دو سمت **هرگز** و نام‌بردنش در `WEB_CONTRACT_READER_ROLES` راه‌اندازی پورتال را متوقف
> می‌کند؛ `SYSTEM_ADMIN` همراه `CONTRACTOR` سمت پیمانکار را ندارد. مجوز را همچنان contract-service می‌دهد؛ این فقط نمایش
> یک پیوند است. امضا، لغو، الحاقیه‌ها و Milestoneها در یادداشت «دستورهای قرارداد» آمده‌اند.

> **صورت‌وضعیت‌ها روی `/contracts/[id]` (`EXP-004`، CON-003 PR 4 تا 6).** زیر قرارداد، بخش «صورت‌وضعیت‌ها» فهرست
> `GET /v1/contracts/{id}/statements` را با شماره، وضعیت و مبلغ ناخالص، کسورات و خالص — **رشتهٔ دهدهی سرویس، فقط
> قالب‌بندی‌شده، هرگز `number`** — نشان می‌دهد و هر ردیف به `/contracts/[id]/statements/[statementId]` پیوند دارد: ردیف‌ها،
> کسورات (نام، نرخ bp و مبلغ، همان‌طور که سرویس یک بار حساب کرده) و **هر دو زنجیرهٔ تأیید** (فنی، سپس مالی)، هر مرحله با
> مرجعش (سازمان، نقش، برچسب سیاست)، تصمیمش و زمانش. **نام تصمیم‌گیرنده نشان داده نمی‌شود**: نمای صورت‌وضعیت هیچ شخصی را
> نام نمی‌برد («never by which person»). صفحهٔ صورت‌وضعیت مستقل از خواندن قرارداد است: سازمانی که مرحله‌ای نامش را می‌برد
> و نقش آن مرحله را دارد **فقط همین صورت‌وضعیت** را می‌خواند (قرارداد برایش رد می‌شود)؛ سازمان سوم و شناسهٔ ناموجود هر دو
> `404` و یک متن‌اند. **فرم‌ها فقط جایی که سرویس می‌پذیرد:** نمای صورت‌وضعیت فهرست اقدام‌های مجاز فراخوان را ندارد، پس
> `server/contract-statements.ts` همان بررسی‌های contract-service را از Token تکرار می‌کند و `contract-statements.contract.spec.ts`
> آن‌ها را به کد سرویس سنجاق می‌کند — پیش‌نویس و ارسال فقط برای سمت پیمانکار با `CONTRACTOR` روی قرارداد `SIGNED` (و ارسال
> فقط برای `DRAFT`)؛ تأیید/رد فقط برای مرحلهٔ بعدیِ زنجیرهٔ باز، برای سازمانِ همان مرحله با نقش دقیق آن، نه `AUDITOR`، نه
> `SYSTEM_ADMIN`، نه عضو سازمان پیمانکار. آنچه نما نمی‌گوید — ارسال‌کننده یا تصمیم‌گیرندهٔ قبلی بودنِ همین شخص (تفکیک
> وظایف، Q-96 (3)) — را سرویس رد می‌کند و صفحه با **متن فارسی ثابتِ** هر دلیل بسته (`details[].code`) می‌گوید، هرگز با متن
> سرویس؛ `403`ها هم دلیل بسته‌شان را به فرم می‌رسانند (`write.ts`، `reasons`). DTO تصمیم میدان دلیل ندارد، پس رد بی‌دلیل
> فرستاده می‌شود. **کلید و مُهر:** هر فرم شناسهٔ ارسال (`Idempotency-Key`) و مُهر امضاشدهٔ خودش را دارد
> (`server/statement-replay.ts`، مهلت = `WEB_CONTRACT_IDEMPOTENCY_TTL_HOURS` آینهٔ `CONTRACT_IDEMPOTENCY_TTL_HOURS` منهای
> `WEB_CONTRACT_REPLAY_MARGIN_SECONDS`)؛ بدنهٔ ارسال و تصمیم **کامل از مُهر** می‌آید (نسخهٔ خوانده‌شده و برای تصمیم زنجیره و
> مرحله)، پس فرمی که پیش از جابه‌جایی صورت‌وضعیت کشیده شده با `409 OPTIMISTIC_LOCK_FAILED` و متن ثابت رد می‌شود. ارسالِ
> تأییدنشده الگوی `/transactions/[id]` است (`lib/unresolved-statement.ts`): پیش از ارسال در مرورگر نگه داشته می‌شود، با همان
> کلید و همان ردیف‌ها دوباره فرستاده می‌شود، پس از مهلت فقط‌نمایش است و هنگام خروج به نشانگرِ «نتیجه نامعلوم» کاهش می‌یابد —
> پیش‌نویسی که با کلید تازه تکرار شود صورت‌وضعیت دوم است. فرم‌های تأیید و رد یک صورت‌وضعیت **یک جایگاه** دارند (#332
> دور ۱): تا نتیجهٔ یکی نامعلوم است، دیگری فقط‌نمایش با همان هشدار است و ارسالش پیش از رفتن رد می‌شود؛ رکورد ارسالی دیگر
> هرگز جایگزین نمی‌شود و هر رکورد فقط با شناسهٔ ارسال خودش، روی پاسخ قطعیِ همان ارسال، پاک می‌شود. کسورات از فرم اعمال نمی‌شوند: هیچ مسیری قاعدهٔ کسر کارفرما را
> فهرست یا ثبت نمی‌کند (Q-125). تسویه در این برش نیست.

> **دستورهای قرارداد روی `/contracts/[id]` (`EXP-004`، CON-003 PR 2 و ۳).** هر فرم جایی کشیده می‌شود که عمل می‌کند:
> **امضا** (`POST …/sign`، پذیرش پیش‌نویس از سوی طرفِ فراخوان) و **لغو پیش‌نویس** (`POST …/cancel`، فقط کارفرما، با دلیلی
> از فهرست بسته و یادداشت اختیاری) زیر «امضاها»؛ **پیشنهاد الحاقیه** (`POST …/amendments`، فقط کارفرما، مبلغ مثبت به ریال
> که رشتهٔ دهدهی فرستاده می‌شود، دلیل و شرح) زیر فهرست الحاقیه‌ها و **امضای الحاقیه** (`POST …/amendments/{id}/sign`) در
> ردیف هر الحاقیه؛ **برنامه‌ریزی Milestone** (`POST …/milestones`: عنوان، روز تقویمی `YYYY-MM-DD` — هرگز لحظه — و سهم اختیاری
> به درصد که bp فرستاده می‌شود) و **ویرایش Milestone** (`PATCH …/milestones/{id}`، در ردیف، تا وقتی صورت‌وضعیتی به آن اشاره
> نکرده). **فرم‌ها فقط جایی که سرویس می‌پذیرد:** هیچ نمایی فهرست اقدام‌های مجاز ندارد، پس `server/contract-commands.ts`
> بررسی‌های contract-service را به همان ترتیب از Token تکرار می‌کند و `contract-commands.contract.spec.ts` آن‌ها را به کد سرویس
> سنجاق می‌کند: فراخوانِ دستوردهنده (شخص با شناسهٔ کاربر پلتفرم، برای یک سازمان؛ نه `AUDITOR`، نه `SYSTEM_ADMIN`)، طرف بودن،
> عضو هر دو طرف نبودن (برای امضا)، امضانشده بودنِ همان طرف، وضعیت (`DRAFT` برای امضا و لغو، `SIGNED` برای الحاقیه و Milestone،
> `PROPOSED` برای امضای الحاقیه)، `CONTRACTOR` برای سمت پیمانکار، و برای سمت کارفرما **سیاست `contract.signature` برقرارِ
> سازمان کارفرما**: صفحه آن را می‌خواند (`GET /v1/contract-approval-policies`، که خوانندگان قرارداد کارفرما می‌بینند، صفحه‌به‌صفحه تا
> یافتن سیاست حاکم یا آخرین صفحه، با سقف `MAX_POLICY_PAGES`؛ خواندن ناتمام «نامعلوم» است و متن ثابت خودش را دارد، نه «نیست») و فرم امضا
> را فقط وقتی می‌کشد که گامی از آن خودِ کارفرما و نقشی از فراخوان را نام ببرد؛ بی سیاست برقرار، متن ثابت می‌گوید هیچ‌کس از سوی
> کارفرما امضا نمی‌کند، و اگر خوانده نشود فرمی کشیده نمی‌شود — هرگز حدس. نقش‌های پیکربندی‌شدهٔ لغو، الحاقیه و Milestone و
> فهرست‌های بستهٔ دلیل لغو و الحاقیه آینهٔ تنظیم‌های سرویس‌اند (`WEB_CONTRACT_CANCEL_ROLES`، `WEB_CONTRACT_AMENDMENT_ROLES`،
> `WEB_CONTRACT_MILESTONE_ROLES`، `WEB_CONTRACT_CANCEL_REASON_CODES`، `WEB_CONTRACT_AMENDMENT_REASON_CODES`،
> `WEB_CONTRACT_CANCEL_AFTER_SIGNATURE`؛ پیش‌فرض‌ها همان پیش‌فرض‌های سرویس و سنجاق‌شده) و باید با آن‌ها با هم تغییر کنند؛ کدی که
> پورتال برایش واژه ندارد، خودش نشان داده می‌شود. آنچه نما نمی‌گوید — امضای همین شخص از سوی طرف دیگر (`SAME_PERSON_BOTH_SIDES`)،
> حاکم‌نبودنِ اتحادیهٔ نویسندهٔ سیاست، سقف شمار Milestoneها — را سرویس رد می‌کند و صفحه با **متن فارسی ثابتِ** هر دلیل بسته
> می‌گوید، هرگز با متن سرویس. **کلید، مُهر و جایگاه:** هر فرم شناسهٔ ارسال و مُهر امضاشدهٔ خودش را دارد
> (`server/contract-command-replay.ts`، همان مهلت صورت‌وضعیت‌ها) که شیء، نسخهٔ نمایش‌داده و برای امضا طرفِ آن را می‌بندد؛
> `expectedVersion` از مُهر می‌آید، نه از فرم، پس فرم کهنه با `409` و متن ثابت رد می‌شود (Milestone تازه نسخه‌ای ندارد و DTO آن
> نمی‌گیرد). ارسالِ تأییدنشده الگوی صورت‌وضعیت‌هاست (`lib/unresolved-contract-command.ts`)، با **یک جایگاه برای هر شیء**: امضا و
> لغوِ خود قرارداد یک جایگاه‌اند؛ الحاقیهٔ تازه، هر الحاقیه، Milestone تازه و هر Milestone هرکدام جایگاه خود را دارند؛ هر جایگاه
> حتی وقتی چیزی عرضه نمی‌شود کشیده می‌شود تا درخواستِ نامعلوم پس از تازه‌سازی همان‌جا دیده شود. پاسخ تأییدشده با تأیید امضاشده
> (`server/flash.ts`) به همین صفحه برمی‌گردد. **مرز باز:** پذیرش امضا یا لغو بدون شرط نسخه در سرویس اختیاری است؛ پورتال همیشه
> `expectedVersion` می‌فرستد.

> **دستورهای چرخهٔ حیات روی `/assets/[id]` (`EXP-002`، برش ۵).** سه دستور در بخش «وضعیت و چرخهٔ حیات»
> صفحه: **فعال‌سازی** (`REGISTERED ← ACTIVE`؛ سرویس پروندهٔ ناقص را با فهرست آنچه کم است رد می‌کند)،
> **تغییر وضعیت** (فقط گذارهایی که کاربر مجاز است: `ACTIVE ⇄ IDLE`، `REGISTERED`/`ACTIVE`/`IDLE` ← `OUT_OF_SERVICE`،
> `OUT_OF_SERVICE ← ACTIVE`؛ `ASSIGNED` و `IN_MAINTENANCE` را سرویس ناوگان و تعمیرات تعیین می‌کنند و در فرم
> نیست — و تا وقتی کار باز دارند هیچ فرمی هم ندارند، فقط یادداشتی که می‌گوید کار را کجا ببندید، Q-94) با دلیل اجباری، و **اسقاط** (نهایی؛ فرمِ بسته که با نام دارایی هشدار می‌دهد، دلیل می‌خواهد و تیک
> «می‌دانم بازگشت‌ناپذیر است» را اجباری می‌کند). فرم‌ها فقط به نقش‌هایی نشان داده می‌شوند که `@Roles` همان مسیر
> در `asset-service` می‌پذیرد (فعال‌سازی و تغییر وضعیت: مدیر سازمان، مدیر ناوگان، مدیر اتحادیه؛ اسقاط: مدیر
> سازمان و مدیر اتحادیه) — این فقط UX است و سرویس دوباره تصمیم می‌گیرد. الگوی نوشتن همان برش ۴ است: نشست،
> CSRF، شناسهٔ ارسال بسته به نشست، و یک **baseline امضاشده** (هدف `asset-lifecycle-baseline`، ۳۰ دقیقه) که
> **شناسهٔ دارایی، دستور، نسخه، وضعیت و نامِ نمایش‌داده‌شده** را می‌بندد؛ اکشن هیچ‌کدام را از فرم نمی‌خواند. نسخه
> به‌صورت `expectedVersion` به سرویس می‌رود ([docs/06](06-api-architecture.md)): صفحهٔ کهنه ‑ یا همان فرمِ
> دوبار فرستاده‌شده ‑ `409` می‌گیرد و پورتال به خواندنی تازه با هشدار «این بار چیزی نوشته نشد» می‌رود، نه
> به بازنویسی. دارایی سازمان دیگر برای خواندن و هر نوشتن `404` است، دقیقاً مثل شناسهٔ ناموجود. دارایی
> اسقاط‌شده هیچ فرمی ندارد (نه چرخهٔ حیات، نه ویرایش) و فقط خبر نهایی بودن را نشان می‌دهد.

> **بیمه‌نامه و معاینهٔ فنی روی `/assets/[id]` (`EXP-002`، برش ۶).** دو بخش زیر «آمادگی بهره‌برداری»:
> **بیمه‌نامه‌ها** (`GET /v1/assets/{id}/insurance-policies`: پوشش، شرکت بیمه، شمارهٔ بیمه‌نامه، بازهٔ اعتبار، حق بیمه و
> سرمایه) و **معاینهٔ فنی** (`GET …/inspections`: نتیجه، تاریخ معاینه، شمارهٔ گواهی، مرکز، و «معاینهٔ بعدی تا» که همان
> `validTo` قرارداد است). هر رکورد یکی از سه برچسب **معتبر / منقضی / هنوز آغاز نشده** را دارد که **با ساعت سرور** هنگام
> رندر صفحه سنجیده می‌شود (بازهٔ نیم‌باز `[از، تا)`، مثل سرویس) و در خود HTML نوشته می‌شود؛ کامپوننتی که این را تعیین کند
> کلاینتی نیست و ساعت مرورگر در آن دخلی ندارد (E2E با ساعت مرورگر ۲۰۴۰ و ۲۰۰۱ همان برچسب‌ها را می‌خواند). بیمهٔ `CANCELLED` هر
> تاریخی داشته باشد «لغوشده» است. دو دستور: **ثبت بیمه‌نامه** و **ثبت معاینهٔ فنی** (فرم‌های بسته که پس از تلاش ناموفق باز
> می‌مانند)، فقط برای نقش‌هایی که `@Roles` همان مسیر می‌پذیرد (مدیر سازمان، مدیر ناوگان، مدیر اتحادیه) و برای دارایی
> اسقاط‌نشده — UX است و سرویس دوباره تصمیم می‌گیرد. ادعای خسارت در این برش نیست. الگوی نوشتن همان برش ۵ است
> (نشست، CSRF، شناسهٔ ارسال بسته به نشست و **baseline امضاشده**، هدف `asset-record-baseline`) با این تفاوت که baseline فقط
> **دارایی و فرم** (بیمه‌نامه یا معاینه) را می‌بندد، نه نسخه یا وضعیت: رکورد روی نسخه یا وضعیتی بنا نمی‌شود، پس چیزی در آن
> کهنه نمی‌شود و تا پایان همان نشست معتبر است. اکشن با `action.bind(null, assetId)` به دارایی صفحه بسته شده، ولی این کار در
> کامپوننت کلاینت انجام می‌شود و مرورگر شناسه را خودش برمی‌گرداند؛ پس اکشن فقط وقتی چیزی می‌فرستد که شناسهٔ بسته‌شده همان
> دارایی‌ای باشد که baseline نام می‌برد. هیچ فیلد فرمی دارایی را نام نمی‌برد. **شناسهٔ ارسال همان `Idempotency-Key` است** ([docs/06](06-api-architecture.md)): فرمی که دو بار فرستاده شود
> (دوبار کلیک، تلاش دوبارهٔ مرورگر، ارسال پس از «تأیید نشد») یک رکورد می‌سازد و پاسخ دوم بازپخش اولی است؛ همان فرم با بدنهٔ دیگر
> رد می‌شود و پورتال می‌گوید صفحه را تازه کنید و فهرست را ببینید. **تاریخ‌ها:** روز تقویمی (`type="date"`) به‌صورت نیمه‌شب
> تهران همان روز (UTC ISO) فرستاده می‌شود و با تقویم هجری شمسی نشان داده می‌شود و هرگز یک روز جابه‌جا نمی‌شود (قاعدهٔ L5-01)؛
> پیامد: «تاریخ پایان» **آغاز** همان روز است و بیمه‌نامه از آغاز آن روز دیگر معتبر شمرده نمی‌شود (سمت ایمن گیت اعزام؛
> پرسش «آیا روز پایان هم پوشش دارد؟» نزد مدیر پروژه است). فرم‌های تغییر وضعیت و اسقاط هنگام `503` از سرویس‌های صاحب کار می‌گویند
> بررسی کار باز ممکن نشد و چیزی تغییر نکرد (Q-94: «در دسترس نیست» بر «مسدود» پیش می‌افتد).

> **مدارک و آمادگی اعزام روی `/assets/[id]` (`EXP-002`، برش ۷).** دو بخش زیر بیمه و معاینه. **مدارک**
> (فهرست از `GET /v1/assets/{id}/dossier`، فیلد `documents`: عنوان، نوع، تاریخ صدور و انقضا، شناسهٔ سند در document-service)
> فقط **ارجاع‌هایی** را نشان می‌دهد که asset-service نگه می‌دارد، نه خود فایل؛ دانلود در این برش نیست (فایل پس از اسکن و با URL
> امضاشدهٔ کوتاه‌عمر تحویل می‌شود و رسیدن مرورگر به آن تصمیم جداگانه می‌خواهد). «منقضی» برای مدرکی که انقضا دارد با **ساعت
> سرور** سنجیده و در HTML نوشته می‌شود؛ مدرک بی‌انقضا هیچ‌گاه منقضی نیست. **پیوست مدرک** زنجیره‌ای چهارمرحله‌ای است که **سرور
> پورتال** اجرا می‌کند، نه مرورگر (CSP برابر `connect-src 'self'` است، ذخیره‌ساز CORS ندارد و نشانی URL امضاشده نشانی داخلی
> است): ۱) `POST /v1/documents/upload-url` — document-service نوع و اندازهٔ اعلام‌شده را با سیاست **خودش** می‌سنجد؛ ۲) `PUT`
> بایت‌ها به URL امضاشده از سرور پورتال (`redirect: 'error'`، مهلت نام‌دار، URL هرگز در Log یا خطا نمی‌آید)؛ ۳) `POST
/v1/documents` — ثبت سند؛ سرور اندازه را از ذخیره‌ساز و نوع را از بایت‌های نخست می‌خواند؛ ۴) `POST
/v1/assets/{id}/documents` — ارجاع روی دارایی، با شناسهٔ ارسال بسته به نشست به‌عنوان `Idempotency-Key`. فایل هرگز از
> document-service یا asset-service نمی‌گذرد (ADR-014)، ولی از سرور پورتال می‌گذرد — این تصمیم **ADR-069** (`Proposed`) است: مرورگر هرگز
> با ذخیره‌ساز حرف نمی‌زند، CSP همان `connect-src 'self'` می‌ماند و روی ذخیره‌ساز CORS باز نمی‌شود. **پورتال هیچ جدول نوع و اندازهٔ مجازی ندارد**: نوع و اندازهٔ اعلام‌شدهٔ مرورگر را می‌فرستد و رد
> document-service را فارسی می‌کند؛ چون زمینهٔ ردّ سرویس بیرون نمی‌آید، جمله می‌گوید «پذیرفته نمی‌شود»، نه «حداکثر N». تنها عدد
> پورتال، سقف بدنهٔ Server Action (`WEB_UPLOAD_MAX_BYTES`، پیش‌فرض ۲۶ MiB، هنگام ساخت خوانده می‌شود) است که **انتقال** است نه
> سیاست و کمی بالاتر از سقف پیش‌فرض document-service (۲۵ MiB) نشسته تا آن سرویس رد کند؛ **سراسری است** (هر Action ممکن است بدنه‌ای
> این‌قدر بگیرد) و ADR-069 می‌گوید چه چیز آن را می‌بندد و چه چیز نه. یک پیوست دو درخواست ناامن به `/v1/documents` است، پس سقف ۲۰ در ساعت
> حدود **ده پیوست در ساعت برای هر نفر** می‌دهد (Q-98، ج). نوع مدرک ← کلاس document-service: `INSURANCE_POLICY→INSURANCE_POLICY`،
> `TECHNICAL_INSPECTION→INSPECTION_REPORT`، `PHOTO→DAMAGE_PHOTO` و بقیه `OTHER` (کم‌دامنه‌ترین) — انتخاب مسیریابی است نه قاعدهٔ
> حقوقی، در یک جدول و با تست قرارداد؛ Q-98 (الف). **متن پیش از حرکت فایل سنجیده می‌شود** (فرمی که برای عنوانش رد
> می‌شود سندی ثبت‌شده و بی‌ارجاع باقی نمی‌گذارد). **ارسال دوباره بارگذاری دوباره نیست:** پس از ثبت سند، هر نتیجه‌ای جز موفقیت
> یک **توکن امضاشده** (برای همین نشست، همین دارایی و **همین شناسهٔ ارسال**) برمی‌گرداند که سند ثبت‌شده را نام می‌برد؛ ارسال
> دوبارهٔ همان فرم، فایل را دوباره بارگذاری نمی‌کند و همان `documentId` را زیر همان کلید پیوست می‌کند (بازپخشی که asset-service
> می‌شناسد). **توکن، نوع مدرک، اندازه و SHA-256 فایل را هم می‌بندد** (بازبینی #225 دور ۱): ارسال دوباره با نوع دیگر یا فایل دیگر،
> سند قدیمی را زیر نوع جدید پیوست **نمی‌کند**؛ رد می‌شود، مقدارهای فرم می‌ماند و شناسهٔ ارسال تازه‌ای می‌دهد. **ادعای درست:**
> هرگز دو ارجاع برای یک ارسال ساخته نمی‌شود؛ ولی پاسخ گمشده (ثبت یا پیوست انجام شد و پاسخ و توکنش به مرورگر نرسید) می‌تواند
> **یک سند بی‌ارجاع** در document-service بگذارد — document-service ارسال دوباره را نمی‌شناسد (کلید `upload-url` را نمی‌خواند و
> شناسهٔ قصد را خودش می‌سازد)، پس بازیابی سمت‌سرور ممکن نیست. ارسال دوباره‌ای که کلیدش اکنون سند دیگری را نام می‌برد
> (`IDEMPOTENCY_KEY_REUSED`) بن‌بست نیست: صفحه صریح می‌گوید «ارسال تازه شروع کنید» و شناسهٔ ارسال تازه می‌دهد. فرم پس از هر
> تلاش، فایل انتخاب‌شده را (مرورگر) پاک می‌کند و می‌گوید دوباره انتخاب کنید. **پیش از خواندن بدنه** (Middleware، ADR-069 § الف):
> `POST` با `Next-Action` بی‌نشستِ بازشدنی `401` می‌گیرد؛ `Content-Length` بالاتر از `WEB_REQUEST_MAX_BYTES` (پیش‌فرض ۱ MiB)
> برای هر مسیری جز `/assets/<id>` `413` و بدنهٔ بی‌طول `411` می‌گیرد.
>
> **آمادگی اعزام در ناوگان** (`GET /v1/fleet/availability?assetId=` و `GET /v1/fleet/availability/windows?assetId=`):
> وضعیت ترکیبی («برای اعزام آزاد است» / «هم‌اکنون قابل اعزام نیست») با **همهٔ مانع‌ها**، هرکدام با متن فارسی ساخته‌شده از `code` و
> `cause`/`coverages` ساخت‌یافتهٔ ناوگان — **هرگز از جملهٔ انگلیسی `detail`** — و با «مالک این واقعیت» و «چه کسی برمی‌دارد».
> سه نوع مانع: **اعلام ناوگان** (`DECLARED_UNAVAILABLE`، تنها نوعی که پنجره و شناسه دارد)، **مانعی که سامانه اعمال می‌کند**
> (معاینهٔ مردود و بیمهٔ منقضی با `DISPATCH_BLOCKED`، در تعمیر، وضعیت دارایی) و **تخصیص فعال**. **تنها یک کنترل وجود دارد:
> «ابطال این اعلام»، کنار اعلامی که در اجراست یا هنوز آغاز نشده** — و برای مانعی که سامانه اعمال کرده هیچ کنترلی کشیده
> نمی‌شود، با هر نقشی، چون پنجره نیست و هیچ نقطهٔ پایانی آن را برنمی‌دارد؛ اعلام «قابل‌استفاده» هم آن را برنمی‌دارد (سرویس
> روی مسیر می‌گوید و صفحه هم می‌گوید). وضعیت هر اعلام (**در اجرا / هنوز آغاز نشده / پایان‌یافته / باطل‌شده**) با ساعت سرور سنجیده
> می‌شود (بازهٔ بسته مثل سرویس، `از ≤ اکنون ≤ تا`، پایان خالی یعنی تا ابطال). **اعلام وضعیت:** «قابل‌استفاده/غیرقابل‌استفاده»،
> دلیل (`displayText(3, 500)`)، و دو روز اختیاری — «از» خالی یعنی اکنون و «تا» خالی یعنی تا ابطال، و هر دو تصمیم **سرویس**
> است نه ساعت پورتال؛ روز تایپ‌شده نیمه‌شب تهران همان روز است (قاعدهٔ برش ۶). اعلام تازه جای اعلام پیشین همان دارایی را می‌گیرد.
> `POST /v1/fleet/availability` اکنون `Idempotency-Key` اجباری دارد (docs/06): بدون آن، ارسال دوبارهٔ یک درخواست قدیمی می‌توانست
> اعلام تازه‌تر را بی‌صدا باطل کند. ابطال کلید ندارد: وضعیت‌محور است و بازپخشش «پیش‌تر باطل شده» است. اگر ناوگان هنوز دارایی را
> دریافت نکرده باشد (رونوشت با رویداد پر می‌شود) صفحه می‌گوید «هنوز در ناوگان نیامده است» و فرم نمی‌کشد، چون اعلام برای دارایی
> ناشناخته `404` می‌شد و خطای کاربر به‌نظر می‌آمد. همان الگوی نوشتن برش ۶ (نشست، CSRF، شناسهٔ ارسال بسته به نشست، baseline
> امضاشده که دارایی — و برای ابطال، پنجره — را می‌بندد) و همان `404` یکسان برای دارایی یا پنجرهٔ مستأجر دیگر در خواندن و
> نوشتن.

> **ثبت سفارش روی `/marketplace/[productId]` (`EXP-003`).** تا اینجا پورتال سفارش را می‌خواند و فرمان می‌داد، ولی راهی

> صفحهٔ سفارش نشان می‌دهد. **دربارهٔ پول فقط آنچه درست است:** پلتفرم به بانک واقعی وصل نیست؛ وجه سفارش از موجودی کیف پول
> شبیه‌سازی‌شدهٔ سازمان نگه داشته می‌شود و سفارش تا پذیرش تأمین‌کننده قطعی نیست — فرم «پرداخت» نمی‌گوید، و صفحهٔ سفارشِ

> پیشنهادهای **خود سازمان** در انتخاب نیست (سرویس سفارش از خود را رد می‌کند و فرم ساخته‌شده فقط برای ردشدن بی‌معنی است).
> الگوی نوشتن همان برش ۷ است: نشست، CSRF، شناسهٔ ارسال بسته به نشست که همان `Idempotency-Key` است (`orders` کلید را در دروازه

> (`BUSINESS_RULE_VIOLATION`) و کد نمی‌گوید کدام؛ پس جمله‌های ثابت (سفارش از خود، مجموع غیرمثبت) با تطبیق دقیق ترجمه می‌شوند و
> دو جملهٔ دارای شناسه و عدد زنده (کمینهٔ سفارش، موجودی) به متن **کد** می‌افتند — که برای هر دو درست است و چیزی از انگلیسی سرویس
> نشت نمی‌کند. پیشنهادِ نبود یا منتشرنشده هر دو `404` است و یک پیام می‌گیرد («دیگر در دسترس نیست و سفارشی ثبت نشد»)؛ کلید
> دوباره‌مصرف‌شده (`409` بی‌`Retry-After`) «پیش‌تر ثبت شده» است؛ نتیجهٔ نامعلوم هرگز «سفارشی ثبت نشد» نمی‌گوید. `select` پیشنهاد

> فراخوانی‌ای که پرتاب شد)؛ هر شکست دیگر «پاسخی نیامد» است و دکمهٔ ارسال دوباره می‌ماند (یافتهٔ ۴). نشستی که Middleware فقط به این
> دلیل پنهان کرد که توکن دسترسی‌اش تمام شده و تازه‌سازی‌اش موقتاً در دسترس نیست (`REFUSED`، نه `ENDED`) پایان‌یافته نیست: Middleware
> هر درخواستی را که تازه‌سازی‌اش رد شد — حتی اگر توکن آن لحظه هنوز معتبر می‌نمود، چون ممکن است میان تازه‌سازی و بررسیِ خودِ مسیر منقضی
> شود؛ اعتبار هم با ساعتِ پس از پایان تازه‌سازی سنجیده می‌شود (#319 دور ۳، یافتهٔ ۲) — با سرآیند `x-rasta-session-state` (که از مرورگر
> پذیرفته نمی‌شود) علامت می‌زند، `/auth/session` برای آن `503` می‌دهد و
> اکشن `SESSION_UNAVAILABLE` (چیزی فرستاده نشد؛ در ارسال دوباره «نامعلوم» با دکمهٔ ارسال دوباره) — `server/session-state.ts`
> (#319 دور ۲، یافتهٔ ۳). **مانند سفارش، ارسالِ نامعلوم
> در `sessionStorage` می‌ماند** (`lib/unresolved-dispute.ts`، به‌ازای هر تراکنش و بسته به ورود): جدول حالت دستور دوم با کلید تازه
> را بی‌خطر نمی‌کند — `PENDING_SETTLEMENT → DISPUTED → PENDING_SETTLEMENT` مجاز است، پس رسیدگیِ ثبت‌شده‌ای که دیده نشد، اگر پس
> از اعتراض تازهٔ پرداخت‌کننده با کلید تازه فرستاده شود، اعتراض تازه را رسیدگی می‌کند (یافتهٔ ۲). ورودی پیش از ارسال نوشته
> می‌شود؛ تا روشن‌شدن نتیجه هیچ فرم تازه‌ای روی آن تراکنش کشیده نمی‌شود و فقط همان درخواست با همان کلید و بدنه دوباره فرستادنی
> است — فقط از همان ورود و فقط تا مهلتی که **سرور** تعیین می‌کند (#319 دور ۲، یافتهٔ ۲، `server/dispute-replay.ts`): صفحه هنگام
> رسم فرم، همراه شناسهٔ ارسال، مُهری امضاشده برای همین تراکنش و همین شناسه صادر می‌کند که انقضای امضاشده‌اش «نگه‌داری Idempotency
> در economic-service منهای حاشیهٔ رفت‌وآمد» است (`WEB_ECONOMIC_IDEMPOTENCY_TTL_HOURS`، آینهٔ `ECONOMIC_IDEMPOTENCY_TTL_HOURS` با پیش‌فرضِ
> کفِ آن یعنی ۱؛ `WEB_DISPUTE_REPLAY_MARGIN_SECONDS` با پیش‌فرض ۶۰۰)، و اکشن پیش از **هر** ارسال زیر آن کلید آن را می‌سنجد — هم با
> انقضای امضاشدهٔ خودش و هم با «زمان صدورِ امضاشده + پنجرهٔ پیکربندیِ کنونی»، تا کوتاه‌کردن نگه‌داری مُهرهای پیشین را هم کوتاه کند
> (#319 دور ۳، یافتهٔ ۱)؛ گذشته
> از مهلت، ارسال نخست با «فرم کهنه شده» رد می‌شود و ارسال دوباره چیزی نمی‌فرستد و برای همیشه فقط‌نمایشی و «نامعلوم» می‌ماند.
> economic-service تغییری نکرده است. پاسخ تأییدشده ورودی را پاک می‌کند؛ وگرنه فقط خود شخص، پس از ارسال دوبارهٔ ردشده یا وقتی
> دیگر نمی‌توان فرستاد، آن را کنار می‌گذارد. **انقضا یا خروج هرگز آن را بی‌صدا پاک نمی‌کند** (#319 دور ۲، یافتهٔ ۱): ورودیِ
> کهنه‌تر از عمر نشست، و هر ورودی هنگام خروج، به نشانگری بی‌متن، بی‌برچسب ورود و بی‌مُهر کاسته می‌شود که فقط‌نمایشی «نتیجه
> نامعلوم» می‌گوید و تا تأیید صریح شخص هیچ فرم تازه‌ای روی آن تراکنش کشیده نمی‌شود؛ صفحهٔ شخص دیگر ورودی‌ها و نشانگرهای دیگران
> را پاک می‌کند (`AccountBoundary`). **تأیید پس از موفقیت** پارامتر پرس‌وجوی دلخواه نیست: توکن امضاشدهٔ `flash` برای همین
> نشست، همین تراکنش و همین دستور (`server/flash.ts`) است، پس از نمایش از نشانی برداشته می‌شود، و فقط کاری را که درخواست خودِ
> شخص کرد با فعل گذشته می‌گوید — وضعیت کنونی همان رکوردِ تازه‌خوانده است (یافتهٔ ۳). ردهای سرویس با متن فارسی ثابت بر پایهٔ کد خطا نمایش داده می‌شوند و جملهٔ سرویس هرگز بازتاب نمی‌یابد. **جداسازی
> مستأجر (زنده در CI، `e2e/transactions.spec.ts`):** تراکنشِ سازمانی که طرف آن نیست برای خواندن و ثبت اعتراض دقیقاً همان پاسخ
> شناسهٔ ناموجود را می‌گیرد و صفحه همان متن را نشان می‌دهد؛ پرداخت‌کننده اعتراض می‌کند، دریافت‌کننده آن را می‌بیند و فرمی ندارد، و
> مدیر اتحادیه رسیدگی می‌کند.

> **بازگشت کالا روی `/orders/[id]`، `/returns` و `/returns/[id]` (`EXP-003`، RUN-005، ADR-048).** خریدارِ سفارشِ
> `COMPLETED` از صفحهٔ سفارش درخواست بازگشت می‌دهد (`POST /v1/orders/{id}/returns`: دلیل ۱۰ تا ۱۰۰۰ نویسه و ردیف‌های سفارش با
> تعداد — بدنهٔ `.strict()` سرویس، بی‌قیمت و بی‌مبلغ)؛ هر ردیف «فروخته‌شده» و «قابل بازگشت» (فروخته منهای درخواست‌های باز
> همان سفارش، همان `openQuantities` سرویس) را نشان می‌دهد. `/returns` درخواست‌ها را از هر دو سمت (`role=BUYER|SUPPLIER`، مثل
> سفارش‌ها) فهرست می‌کند؛ `/returns/[id]` وضعیت، سابقه (از مهرهای زمانی خود درخواست)، دلیل، ردیف‌ها و — اگر inventory-service
> به نقش شخص نشان دهد — محمولهٔ بازگشت، دریافت، بازرسی و تعیین تکلیف را نشان می‌دهد؛ ردِ آن سمت فقط دربارهٔ کالاست و چیزی از
> درخواست پنهان نمی‌کند. تأمین‌کننده `REQUESTED` را می‌پذیرد یا رد می‌کند (`POST …/decisions`، بدنه فقط `decision`) و
> خریدار `REQUESTED` یا `AUTHORIZED` را لغو می‌کند (`POST …/cancellation`). **نه بازپرداختی و نه ادعای آن:** هیچ وضعیتی
> وجه جابه‌جا نمی‌کند (Q-76) و صفحه این را می‌گوید. **چه کسی چه می‌کند** نسخه‌برداری از بررسی‌های خود سرویس است (نمای
> بازگشت `availableActions` ندارد)، از نقش‌های توکن: `@Roles` هر مسیر با `rolesGuardAdmits`، سپس `assertBuyer`/`assertSupplier`
> (سازمان درخواست = خریدار/فروشندهٔ سفارش؛ نقش پلتفرم معاف نیست)، سپس جدول گذار؛ `returns.contract.spec.ts` همه را به سورس
> marketplace-service سنجاق می‌کند. **مهلت بازگشت** پیکربندی سرویس است (`MARKETPLACE_RETURN_WINDOW_DAYS`، بی‌پیش‌فرض، Q-132) و
> هیچ endpoint آن را نمی‌گوید؛ پس فرم برای سفارش تکمیل‌شده کشیده می‌شود و «مهلت پیکربندی نشده» و «مهلت گذشته» از رد سرویس
> دانسته می‌شوند. **ردها:** هر قاعدهٔ کسب‌وکاری این مسیرها `422 BUSINESS_RULE_VIOLATION` است و علت فقط در Log سرویس است؛ پس
> جمله‌ها — یکی ثابت (Q-132) با تطبیق دقیق و بقیه که شناسه یا عدد دارند (مهلت گذشته، سفارش ناتمام، تعداد بیش از مانده،
> وضعیت نادرست) با الگوی کامل (`FieldMapping.patterns`، `server/write.ts`) — به متن فارسی ثابت می‌روند و جملهٔ سرویس هرگز نشان
> داده نمی‌شود؛ هر الگو از قالب جملهٔ سورس ساخته و آزموده می‌شود. **نتیجهٔ نامعلوم و یک خانهٔ مشترک** (`lib/unresolved-return.ts`):
> قواعد اعتراض تراکنش و صورت‌وضعیت — به خاطر سپردن پیش از ارسال، ارسال دوباره با همان کلید و همان بدنه تا مهلت امضاشده
> (`server/return-replay.ts`، آینهٔ `MARKETPLACE_IDEMPOTENCY_TTL_HOURS` با `WEB_MARKETPLACE_IDEMPOTENCY_TTL_HOURS` و
> `WEB_RETURN_REPLAY_MARGIN_SECONDS`)، نشانگر هنگام خروج — و هر سفارش یک خانه و هر درخواست یک خانه دارد: پذیرش، رد و لغوِ
> یک درخواست خانه را مشترک دارند، ارسال تازه هرگز رکورد دیگری را جایگزین نمی‌کند و رکورد فقط با شناسهٔ ارسال خودش و بر پاسخ
> قطعی همان ارسال پاک می‌شود؛ تا یکی نامعلوم است، فرم‌های دیگر فقط اعلان عدم قطعیت دارند. **فهرستِ inventory ادعاست، نه
> پیشرفت** (#336 دور ۱، یافتهٔ ۱): inventory-service ارجاع‌های marketplace را حل نمی‌کند، پس هر سازمانی می‌تواند در انبار خودش
> محموله‌ای با شناسهٔ این درخواست و نام خریدار ثبت کند و خریدار آن را می‌بیند؛ صفحه همهٔ صفحه‌های فهرست را می‌خواند و فقط محموله‌ای را
> پیشرفت می‌داند که همان بررسی‌های mirror (`decideMirror`) را بگذراند — ثبت‌کننده تأمین‌کنندهٔ درخواست، فرستنده خریدار آن، همان
> سفارش، درخواستِ پذیرفته، همان محموله‌ای که marketplace بر درخواست نشانده، و ردیف‌ها دقیقاً ردیف‌های درخواست (تا mirror چیزی
> ننشانده، قاعدهٔ سخت‌گیر، چون تنظیم ارسال جزئی دیده نمی‌شود)؛ بقیه فقط با اعلان «جور نیست» شمرده می‌شوند و هیچ جزئی از آن‌ها نشان
> داده نمی‌شود. **لغوِ درخواستِ پذیرفته‌شده در درگاه عرضه نمی‌شود** (یافتهٔ ۲، دور ۲ و ۳؛ تصمیم PM): mirror به‌طور پیش‌فرض خاموش است و
> درخواست پس از ارسال کالا همچنان `AUTHORIZED` است، و لغو واحدها را آزاد می‌کند؛ و درگاه نمی‌تواند ثابت کند که هنوز محموله‌ای
> نیست (محمولهٔ جزئی، نقشی که سوی کالا را نمی‌بیند، فرمی که پیش از ارسال کشیده شده). این تضمین از آنِ backend است؛ تا وقتی
> marketplace لغو را پس از وجود محموله رد نکند، درگاه لغو را فقط برای `REQUESTED` عرضه می‌کند (`PORTAL_CANCEL_FROM`)، برای
> درخواست پذیرفته با متن ثابت می‌گوید که لغو هنوز در درگاه ممکن نیست، و action پیش از ارسال درخواست را دوباره می‌خواند و جز
> `REQUESTED` (یا `CANCELLED`، که ارسالش فقط بازپخشِ همان لغو است) را بی‌آنکه چیزی بفرستد رد می‌کند. **مانده با همهٔ
> درخواست‌ها** (یافتهٔ ۳): درخواست‌های سفارش تا پایان `nextCursor` خوانده می‌شوند و هر درخواستی جز ردشده و لغوشده واحدهایش را
> نگه می‌دارد (`RETURN_STATUSES_HOLDING_UNITS`)؛ شمارشِ ناقص یعنی نامعلوم، و فرم درخواست با اعلان کشیده نمی‌شود. **زنده در CI**
> (`e2e/returns.spec.ts`، دو سفارش تکمیل‌شده از `e2e/fixtures/marketplace-returns.sql` و مهلت آزمایشیِ همان پشته): خریدار
> درخواست می‌دهد، سفارش قدیمی با متن ثابت رد می‌شود، تأمین‌کننده می‌پذیرد، کالا در راه و دریافت‌شده دیده می‌شود، خریدار درخواست
> دوم را لغو می‌کند، و سازمان سوم درخواست و سفارش را همان‌گونه می‌بیند که شناسهٔ ناموجود را.

> **نقش‌ها همه‌جا از توکن؛ «نشست پایان یافته» همه‌جا فقط با پاسخ قطعی.** دو قاعدهٔ #319 به بقیهٔ پورتال رسیده است. (۱) هر
> چیزی که بر پایهٔ نقش کشیده یا انتخاب می‌شود — پیوندهای نوار کناری، دو درِ مناقصه‌ها (`/tenders` و `/tenders/[id]`) و فرم‌های
> دارایی، راننده، تعمیر و نگهداری و ثبت سفارش — از **نقش‌های خودِ توکن دسترسی** برای سازمانی که توکن به آن می‌رسد خوانده می‌شود
> (`tokenRoles` روی `tokenAuthority`: جفت‌های `org_roles` همان `org_id` به‌علاوهٔ نقش‌های سراسری realm، همان `rolesForRequest`
> سرویس‌ها)، نه از `effectiveRoles` در `/v1/users/me` که تا تازه‌شدن توکن جلوتر از آن است: نقشی که در هویت برداشته شد ولی هنوز در
> توکن هست هنوز پذیرفته می‌شود و فرمش می‌ماند، و نقشی که افزوده شد ولی هنوز در توکن نیست هنوز رد می‌شود و فرمی نمی‌آورد. توکنی که
> نقشش خوانده نشود یا دروازه آن را رد کند هیچ چیز دروازه‌دار نمی‌آورد؛ مناقصه‌ها در این حالت درِ مالک را می‌پرسند و پاسخ خودِ
> سرویس را نشان می‌دهند. این صفحه‌ها برای نقش دیگر `/v1/users/me` را نمی‌خوانند. فهرست نقش‌های پذیرفته تغییری نکرده است. صفحهٔ
> خانه همچنان سابقهٔ هویت را «مرجع مجوزدهی نیست» نمایش می‌دهد، و نردبان اعطای نقش در `/organizations` را خودِ identity-service از
> نقش‌های همان درخواست حساب می‌کند. (۲) هر اکشن نوشتنی که نشستی نیابد، اگر Middleware درخواست را «تازه‌سازی در دسترس نیست»
> علامت زده باشد `SESSION_UNAVAILABLE` («همین حالا در دسترس نیست، چند لحظه بعد دوباره بفرستید») و وگرنه `NO_SESSION` («پایان
> یافته، دوباره وارد شوید») برمی‌گرداند (`missingSessionReason`، متن‌ها در `lib/session-refusal.ts`)؛ در هر دو حالت چیزی فرستاده
> نشده است.
>
> **قاعدهٔ نقش هر فرم نوشتنی همان `RolesGuard` است** (#325 دور ۱، یافتهٔ ۲؛ `server/roles-guard.ts`، پین‌شده به سورس
> `packages/nest-common`): `AUDITOR` هر جا که مسیر نامش را نبرد رد می‌شود — حتی کنار نقش دیگر یا `SYSTEM_ADMIN` — و `SYSTEM_ADMIN`
> (دامنه‌دار یا نقش سراسری realm) هر مسیری را که نقش نام می‌برد می‌پذیرد؛ وگرنه یکی از نقش‌های فهرست. فرم نوشتنی فقط برای توکنی
> کشیده می‌شود که به سازمانی برسد (`tokenWriteRoles`): هر نوشتنِ پورتال تک‌مستأجری است و سرویس بی‌سازمانِ درخواست نمی‌تواند
> عمل کند. فقط نمایش است؛ سرویس هر بار دوباره تصمیم می‌گیرد.

## ۱۶٫۸ Gamification در UI

**قید صریح سند محصول:** «از الگوهای کودکانه یا سرگرمی‌محور پرهیز کند» و «متناسب با یک
سند دولتی-تعاونی».

```
✅ نمایش امتیاز به‌صورت شاخص عددی حرفه‌ای
✅ سطح کاربر به‌صورت نشان متنی ساده
✅ نوار پیشرفت آرام تا سطح بعد
✅ تمرکز پیام بر «کامل بودن داده» و «به‌موقع بودن»
✅ نمایش علت هر تغییر، نسخه قاعده و مسیر اعتراض
✅ مقایسهٔ شخص با بازهٔ گروه همتای هم‌نقش، بدون افشای دادهٔ ریز دیگران
✅ تفکیک «امتیاز مشارکت» از «امتیاز قابل تبدیل به مزیت»

❌ Confetti، انیمیشن جشن، صدا
❌ نشان‌های کارتونی، شخصیت، آواتار بازی‌گونه
❌ جدول رده‌بندی عمومی میان دهیاری‌ها یا نقش‌های نابرابر
❌ اصطلاحات بازی («امتیاز بگیر!»، «رکورد بزن!»)
```

معیار موفقیت: **نرخ ثبت به‌موقع داده**، نه میزان تعامل ظاهری.

مزایا، هدف گروهی و مشاهدهٔ رتبه فقط پس از پیکربندی مصوب فعال می‌شوند. حالت خالی باید
بگوید «مزیتی برای این دوره تعریف نشده است»، نه اینکه وعدهٔ پاداشی خارج از قرارداد بدهد.

## ۱۶٫۹ دسترس‌پذیری (WCAG 2.1 AA)

| الزام                                                      |
| ---------------------------------------------------------- |
| کنتراست ≥ ۴٫۵:۱ برای متن، ≥ ۳:۱ برای عناصر رابط            |
| هر عملکرد با صفحه‌کلید در دسترس؛ ترتیب Tab منطقی           |

## ۱۶٫۱۰ کارایی و PWA

| هدف                       | مقدار            |
| ------------------------- | ---------------- |
| First Contentful Paint    | < ۱٫۵ ثانیه (3G) |
| Largest Contentful Paint  | < ۲٫۵ ثانیه      |
| Interaction to Next Paint | < ۲۰۰ms          |
| Cumulative Layout Shift   | < ۰٫۱            |
| Bundle اولیه JS           | < ۲۰۰KB gzip     |

**راهبرد:** Server Component به‌صورت پیش‌فرض · تقسیم کد بر اساس مسیر ·
`next/image` با AVIF/WebP · فونت محلی با `font-display: swap` · صفحه‌بندی سمت سرور.

**PWA (الزام سند محصول: «نسخه سازگار با تلفن همراه یا اپلیکیشن تحت وب پیشرونده»):**

- Manifest + آیکون
- Service Worker: Cache پوسته اپ و داده مرجع
- **صف Offline برای ثبت کارکرد** — اپراتور میدانی ممکن است اینترنت نداشته باشد؛
  ثبت محلی می‌شود و با بازگشت اتصال همگام‌سازی می‌شود (با `Idempotency-Key` تا تکراری نشود)
- نشانگر صریح وضعیت آنلاین/آفلاین

**آمادگی موبایل بومی.** همه منطق در API است، نه در UI. یک کلاینت Flutter یا Native در آینده
همان APIها را مصرف می‌کند بدون هیچ تغییر Backend.

## ۱۶٫۱۱ امنیت سمت کلاینت

```
✅ Access Token فقط در حافظه (نه localStorage — بردار XSS)
✅ Refresh Token در Cookie با HttpOnly + Secure + SameSite=Strict
✅ CSP سخت‌گیرانه؛ بدون inline script
✅ همه ورودی‌ها با همان Zod Schema سرور اعتبارسنجی می‌شوند
✅ Route Guard بر اساس نقش  (به‌عنوان UX، نه امنیت)
✅ نمایش correlationId در ErrorState برای پشتیبانی

🚫 dangerouslySetInnerHTML
🚫 هیچ Secret در متغیرهای NEXT_PUBLIC_
🚫 اتکا به مخفی کردن UI به‌عنوان کنترل امنیتی — سرور همیشه دوباره بررسی می‌کند
```

**CONSTRAINT.** پنهان کردن یک دکمه در UI **کنترل امنیتی نیست**. هر بررسی مجوز در UI
صرفاً برای تجربه کاربری است؛ سرور همیشه مستقلاً مجوزدهی می‌کند.
