# ۲۳ — Risks & Trade-offs

> هر تصمیم معماری هزینه دارد. این سند هزینه‌ها را **صریح** ثبت می‌کند.
> تصمیمی که «هیچ عیبی ندارد»، احتمالاً به‌درستی بررسی نشده است.

قالب هر مورد: **Risk · Benefit · Cost · Alternative · Mitigation**

---

## ۲۳٫۱ معاوضه‌های معماری

### T-01 · Microservices در مقیاسی که Monolith کافی بود

| بُعد            | شرح                                                                                                                                                                     |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Risk**        | ۱۷ سرویس برای بار فاز ۱ (۳۲۸ سازمان، ده‌ها تراکنش در روز) بیش از حد است. پیچیدگی عملیاتی، تأخیر شبکه، دشواری اشکال‌زدایی توزیع‌شده.                                     |
| **Benefit**     | مرز داده‌ای واقعی از روز اول؛ گذار به مقیاس ملی یک تصمیم استقرار است، نه بازنویسی؛ تیم‌های مستقل.                                                                       |
| **Cost**        | زمان توسعه بیشتر، زیرساخت سنگین‌تر، منحنی یادگیری بالاتر برای تیم انسانی.                                                                                               |
| **Alternative** | Modular Monolith با تقسیم بعدی.                                                                                                                                         |
| **چرا رد شد**   | مرز داده‌ای در Monolith عملاً هرگز رعایت نمی‌شود. یک `JOIN` بی‌ضرر امروز، یک وابستگی غیرقابل جدا کردن فرداست. هزینه اصلاح بعدی از هزینه اولیه بیشتر است.                |
| **Mitigation**  | `docker compose up` کل Stack را محلی بالا می‌آورد · Trace انتها به انتها · قواعد ESLint مرزها را تحمیل می‌کنند · تجمیع آگاهانه سه سرویس برای پرهیز از Over-Engineering. |

### T-02 · Kafka برای حجمی که یک صف ساده کافی بود

| بُعد            | شرح                                                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Risk**        | Kafka برای هزاران رویداد در روز، سنگین است. یک جزء زیرساختی بیشتر برای نگهداری.                                                                         |
| **Benefit**     | ترتیب تضمین‌شده به‌ازای Aggregate · بازپخش تاریخی برای ساخت Read Model جدید · Log حسابرسی‌پذیر · مسیر مقیاس ملی.                                        |
| **Cost**        | حافظه و پیچیدگی عملیاتی؛ نیاز به دانش Kafka در تیم.                                                                                                     |
| **Alternative** | RabbitMQ، NATS، یا صف مبتنی بر PostgreSQL.                                                                                                              |
| **چرا رد شد**   | هیچ‌کدام **بازپخش تاریخی** نمی‌دهند. وقتی `analytics-service` اضافه شود، باید بتواند از Offset صفر همه تاریخ را بخواند. با صف معمولی، آن داده رفته است. |
| **Mitigation**  | KRaft (بدون ZooKeeper) · تک‌گره در dev · Kafka UI برای مشاهده · Outbox تضمین می‌کند افت Kafka رویداد را نمی‌خورد.                                       |

### T-03 · Temporal به‌عنوان وابستگی سنگین

| بُعد            | شرح                                                                                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Risk**        | Temporal یک سیستم توزیع‌شده کامل با پایگاه داده خودش است. اگر تیم انسانی با آن آشنا نباشد، نگهداری‌اش دشوار می‌شود.                                    |
| **Benefit**     | Timer ماندگار برای مهلت مناقصه (هفته‌ها) · تاریخچه کامل اجرا · Retry و جبران داخلی · Determinism.                                                      |
| **Cost**        | یک پایگاه داده و یک Cluster بیشتر؛ منحنی یادگیری؛ محدودیت Determinism در کد Workflow.                                                                  |
| **Alternative** | Cron + جدول وضعیت · BPMN Engine · صف تأخیردار.                                                                                                         |
| **چرا رد شد**   | با Cron، اگر سرویس در میانه مهلت مناقصه Restart شود، مهلت از دست می‌رود. برای فرآیندی با اثر حقوقی، این غیرقابل قبول است.                              |
| **Mitigation**  | State Machineها **صریح و جدا از Temporal** تعریف شده‌اند — اگر Temporal حذف شود، منطق دامنه سالم می‌ماند · Temporal UI برای مشاهده · مستندسازی الگوها. |

### T-04 · Kong/APISIX کنار گذاشته شد

| بُعد            | شرح                                                                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Risk**        | Gateway اختصاصی یعنی بازنویسی چیزهایی که Kong آماده دارد (Rate Limit، Auth Plugin، پایش).                                             |
| **Benefit**     | حل `activeOrganizationId` از عضویت‌های کاربر — منطق دامنه‌ای که در Plugin جای درستی ندارد؛ همان زبان و همان تست‌ها.                   |
| **Cost**        | نگهداری کد بیشتر؛ باید Rate Limit و Circuit Breaker را خودمان درست پیاده کنیم.                                                        |
| **Alternative** | Kong یا APISIX با Plugin سفارشی.                                                                                                      |
| **Mitigation**  | **در Production یک Edge Gateway (Kong/APISIX) برای TLS، WAF و Rate Limit سراسری جلوی این می‌نشیند** — دو نقش مکمل، نه رقیب. → ADR-009 |

### T-05 · Prisma به‌ازای هر سرویس

| بُعد            | شرح                                                                                                                    |
| --------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Risk**        | Prisma برای Query پیچیده (پنجره‌ای، بازگشتی، PostGIS پیشرفته) محدود است.                                               |
| **Benefit**     | Migration اعلانی · Type-Safety کامل · Schema جدا به‌ازای هر سرویس (تحمیل مالکیت داده).                                 |
| **Cost**        | مرحله Generate در Build؛ `$queryRaw` برای موارد پیچیده.                                                                |
| **Alternative** | TypeORM · Drizzle · SQL خام با Kysely.                                                                                 |
| **Mitigation**  | `$queryRaw` با Template Tag برای Query پیچیده (پارامتری، امن) · Query کند در Log · بازبینی اجباری برای هر `$queryRaw`. |

## ۲۳٫۵-الف بدهی ثبت‌شده

### D-013 · `ledger_entry` پارتیشن‌بندی نشده

- **چه چیزی:** `docs/05` § ۵٫۴ جدول را با `PARTITION BY RANGE (posted_at)` و
  § ۵٫۶ با بازه ماهانه تعریف کرده. امروز یک جدول ساده است.
- **چرا:** یک جدول پارتیشن‌بندی‌شده بدون پارتیشنِ ماهِ جاری، `INSERT` را رد
  می‌کند — یعنی حالت شکستش «نیمه‌شب اول ماه، نوشتن مالی متوقف می‌شود» است.
  جلوگیری از آن یک ساز‌و‌کار خودکار ساخت پارتیشن می‌خواهد (`pg_partman` یا یک
  Job) که این پلتفرم ندارد. تحلیل کامل در **ADR-030**.
- **ریسک:** پایین امروز (حجم صفر). با رشد، Query تاریخی از Partition Pruning
  بهره نمی‌برد و حذف داده کهنه `DELETE` است نه `DROP PARTITION`.
- **رفع:** شرط فعال‌سازی **عددی** است، نه یادداشت: وقتی
  `rasta_economic_ledger_entries_total` از یک میلیون در ماه بگذرد — ده برابر
  زودتر از آستانه استخراج در `docs/04` § ۴٫۱. مسیر اجرا در ADR-030.
- **اولویت:** پایین (تا رسیدن به آستانه)
- **ثبت‌شده:** 2026-08-29

### D-014 · تسویه بدون Temporal

- **چه چیزی:** `docs/08` § ۸٫۶ و `docs/10` § ۱۰٫۱۰ تسویه را یک Workflow در
  Temporal تعریف کرده‌اند. پیاده‌سازی یک تراکنش ACID با ماشین حالت صریح است.
- **چرا:** خودِ CONSTRAINT همان بند می‌گوید مراحل ۳ و ۴ در یک تراکنش‌اند و پس
  از مرحله ۳ هیچ جبران خودکاری وجود ندارد — یعنی هسته این فرآیند Saga نیست، و
  Temporal برای چیزی که جبران ندارد هماهنگی اضافه نمی‌کند. هیچ سرویسی هم هنوز
  Temporal را بالا نیاورده (ADR-027). تحلیل کامل در **ADR-031**.
- **ریسک:** دید عملیاتی به تسویه‌های شکست‌خورده از Metric و Log می‌آید، نه از
  یک UI Workflow. برای بازیابی، اپراتور باید Query بزند.
- **رفع:** `SettlementService.settle()` به‌شکلی نوشته شده که تبدیلش به یک
  Temporal Activity تغییر امضا نمی‌خواهد.
- **اولویت:** متوسط — وقتی `marketplace-service` انتظار چندروزه تأیید دریافت را
  لازم کند، آن سرویس باید تصمیم بگیرد Temporal را بالا بیاورد.
- **ثبت‌شده:** 2026-08-29

### D-015 · مصرف‌کننده‌های `ORDER_*` و `STATEMENT_APPROVED` موکول

- **چه چیزی:** `docs/04` § ۴٫۱۴ آن‌ها را در فهرست مصرف دارد؛ پیاده نشده‌اند و
  **Stub هم ندارند**.
- **چرا:** قراردادشان فقط طرح فیلدهای کلیدی است — `ORDER_RECEIPT_CONFIRMED`
  هیچ مبلغی ندارد و شکل `total` در `ORDER_CREATED` نامعلوم است. نوشتنشان یعنی
  `economic-service` شکل Payload سرویس دیگری را اختراع کند (**ADR-032**).
- **ریسک:** هیچ امروز؛ تولیدکننده‌هایشان وجود ندارند. چرخه کامل مالی از راه API
  در دسترس و تست‌شده است، که همان چیزی است که `docs/08` § ۸٫۶ می‌خواهد.
- **رفع:** هنگام ساخت `marketplace-service` و `contract-service`، همان سرویس‌ها
  قرارداد رویدادشان را تعریف می‌کنند و مصرف‌کننده یک لایه نازک روی متدهای موجود
  می‌شود.
- **اولویت:** به `marketplace-service` گره خورده
- **ثبت‌شده:** 2026-08-29

### D-016 · پورت میزبان Kafka روی ویندوز

- **چه چیزی:** روی این ماشین توسعه، ۹۰۹۲ داخل یک بازه رزروشده ویندوز است
  (`netsh interface ipv4 show excludedportrange protocol=tcp` → `9081-9180`) و
  Docker اصلاً نمی‌تواند آن را Publish کند.

- **چه چیزی:** `ProxyService` در `api-gateway` روی **هر** درخواست

    آسیب‌پذیری High پین کردیم).
  - `trustPolicy: no-downgrade` چهار بسته را
    `High-risk trust downgrade (possible package takeover)` علامت می‌زند:
    `chokidar@4.0.3`، `pino@9.14.0`، `semver@6.3.1`،
    `undici-types@6.21.0`.
- **ریسک:** پنجره‌ای که یک نسخه تازه‌منتشرشده و مخرب می‌تواند وارد درخت
  وابستگی شود، همچنان باز است. چهار هشدار `trust downgrade` هنوز
  **بررسی نشده‌اند** — ممکن است صرفاً بازتاب نبودِ Provenance روی
  نسخه‌های قدیمی باشند، یا نباشند. تا بررسی نشوند نمی‌توان گفت کدام.
- **رفع:** یک کار مستقل: هر چهار هشدار Trust بررسی شود، درخت دوباره
  Resolve شود، و سه قاعده دوباره فعال شوند. این کار Lockfile را به‌طور
  گسترده تغییر می‌دهد و نباید با یک Task امنیتی دیگر مخلوط شود.
- **اولویت:** متوسط
- **ثبت‌شده:** 2026-08-27

### D-009 · Healthcheck کانتینر Temporal همیشه Fail است

- **چه چیزی:** `docker compose ps` کانتینر `rasta-temporal` را
  **unhealthy** نشان می‌دهد، با `FailingStreak: 754` — یعنی از لحظه
  بالا آمدن، هرگز یک‌بار هم موفق نشده. این با ثبت قبلی در
  `PROJECT_MEMORY.md` («همه `healthy`») در تناقض است؛ ثبت قبلی اشتباه
  بوده است.
- **ریشه (بررسی‌شده، نه حدس‌زده):** Healthcheck فرمان
  `temporal operator cluster health --address localhost:7233` را اجرا
  می‌کند و در ۱۰ ثانیه Timeout می‌خورد. اما مسئله شبکه نیست:
  - `docker exec rasta-temporal echo hi` → `0`، بلافاصله.
  - `docker exec rasta-temporal temporal --version` → **Hang** تا Timeout.
    این فرمان هیچ شبکه‌ای لمس نمی‌کند.

  یعنی **خودِ باینری `temporal` داخل این Image روی این میزبان اجرا
  نمی‌شود**؛ نه اینکه Server پاسخ ندهد. تعویض `localhost` با `127.0.0.1`
  هیچ تفاوتی نکرد، پس فرضیه IPv6 هم رد شد.

- **وضعیت واقعی Server:** شواهد **غیرمستقیم** می‌گویند سالم است — پورت
  gRPC `7233` از میزبان باز است، Log ها جریان عادی
  `Started/Stopped physicalTaskQueueManager` را نشان می‌دهند، هیچ خطا یا
  Restart ای نیست. اما چون هر ابزار Probe در دسترس Hang می‌کند،
  **سلامت gRPC مثبتاً تأیید نشده است.** وضعیت درست: `NOT_VERIFIED`.
- **اثر امروز:** هیچ. هیچ سرویسی هنوز از Temporal استفاده نمی‌کند
  (`docs/08` برنامه‌ریزی‌شده است، پیاده نشده) و CI هم Temporal را بالا
  نمی‌آورد.
- **رفع:** موکول به نخستین سرویسی که واقعاً Workflow می‌نویسد. آن‌وقت هم
  Healthcheck باید به یک Probe مستقل از CLI تغییر کند (مثلاً `grpc_health_probe`
  یا یک TCP Probe ساده)، هم سلامت واقعی Server مثبتاً تأیید شود.
- **اولویت:** پایین (تا وقتی هیچ سرویسی Temporal را لمس نکند)
- **ثبت‌شده:** 2026-08-27

### D-011 · تغییر برنامه سرویس، هیچ رویدادی تولید نمی‌کند

- **چه چیزی:** `maintenance-service` برای ساخت، ویرایش، توقف و بایگانی یک
  `MaintenanceSchedule` هیچ رویدادی منتشر نمی‌کند. دلیل تغییر وضعیت در ستون
  `notes` الحاق می‌شود، نه در یک رد حسابرسی.
- **چرا:** کاتالوگ رویدادها (`docs/events/README.md`) هیچ رویداد `SCHEDULE_*`
  ندارد، و قاعده‌ای که این فاز برای خودش گذاشت این بود: **رویدادی فراتر از
  کاتالوگ فقط برای درست نگه داشتن ادعایی که قبلاً منتشر شده اضافه می‌شود.**
  ساخت یک برنامه هرگز منتشر نشده، پس ادعای نادرستی هم برای اصلاح وجود ندارد.
- **ریسک:** یک برنامه سرویس تعیین می‌کند دستگاهی هر چند وقت سرویس می‌شود.
  خاموش کردن بی‌صدای آن تصمیمی است که `audit-service` — که تنها ورودی‌اش رویداد
  است — هرگز نخواهد دید. امروز بی‌اثر است چون `audit-service` وجود ندارد؛ روزی
  که بیاید، این شکاف واقعی می‌شود.
- **رفع:** هنگام ساخت `audit-service`، یا یک `MAINTENANCE_SCHEDULE_CHANGED` به
  کاتالوگ افزوده شود، یا رد حسابرسی از راه دیگری تأمین شود. ستون `notes` تا آن
  زمان دلیل را نگه می‌دارد، پس داده گم نمی‌شود.
- **اولویت:** متوسط (تا وقتی `audit-service` نیست، پایین)
- **ثبت‌شده:** 2026-08-28

### D-012 · کنتور کارکرد هرگز عقب نمی‌رود

- **چه چیزی:** `asset_usage_meter` از `GREATEST(کنتور فعلی + Delta, قرائت
گزارش‌شده)` ساخته می‌شود، پس یک کنتور ساعت‌شمار **تعویض‌شده** که عدد کمتری
  نشان می‌دهد، شمارنده را عقب نمی‌برد — از آن لحظه شمارنده فقط با Delta ها جلو
  می‌رود.
- **چرا:** تنها بدیل، پذیرفتن هر قرائت پایین‌تر است، که یعنی یک اشتباه تایپی در
  میدان می‌تواند سررسید یک سرویس را ماه‌ها به عقب بیندازد. یک‌طرفه بودن، خطای
  محافظه‌کارانه‌تری است.
- **ریسک:** پس از تعویض کنتور، برنامه‌های کارکردمحور آن دستگاه تا زمانی که
  دوباره Anchor نشوند، نسبت به عدد روی دستگاه جلوترند.
- **رفع:** مسیر پشتیبانی‌شده وجود دارد و مستند است —
  `PATCH /v1/maintenance-schedules/{id}` با `lastServicedHourMeter`. تاریخچه
  کارکرد بازنویسی نمی‌شود، چون مالکش `fleet-service` است.
- **اولویت:** پایین
- **ثبت‌شده:** 2026-08-28

## ۲۳٫۶ ثبت بدهی معماری

بدهی جدید در همین فایل، در همین قالب، با شناسه ثبت می‌شود:

```markdown
### D-0XX · <عنوان>

- **چه چیزی:** ساده‌سازی یا میان‌بر
- **چرا:** فشار زمانی / وابستگی خارجی / اطلاعات ناکافی

- **رفع:** اقدام مشخص
- **اولویت:** بالا | متوسط | پایین
- **ثبت‌شده:** YYYY-MM-DD
```

**قاعده.** بدهی ثبت‌نشده، بدهی فراموش‌شده است. اگر میان‌بری زدید، همان لحظه ثبتش کنید.

**بازبینی روز ۲۱.** روز ۲۱ به ممیزی کامل این فهرست اختصاص دارد: هر مورد یا رفع می‌شود،
یا با دلیل به Backlog تیم انسانی منتقل می‌شود. هیچ موردی بی‌تصمیم نمی‌ماند.
