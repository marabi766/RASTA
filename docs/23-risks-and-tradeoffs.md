# ۲۳ — Risks & Trade-offs

> هر تصمیم معماری هزینه دارد. این سند هزینه‌ها را **صریح** ثبت می‌کند.
> تصمیمی که «هیچ عیبی ندارد»، احتمالاً به‌درستی بررسی نشده است.

قالب هر مورد: **Risk · Benefit · Cost · Alternative · Mitigation**

---

## ۲۳٫۱ معاوضه‌های معماری

### T-01 · Microservices در مقیاسی که Monolith کافی بود

| بُعد            | شرح                                                                                                                                                                     |
| --------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Risk**        | ۱۷ سرویس برای بار فاز ۱ (۳۲۸ سازمان، ده‌ها تراکنش در روز) بیش از حد است. پیچیدگی عملیاتی، تأخیر شبکه، دشواری اشکال‌زدایی توزیع‌شده.                                     |
| **Benefit**     | مرز داده‌ای واقعی از روز اول؛ گذار به مقیاس ملی یک تصمیم استقرار است، نه بازنویسی؛ تیم‌های مستقل.                                                                       |
| **Cost**        | زمان توسعه بیشتر، زیرساخت سنگین‌تر، منحنی یادگیری بالاتر برای تیم انسانی.                                                                                               |
| **Alternative** | Modular Monolith با تقسیم بعدی.                                                                                                                                         |
| **چرا رد شد**   | مرز داده‌ای در Monolith عملاً هرگز رعایت نمی‌شود. یک `JOIN` بی‌ضرر امروز، یک وابستگی غیرقابل جدا کردن فرداست. هزینه اصلاح بعدی از هزینه اولیه بیشتر است.                |
| **Mitigation**  | `docker compose up` کل Stack را محلی بالا می‌آورد · Trace انتها به انتها · قواعد ESLint مرزها را تحمیل می‌کنند · تجمیع آگاهانه سه سرویس برای پرهیز از Over-Engineering. |

### T-02 · Kafka برای حجمی که یک صف ساده کافی بود

| بُعد            | شرح                                                                                                                                                     |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Risk**        | Kafka برای هزاران رویداد در روز، سنگین است. یک جزء زیرساختی بیشتر برای نگهداری.                                                                         |
| **Benefit**     | ترتیب تضمین‌شده به‌ازای Aggregate · بازپخش تاریخی برای ساخت Read Model جدید · Log حسابرسی‌پذیر · مسیر مقیاس ملی.                                        |
| **Cost**        | حافظه و پیچیدگی عملیاتی؛ نیاز به دانش Kafka در تیم.                                                                                                     |
| **Alternative** | RabbitMQ، NATS، یا صف مبتنی بر PostgreSQL.                                                                                                              |
| **چرا رد شد**   | هیچ‌کدام **بازپخش تاریخی** نمی‌دهند. وقتی `analytics-service` اضافه شود، باید بتواند از Offset صفر همه تاریخ را بخواند. با صف معمولی، آن داده رفته است. |
| **Mitigation**  | KRaft (بدون ZooKeeper) · تک‌گره در dev · Kafka UI برای مشاهده · Outbox تضمین می‌کند افت Kafka رویداد را نمی‌خورد.                                       |

### T-03 · Temporal به‌عنوان وابستگی سنگین

| بُعد            | شرح                                                                                                                                                    |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **Risk**        | Temporal یک سیستم توزیع‌شده کامل با پایگاه داده خودش است. اگر تیم انسانی با آن آشنا نباشد، نگهداری‌اش دشوار می‌شود.                                    |
| **Benefit**     | Timer ماندگار برای مهلت مناقصه (هفته‌ها) · تاریخچه کامل اجرا · Retry و جبران داخلی · Determinism.                                                      |
| **Cost**        | یک پایگاه داده و یک Cluster بیشتر؛ منحنی یادگیری؛ محدودیت Determinism در کد Workflow.                                                                  |
| **Alternative** | Cron + جدول وضعیت · BPMN Engine · صف تأخیردار.                                                                                                         |
| **چرا رد شد**   | با Cron، اگر سرویس در میانه مهلت مناقصه Restart شود، مهلت از دست می‌رود. برای فرآیندی با اثر حقوقی، این غیرقابل قبول است.                              |
| **Mitigation**  | State Machineها **صریح و جدا از Temporal** تعریف شده‌اند — اگر Temporal حذف شود، منطق دامنه سالم می‌ماند · Temporal UI برای مشاهده · مستندسازی الگوها. |

### T-04 · Kong/APISIX کنار گذاشته شد

| بُعد            | شرح                                                                                                                                   |
| --------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| **Risk**        | Gateway اختصاصی یعنی بازنویسی چیزهایی که Kong آماده دارد (Rate Limit، Auth Plugin، پایش).                                             |
| **Benefit**     | حل `activeOrganizationId` از عضویت‌های کاربر — منطق دامنه‌ای که در Plugin جای درستی ندارد؛ همان زبان و همان تست‌ها.                   |
| **Cost**        | نگهداری کد بیشتر؛ باید Rate Limit و Circuit Breaker را خودمان درست پیاده کنیم.                                                        |
| **Alternative** | Kong یا APISIX با Plugin سفارشی.                                                                                                      |
| **Mitigation**  | **در Production یک Edge Gateway (Kong/APISIX) برای TLS، WAF و Rate Limit سراسری جلوی این می‌نشیند** — دو نقش مکمل، نه رقیب. → ADR-009 |

### T-05 · Prisma به‌ازای هر سرویس

| بُعد            | شرح                                                                                                                    |
| --------------- | ---------------------------------------------------------------------------------------------------------------------- |
| **Risk**        | Prisma برای Query پیچیده (پنجره‌ای، بازگشتی، PostGIS پیشرفته) محدود است.                                               |
| **Benefit**     | Migration اعلانی · Type-Safety کامل · Schema جدا به‌ازای هر سرویس (تحمیل مالکیت داده).                                 |

### T-06 · کهنگی نقش در توکن: تنزل و ابطال تا ۹۰۵ ثانیه دیر اثر می‌کنند

| بُعد            | شرح                                                                                                                                                                                                                                                                                                                                                                                                            |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **Risk**        | با `ADR-060` نقش‌ها در توکن به ازای سازمان حمل می‌شوند. مدیری که تنزل یافته یا عضویتش باطل شده، تا انقضای Access Token فعلی‌اش — حداکثر **۹۰۰ ثانیه** عمر توکن در Realm + **۵ ثانیه** تحمل ساعت — همچنان با نقش قبلی عمل می‌کند.                                                                                                                                                                               |
| **Benefit**     | هر سرویس JWT را با JWKS **محلی** تأیید می‌کند و در هر درخواست به هیچ سرویس دیگری وابسته نیست. `identity-service` Single Point of Failure کل پلتفرم نمی‌شود.                                                                                                                                                                                                                                                    |
| **Cost**        | یک پنجرهٔ ۱۵ دقیقه‌ای که در آن تصمیم «این شخص دیگر مدیر نیست» اجرا نشده است.                                                                                                                                                                                                                                                                                                                                   |
| **Alternative** | جست‌وجوی نقش در هر درخواست از `identity-service` (با یا بی Cache).                                                                                                                                                                                                                                                                                                                                             |
| **چرا رد شد**   | هر درخواستِ هر سرویس را به دسترس‌بودن یک سرویس گره می‌زند؛ و Cacheی که برای جبرانش گذاشته شود، کهنگی را برمی‌گرداند — این بار بی‌کرانِ مستند (`ADR-060` § Alternatives الف).                                                                                                                                                                                                                                   |
| **Mitigation**  | کران **صریح** است و در `ADR-060` § ۷ نوشته شده. کار بعدی ثبت‌شده: **فهرست ابطال در Gateway** که `ROLE_REVOKED` و `MEMBERSHIP_REVOKED` را مصرف و جفت (کاربر، سازمان) را تا انقضای توکن‌های قدیمی رد می‌کند (`planning/backlog.json`، `EXT-005`) — پنجره را برای جهت خطرناک به تأخیر Kafka کاهش می‌دهد. کوتاه‌کردن عمر توکن به ۳۰۰ ثانیه تصمیم جدا و بعدی است. **برای MVP پذیرفته شد** (مدیر پروژه، 2026-09-24). |

## ۲۳٫۵-الف بدهی ثبت‌شده

### D-013 · `ledger_entry` پارتیشن‌بندی نشده

- **چه چیزی:** `docs/05` § ۵٫۴ جدول را با `PARTITION BY RANGE (posted_at)` و
  § ۵٫۶ با بازه ماهانه تعریف کرده. امروز یک جدول ساده است.
- **چرا:** یک جدول پارتیشن‌بندی‌شده بدون پارتیشنِ ماهِ جاری، `INSERT` را رد
  می‌کند — یعنی حالت شکستش «نیمه‌شب اول ماه، نوشتن مالی متوقف می‌شود» است.
  جلوگیری از آن یک ساز‌و‌کار خودکار ساخت پارتیشن می‌خواهد (`pg_partman` یا یک
  Job) که این پلتفرم ندارد. تحلیل کامل در **ADR-030**.
- **ریسک:** پایین امروز (حجم صفر). با رشد، Query تاریخی از Partition Pruning
  بهره نمی‌برد و حذف داده کهنه `DELETE` است نه `DROP PARTITION`.
- **رفع:** شرط فعال‌سازی **عددی** است، نه یادداشت: وقتی
  `rasta_economic_ledger_entries_total` از یک میلیون در ماه بگذرد — ده برابر
  زودتر از آستانه استخراج در `docs/04` § ۴٫۱. مسیر اجرا در ADR-030.
- **اولویت:** پایین (تا رسیدن به آستانه)
- **ثبت‌شده:** 2026-08-29

### D-014 · تسویه بدون Temporal

- **چه چیزی:** `docs/08` § ۸٫۶ و `docs/10` § ۱۰٫۱۰ تسویه را یک Workflow در
  Temporal تعریف کرده‌اند. پیاده‌سازی یک تراکنش ACID با ماشین حالت صریح است.

- **چه چیزی:** `ProxyService` در `api-gateway` روی **هر** درخواست

  عوض کند — اول `@Public()` را چک کند، فقط اگر `bearer` هم نبود و Public
  نبود سراغ توکن داخلی برود.

- **ثبت‌شده:** 2026-08-27

#### رفع — 2026-08-27

- **وضعیت پیشین:** `POST /v1/registration-requests` از راه Gateway

    و سخت‌گیرانه‌ترین قرائت.

### D-032 · فرمان سفارش، وجود سفارش را به سازمان بیگانه لو می‌داد — ✅ **بسته شد (2026-09-24)**

- **چه چیزی:** `GET /v1/orders/:id` به سازمانی که طرف سفارش نیست `404` می‌داد، ولی **هر
  فرمان** روی همان سفارش (`confirm`، `fulfill`، `confirm-receipt`، `disputes`، `cancel`،
  `reviews`) `403` می‌داد. `transition()` پس از `lockOrder` — که عمداً بی‌Tenant است تا
  فروشنده به ردیف خریدار برسد — مستقیم به `assertSupplier`/`assertBuyer` می‌رفت و بررسی
  دیده‌شدنی را که `get()` انجام می‌دهد جا می‌انداخت. پس هر شناسهٔ سفارش را می‌شد با یک فرمان
  آزمود: `403` یعنی وجود دارد، `404` یعنی نه — و پیام خطا («فقط سازمان فروشنده…») هم می‌گفت
  سفارش طرف فروشنده دارد.
- **چرا:** قاعده در Controller و `access.ts` نوشته شده بود — «سازمانی که طرف سفارش نیست
  ۴۰۴ می‌گیرد، چون ردکردن با نام، وجود سفارش را تأیید می‌کند» — ولی فقط در مسیر خواندن اعمال
  شده بود. یک آزمون یکپارچگی موجود **نامش «۴۰۴» بود و `403` را تأیید می‌کرد**؛ نام و
  ادعا از هم جدا شده بودند و کسی ندید.
- **ریسک:** شناسه‌ها ULID‌اند و حدس‌زدنی نیستند، پس شدت از نشت‌های `identity` کمتر است؛
  ولی شناسهٔ سفارشی که به هر راهی به دست آمده باشد، قابل تأیید بود.
- **رفع:** `assertOrderVisible` پیش از بررسی طرف، در `transition()` و در `submitReview`.
  طرف دیگر سفارش همچنان `403` می‌گیرد — او سفارش را می‌بیند و `404` به او دروغ است. دو
  آزمون موجود با رفتار تازه همسو شدند و دلیلشان در خودشان نوشته شد. دو مسیر دیگر
  `lockOrder` (`recordReminder`، `systemTransition`) درون‌فرایندی Saga‌اند و فراخواننده‌ای
  برای بررسی ندارند.
- **اولویت:** متوسط
- **ثبت‌شده:** 2026-09-24

### D-033 · انتقال دارایی می‌تواند از رویداد مصرف‌نشدهٔ تخصیص یا تعمیر جلو بزند — **رفع شد (ADR-062)، با پنجرهٔ باقی‌ماندهٔ کراندار**

> **به‌روزرسانی 2026-09-27 — شاخهٔ `fix/asset-transfer-clearance`، [ADR-062](adr/ADR-062-asset-transfer-clearance.md).**
>
> - **رفع‌شده:** asset-service پیش از ثبت انتقال، از fleet-service و maintenance-service با Endpoint داخلی احرازشده
>   (`POST /v1/internal/assets/{id}/transfer-clearance`، فقط توکن `SERVICE` asset-service با مستأجر امضاشده؛ الگوی
>   ADR-061 § ۴) می‌پرسد که تخصیص فعال، درخواست یا دستور تعمیر باز دارند یا نه. پاسخ از **پایگاه دادهٔ مالک کار** است، پس
>   کاری که رویدادش هنوز مصرف نشده و گزارش خرابی‌ای که هرگز وضعیت دارایی را تغییر نداده هم شمرده می‌شود. «باز» یا «پاسخی
>   نیامد» (Timeout، ۵xx، ۴۰۳، بدنهٔ بدشکل، ۴۰۴ سطح مسیر) انتقال را رد می‌کند — شکست بسته.
> - **پنجرهٔ میان پرسش و Commit بسته است:** مالکی که کار بازی نیابد، در همان تراکنش و زیر همان قفل که مسیرهای شروع کار
>   می‌گیرند، یک حصار با انقضا (`asset_transfer_fence`، پیش‌فرض ۶۰۰ ثانیه) می‌گذارد؛ تخصیص و درخواست تعمیر تازه زیر حصار رد
>   می‌شوند. انتقال فقط اگر پیش از نیمهٔ عمر حصار (با ساعت یکنوای asset-service، از پیش از پرسش) به پایان تراکنش برسد ثبت
>   می‌شود. Consumer `ASSET_TRANSFERRED` در هر مالک حصار را برمی‌دارد؛ انتقالِ ثبت‌نشده آن را آزاد می‌کند.
> - **سناریوی دور ۲ Codex بسته است:** تعمیری که `MAINTENANCE_STARTED`ش هنوز مصرف نشده، در maintenance شمرده می‌شود و
>   انتقال رد می‌شود.
> - **بدون پنجرهٔ زمانی (بازبینی دور ۱ PR #127):** حصار منقضی دیگر با گذشت زمان برداشته نمی‌شود. آغاز کار یا پرسش تازه‌ای
>   که حصار منقضی بیابد، از asset-service (`GET /v1/internal/assets/{id}/transfers/{fenceId}`، فقط fleet و maintenance،
>   مستأجر امضاشده) می‌پرسد آن انتقال ثبت شده یا نه: ثبت‌شده ← رد با `ASSET_OWNER_CHANGED`؛ ثبت‌نشده ← حصار زیر قفل
>   برداشته می‌شود؛ بی‌پاسخ ← رد، قابل تکرار. پاسخ‌دهنده پیش از خواندن رکورد، ردیف دارایی را قفل می‌کند، پس Commitِ در
>   جریان را منتظر می‌ماند. ارجاع و شروع تعمیر هم زیر قفل هر دارایی با بازخوانی درخواست؛ آزادسازی به همهٔ مالکان و زیر
>   قفل انحصاری؛ خطای پس از مرز Commit حصار را نگه می‌دارد؛ `ASSET_TRANSFERRED` بدشکل به DLQ می‌رود.
> - **باقی‌مانده:** کار بازی که پیش از این رفع مانده، تأیید هزینهٔ کاری که پیش از انتقال `COMPLETED` شده (Q-74 بند ۲)، و
>   فرایند مالکی که پیش از Middleware خودش بیش از یک ساعت منجمد بماند — حصاری بی‌انتقال که بسته شکست می‌خورد (ADR-062 § ۲).
>   هر دو دیدنی‌اند (`rasta_maintenance_transfer_open_work_total`). هزینهٔ دسترس‌پذیری: آغاز کار روی دارایی‌ای که حصار
>   منقضیِ حل‌نشده دارد به asset-service وابسته است.
> - **تصمیم کسب‌وکاری:** سرنوشت کار باز مالک قبلی [Q-74](24-open-questions.md) است؛ پاسخ موقت: تا کار باز هست، انتقال
>   رد می‌شود.
> - **هزینه:** انتقال به دسترس‌بودن fleet و maintenance وابسته است (`rasta_asset_transfer_clearance_total{outcome="unavailable"}`).
>
> متن زیر وضعیت پیش از این رفع است و برای سابقه دست‌نخورده مانده.

- **چه چیزی:** asset-service انتقال دارایی `ASSIGNED` یا `IN_MAINTENANCE` را رد می‌کند، ولی این وضعیت را از رویدادهای
  fleet و maintenance می‌سازد. تخصیص یا تعمیری که پیش از مصرف `ASSET_ASSIGNED` یا `MAINTENANCE_STARTED` شروع شده، جلوی
  انتقال را نمی‌گیرد. آن رویداد که بعد از انتقال برسد، در مستأجر مالک قبلی دارایی را نمی‌یابد و `SKIPPED` می‌شود:
  ورودی پرونده و تغییر وضعیتش اعمال نمی‌شوند (بازبینی PR #108، یافتهٔ ۱).
- **چرا:** رفع کامل یک Workflow میان‌سرویسی است: رزرو انتقال، یا گرفتن تأیید احرازشدهٔ «تخصیص یا تعمیر باز نیست» از
  fleet و maintenance پیش از ثبت مالکیت، یا پروتکل نسخهٔ مالکیت برای رویدادهای کهنه. هر سه طراحی است، نه رفع یک خط.
- **ریسک:** دارایی نزد مالک جدید است، در حالی که fleet یا maintenance هنوز کار باز مالک قبلی را دارند؛ و پرونده آن
  رویداد را ندارد.
- **کاهش امروز:** سمت تخصیص بسته است: fleet با `ASSET_TRANSFERRED` هر تخصیص فعال را پایان می‌دهد و `ASSIGNMENT_ENDED` را
  زیر مستأجر نگه‌دارنده منتشر می‌کند (PR #112). رویدادی که به این دلیل کنار گذاشته شود دیگر بی‌صدا نیست: هشدار در Log و
  `rasta_asset_timeline_events_skipped_total{reason="owner_changed"}`. سمت تعمیر هنوز باز است.
- **سناریوی بازبینی دور ۲ (Codex):** maintenance برای مستأجر A `MAINTENANCE_STARTED` را Commit می‌کند. پیش از آنکه
  asset-service آن را مصرف کند، A دارایی را که هنوز `ACTIVE` است به B منتقل می‌کند. maintenance بعداً `ASSET_TRANSFERRED`
  را مصرف می‌کند و فقط `asset_ref` خودش را جابه‌جا می‌کند؛ تعمیر باز زیر A می‌ماند. asset-service رویداد کهنه را که
  می‌رسد در A نمی‌یابد، `owner_changed` را ثبت و Ack می‌کند. نتیجه: B مالک است و می‌تواند دارایی را دوباره راه‌اندازی کند
  در حالی که A هنوز تعمیر باز دارد، و پرونده نه خط تعمیر را دارد نه `IN_MAINTENANCE` را. ثبت در Log و متریک این ناوردا را
  حفظ نمی‌کند؛ فقط آن را دیدنی می‌کند.
- **دامنه:** این نقص **پیش از PR #108 وجود داشت** و آن PR آن را پدید نیاورده است. رفعش طراحی میان‌سرویسی لازم دارد، پس
  در PR #108 به‌عنوان ریسک شناخته‌شده می‌ماند (تصمیم مدیر پروژه، 2026-09-25).
- **رفع:** **کار بعدی پس از ادغام PR #108** (تصمیم مدیر پروژه). جهت محتمل: asset-service پیش از ثبت انتقال، از fleet و
  maintenance از راه Endpointهای داخلیِ منبع (ADR-061 § ۴) می‌پرسد که تخصیص یا تعمیر باز ندارند، و بدون پاسخ احرازشده
  انتقال نمی‌کند. با یک ADR.
- **اولویت:** بالا
- **ثبت‌شده:** 2026-09-25 · **به‌روز:** 2026-09-27 (ADR-062، شاخهٔ `fix/asset-transfer-clearance`)

### D-035 · پرداخت Capture‌شده‌ای که نه اعتبار گرفت نه بازپرداخت شد، آشتی‌دهندهٔ خودکار ندارد

- **چه چیزی:** اگر Provider پول را Capture کند، اعتبار کیف پول (مثلاً به‌دلیل سقف موجودی) رد شود و بازپرداخت
  Provider هم شکست بخورد، Intent با `failure_reason = CAPTURED_NOT_CREDITED` در `AUTHORIZED` می‌ماند (بازبینی دور ۲
  PR #121، یافتهٔ ۲).
- **کاهش امروز (PR #121):** این وضعیت در همان تراکنشِ ثبت علامت با `PAYMENT_CAPTURE_UNRECONCILED` در Outbox اعلام
  می‌شود، با Log سطح Error و متریک `outcome="CAPTURED_NOT_CREDITED"`. تلاش دوباره با همان Idempotency-Key همان Intent
  را از سر می‌گیرد و اگر کیف پول جا داشته باشد اعتبار را ثبت می‌کند، بی‌آنکه دوباره از Provider بخواهد. خطای مبهم
  Commit دیگر بازپرداخت نمی‌شود: Intent دوباره خوانده می‌شود و فقط وقتی جبران می‌شود که ثابت شود چیزی Commit نشده
  (یافتهٔ ۱). از دور ۳ بازبینی، این بازخوانی در تراکنشی تازه و پشت قفل ردیف Intent انجام می‌شود، پس تا Commit در
  جریان روشن نشود تصمیمی گرفته نمی‌شود؛ و از سرگیری فقط وقتی پذیرفته است که Hash درخواست ذخیره‌شده روی Intent (کیف
  پول، مبلغ، ارز، Instrument) با درخواست تازه یکی باشد.
- **آنچه نمانده:** آشتی‌دهندهٔ پایدار که با `provider.getStatus()` وضعیت واقعی را بپرسد و بازپرداخت را تا موفقیت تکرار
  کند (ماشین حالت `REFUND_PENDING`). تا آن زمان، Intent که هیچ تلاش دوباره‌ای به آن نرسد، کار یک انسان است.
- **کاهش بیشتر (ADR-064، گام B0 — شاخهٔ `fix/economic-refund-safety`، #143):** دو مسیری که پول را هم به پرداخت‌کننده
  برمی‌گرداند و هم در کیف پول نگه می‌داشت بسته شد. (R2) بازپرداخت اپراتور سه گام است: زیر قفل ردیف Intent و سپس کیف پول
  مبلغ از مسیر Hold موجود (ADR-034) **Hold** و Intent با `REFUND_REQUESTED` علامت‌گذاری می‌شود؛ Provider بیرون از تراکنش
  پرسیده می‌شود؛ و در تراکنش سوم Hold برگردانده و Top-up معکوس می‌شود (یا در صورت رد Provider فقط Hold برمی‌گردد). خرجِ
  هم‌زمان روی Hold شکست می‌خورد، نه معکوس‌کردن. فراخوانی بی‌پاسخ Provider علامت `REFUND_UNKNOWN` می‌گیرد و شکست ثبت
  معکوس‌کردن `REFUNDED_NOT_REVERSED`، هر دو با `PAYMENT_REFUND_UNRECONCILED` در همان تراکنش و با Hold باقی؛ بازپرداخت دوم
  روی `REFUND_REQUESTED` یا `REFUND_UNKNOWN` رد می‌شود و روی `REFUNDED_NOT_REVERSED` فقط معکوس‌کردن را بی Provider تکرار
  می‌کند. اگر Provider رد کند و برگرداندن Hold شکست بخورد، علامت `REFUND_DECLINED_RELEASE_PENDING` با همان رویداد ثبت
  می‌شود و تلاش دوباره فقط Hold را برمی‌گرداند، بی Provider. تلاش دوبارهٔ Top-up روی هر یک از این چهار علامت «ناتمام» پاسخ
  می‌گیرد، نه `CAPTURED`؛ بازپخش HTTP همان کلید اما پاسخ تاریخی `CAPTURED` را برمی‌گرداند و وضعیت امروز را
  `GET /v1/payment-intents/{id}` می‌گوید (docs/06 § ۶٫۸). (U6) بازپرداختی که **بی‌پاسخ**

### D-037 · Projector کیکلوک ایمیل، نام و هر صفت غیرپلتفرمی را «بخوان-بنویس» می‌کند — ایمیل شناسهٔ ورود است

- **چه چیزی:** `KeycloakAdminClient.replacePlatformAttributes` (ADR-060 § ۵) کاربر را می‌خواند و سپس می‌نویسد. تا
  #129 **کل** نمایش کاربر را پس می‌نوشت، پس هر تغییر هم‌زمان میان خواندن و نوشتن برگردانده می‌شد: `UPDATE_PASSWORD`ی
  که تازه پاک شده بود برمی‌گشت (ناپایداری E2E ‏`03-keycloak-projection`) و — **اثر امنیتی** — حسابی که مدیر همان لحظه
  **غیرفعال** کرده بود دوباره **فعال** می‌شد. #129 بدنه را فهرست‌مجاز کرد (`email`، `firstName`، `lastName`،
  `attributes`)؛ `requiredActions`، `enabled` و `emailVerified` دیگر فرستاده نمی‌شوند و آن دو اثر بسته شد.
- **آنچه هنوز کهنه نوشته می‌شود:** مقدار خوانده‌شدهٔ لحظه‌ای پیش از **`email`، `firstName`، `lastName` و هر صفت
  غیرپلتفرمی** که `GET` برگرداند — همه در همان `PUT`. هر تغییر هم‌زمان هر کدام از این‌ها در پنجرهٔ میان `GET` و `PUT`
  برگردانده می‌شود.
- **اهمیت واقعی:**
  - **ایمیل شناسهٔ ورود و بازیابی گذرواژه است** (`loginWithEmailAllowed: true` در Realm)، نه دادهٔ نمایشی. تغییر
    ایمیلی که Projection برگرداند، **شناسهٔ ورود** را برمی‌گرداند؛ و چون `email` و `emailVerified` با هم نوشته
    نمی‌شوند (دومی دیگر فرستاده نمی‌شود)، نتیجه می‌تواند **نشانی قدیمی با وضعیت «تأییدنشده»** باشد. آزمون زندهٔ
    «D-037: a concurrent EMAIL change is reverted» دقیقاً همین را روی Keycloak 26.0 سنجاق می‌کند.
  - **هر صفت کاربر-ویرایش‌پذیری که بعداً به User Profile افزوده شود** همین‌طور در معرض است: Projector هر صفت
    غیرپلتفرمی خوانده‌شده را پس می‌نویسد.
  - امروز Realm جز چهار صفت پلتفرم و سه فیلد نمایه صفت اعلام‌شده‌ای ندارد و `unmanagedAttributePolicy` خاموش است.
- **رفتار سنجیدهٔ Keycloak 26.0.8** (2026-09-27؛ ADR-060 § ۵): `PUT /users/{id}` نه ETag دارد نه `If-Match` را
  می‌پذیرد، و Endpoint سطح صفت ندارد — پس به‌روزرسانی شرطی ممکن نیست (آزمون زندهٔ «no conditional update» در CI این را
  سنجاق می‌کند). `PUT`ی با `attributes` هر صفت غایب — **از جمله `email`، `firstName` و `lastName`** — را پاک می‌کند؛ پس
  این‌ها باید فرستاده شوند و از خواندنِ لحظه‌ای پیش می‌آیند.
- **سنجیده نشده:** رفتار صفات **Federated** (LDAP/User Federation)، **فقط-خواندنی** (`permissions.edit` بی `admin`) و
  **پنهان** در این مسیر — Realm امروز هیچ‌کدام را ندارد و آزمونی برایشان نیست. پیش از افزودن هر کدام، این مسیر دوباره
  سنجیده شود.
- **گزینه‌ها — تصمیم مالک، نه مهندسی** (مدیر پروژه به مالک ارجاع می‌دهد):
  1. **نمایه مال `identity-service`:** این سه از ردیف `user` نوشته شوند — بی `GET`، بی مسابقه — و ویرایش آن‌ها در Keycloak
     (Account Console و Console مدیر) بسته شود؛ تغییر نام/ایمیل فقط از API پلتفرم.
  2. **تغییر ایمیل فقط از مسیر تأییدشده:** ایمیل فقط با یک Required Action تأیید ایمیل در Keycloak عوض شود و ویرایش
     مستقیم آن بسته شود (در Keycloak 26 قابلیت `update-email` پیش‌نمایش است و در این Realm روشن نیست — سنجیده نشده)؛
     پنجره برای نام باقی می‌ماند.
  3. **Claimها از صفات کاربر بیرون بروند:** عضویت و نقش در جای دیگری جز نمایش کاربر نگه داشته شوند (مثلاً Mapper ای
     که از منبعی جدا می‌خواند)، تا Projector اصلاً کاربر را ننویسد — بازنگری ADR-060 § ۵.
- **پیگیری:** `KeycloakAdminClient.setEnabled` یک `PUT {enabled}` جزئی است که با رفتار بالا امن است، اما هیچ فراخواننده‌ای
  ندارد — بی‌تغییر ماند (تصمیم مدیر پروژه)؛ حذف یا به‌کارگیری‌اش کار جداگانه است.
- **اولویت:** متوسط — ایمیل شناسهٔ ورود است؛ پنجره میلی‌ثانیه‌ای است اما وجود دارد
- **ثبت‌شده:** 2026-09-27 (#129) · **به‌روز:** 2026-09-28 (بازبینی دور ۱ روی #129، یافتهٔ ۲)

### D-040 · پیام DLQ کلید پیام Kafka را نگه نمی‌دارد

- **چه چیزی:** `EventConsumer.deadLetter()` (`packages/nest-common/src/consumer/event-consumer.ts`) پیام DLQ را **بی‌کلید**
  می‌نویسد؛ کلید پیام اصلی — کلید پارتیشن ناشر، که ترتیب هر Aggregate را نگه می‌دارد (ADR-036، ADR-051) — دور ریخته می‌شود.
  بدنه، Headerهای پلتفرم و `x-dlq-original-topic/partition/offset` نگه داشته می‌شوند (#135).
- **چرا مانده:** پیش از #135 بود و در بازبینی آن دیده شد؛ هنوز هیچ ابزار بازپخشی نیست که آن کلید را بخواهد (ADR-051 § R6)،
  و #135 فقط سند است برای این بند (تصمیم مدیر پروژه، 2026-09-28).
- **ریسک:** ابزار بازپخش آینده کلید را همیشه از بدنه بازسازی نمی‌تواند: پیش‌فرض کلید `aggregateId` است، اما ناشرانی که
  `partitionKey` صریح می‌دهند (asset، construction، document، economic ledger، fleet، identity، maintenance، marketplace،
  notification) آن را فقط در `streamKey` بدنه — وقتی Sequence دارد — یا ردیف Outbox خود نگه می‌دارند. پیام بازپخش‌شده با
  کلید نادرست در پارتیشن دیگری می‌نشیند و ترتیبش نسبت به همان Aggregate از دست می‌رود.
- **رفع:** `deadLetter()` کلید پیام اصلی (`message.key`) را بر پیام DLQ بگذارد — کنار Headerهای موجود — و آزمون آن را سنجاق
  کند؛ پیش از ساخت ابزار بازپخش یا همراه آن.
- **اولویت:** متوسط
- **وضعیت:** رفع‌شده (2026-09-29، `fix/event-consumer-retry-and-dlq-key`): `deadLetter()` کلید اصلی را نگه می‌دارد (بی‌کلید
  اگر اصلی بی‌کلید بود) و آزمون واحد و یکپارچهٔ `audit-service` آن را سنجاق می‌کنند. رکوردهای DLQ پیش از این تغییر بی‌کلیدند.
- **ثبت‌شده:** 2026-09-28 (#135)

### D-041 · هر `ORGANIZATION_MOVED` برای همهٔ سیاست‌های اتحادیه‌ایِ فعال و منتظر تصویب، در همهٔ مستأجرها، کار در صف می‌گذارد

- **چه چیزی:** `PolicySuspensionService.enqueueMove` (Q-83) برای هر رویداد جابه‌جایی، برای همهٔ سیاست‌های `ACTIVE` و
  `PENDING_PLATFORM_APPROVAL` نوشتهٔ `UNION_ADMIN` برای سازمانی جز خودِ اتحادیه، یک ردیف در `policy_reconciliation_task`
  می‌گذارد (به زیردرخت جابه‌جاشده محدود نمی‌شود). **Handler کافکا فقط همین درج پایگاه‌داده را می‌کند و هیچ تماس شبکه‌ای
  ندارد.** `PolicyReconciliationSweeper` دسته‌های محدودی از کارهای سررسیده را برمی‌دارد، از `organization-service` می‌پرسد
  (به‌نام اتحادیهٔ نویسنده) و همان انتقال شرطی `ACTIVE|PENDING → SUSPENDED` + رویداد Outbox را در یک تراکنش، همراه با `DONE`
  شدن کار، انجام می‌دهد.
- **چرا:** `construction-service` درخت را ندارد و محتوای رویداد (مسیر پیشین و پسین) را عمداً باور نمی‌کند — رویداد فقط محرک
  است، درستیِ «زیر اتحادیه بودن» را فقط `organization-service` می‌گوید (تحویل کهنه، تکراری یا از `.retry` را بی‌خطر
  می‌کند). محدودسازی به زیردرخت یعنی باور به `previousPath`/`newPath`.
- **ریسک و کران:** هزینهٔ هر رویداد با شمار سیاست‌های اتحادیه‌ای (نه اندازهٔ زیردرخت) بالا می‌رود، ولی دیگر روی مسیر Kafka
  نیست: درج یک‌باره در پایگاه‌داده، و رویدادِ جعلی فقط صف را پر می‌کند، نه اثری می‌گذارد. کران کار جاروکننده = **اندازهٔ دسته**
  (`CONSTRUCTION_RECONCILE_BATCH_SIZE`، پیش‌فرض ۲۰) × **مهلت هر تماس** (`CONSTRUCTION_ORGANIZATION_REQUEST_TIMEOUT_MS`)
  در هر دور (`CONSTRUCTION_RECONCILE_INTERVAL_MS`، پیش‌فرض ۵ ثانیه)؛ اجارهٔ کار (`_LEASE_SECONDS`) باید از این بیشتر باشد.
  چندین نمونه با `FOR UPDATE SKIP LOCKED` + اجاره + نشانهٔ حصار بی‌خطر همکاری می‌کنند. **هیچ سیاستی برای کمبود وقت جا
  نمی‌ماند:** کار تا پاسخ گرفتن در صف می‌ماند؛ شکستِ `organization-service` فقط `attempts` را بالا می‌برد و
  `next_attempt_at` را با عقب‌نشینی نمایی (`_BACKOFF_SECONDS` تا `_BACKOFF_MAX_SECONDS`) جلو می‌برد، بی‌آنکه سیاست دست بخورد.
  یک کارِ در هم‌ریخته دستهٔ دیگر را نمی‌ایستاند. تکرار/`.retry` همان رویداد یا جابه‌جایی دوم تا وقتی کار باز است در همان کار
  ادغام می‌شود (یک کار باز به‌ازای هر سیاست) — ولی ادغام بازبینی لازم را گم نمی‌کند: ادغام `generation` کار را بالا می‌برد و
  آن را سررسیده می‌کند (اجارهٔ زنده دزدیده نمی‌شود)؛ جاروکنندهٔ دارندهٔ کار فقط اگر نسل هنگام برداشتن هنوز همان باشد پاسخِ
  «داخل» را `DONE` می‌کند، وگرنه اجاره را رها می‌کند و دور بعد دوباره می‌پرسد. حصار اثر را هم نگه می‌دارد: تراکنش تعلیق
  **پیش از هر خواندن یا نوشتن** ردیف کار را قفل و اجارهٔ خود را وارسی می‌کند؛ کارگری که اجاره‌اش پرید و دوباره برداشته شد
  بی‌تغییر و بی‌رویداد برمی‌گردد. دفاع در عمق: باز شدن دور روی سیاستِ جامانده آن را **معلق** هم می‌کند (رویداد
  `ROUND_OPENING_RECHECK`)، نه فقط رد.
- **پایش و هشدار:** گیج‌های `rasta_construction_policy_reconciliation_backlog` (کارهای باز) و
  `rasta_construction_policy_reconciliation_oldest_due_age_seconds` (مدت انتظار قدیمی‌ترین کار سررسیده)، شمارندهٔ
  `rasta_construction_policy_reconciliation_total{result}` و یک خط ثبت ساخت‌یافته در هر دور با اندازهٔ صف و سنِ قدیمی‌ترین.
  **هشدار پیشنهادی** (قاعدهٔ Prometheus را PM/Ops ثبت کند): `oldest_due_age_seconds > 900` به مدت ۱۵ دقیقه ← `organization-service`
  ناپاسخگوست یا جاروکننده نمی‌چرخد؛ در این حالت سیاست‌های جامانده تا رفع فقط در باز شدن دور رد می‌شوند. کارِ `retried` با
  `last_error_code` در ردیف قابل بازرسی است.
- **پیگیری سکو (خارج از این تغییر):** `EventConsumer` به Handler نشست ۶۰ ثانیه‌ای Kafka را با Heartbeat زنده نگه نمی‌دارد (نه
  در `main`، نه در #145) و تا ۳ تلاش پیاپی برای هر تحویل دارد؛ امروز فقط چون Handler ساخت‌وساز سریع و بی‌شبکه است اهمیت
  ندارد. هر Consumer آینده که کار کند یا شبکه‌ای دارد باید صف بسازد یا سکو Heartbeat بدهد.
- **رفع (وقتی لازم شد):** کاهش شمار کارها و پرسش‌ها: یا یک نقطهٔ پایانی دسته‌ای در `organization-service` («کدام‌یک از این
  جفت‌ها هنوز زیر هم‌اند؟») یا محدودسازی نامزدها به زیردرخت با پرسشِ «شناسه‌های زیر این سازمان» از خودِ `organization-service`
  (نه از بدنهٔ رویداد).

### D-042 · نگه‌داشتن ردیف‌های بعدیِ یک کلید پس از شکست ردیف قبلی در همان دسته، به ADR-051 B4 موکول شده است

- **چه چیزی:** `fix/outbox-relay-stream-order` ترتیب انتشار ردیف‌های **هر جریان درون یک دستهٔ Claim‌شده** را بر
  `stream_seq` می‌گذارد (`orderForPublish` در `packages/nest-common/src/outbox`؛ `created_at` زمان **شروع** تراکنش است، نه ترتیب
  Commit). آنچه انجام **نشد** («گام ۴»): اگر در مسیر انتشار تک‌ردیفی (`publishIndividually`) ردیف seq 3 شکست بخورد و به
  عقب‌نشینی برود، ردیف seq 4 از همان دسته همچنان منتشر و تأیید می‌شود.
- **چرا:** هیچ مصرف‌کننده‌ای هنوز `streamSeq` را اجرا نمی‌کند (`EventConsumer` آن را نمی‌خواند؛ `audit-service` فقط ذخیره
  می‌کند)، و این شکاف تنها بخشی از مسئلهٔ بزرگ‌تر است: ردیفی که Lease زندهٔ Relay دیگر یا عقب‌نشینی دارد و ردیف بعدی‌اش را
  Relay دیگر منتشر می‌کند، با نگه‌داشتنِ درون‌دسته‌ای حل نمی‌شود. راه‌حل درست، Claim با مسدودسازی سرصف است (`is_stream_head`،

- **ریسک:** تا B4 (و B5 پیش از آن)، ردیف بعدی یک کلید می‌تواند پیش از ردیف قبلی‌اش به Kafka برسد، در همان دسته پس از شکست،
