# ADR-004: PostgreSQL + PostGIS + Prisma

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-26

## Context

نیازهای داده‌ای پلتفرم سه ویژگی دارند:

1. **دفتر کل مالی** نیازمند تراکنش ACID واقعی، قفل ردیف و امکان تحمیل تغییرناپذیری در سطح
   پایگاه داده است.
2. **داده جغرافیایی** برای موقعیت سازمان، دارایی، محدوده پروژه و انبار لازم است — «کدام
   ماشین‌آلات نزدیک این پروژه آزادند؟» یک پرسش واقعی محصول است.
3. **سلسله‌مراتب سازمانی** باید با یک Query پیمایش شود، نه با Recursive CTE در هر داشبورد.

## Decision

**PostgreSQL 16 + PostGIS 3.4** به‌عنوان پایگاه داده همه سرویس‌ها، با **Prisma 6** به‌عنوان
لایه دسترسی، و **یک Schema Prisma مستقل به‌ازای هر سرویس**.

افزونه‌ها بر حسب نیاز: `postgis`, `pg_trgm`, `ltree`, `pgcrypto`.

## Alternatives Considered

| گزینه | مزیت | عیب | چرا رد شد |
| --- | --- | --- | --- |
| MongoDB برای بعضی سرویس‌ها | Schema انعطاف‌پذیر | تراکنش چندسندی ضعیف؛ GIS محدودتر | یکپارچگی مالی و یکنواختی عملیاتی مهم‌تر است |
| MySQL | رایج، سبک | بدون PostGIS بومی؛ ضعف در نوع‌های پیشرفته | GIS یک نیاز واقعی محصول است |
| TypeORM | انعطاف بالاتر در Query | Migration کمتر قابل اتکا؛ Type-Safety ضعیف‌تر | Migration اعلانی Prisma برای ۱۶ سرویس ارزشمندتر است |
| SQL خام با Kysely | کنترل کامل | Migration دستی؛ سرعت توسعه کمتر | برای ۱۶ سرویس در ۳۰ روز مناسب نیست |
| یک Schema Prisma مشترک | نگهداری ساده‌تر | **همان Shared Database با ظاهر دیگر** | نقض ADR-005 |

## Consequences

**مثبت**

- تراکنش ACID برای دفتر کل؛ Trigger برای تحمیل تغییرناپذیری
- PostGIS در همان موتور — بدون سیستم جداگانه GIS
- `ltree` برای سلسله‌مراتب سازمانی با Index
- Type-Safety کامل از Schema تا کد
- Migration اعلانی، قابل بازبینی و قابل بازگشت

**منفی**

- Prisma برای Query پیچیده (پنجره‌ای، بازگشتی، PostGIS پیشرفته) محدود است و نیاز به Query خام دارد
- مرحله `prisma generate` به Build اضافه می‌شود
- ۱۶ Schema جدا یعنی تکرار مدل‌های مرجع — پذیرفته‌شده، به‌صورت Replica از رویداد
- PostgreSQL تک‌گره در MVP یک نقطه شکست است (ثبت‌شده در Risks S-01)

## Compliance

- هر `schema.prisma` فقط مدل‌های همان سرویس را دارد
- هر Query خام نیازمند بازبینی و استفاده از Template Tag پارامتری است
- تست یکپارچگی با Testcontainers روی PostgreSQL واقعی، نه Mock
- Trigger تغییرناپذیری دفتر کل با تست اثبات می‌شود
