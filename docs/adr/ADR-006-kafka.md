# ADR-006: Kafka به‌عنوان Event Backbone

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-26

## Context

سرویس‌ها باید بدون جفت‌شدگی زمانی با هم کار کنند. چهار نیاز مشخص وجود دارد:

1. **ترتیب به‌ازای Aggregate.** رویدادهای یک کیف پول (Hold، Release، Settle) نباید نامرتب
   پردازش شوند.
2. **بازپخش تاریخی.** وقتی `analytics-service` اضافه می‌شود، باید بتواند کل تاریخ را از
   ابتدا بخواند و Read Model بسازد.
3. **چند مصرف‌کننده مستقل.** یک رویداد سفارش را `economic`، `audit`، `analytics`،
   `notification` و `supplier` هر کدام مستقل مصرف می‌کنند.
4. **حسابرسی‌پذیری.** جریان مالی باید Log تغییرناپذیر و قابل استناد داشته باشد.

## Decision

**Apache Kafka 3.9 در حالت KRaft** به‌عنوان تنها Event Backbone پلتفرم.

- یک Topic به‌ازای هر دامنه: `rasta.<domain>.v1` — به‌علاوه `.retry` و `.dlq`
- کلید پارتیشن همیشه `aggregateId`
- `auto.create.topics.enable=false`
- `unclean.leader.election.enable=false`
- انتشار همیشه از راه Transactional Outbox (ADR-021)

## Alternatives Considered

| گزینه                  | مزیت                     | عیب                                            | چرا رد شد                                   |
| ---------------------- | ------------------------ | ---------------------------------------------- | ------------------------------------------- |
| RabbitMQ               | سبک‌تر، مدل مسیریابی غنی | بدون بازپخش تاریخی؛ پیام پس از مصرف می‌رود     | ساخت Read Model جدید از تاریخ ناممکن می‌شود |
| NATS JetStream         | بسیار سبک، سریع          | اکوسیستم کوچک‌تر؛ تضمین‌های ماندگاری کمتر بالغ | برای جریان مالی، بلوغ اهمیت دارد            |
| صف مبتنی بر PostgreSQL | بدون زیرساخت اضافه       | مقیاس محدود؛ بدون بازپخش کارآمد                | مسیر مقیاس ملی را می‌بندد                   |
| Redis Streams          | ساده، موجود در Stack     | ماندگاری ضعیف‌تر؛ حافظه‌محور                   | داده مالی نباید در حافظه زندگی کند          |

## Consequences

**مثبت**

- ترتیب تضمین‌شده به‌ازای Aggregate
- بازپخش کامل برای ساخت Read Model یا بازیابی
- Consumer Groupهای مستقل بدون تداخل
- مسیر روشن مقیاس با افزودن پارتیشن

**منفی**

- **برای حجم فاز اول بیش از حد است** — ثبت‌شده در Risks T-02
- یک جزء زیرساختی سنگین برای نگهداری
- نیاز به دانش Kafka در تیم انسانی
- تنظیم اشتباه (مثلاً `unclean.leader.election`) می‌تواند رویداد را از بین ببرد

**خنثی**

- KRaft وابستگی به ZooKeeper را حذف کرده و عملیات را ساده‌تر کرده است

## Compliance

- ساخت Topicها فقط از `create-topics.sh`؛ ساخت خودکار غیرفعال است
- هر رویداد پیش از انتشار و پس از دریافت با Zod اعتبارسنجی می‌شود
- متریک `kafka_consumer_lag` و `rasta_dlq_messages_total` پایش می‌شوند
- هر پیام DLQ هشدار تولید می‌کند
- در Production: SASL/SCRAM + TLS + ACL به‌ازای سرویس (Risks S-04)
