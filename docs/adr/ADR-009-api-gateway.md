# ADR-009: API Gateway اختصاصی NestJS به‌جای Kong/APISIX

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-26
- **نوع:** انحراف آگاهانه از Stack پیشنهادی اولیه

## Context

Stack پیشنهادی اولیه Kong یا Apache APISIX را برای API Gateway تعیین کرده بود.
هنگام طراحی مشخص شد Gateway رستا باید کاری انجام دهد که یک Gateway عمومی برای آن ساخته
نشده است:

**حل `activeOrganizationId`.** یک کاربر می‌تواند در چند سازمان عضویت داشته باشد. Gateway
باید Header `X-Organization-Id` را در برابر عضویت‌های واقعی کاربر اعتبارسنجی کند، سازمان
فعال را تعیین کند، و Scope مستأجر را **پیش از مسیریابی** اعمال کند.

این یک تصمیم **دامنه‌ای** است، نه یک تصمیم زیرساختی. پیاده‌سازی آن در Plugin Lua یا Go
یعنی بردن منطق دامنه به لایه‌ای که تست، اشکال‌زدایی و نگهداری‌اش برای تیم دشوار است.

## Decision

**API Gateway اختصاصی با NestJS** که مسئول موارد زیر است:

اعتبارسنجی JWT با JWKS · **حل و اعتبارسنجی مستأجر** · RBAC سطح مسیر · Rate Limit ·
CORS · Secure Headers · تولید و انتشار Correlation ID · Cache پاسخ Idempotency ·
Circuit Breaker · تجمیع OpenAPI · Log درخواست.

**مسیر Production:** یک **Edge Gateway** (Kong، APISIX یا Ingress با WAF) برای TLS
Termination، WAF و Rate Limit سراسری **جلوی** این Gateway می‌نشیند. دو نقش مکمل، نه رقیب.

## Alternatives Considered

| گزینه                         | مزیت                       | عیب                                           | چرا رد شد                             |
| ----------------------------- | -------------------------- | --------------------------------------------- | ------------------------------------- |
| Kong با Plugin سفارشی         | امکانات آماده، بلوغ بالا   | منطق دامنه در Plugin Lua؛ تست دشوار؛ زبان سوم | مرز میان دامنه و زیرساخت مخدوش می‌شود |
| APISIX با Plugin              | کارایی بالا، پیکربندی پویا | همان مشکل؛ اکوسیستم کوچک‌تر                   | همان                                  |
| بدون Gateway، هر سرویس مستقیم | ساده‌ترین                  | تکرار Auth، Rate Limit و CORS در ۱۶ سرویس     | نقض DRY در حساس‌ترین جای ممکن         |
| BFF به‌ازای هر Frontend       | بهینه‌سازی برای هر کلاینت  | دو لایه بیشتر برای نگهداری                    | در این مقیاس توجیه ندارد              |

## Consequences

**مثبت**

- منطق مستأجر در همان زبان، با همان ابزار تست بقیه سیستم
- یک نقطه برای Auth، Rate Limit، Correlation و Idempotency
- امکان استفاده مستقیم از `@rasta/contracts` برای اعتبارسنجی

**منفی**

- **باید Rate Limit، Circuit Breaker و Retry را خودمان درست پیاده کنیم** — Kong این‌ها را آماده دارد
- کد بیشتری برای نگهداری
- کارایی پایین‌تر از Gateway نوشته‌شده با Go یا C
- خطر تبدیل شدن به «Monolith پنهان» اگر منطق دامنه به آن اضافه شود

## Compliance

- **Gateway هیچ پایگاه داده‌ای ندارد** — فقط Cache در Redis
- **هیچ منطق کسب‌وکاری در Gateway** — بازبینی کد این را تضمین می‌کند
- Gateway هیچ داده دامنه‌ای را تبدیل نمی‌کند؛ فقط مسیریابی و اعتبارسنجی
- `X-Organization-Id` **همیشه** در برابر عضویت اعتبارسنجی می‌شود؛ نقض آن `TENANT_MISMATCH`
- تست: هر سرویس Downstream **مستقلاً** مجوزدهی می‌کند و به Gateway اعتماد نمی‌کند (Zero Trust)
