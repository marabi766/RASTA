# ADR-011: راهبرد Multi-Tenancy

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-26
- **اهمیت:** قاعده بنیادین امنیتی

## Context

پلتفرم از ۳۲۸ دهیاری شروع می‌شود و به شهرداری‌ها، سازمان‌های دولتی و مقیاس ملی می‌رسد.
هر سازمان یک مستأجر است. داده دارایی، مالی و قراردادی هر سازمان **نباید** برای سازمان
دیگر قابل مشاهده باشد.

سه مدل Multi-Tenancy وجود دارد: پایگاه داده به‌ازای مستأجر، Schema به‌ازای مستأجر،
و ستون تفکیک‌کننده (Shared Schema).

با ده‌ها هزار سازمان در افق ملی، دو مدل اول عملاً غیرقابل مدیریت‌اند.

## Decision

**مدل ستون تفکیک‌کننده (`organization_id`) با دفاع در عمق در شش لایه.**

| لایه          | مکانیزم                                                                            |
| ------------- | ---------------------------------------------------------------------------------- |
| API           | `org_id` از JWT؛ `X-Organization-Id` در برابر عضویت اعتبارسنجی می‌شود              |
| Application   | `AsyncLocalStorage` با `RequestContext` غیرقابل تغییر                              |
| Database      | هر جدول مستأجرمحور ستون `organization_id` دارد؛ Repository پایه آن را تزریق می‌کند |
| Authorization | بررسی سطح **Object**، نه فقط Endpoint                                              |
| Cache         | هر کلید Redis پیشوند `org:{id}:` دارد                                              |
| Events        | Envelope رویداد `tenantId` دارد؛ Consumer آن را اعمال می‌کند                       |

**قاعده پاسخ:** منبع متعلق به مستأجر دیگر → **`404 NOT_FOUND`**، نه `403`.

**MVP → PRODUCTION.** MVP: تضمین در لایه Application. Production: **PostgreSQL Row-Level
Security** به‌عنوان لایه دوم دفاعی.

## Alternatives Considered

| گزینه                      | مزیت             | عیب                                               | چرا رد شد                               |
| -------------------------- | ---------------- | ------------------------------------------------- | --------------------------------------- |
| پایگاه داده به‌ازای مستأجر | جداسازی حداکثری  | ده‌ها هزار پایگاه داده؛ Migration کابوس می‌شود    | در افق ملی غیرقابل مدیریت               |
| Schema به‌ازای مستأجر      | جداسازی خوب      | همان مشکل Migration؛ محدودیت تعداد Schema         | مقیاس‌ناپذیر                            |
| ستون تفکیک‌کننده بدون RLS  | ساده، مقیاس‌پذیر | یک Query فراموش‌شده = نشتی داده                   | پذیرفته شد **اما با دفاع در عمق**       |
| RLS از روز اول             | امن‌ترین         | با Prisma نیازمند مدیریت `SET LOCAL` در هر تراکنش | پیچیدگی MVP؛ ستون‌ها از امروز آماده‌اند |

## Consequences

**مثبت**

- مقیاس‌پذیر تا ده‌ها هزار سازمان
- Migration واحد برای همه مستأجرها
- Repository پایه، Scope را خودکار اعمال می‌کند

**منفی**

- **یک Query که Scope را فراموش کند، داده لو می‌دهد** — بزرگ‌ترین ریسک این مدل
- ستون `organization_id` روی همه جداول تکرار می‌شود (پذیرفته‌شده — ارزان‌تر از Join)
- تا افزودن RLS، تنها دفاع لایه Application است (Risks S-02، اولویت بالا)

**خنثی**

- هر Index مرکب باید با `organization_id` شروع شود

## Compliance

- **Repository پایه در `@rasta/nest-common` Scope را اجباری می‌کند** — دور زدنش نیازمند کد صریح است
- **تست Tenant Isolation به‌ازای هر سرویس اجباری است:** مستأجر A می‌سازد، مستأجر B تلاش
  می‌کند بخواند/تغییر دهد/حذف کند → باید `404` بگیرد
- شکست این تست **هرگز** به‌عنوان تست شکننده نادیده گرفته نمی‌شود — یک نشتی داده است
- تست قاعده‌محور در CI: هیچ کلید Cache بدون پیشوند مستأجر
- بازبینی کد: هر Query جدید بررسی می‌شود که Scope دارد
