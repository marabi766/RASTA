# ADR-017: OpenTelemetry + Prometheus + Grafana

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-26

## Context

در یک سیستم با ۱۷ سرویس، Event Bus و Workflow Engine، یک درخواست کاربر ممکن است از
پنج سرویس، سه رویداد Kafka و یک Workflow عبور کند. بدون ردیابی توزیع‌شده، تشخیص اینکه
«چرا سفارش من ثبت نشد» عملاً ناممکن است.

## Decision

**OpenTelemetry** به‌عنوان استاندارد واحد برای Log، Metric و Trace.
**Prometheus** برای ذخیره متریک، **Grafana** برای نمایش، **pino** برای Log ساخت‌یافته.

**پنج شناسه از نخستین لحظه در همه سرویس‌ها جریان دارند:**
`correlationId` · `traceId` · `tenantId` · `userId` · `serviceName`

انتشار: HTTP → Service → **Envelope رویداد Kafka** → Workflow → Log.

## Alternatives Considered

| گزینه                | مزیت                     | عیب                           | چرا رد شد                        |
| -------------------- | ------------------------ | ----------------------------- | -------------------------------- |
| Log ساده بدون Trace  | ساده‌ترین                | ردیابی میان‌سرویسی ناممکن     | در معماری توزیع‌شده غیرقابل قبول |
| Datadog یا New Relic | مدیریت‌شده، امکانات کامل | هزینه؛ داده به بیرون می‌رود   | ملاحظات میزبانی داده             |
| Jaeger مستقیم        | تمرکز بر Trace           | استاندارد اختصاصی؛ Metric جدا | OpenTelemetry بدون قفل‌شدگی است  |
| ELK Stack            | جست‌وجوی قوی Log         | سنگین؛ Metric و Trace جدا     | یک استاندارد برای هر سه بهتر است |

## Consequences

**مثبت**

- یک استاندارد برای هر سه ستون؛ بدون قفل‌شدگی به فروشنده
- یک `correlationId` کل مسیر را از مرورگر تا ورودی دفتر کل وصل می‌کند
- تعویض Backend مشاهده‌پذیری بدون تغییر کد ممکن است

**منفی**

- سربار Instrumentation در هر سرویس
- OTel Collector یک جزء بیشتر برای نگهداری
- نمونه‌برداری کامل در Production گران است — نیاز به راهبرد نمونه‌برداری

## Compliance

**نمونه‌برداری:** توسعه و Staging ۱۰۰٪. Production ۱۰٪ به‌علاوه **۱۰۰٪ خطاها و
۱۰۰٪ مسیرهای مالی** — نمونه‌برداری تصادفی روی مسیری که ممکن است موضوع حسابرسی شود، اشتباه است.

**Redaction اجباری در Log:** رمز، توکن، کلید، کد ملی، شماره تماس، محتوای پیشنهاد مناقصه
پیش از مهلت، و بدنه کامل درخواست حاوی داده شخصی — همه پیش از سریال‌سازی جایگزین می‌شوند.

**Cardinality:** متریک کسب‌وکاری هرگز برچسب `userId`، `orderId` یا `assetId` نمی‌گیرد.
تفکیک سازمانی فقط در `analytics-service` روی پایگاه داده انجام می‌شود.

**قاعده هشدار:** هر هشدار باید Runbook داشته باشد. هشدار بدون دستورالعمل پاسخ، نویز است.
