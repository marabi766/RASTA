# ADR-020: احراز هویت سرویس‌به‌سرویس و Zero Trust

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-26

## Context

در معماری Microservices، فرض رایج و خطرناک این است: «چون درخواست از شبکه داخلی آمده،
معتبر است». این فرض یعنی هر مهاجمی که به یک Pod دسترسی پیدا کند، می‌تواند به همه
سرویس‌ها — از جمله `economic-service` — درخواست بزند.

سیستمی که پول جابه‌جا می‌کند و پیشنهاد مناقصه نگه می‌دارد، نمی‌تواند این فرض را بپذیرد.

## Decision

**اصل Zero Trust: هیچ اعتماد ضمنی میان سرویس‌ها.**

هر سرویس، برای هر درخواست ورودی:

1. توکن داخلی را اعتبارسنجی می‌کند (امضا، انقضا، صادرکننده، سرویس مبدأ، سرویس مقصد)
2. `organizationId` را از Context استخراج می‌کند و **دوباره** بر آن Scope می‌گذارد
3. مجوزدهی سطح Object را **مستقل از Gateway** بررسی می‌کند

**MVP:** JWT کوتاه‌عمر (۵ دقیقه) امضاشده با کلید مشترک، حاوی `iss`، `sub` (سرویس مبدأ)،
`aud` (سرویس مقصد) و `exp`.

**Production:** **mTLS** با گواهی کوتاه‌عمر به‌ازای هر Workload (SPIFFE/SPIRE یا Service Mesh).

## Alternatives Considered

| گزینه | مزیت | عیب | چرا رد شد |
| --- | --- | --- | --- |
| اعتماد به شبکه داخلی | ساده‌ترین | یک Pod آلوده = دسترسی کامل | غیرقابل قبول برای سیستم مالی |
| API Key ثابت به‌ازای سرویس | ساده | کلید ثابت نشت می‌کند و چرخش سخت است | ریسک بلندمدت |
| انتشار توکن کاربر به Downstream | ساده، Context حفظ می‌شود | سرویس Downstream می‌تواند از هویت کاربر سوءاستفاده کند | نقض حداقل دسترسی |
| mTLS از روز اول | امن‌ترین | نیازمند PKI و مدیریت چرخه گواهی | پیچیدگی MVP؛ به Production موکول شد |
| Service Mesh (Istio) | mTLS خودکار | سربار عملیاتی بالا در MVP | برای Production ارزیابی می‌شود |

## Consequences

**مثبت**

- یک Pod آلوده نمی‌تواند آزادانه به سرویس‌های دیگر درخواست بزند
- هر سرویس مستقلاً مجوزدهی می‌کند — Gateway نقطه شکست امنیتی واحد نیست
- مسیر روشن به mTLS بدون تغییر منطق دامنه

**منفی**

- **در MVP یک کلید مشترک وجود دارد** — نشت آن یعنی جعل هویت سرویس (Risks S-03، اولویت بالا)
- سربار اعتبارسنجی در هر فراخوانی داخلی
- بررسی دوباره مجوزدهی در هر سرویس، کد تکراری می‌سازد (در `@rasta/nest-common` مشترک شده)

## Compliance

- هیچ سرویس دامنه‌ای Ingress عمومی ندارد — **NetworkPolicy این را تحمیل می‌کند**
- `X-Organization-Id` **هرگز** بدون اعتبارسنجی پذیرفته نمی‌شود
- تست: فراخوانی سرویس داخلی بدون توکن معتبر → `401`
- تست: سرویس Downstream مستقلاً مجوزدهی می‌کند و به Gateway اعتماد نمی‌کند
- کلید داخلی از محیط تزریق می‌شود و قابل چرخش بدون تغییر کد است
- Kafka در Production با SASL/SCRAM + ACL — هر سرویس فقط روی Topicهای خودش می‌نویسد
