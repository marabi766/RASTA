# ADR-021: Transactional Outbox برای انتشار رویداد

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-26
- **اهمیت:** تضمین تحویل رویداد — بنیادی برای یکپارچگی مالی

## Context

الگوی ساده و رایج این است:

```typescript
await db.order.update({ status: 'COMPLETED' });
await kafka.produce('ORDER_COMPLETED', payload);   // ← نقطه شکست
```

این دو عمل **اتمیک نیستند**. یک Crash یا قطع شبکه میان آن‌ها دو حالت خراب می‌سازد:

- **رویداد گمشده:** سفارش تکمیل شد اما کارمزد هرگز محاسبه نشد
- **رویداد شبح:** رویداد منتشر شد اما تراکنش Rollback شد — کارمزد بدون سفارش

در پلتفرمی که پول جابه‌جا می‌کند، هیچ‌کدام قابل قبول نیست.

## Decision

**هیچ رویدادی مستقیماً از یک Service Method منتشر نمی‌شود.**

```
┌─ یک تراکنش پایگاه داده (اتمیک) ─────────┐
│  ۱. تغییر وضعیت Aggregate                │
│  ۲. INSERT INTO outbox_message           │
└──────────────────┬───────────────────────┘
                   │ COMMIT
                   ▼
      Outbox Relay (Poll هر ۵۰۰ms)
      SELECT ... FOR UPDATE SKIP LOCKED
                   ▼
              Kafka Topic
                   ▼
      UPDATE outbox_message SET published_at = now()
```

**تضمین: At-Least-Once** + **مصرف‌کننده Idempotent** با جدول `processed_event`.

## Alternatives Considered

| گزینه | مزیت | عیب | چرا رد شد |
| --- | --- | --- | --- |
| انتشار مستقیم | ساده‌ترین | رویداد گمشده یا شبح | غیرقابل قبول |
| Two-Phase Commit | اتمیک واقعی | Kafka از XA پشتیبانی نمی‌کند؛ کند و شکننده | عملاً ممکن نیست |
| Change Data Capture (Debezium) | بدون کد اضافه در سرویس | یک جزء سنگین دیگر؛ Payload از Schema داخلی می‌آید | Schema داخلی نباید قرارداد عمومی شود |
| Listen/Notify پایگاه داده | سبک | بدون ماندگاری؛ اگر Listener نباشد پیام می‌رود | تضمین تحویل ندارد |

## Consequences

**مثبت**

- **تغییر وضعیت و انتشار رویداد اتمیک‌اند** — هیچ رویدادی گم نمی‌شود، هیچ رویداد شبحی ساخته نمی‌شود
- **از دست رفتن Kafka باعث از دست رفتن رویداد نمی‌شود** — رویدادها در `outbox` می‌مانند و
  پس از بازیابی منتشر می‌شوند (این یک مزیت جانبی بسیار بزرگ است)
- Payload صریحاً ساخته می‌شود، نه از Schema داخلی مشتق

**منفی**

- **تأخیر انتشار** (تا ۵۰۰ میلی‌ثانیه) — برای این دامنه بی‌اهمیت است
- یک جدول و یک فرایند Relay به هر سرویس اضافه می‌شود
- **رویداد تکراری ممکن است** (اگر Crash بین Produce و به‌روزرسانی رخ دهد) → همه
  مصرف‌کننده‌ها **باید** Idempotent باشند
- جدول `outbox_message` نیازمند پاکسازی دوره‌ای است

**چرا At-Least-Once و نه Exactly-Once؟** تضمین Exactly-Once در سیستم توزیع‌شده گران و
شکننده است. At-Least-Once به‌علاوه Idempotency همان نتیجه را ارزان‌تر و قابل‌اعتمادتر می‌دهد.

## Compliance

- `@rasta/nest-common` یک `OutboxService` و `OutboxRelay` مشترک می‌دهد
- **بازبینی کد: هیچ فراخوانی مستقیم Producer در Service** — فقط از راه Outbox
- هر Consumer پیش از پردازش در `processed_event` درج می‌کند؛ نقض کلید یکتا = رد بی‌صدا
- درج `processed_event` و اثر کسب‌وکاری **در یک تراکنش**
- متریک `rasta_outbox_pending_age_seconds` بیش از ۶۰ ثانیه = هشدار
- **آزمایش آشوب اجباری (روز ۲۶):** قطع Kafka حین ثبت سفارش → اثبات اینکه رویداد گم نمی‌شود
