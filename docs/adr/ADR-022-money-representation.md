# ADR-022: نمایش پول با bigint و نرخ با Basis Point

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-26
- **اهمیت:** دقت مالی

## Context

`0.1 + 0.2 !== 0.3` در محاسبات اعشار شناور. در یک دفتر کل دوطرفه که **باید** به صفر
برسد، این خطا انباشته می‌شود و توازن را می‌شکند.

همچنین مبالغ ریالی بزرگ‌اند: یک قرارداد عمرانی می‌تواند از `Number.MAX_SAFE_INTEGER`
(حدود ۹×۱۰¹⁵) عبور کند و در JSON بی‌صدا خراب شود.

نرخ کارمزد نیز مسئله دارد: «۲٫۵٪» به‌صورت `0.025` در اعشار شناور دقیقاً ۲٫۵٪ نیست.

## Decision

| مورد                 | قاعده                                                       |
| -------------------- | ----------------------------------------------------------- |
| نمایش داخلی          | **`bigint` در واحد فرعی** (ریال)                            |
| ذخیره در پایگاه داده | `BIGINT`                                                    |
| انتقال در JSON       | **رشته** — `{"amountMinor": "10000000", "currency": "IRR"}` |
| ارز                  | همیشه صریح؛ بدون پیش‌فرض ضمنی                               |
| نرخ                  | **Basis Point صحیح** — ۲۵۰ یعنی ۲٫۵٪                        |
| گرد کردن             | **نیم به بالا** روی مقدار مطلق، با تابع مشترک               |

پیاده‌سازی مرجع: `packages/contracts/src/common/money.ts`

## Alternatives Considered

| گزینه                                      | مزیت                | عیب                                      | چرا رد شد                   |
| ------------------------------------------ | ------------------- | ---------------------------------------- | --------------------------- |
| `number` (اعشار شناور)                     | ساده‌ترین           | **خطای اعشار انباشته می‌شود**            | دفتر کل نامتوازن می‌شود     |
| `Decimal` کتابخانه‌ای                      | دقیق، API راحت      | کندتر؛ یک وابستگی بیشتر؛ سریال‌سازی مبهم | `bigint` بومی و سریع‌تر است |
| `NUMERIC` در پایگاه داده با `number` در کد | دقیق در پایگاه داده | خطا هنگام تبدیل به `number` وارد می‌شود  | مرز تبدیل، نقطه شکست است    |
| عدد در JSON به‌جای رشته                    | طبیعی‌تر            | **مبالغ بزرگ در JSON خراب می‌شوند**      | ریسک بی‌صدا و خطرناک        |
| درصد اعشاری برای نرخ                       | خوانا               | ۲٫۵٪ دقیقاً ۰٫۰۲۵ نیست                   | Basis Point صحیح دقیق است   |

## Consequences

**مثبت**

- **بدون خطای اعشار** — دفتر کل همیشه دقیقاً متوازن می‌شود
- مبالغ بزرگ در JSON سالم می‌مانند
- `bigint` بومی است — بدون وابستگی و سریع
- گرد کردن قطعی و یکسان در همه‌جا

**منفی**

- **`bigint` در `JSON.stringify` پشتیبانی نمی‌شود** → نیاز به تبدیل صریح در هر مرز
- کد کمی طولانی‌تر: `BigInt(x) + BigInt(y)` به‌جای `x + y`
- Frontend باید رشته را برای نمایش تجزیه کند
- Prisma برای `BIGINT` نوع `bigint` برمی‌گرداند که باید در DTO تبدیل شود

## Compliance

**قواعد اجباری:**

- **`float` یا `number` برای پول در هیچ‌جا** — قاعده Lint و بازبینی کد
- همه محاسبات مالی از توابع مشترک `@rasta/contracts` استفاده می‌کنند
- `applyBasisPoints` تنها راه محاسبه کارمزد است
- ورودی کاربر: رقم فارسی و عربی به لاتین نرمال می‌شود، جداکننده هزارگان حذف می‌شود،
  سپس به `bigint` تبدیل می‌شود — **هرگز `parseFloat`**

**تست‌های اجباری:**

- محاسبه کارمزد ۲٫۵٪ روی ۱۰٬۰۰۰٬۰۰۰ دقیقاً ۲۵۰٬۰۰۰ می‌دهد
- گرد کردن نیم به بالا قطعی است
- مبلغ بزرگ‌تر از `MAX_SAFE_INTEGER` در رفت و برگشت JSON سالم می‌ماند
- Basis Point منفی رد می‌شود
