# ADR-024: Abstraction پرداخت و Mock Provider

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-26
- **نوع:** CONSTRAINT مقرراتی — از سند محصول

## Context

سند محصول در سه جای مستقل تصریح می‌کند:

> «اجرای واقعی کیف پول، پرداخت الکترونیکی، نگهداری وجوه یا تسویه مالی، مشروط به بررسی و
> تأیید الزامات بانکی، پرداختی، مالیاتی و مقرراتی مربوط است. آنچه در این سند ارائه شده،
> معماری مفهومی پیشنهادی است، نه ادعای آمادگی اجرای قطعی.»

> «پیاده‌سازی واقعی هر یک از عناصر بالا، از جمله نگهداری وجوه در کیف پول، انتقال وجه میان
> کاربران و اتصال به درگاه‌های پرداخت بانکی، مشروط به بررسی و تأیید الزامات … است.»

این یعنی: **معماری باید ساخته شود، اما هیچ اتصال بانکی واقعی نباید ادعا شود.**

## Decision

**`PaymentProvider` یک Interface است. Core Platform هرگز به یک PSP یا بانک خاص وابسته
نمی‌شود.**

```typescript
interface PaymentProvider {
  readonly name: string;
  authorize(req: AuthorizeRequest): Promise<AuthorizeResult>;
  capture(req: CaptureRequest): Promise<CaptureResult>;
  refund(req: RefundRequest): Promise<RefundResult>;
  getStatus(providerRef: string): Promise<PaymentStatus>;
}
```

| پیاده‌سازی            | محیط              | رفتار                                                  |
| --------------------- | ----------------- | ------------------------------------------------------ |
| `MockPaymentProvider` | local، test، demo | موفقیت قطعی؛ شکست قابل تحریک برای تست؛ تأخیر شبیه‌سازی |
| Provider واقعی        | Production        | **ساخته نشده** — Open Question Q-01 و Q-14             |

`PaymentIntent` الگوی مرکزی است: هر پرداخت با `Idempotency-Key` چرخه
`CREATED → AUTHORIZED → CAPTURED | FAILED | REFUNDED` را طی می‌کند.

## Alternatives Considered

| گزینه                              | مزیت           | عیب                                             | چرا رد شد                       |
| ---------------------------------- | -------------- | ----------------------------------------------- | ------------------------------- |
| ادغام مستقیم با یک PSP             | واقعی‌تر       | **نقض CONSTRAINT مقرراتی؛ قفل‌شدگی به فروشنده** | مجوز قانونی وجود ندارد          |
| بدون لایه پرداخت در MVP            | ساده‌ترین      | جریان Demo ناقص می‌ماند                         | سناریوی روز ۱۰ باید کامل باشد   |
| فقط کیف پول داخلی بدون Abstraction | ساده           | افزودن PSP بعداً یعنی تغییر Domain Core         | معماری باید از امروز آماده باشد |
| ادعای «آماده اتصال بانکی»          | بازاریابی بهتر | **ادعای نادرست**                                | صداقت مهندسی                    |

## Consequences

**مثبت**

- جریان کامل Demo بدون هیچ اتصال واقعی قابل اجراست
- افزودن PSP واقعی = **یک کلاس جدید + یک رکورد پیکربندی** — بدون تغییر Domain Core
- تست شکست پرداخت ساده است (Mock قابل تحریک)
- هیچ ادعای نادرستی درباره قابلیت مالی سیستم نمی‌شود

**منفی**

- **Demo با پول واقعی کار نمی‌کند** — باید صریحاً به مخاطب گفته شود
- رفتارهای واقعی PSP (Timeout، تسویه تأخیری، اختلاف بانکی) در MVP آزموده نمی‌شوند
- برخی الزامات انطباق (PCI-DSS، گزارش مالیاتی) تا انتخاب PSP نامعلوم می‌مانند

## Compliance

**قواعد اجباری — بدون استثنا:**

```
🚫 هیچ ادعایی درباره اتصال بانکی واقعی — در کد، UI، مستند، Demo یا ارائه
🚫 هیچ منطق مالی وابسته به یک PSP خاص
🚫 هیچ عبارتی مانند «آماده اتصال به بانک» بدون قید صریح
✅ Domain Core فقط Interface را می‌شناسد
✅ UI صریحاً «حالت نمایشی پرداخت» را نشان می‌دهد وقتی Provider، Mock است
✅ README و مستندات این محدودیت را صریح بیان می‌کنند
```

**نکته مهم.** دفتر کل، کیف پول، کارمزد و پاداش **کاملاً و به‌درستی** پیاده شده‌اند و
تست‌های یکپارچگی مالی روی آن‌ها سبزند. آنچه شبیه‌سازی‌شده است، **فقط لایه ارتباط با
ارائه‌دهنده پرداخت بیرونی** است. این تمایز باید در هر ارائه‌ای روشن بیان شود.
