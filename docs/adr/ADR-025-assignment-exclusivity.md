# ADR-025: انحصار تخصیص و کنترل همروندی در fleet-service

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-27
- **اهمیت:** یکپارچگی داده عملیاتی، ایمنی
- **مرتبط:** ADR-005 (Database Ownership)، ADR-011 (Multi-Tenancy)، ADR-012 (Asset-Centric)، ADR-021 (Outbox)

## Context

`Assignment` رابطه زمان‌دار راننده ↔ دارایی است. دو پرسش باید پاسخ قطعی بگیرند:

**۱. آیا یک راننده می‌تواند هم‌زمان دو تخصیص فعال داشته باشد؟**

خیر — و این **مستند است، نه تصمیم ما**. دو سند مستقل آن را صریح گفته‌اند:

- `docs/03-domain-model.md` § ۳٫۳: «`Assignment` — یک راننده، حداکثر یک تخصیص
  فعال در هر لحظه — Unique Index جزئی»
- `docs/05-data-architecture.md` § ۵٫۵: `assignment` → `UNIQUE (driver_id) WHERE ended_at IS NULL`

**۲. آیا یک دارایی می‌تواند هم‌زمان به دو راننده تخصیص یابد؟**

**هیچ سندی این را نگفته.** این شکاف واقعی است و باید تصمیم گرفته شود، نه فرض.

دو شاهد در معماری موجود به سمت انحصار اشاره می‌کنند:

- `OperationalStatus` در `asset-service` **تک‌مقداری** است. رویداد `ASSET_ASSIGNED`
  دارایی را به `ASSIGNED` می‌برد (جدول `PROJECTIONS` در `TimelineConsumer`). اگر دو
  تخصیص هم‌زمان ممکن باشد، پایان یکی دارایی را به `ACTIVE` برمی‌گرداند در حالی که
  راننده دوم هنوز پشت فرمان است — وضعیت دارایی دروغ می‌گوید.
- سند محصول (§ ۲٫۴-ج): «پلتفرم نشان می‌دهد چه ماشین‌آلاتی آزادند، کدام در پروژه
  دیگری فعال‌اند». اگر «مشغول» تک‌مقداری نباشد، این پاسخ بی‌معنا می‌شود.

در برابر آن، یک واقعیت عملیاتی معقول وجود دارد که سند محصول **نگفته**: شیفت. یک
کامیون می‌تواند راننده روز و راننده شب داشته باشد.

**۳. مکانیزم اجرا چیست؟**

بررسی در لایه Application (`SELECT` سپس `INSERT`) این Invariant را **اجرا نمی‌کند**.
دو درخواست هم‌زمان هر دو «تخصیص فعالی نیست» می‌خوانند و هر دو درج می‌کنند. این دقیقاً
شکل شکستی است که در تولید دیده می‌شود و در تست ترتیبی هرگز دیده نمی‌شود.

## Decision

| مورد                         | تصمیم                                                                  |
| ---------------------------- | ---------------------------------------------------------------------- |
| یک تخصیص فعال به‌ازای راننده | **اجرا با Partial Unique Index** — `ux_assignment_active_driver`       |
| یک تخصیص فعال به‌ازای دارایی | **اجرا با Partial Unique Index** — `ux_assignment_active_asset`        |
| منبع حقیقت «فعال بودن»       | فقط ستون `ended_at IS NULL`. **هیچ ستون `status` موازی وجود ندارد.**   |
| ایجاد تخصیص                  | خوش‌بینانه: درج، و ترجمه نقض Constraint به خطای کسب‌وکاری              |
| پایان تخصیص                  | `UPDATE ... WHERE id = ? AND ended_at IS NULL` + بررسی تعداد سطر متأثر |
| تغییر وضعیت راننده           | Optimistic Locking با ستون `version`                                   |
| ثبت کارکرد تکراری            | Unique Index روی `(organization_id, client_reference)`                 |
| قفل (Pessimistic / Redis)    | **استفاده نمی‌شود**                                                    |

### چرا Partial Index و نه ستون `status`

یک ستون `status` در کنار `ended_at` دو نمایش از یک واقعیت است و سرانجام با هم مخالف
می‌شوند. Index جزئی مستقیماً روی `ended_at` نوشته می‌شود، پس ستون و Invariant
نمی‌توانند واگرا شوند. `active` در پاسخ API **محاسبه** می‌شود، نه ذخیره.

### چرا بدون قفل

هر سه مسیر نوشتن با یک Constraint یا یک `WHERE` مشروط ایمن می‌شوند. قفل بدبینانه
هزینه Deadlock و یک وابستگی جدید (Redis) می‌آورد بی‌آنکه تضمین بیشتری بدهد. قفل
توزیع‌شده در `inventory-service` (رزرو موجودی) لازم است چون آنجا Invariant یک
**مجموع** است، نه یک یکتایی — و مجموع را نمی‌توان با Unique Index بیان کرد.

### نقش بررسی پیش‌پرواز

`AssignmentService` پیش از درج بررسی می‌کند که تخصیص فعالی نباشد. این بررسی
**اجرا نیست، پیام است**: حالت عادی خطای خوانا می‌گیرد به‌جای نقض Constraint خام. در
مسابقه واقعی هر دو درخواست از این بررسی عبور می‌کنند و Index تصمیم می‌گیرد؛ بازنده
از راه `translateExclusivityViolation` **همان** خطایی را می‌گیرد که یک میلی‌ثانیه
زودتر می‌گرفت. یعنی مسابقه از تعارض عادی قابل تشخیص نیست — که هدف است.

## Alternatives Considered

| گزینه                                         | مزیت                      | عیب                                                                  | چرا رد شد                             |
| --------------------------------------------- | ------------------------- | -------------------------------------------------------------------- | ------------------------------------- |
| فقط بررسی در Application                      | ساده، بدون SQL دستی       | **هیچ Invariant ای اجرا نمی‌شود**؛ دو درخواست هم‌زمان هر دو موفق‌اند | دقیقاً همان باگی که باید جلویش گرفت   |
| ستون `status` + Unique روی `(driver, status)` | Prisma می‌تواند بیانش کند | دو منبع حقیقت؛ `status` و `ended_at` واگرا می‌شوند                   | نمایش دوگانه یک واقعیت                |
| `SELECT ... FOR UPDATE` روی راننده            | آشنا                      | Deadlock میان دو درخواست با ترتیب معکوس راننده/دارایی؛ کندتر         | Index همان کار را بدون قفل می‌کند     |
| قفل توزیع‌شده Redis                           | فرا-پایگاه‌داده           | وابستگی جدید؛ افت Redis = توقف تخصیص؛ Split-brain ممکن               | Invariant یک یکتایی است، نه یک مجموع  |
| **آزاد گذاشتن انحصار دارایی**                 | شیفت را پشتیبانی می‌کند   | `OperationalStatus` تک‌مقداری دروغ می‌گوید؛ «آزاد/مشغول» بی‌معنا     | تا وقتی مدل شیفت وجود ندارد، ناسازگار |

## Consequences

**مثبت:**

- Invariant در پایگاه داده است، پس یک اسکریپت اصلاحی، یک مسیر کد آینده یا یک عامل
  توسعه عجول نمی‌تواند دورش بزند.
- تست همروندی واقعی ممکن شد: دو `service.create()` هم‌زمان، دقیقاً یکی موفق
  (`test/assignment-concurrency.int-spec.ts`).
- تراکنش مشترک با Outbox یعنی تخصیص رد‌شده **رویداد جا نمی‌گذارد** — هیچ
  `ASSET_ASSIGNED` شبحی دارایی را در پرونده‌اش به `ASSIGNED` نمی‌برد.

**منفی — صادقانه:**

- **Prisma نمی‌تواند Partial Index را بیان کند.** هر دو Index در SQL دست‌نویس انتهای
  Migration زندگی می‌کنند. `prisma migrate dev` بعدی ممکن است پیشنهاد `DROP` بدهد؛
  آن Hunk باید رد شود. هشدار بلند در همان فایل و در `schema.prisma` ثبت شده، اما این
  یک تله واقعی برای مهندس بعدی است.
- **Prisma نام Index را گزارش نمی‌کند.** این ADR ابتدا فرض کرده بود که ترجمه خطا
  می‌تواند روی نام Index تطبیق دهد. **غلط بود:** Prisma در `P2002` نام **ستون**
  را در `meta.target` می‌گذارد (`driver_id`)، نه نام Index. پس هر مسابقه واقعی
  به مسیر عمومی `ALREADY_EXISTS` می‌افتاد و وعده «مسابقه از تعارض عادی قابل
  تشخیص نیست» **در عمل برقرار نبود**. تست Integration این را در نخستین اجرای
  واقعی گرفت؛ `identifyExclusivityConstraint` اکنون هر دو شکل را می‌پذیرد.
  Invariant هیچ‌وقت نشکست — فقط پیام خطا بد بود.
- **نام Constraint هنوز در دو جا تکرار شده** — Migration و
  `src/fleet/constraints.ts`. تغییر نام در یکی بدون دیگری بی‌صدا کیفیت پیام را
  کم می‌کند. تست Integration این را می‌گیرد، تست واحد نه.
- **ستون `started_at` نباید Default پایگاه داده داشته باشد.** `ended_at` همیشه
  از برنامه می‌آید و `ck_assignment_period` آن دو را مقایسه می‌کند؛ یک
  `now()` یعنی دو ساعت روی یک ردیف. روی WSL2، PostgreSQL ۱۴–۵۶ میلی‌ثانیه
  جلوتر از میزبان اندازه‌گیری شد. Default حذف شد.
- **انحصار دارایی، شیفت را ممنوع می‌کند.** اگر کارفرما بگوید یک کامیون راننده روز و
  شب دارد، این Index باید حذف شود — و حذفش نیازمند پاسخ به «وضعیت دارایی وقتی دو
  راننده دارد چیست؟» است. ثبت‌شده به‌عنوان **Q-23**.
- بازنده مسابقه یک Round-Trip پایگاه داده هدر می‌دهد. در این نرخ نوشتن بی‌اهمیت است.

**خنثی:**

- `endedAt` می‌تواند برابر `startedAt` باشد (تخصیص صفر-مدت). عمداً مجاز است:
  `ck_assignment_period` فقط `>=` را الزام می‌کند، چون ثبت اشتباه و لغو فوری یک
  رخداد واقعی است.

## Compliance

| چطور تأیید می‌شود                             | کجا                                                                                    |
| --------------------------------------------- | -------------------------------------------------------------------------------------- |
| Index ها واقعاً در پایگاه داده وجود دارند     | `test/assignment-concurrency.int-spec.ts` — درج مستقیم با Prisma، دور زدن لایه Service |
| دو درخواست هم‌زمان → دقیقاً یکی موفق          | همان فایل، `Promise.allSettled`                                                        |
| تخصیص رد‌شده رویداد جا نمی‌گذارد              | همان فایل، شمارش `outbox_message`                                                      |
| Index جزئی است (تاریخچه مانع آینده نیست)      | همان فایل، «permits a new assignment once ended»                                       |
| نام Constraint با کد هم‌راستاست               | `src/fleet/constraints.ts` + assertion روی `violatedConstraint`                        |
| ترجمه خطا مسابقه را از تعارض عادی جدا نمی‌کند | `src/fleet/constraints.spec.ts` (هر دو شکل) + تست همزمانی زنده                         |
| هیچ ساعت دومی وارد ردیف نمی‌شود               | `started_at` بدون Default؛ Migration `20260828051500_assignment_started_at_no_default` |
