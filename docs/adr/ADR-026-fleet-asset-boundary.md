# ADR-026: مرز fleet ↔ asset — مسیرهای REST و مالکیت «در دسترس بودن»

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-27
- **اهمیت:** مرز سرویس، صحت معماری
- **مرتبط:** ADR-005 (Database Ownership)، ADR-009 (API Gateway)، ADR-012 (Asset-Centric)

## Context

`fleet-service` نخستین سرویسی است که به‌شدت به `Asset` ارجاع می‌دهد بی‌آنکه مالکش
باشد. دو مسئله مشخص از این وضعیت بیرون آمد.

### مسئله ۱ — مسیر REST

`docs/04-service-decomposition.md` § ۴٫۶ برای fleet این مسیرها را نوشته بود:

```
POST /assets/{assetId}/assignments
POST /assets/{assetId}/usage
```

اما `api-gateway` پیاده‌شده، مسیر را از **نخستین قطعه مسیر** حل می‌کند
(`resolveRoute` در `services/api-gateway/src/config/routes.ts`) و `assets` به
`asset-service` می‌رود. این یک تناقض واقعی میان سند و کد پیاده‌شده است، نه یک ابهام.

طبق ترتیب مرجع (§ ۳ دستور کار): **معماری پیاده‌شده بر سند مقدم است** مگر آنکه آشکارا
منسوخ باشد. مسیریابی تک‌قطعه‌ای منسوخ نیست — ADR-009 صریحاً Gateway را «بدون دانش
دامنه» می‌خواهد.

### مسئله ۲ — «آیا این دستگاه امروز می‌تواند برود؟»

پاسخ به این پرسش از واقعیت‌هایی ساخته می‌شود که **چهار سرویس** مالکشان‌اند:

| واقعیت                    | مالک                  |
| ------------------------- | --------------------- |
| وضعیت چرخه عمر دارایی     | `asset-service`       |
| بیمه منقضی / معاینه مردود | `asset-service`       |
| دستگاه در تعمیرگاه        | `maintenance-service` |
| تخصیص فعال                | `fleet-service`       |
| اعلام دستی عدم دسترسی     | `fleet-service`       |

اگر fleet این‌ها را «مالکیت» کند، دو منبع حقیقت می‌سازیم. اگر برای هر ردیف یک
فراخوانی REST بزند، افت `asset-service` داشبورد ناوگان را می‌خواباند — دقیقاً
جفت‌شدگی زمانی‌ای که `docs/03` § ۳٫۶ رد کرده.

## Decision

### مسیرها

منابع fleet زیر Prefix های خودِ fleet می‌آیند؛ `assetId` یک **فیلد** است، نه یک قطعه مسیر:

```
POST   /v1/assignments              { driverId, assetId, ... }
GET    /v1/assignments?assetId=&driverId=&active=
POST   /v1/assignments/{id}/end
DELETE /v1/assignments/{id}          ← مترادف، چون docs/04 صریحاً DELETE گفته بود
POST   /v1/usage-records            { assetId, ... }
GET    /v1/usage-records?assetId=
GET    /v1/fleet/availability
GET    /v1/fleet/utilization
```

یک ردیف به جدول مسیریابی Gateway افزوده شد: `{ prefix: 'usage-records', service: 'fleet' }`.
این تنها تغییر در `api-gateway` است — داده، نه منطق.

این علاوه بر رفع مشکل مسیریابی، **صادقانه‌تر** هم هست: یک تخصیص به ناوگان تعلق دارد،
نه به دارایی. مسیر تودرتو نشان می‌داد دارایی مالک آن است، که نقض ADR-012 بود.

### مالکیت «در دسترس بودن»

`fleet-service` این وضعیت را **ترکیب می‌کند، نه مالکیت**:

- واقعیت‌های سرویس‌های دیگر از راه **رویداد** به جدول `asset_ref` تکرار می‌شوند
  (الگوی Replica محلی، `docs/03` § ۳٫۶) — نه REST همزمان، نه Join.
- `GET /v1/fleet/availability` برای هر مانع، **مالکش را نام می‌برد**:

```jsonc
{
  "assetId": "AST_...",
  "available": false,
  "blockers": [
    { "code": "DISPATCH_BLOCKED", "owner": "asset-service", "detail": "..." },
    { "code": "ACTIVE_ASSIGNMENT", "owner": "fleet-service", "detail": "..." },
  ],
}
```

**CONSTRAINT.** یک اعلام دستی `available: true` **نمی‌تواند** موانع دیگر را لغو کند.
اعلام کردن یک دستگاه به‌عنوان آزاد، بیمه‌اش را تمدید نمی‌کند.

**CONSTRAINT.** `asset_ref` هرگز مبنای تصمیم **مجوزدهی** نیست. مجوزدهی از توکن
تأییدشده و از `organizationId` روی ردیف‌های خود fleet می‌آید. `asset_ref` عمداً در
`TENANT_SCOPED_MODELS` نیست و هر دسترسی به آن از `runUnscoped` با دلیل نوشته‌شده
می‌گذرد.

### مرز داده

`fleet-service` هرگز: پایگاه داده `asset-service` را نمی‌خواند · مدل Prisma آن را
Import نمی‌کند · داده اصلی دارایی را تکرار نمی‌کند (فقط آنچه برای پاسخ «آزاد است؟»
لازم است) · منطق چرخه عمر دارایی را کپی نمی‌کند.

## Alternatives Considered

| گزینه                                     | مزیت                   | عیب                                                                  | چرا رد شد                      |
| ----------------------------------------- | ---------------------- | -------------------------------------------------------------------- | ------------------------------ |
| مسیریابی قطعه-دوم در Gateway              | مسیر docs/04 حفظ می‌شد | Gateway باید بداند `assets/*/assignments` مال fleet است — دانش دامنه | نقض ADR-009                    |
| `asset-service` تخصیص را Proxy کند        | مسیر تودرتو کار می‌کرد | یک سرویس، API سرویس دیگر را جلو می‌برد؛ جفت‌شدگی استقرار             | مونولیت پنهان                  |
| فراخوانی REST به asset در هر بررسی دسترسی | همیشه تازه             | افت asset = خواب داشبورد ناوگان؛ N+1 در فهرست                        | جفت‌شدگی زمانی (docs/03 § ۳٫۶) |
| `availability` در `asset-service`         | یک منبع                | asset باید تخصیص را بداند — دقیقاً چیزی که مالکش نیست                | نقض مالکیت دامنه               |
| بدون `asset_ref`، ذخیره assetId خام       | ساده‌ترین              | نمی‌توان «کدام آزادند» را بدون فراخوانی هر ردیف پاسخ داد             | همان N+1                       |

## Consequences

**مثبت:**

- مسیر Gateway بدون دانش دامنه باقی ماند.
- داشبورد ناوگان با افت `asset-service` کار می‌کند (با داده کمی قدیمی).
- هر مانع، مالکش را نام می‌برد؛ اپراتور می‌داند به تعمیرگاه زنگ بزند یا بیمه را تمدید کند.
- `INSPECTION_FAILED` به معنای واقعی عمل می‌کند: دستگاه بلافاصله از فهرست اعزام
  خارج می‌شود، بی‌آنکه fleet مجبور باشد فیلد `result` رویدادی عمومی را بازرسی کند.

**منفی — صادقانه:**

- **مسیرهای پیاده‌شده با `docs/04` § ۴٫۶ فرق دارند.** آن سند به‌روزرسانی شد، اما هرکس
  نسخه قدیمی را خوانده باشد سردرگم می‌شود.
- **`asset_ref` در نهایت سازگار است.** پنجره‌ای وجود دارد که در آن fleet نمی‌داند
  دستگاهی تازه اسقاط شده و تخصیص را می‌پذیرد. رویداد چند ثانیه بعد می‌رسد و وضعیت
  تصحیح می‌شود، اما تخصیص لحظه‌ای غلط ثبت شده است. پذیرفته‌شده: بدیل، جفت‌شدگی
  همزمان است.
- **دارایی‌ای که fleet هرگز ندیده، رد می‌شود.** Consumer از Offset صفر می‌خواند، پس
  یک دستگاه واقعی ظرف چند ثانیه حاضر است — اما در نخستین راه‌اندازی، پیش از رسیدن
  Replay، تخصیص‌ها `404` می‌گیرند.
- **`DELETE /v1/assignments/{id}` چیزی حذف نمی‌کند.** فعل با اثر نمی‌خواند. نگه داشته
  شد چون `docs/04` صریحاً آن را نوشته بود؛ `POST .../end` مسیر ترجیحی است.
- داده تکراری (نام و نوع دستگاه) در دو پایگاه داده وجود دارد.

**خنثی:**

- `mission` و رویدادهای `MISSION_*` — که `docs/04` در مالکیت fleet فهرست کرده — پیاده
  **نشدند**. مأموریت به پروژه‌های `construction-service` گره خورده که هنوز وجود ندارد،
  و `docs/17` § MVP هم آن را در دامنه MVP نیاورده. افزودنش یک جدول و یک Handler است.
