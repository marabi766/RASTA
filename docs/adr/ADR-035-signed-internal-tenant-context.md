# ADR-035: Context مستأجر برای فراخوانی سرویس‌به‌سرویس، امضاشده

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-29
- **اهمیت:** قاعده بنیادین امنیتی — مکمل ADR-011 و ADR-020
- **حل‌کننده:** `docs/24-open-questions.md` § Q-28

## Context

`AuthGuard.authenticateInternal` وضعیتی برمی‌گرداند که `organizationId` **ندارد**،
در حالی که کامنت خودش خلافش را می‌گوید: «یک فراخوان سرویس، تنانتِ درخواستی را حمل
می‌کند که آن را ایجاد کرده و فراخوان‌کننده در Header منتشرش می‌کند».
`x-organization-id` فقط در شاخه کاربر خوانده می‌شود.

نتیجه، تأییدشده با تست در `test/service-to-service.int-spec.ts` پیش از این تغییر:
هر **۱۰** Handler دارای `@AllowService` روی پلتفرم (هر ده در `economic-service`:
هفت روی `transaction`، دو روی `settlement`، یکی روی `wallet`) فراخوان‌کننده را
احراز هویت می‌کند و بعد، به‌محض رسیدن به داده مستأجر-محدود، با `500` شکست می‌خورد.

> **تصحیح یک عدد.** گزارش پیشین «۲۶ Endpoint» گفت. آن عدد از یک `grep` خام آمده
> بود که کامنت‌ها، فایل‌های Spec و خط‌های `import` را هم می‌شمرد. عدد واقعی
> Handlerهای دارای Decorator، **۱۰** است.

**این وضعیت Fail-Closed است** — `getOrganizationId()` پرتاب می‌کند و هیچ Query ای
بدون Scope اجرا نمی‌شود، پس هیچ داده‌ای نشت نکرده. اما دو چیز درست نیست:

1. مسیری که `docs/08` § ۸٫۶ برای `OrderSagaWorkflow` تجویز می‌کند — فراخوانی
   `placeHold()` و `settle()` به‌عنوان Activity — کار نمی‌کند.
2. شکست به‌صورت `500 INTERNAL_ERROR` بیرون می‌آید، که یعنی یک قاعده امنیتی
   عمدی، شبیه یک باگ گزارش می‌شود.

`docs/06` § ۶٫۱۲ امروز `X-Organization-Id: <propagated>` را برای فراخوان داخلی
مستند می‌کند. اگر همان Header بدون هیچ بررسی‌ای مستأجر را انتخاب کند، هر سرویسی که
یک توکن داخلی معتبر دارد می‌تواند برای **هر** سازمانی عمل کند — و ADR-020 در بخش
Compliance خودش صریحاً گفته: «`X-Organization-Id` **هرگز** بدون اعتبارسنجی پذیرفته
نمی‌شود».

پس پرسش واقعی این نیست «چطور Header را بخوانیم»، بلکه این است: **مرجع تنانت برای
یک فراخوان سرویسی چیست؟**

## Decision

**تنانت یک فراخوان سرویس‌به‌سرویس از یک Claim امضاشده می‌آید، نه از Header.**

توکن داخلی یک Claim تازه دارد:

```jsonc
{
  "iss": "rasta-internal",
  "sub": "marketplace-service", // سرویس فراخوان‌کننده
  "aud": "economic-service", // سرویس مقصد — توکن به همین یکی مقید است
  "purpose": "SERVICE", // یا RELAY
  "org_id": "ORG-DEH-0001", // ← تازه: تنانتی که این توکن برایش صادر شده
  "exp": 1234567890,
}
```

قواعد، به ترتیبی که اجرا می‌شوند:

| #   | قاعده                                                                                                    |
| --- | -------------------------------------------------------------------------------------------------------- |
| ۱   | `aud`، `iss`، `exp`، امضا و `purpose` مثل قبل بررسی می‌شوند. توکن به **یک** سرویس مقصد مقید است.         |
| ۲   | `@AllowService` همچنان اجباری است. توکن معتبر می‌گوید **چه کسی** فراخوانی می‌کند، نه اینکه **مجاز است**. |
| ۳   | `RELAY` هرگز `@AllowService` را ارضا نمی‌کند — یک Hop است، نه یک بازیگر.                                 |
| ۴   | تنانت **فقط** از `org_id` امضاشده می‌آید.                                                                |
| ۵   | اگر `x-organization-id` بیاید، باید **دقیقاً** با `org_id` امضاشده برابر باشد؛ وگرنه `403`.              |
| ۶   | نبودِ `org_id` روی عملیات مستأجر-محدود → `403` با کد پایدار پلتفرم، **هرگز `500`**.                      |
| ۷   | توکن سرویسی بدون `org_id` فقط به عملیات **غیرمستأجری** دسترسی دارد، و فقط جایی که صریحاً مجاز شده.       |
| ۸   | **هیچ Fallback سازگاری با گذشته‌ای وجود ندارد.** توکنی که `org_id` ندارد، تنانت نمی‌گیرد — نقطه.         |

### چرا Header به‌تنهایی مرجع نیست

یک Header امضا ندارد. هر کسی که بتواند یک درخواست HTTP به سرویس بزند، می‌تواند آن را
بنویسد. اگر Header مستأجر را انتخاب کند، آنگاه:

- یک توکن داخلی نشت‌کرده (Risks S-03 — کلید مشترک در MVP) از «جعل هویت
  `marketplace-service`» به «خواندن دفتر کل **هر** سازمانی» ارتقا پیدا می‌کند؛
- یک سرویس آلوده می‌تواند برای سازمانی عمل کند که هرگز چیزی از آن نخواسته؛
- و «چون از شبکه داخلی آمده» دوباره از در پشتی وارد می‌شود — همان فرضی که ADR-020
  کل وجودش برای ردکردنش است.

با امضا، سطح حمله به کلید امضا محدود می‌شود، و آن کلید همان چیزی است که ADR-020
مسیر جایگزینی‌اش را (mTLS با هویت هر Workload) از قبل نوشته است.

### SERVICE در برابر RELAY

این تمایز از D-007 آمده و دست‌نخورده می‌ماند — فقط دقیق‌تر می‌شود:

|                                 | `SERVICE`                            | `RELAY`                                                     |
| ------------------------------- | ------------------------------------ | ----------------------------------------------------------- |
| معنا                            | یک سرویس از طرف خودش فراخوانی می‌کند | Gateway درخواست شخص دیگری را Forward می‌کند                 |
| `@AllowService` را ارضا می‌کند؟ | بله، اگر در فهرست باشد               | **هرگز**                                                    |
| `org_id` حمل می‌کند؟            | برای عملیات مستأجری، بله             | **نه** — تنانت از توکن کاربر می‌آید                         |
| بدون اعتبارنامه دیگر            | یک فراخوان سرویسی                    | یک درخواست **ناشناس**، که `@Public` درباره‌اش تصمیم می‌گیرد |

Gateway همچنان فقط `RELAY` صادر می‌کند و هرگز `SERVICE`. این یعنی Gateway — که در
معرض ترافیک بیرونی است — نمی‌تواند توکنی بسازد که `@AllowService` را ارضا کند.

### عملیات مستأجری در برابر پلتفرمی

«مستأجر-محدود» تعریف تازه‌ای نمی‌گیرد. همان تعریف موجود است: هر مسیری که
`getOrganizationId()` را صدا می‌زند. تفاوت این است که آن تابع دیگر یک `Error` خام
پرتاب نمی‌کند وقتی فراخوان‌کننده یک سرویس بدون Claim است؛ نگهبان **پیش از رسیدن به
دامنه** جلویش را با `403` می‌گیرد.

عملیات غیرمستأجری — Probeهای سلامت، و هر Endpoint ای که هرگز
`getOrganizationId()` را صدا نمی‌زند — با توکن سرویسیِ بدون `org_id` قابل دسترس
می‌ماند، مشروط به `@AllowService`.

### کد خطای پایدار

یک کد تازه در `packages/contracts`:

```
SERVICE_TENANT_CONTEXT_INVALID → 403
```

هم برای «Claim نیست» و هم برای «Header با Claim نمی‌خواند». **یک کد**، چون از دید
فراخوان‌کننده هر دو یک چیزند: توکنی که داری برای این کار مناسب نیست. تفکیک دقیق در
`internalContext` می‌رود که فقط به Log می‌رسد، نه به بدنه پاسخ (S-09).

هیچ محتوای توکنی — نه `org_id`، نه `sub`، نه خود توکن — در پاسخ یا Log ظاهر
نمی‌شود.

## Alternatives Considered

| گزینه                                | مزیت                                                  | عیب                                                                                  | چرا رد شد                          |
| ------------------------------------ | ----------------------------------------------------- | ------------------------------------------------------------------------------------ | ---------------------------------- |
| اعتماد به `X-Organization-Id`        | ساده‌ترین؛ صفر تغییر در صدور توکن                     | یک Header بدون امضا مستأجر را انتخاب می‌کند؛ توکن نشت‌کرده = دسترسی به همه سازمان‌ها | نقض مستقیم Compliance خودِ ADR-020 |
| Header + بررسی عضویت سرویس در سازمان | امضا لازم ندارد                                       | «عضویت» برای یک سرویس معنا ندارد؛ باید اختراع می‌شد                                  | اختراع واقعیت (AGENTS.md § ۹)      |
| انتشار توکن کاربر به Downstream      | Context کامل حفظ می‌شود                               | سرویس Downstream می‌تواند از هویت کاربر سوءاستفاده کند                               | همان دلیلی که ADR-020 ردش کرد      |
| توکن بلندعمر با فهرست سازمان‌ها      | صدور کمتر                                             | یک توکن = دسترسی به چند مستأجر؛ نشتش گران‌تر است                                     | حداقل دسترسی                       |
| Claim امضاشده تک‌سازمانی             | سطح حمله به کلید امضا محدود می‌شود؛ مسیر روشن به mTLS | صدور توکن به‌ازای (مقصد، سازمان)                                                     | **پذیرفته شد**                     |
| mTLS + SPIFFE از امروز               | امن‌ترین                                              | PKI و مدیریت چرخه گواهی                                                              | همان تعویق ADR-020 به Production   |

## Consequences

**مثبت**

- یک توکن داخلی نشت‌کرده حداکثر به **یک** سازمان و **یک** سرویس مقصد دسترسی می‌دهد.
- مسیر Activity در `docs/08` § ۸٫۶ برای نخستین بار کار می‌کند.
- یک قاعده امنیتی عمدی به‌جای `500`، `403` با کد پایدار برمی‌گرداند.
- `RequestContext` برای فراخوان سرویسی همان شکلی را دارد که برای کاربر دارد، پس
  Repository پایه و بررسی سطح Object هیچ حالت خاصی لازم ندارند.

**منفی**

- فراخوان‌کننده باید به‌ازای هر (سرویس مقصد، سازمان) توکن بسازد. توکن‌ها ۵ دقیقه
  عمر دارند، پس این یعنی صدور بیشتر — که چون امضای HS256 محلی است، هزینه‌اش شبکه
  ندارد.
- هر مصرف‌کننده آینده باید `org_id` را بگذارد. **Fallback عمداً وجود ندارد**، پس
  فراموش کردنش یک `403` صریح است، نه یک دسترسی خاموش.
- کلید مشترک MVP همچنان تک‌نقطه اعتماد است (Risks S-03) — این ADR آن را کوچک‌تر
  می‌کند، حذف نمی‌کند.

**خنثی**

- Gateway تغییری نمی‌کند: همچنان فقط `RELAY` صادر می‌کند.
- توکن کاربر و مسیرش دست‌نخورده‌اند.

## Threat Model

| تهدید                                    | پیش از این ADR                                        | پس از آن                                                  |
| ---------------------------------------- | ----------------------------------------------------- | --------------------------------------------------------- |
| Header جعلی از یک Pod آلوده              | اگر Header خوانده می‌شد: انتخاب هر مستأجری            | `403` — Header باید با Claim امضاشده بخواند               |
| توکن داخلی نشت‌کرده                      | جعل هویت سرویس؛ اگر Header خوانده می‌شد، همه مستأجرها | یک سازمان، یک سرویس مقصد، ۵ دقیقه                         |
| Replay یک توکن به سرویس دیگر             | `aud` جلویش را می‌گرفت                                | بدون تغییر — `aud`                                        |
| Gateway آلوده                            | فقط `RELAY` می‌سازد                                   | بدون تغییر — `RELAY` هرگز `@AllowService` را ارضا نمی‌کند |
| سرویس مجاز که برای سازمان دیگری عمل کند  | ممکن بود اگر Header خوانده می‌شد                      | `403` — `org_id` پس از امضا تغییرناپذیر است               |
| ارتقای دسترسی صرفاً به‌خاطر بودن در شبکه | همان چیزی که ADR-020 رد کرده                          | بدون تغییر — هیچ اعتماد ضمنی                              |

## Compliance

- `X-Organization-Id` روی مسیر سرویسی **هرگز** مرجع نیست؛ فقط می‌تواند با Claim
  امضاشده موافقت کند یا `403` بگیرد.
- تست: توکن `SERVICE` + `org_id` هم‌خوان → پذیرفته
- تست: توکن `SERVICE` بدون Claim روی Endpoint مستأجری → `403`
- تست: Header ناهم‌خوان → `403`
- تست: Header جعلی برای مستأجر B → `403`، و هیچ ردیفی از B دیده نمی‌شود
- تست: `aud` اشتباه / منقضی / بدشکل → `401`
- تست: سرویس خارج از فهرست → `403`
- تست: `SERVICE` روی Endpoint بدون `@AllowService` → `403`
- تست: `RELAY` هرگز `@AllowService` را ارضا نمی‌کند
- تست: هیچ مسیری `500` تولید نمی‌کند
- تست: مسیر کاربر دست‌نخورده است
- `packages/nest-common` فقط اجرای احراز هویت/Context و قرارداد دارد — هیچ منطق
  کسب‌وکاری (A-03)
