# ADR-039: هماهنگی سفارش با Temporal — نخستین Workflow واقعی پلتفرم

- **وضعیت:** Accepted
- **تاریخ:** 2026-08-29
- **اهمیت:** یکپارچگی مالی، پایداری گردش‌کار، افزوده شدن یک SDK به Stack
- **مرتبط:** ADR-010 (Temporal)، ADR-027 (تعویق Temporal در نگهداری)، ADR-031 (تسویه بدون Temporal)، ADR-038 (ماشین حالت)، ADR-040 (مرز اقتصادی)

## Context

Temporal از روز اول در Stack بوده (`docs/01`، ADR-010) و Server اش در
`docker-compose.yml` بالا می‌آید — اما **هیچ سرویسی تا امروز از آن استفاده نکرده**.
دو ADR قبلی آگاهانه از آن پرهیز کردند و دلیلشان هنوز درست است:

- **ADR-027** — سررسید نگهداری یک Scan روزانه است، نه یک Workflow، چون حالتی
  ندارد که بین دو اجرا زنده بماند.
- **ADR-031** — تسویه اقتصادی یک `BEGIN … COMMIT` است. اضافه کردن Temporal به
  چیزی که در یک تراکنش پایگاه داده اتمیک است، فقط یک نقطه شکست اضافه می‌کند.

سفارش فرق دارد و تفاوتش دقیقاً همان چیزی است که Temporal برای آن ساخته شده:
**حالتی که روزها زنده می‌ماند و منتظر انسان است.** میان `FUNDS_HELD` و
`RECEIPT_CONFIRMED` دو انتظار وجود دارد — تحویل تأمین‌کننده و تأیید خریدار — که
هفت و سه روز طول می‌کشند (`docs/08` § ۸٫۴). چیزی باید آن انتظار را نگه دارد،
بازراه‌اندازی سرویس را تاب بیاورد، و در پایان جبران را به ترتیب معکوس اجرا کند.

پس این ADR نخستین مصرف واقعی Temporal است و یک SDK به Stack اضافه می‌کند.

## Decision

### ۱. `OrderSagaWorkflow` روی صف `rasta-order`

یک Workflow به‌ازای هر سفارش، با `workflowId = order-<orderId>`. آن شناسه عمدی
است: Temporal یک Workflow با شناسه تکراری را رد می‌کند، پس **دو Saga برای یک
سفارش ساختاراً ممکن نیست** — حتی اگر دو درخواست هم‌زمان راهش بیندازند.

صف `rasta-order` مخصوص این سرویس است. Worker در همان Process سرویس بالا می‌آید
و با `MARKETPLACE_TEMPORAL_ENABLED=false` خاموش می‌شود، تا یک محیط توسعه بدون
Temporal بتواند بقیه سرویس را اجرا کند.

### ۲. Workflow تصمیم می‌گیرد، Activity کار می‌کند

هیچ I/O ای در کد Workflow نیست. نه HTTP، نه پایگاه داده، نه `Date.now()`، نه
`Math.random()`. Temporal کد Workflow را در هر بازپخش دوباره اجرا می‌کند، و هر
چیز غیرقطعی یعنی بازپخشی که با اجرای اول نمی‌خواند.

| Activity              | چه می‌کند                                         |
| --------------------- | ------------------------------------------------- |
| `createObligation`    | `POST /v1/transactions` با `holdFunds=true`       |
| `markFundsHeld`       | گذار سفارش به `FUNDS_HELD` + رویداد               |
| `markFailed`          | گذار به `FAILED` با دلیل                          |
| `authoriseSettlement` | `POST /v1/transactions/{id}/authorise-settlement` |
| `settle`              | `POST /v1/settlements`                            |
| `markCompleted`       | گذار به `COMPLETED` + `ORDER_COMPLETED`           |
| `refundObligation`    | `POST /v1/transactions/{id}/refund`               |
| `cancelObligation`    | `POST /v1/transactions/{id}/cancel`               |
| `markCancelled`       | گذار به `CANCELLED`                               |
| `disputeObligation`   | `POST /v1/transactions/{id}/dispute`              |
| `recordReminder`      | ثبت یک یادآور — بدون هیچ اثر مالی                 |

### ۳. سیگنال‌ها و پرس‌وجو

| سیگنال             | فرستنده     | اثر                             |
| ------------------ | ----------- | ------------------------------- |
| `orderConfirmed`   | تأمین‌کننده | انتظار تحویل آغاز می‌شود        |
| `orderFulfilled`   | تأمین‌کننده | انتظار تأیید دریافت آغاز می‌شود |
| `receiptConfirmed` | خریدار      | مسیر تسویه آغاز می‌شود          |
| `orderDisputed`    | خریدار      | تسویه **کاملاً** متوقف می‌شود   |
| `orderCancelled`   | خریدار      | جبران آغاز می‌شود               |

Query ‏`status` وضعیت داخلی Workflow را برمی‌گرداند — برای تشخیص، بدون خواندن
پایگاه داده.

**HTTP منبع حقیقت است، سیگنال محرک.** هر فرمان اول در پایگاه داده اعمال و ثبت
می‌شود و **سپس** سیگنال می‌رود. اگر ارسال سیگنال شکست بخورد، وضعیت سفارش درست
است و Workflow با Timeout بعدی‌اش وضعیت را دوباره می‌خواند. عکسش — اول سیگنال —
یعنی یک سفارش که Workflow اش جلوتر از پایگاه داده است.

### ۴. Retry و Timeout، صریح

| مورد                  | مقدار                                                               |
| --------------------- | ------------------------------------------------------------------- |
| `startToCloseTimeout` | ۳۰ ثانیه برای هر Activity                                           |
| سیاست Retry پیش‌فرض   | ۳ تلاش، Backoff نمایی از ۱ ثانیه                                    |
| `settle`              | **۵ تلاش** (`docs/08` § ۸٫۴)، سپس توقف و هشدار — بدون جبران         |
| خطای غیرقابل‌Retry    | `BUSINESS_RULE_VIOLATION` · `TENANT_MISMATCH` · `VALIDATION_FAILED` |
| انتظار تحویل          | پیکربندی سازمانی (ADR-043)                                          |
| انتظار تأیید دریافت   | پیکربندی سازمانی (ADR-043)                                          |

خطای قاعده کسب‌وکاری Retry نمی‌شود چون تلاش دوم همان پاسخ را می‌گیرد؛ Retry کردنش
فقط شکست را دیرتر گزارش می‌کند.

### ۵. جبران — و جایی که عمداً متوقف می‌شود

| مرحله شکست‌خورده   | جبران                                               |
| ------------------ | --------------------------------------------------- |
| `createObligation` | چیزی برای جبران نیست → `FAILED`                     |
| لغو پیش از تحویل   | `refundObligation` → `CANCELLED`                    |
| لغو پس از تحویل    | `refundObligation` → `CANCELLED`                    |
| اعتراض             | `disputeObligation` → توقف؛ **وجه در Hold می‌ماند** |
| شکست تسویه         | ۵ بار Retry، سپس **توقف بدون جبران**                |

**CONSTRAINT (از `docs/08` § ۸٫۴).** پس از تأیید دریافت، جبران خودکار مالی وجود
ندارد. اگر تسویه پنج بار شکست بخورد، Workflow در `RECEIPT_CONFIRMED` می‌ماند، یک
Metric بالا می‌رود و انسان تصمیم می‌گیرد. برگرداندن خودکار پول در سیستمی که
نمی‌داند تسویه انجام شده یا نه، ریسک بزرگ‌تری از مسئله اصلی است.

### ۶. Idempotency: کلید از هویت، نه از زمان

هر Activity مالی یک `Idempotency-Key` قطعی می‌برد:

```
order:<orderId>:hold
order:<orderId>:authorise
order:<orderId>:settle
order:<orderId>:refund
order:<orderId>:cancel
order:<orderId>:dispute
```

از `orderId` مشتق می‌شود، نه از `ulid()` یا زمان. یعنی هر Retry — چه Retry خود
Temporal، چه بازپخش پس از Crash — **همان** کلید را می‌فرستد، و
`economic-service` پاسخ اول را برمی‌گرداند به‌جای اینکه دومین Hold را بزند. اگر
کلید تصادفی بود، هر Retry یک تراکنش تازه می‌ساخت — که دقیقاً همان اثر مالی دوم
است که این ADR باید جلویش را بگیرد.

## Alternatives Considered

1. **بدون Temporal، با یک جدول وضعیت و Cron.** رد شد: انتظار چندروزه با
   جبران به ترتیب معکوس، دقیقاً چیزی است که با Cron به یک Scheduler خانگی تبدیل
   می‌شود. ADR-027 و ADR-031 Temporal را جایی رد کردند که حالت ماندگاری نبود؛
   اینجا هست.
2. **هماهنگی رویدادمحور (Choreography) با Kafka.** رد شد: جبران به ترتیب معکوس
   و «کجای کاریم» در Choreography هیچ جای واحدی ندارد، و `docs/08` § ۸٫۴ صریحاً
   Activity می‌گوید نه رویداد.
3. **Timer داخل Workflow برای تأیید خودکار.** رد شد — ADR-043 و Q-11.
4. **Workflow به‌ازای هر خط سفارش.** رد شد: تعهد مالی به‌ازای کل سفارش است، پس
   جبران هم هست.
5. **`workflowId` تصادفی.** رد شد: تکرارناپذیری Workflow به‌ازای سفارش، ارزان‌ترین
   قفلی است که این Saga می‌تواند داشته باشد.
6. **صف مشترک با سرویس‌های آینده.** رد شد: صف مشترک یعنی Worker یک سرویس باید
   کد Workflow سرویس دیگر را داشته باشد.

## Consequences

**مثبت**

- انتظار چندروزه بازراه‌اندازی سرویس را تاب می‌آورد.
- جبران یک مسیر نوشته‌شده است، نه یک `catch` که کسی یادش رفته.
- بازپخش قطعی است و تست می‌شود.

**منفی، پذیرفته‌شده**

- **چهار بسته `@temporalio/*` به Stack افزوده شد.** نخستین بار است و هزینه‌اش
  واقعی: یک Runtime تازه، یک Worker تازه، و قاعده‌های قطعیت که باید رعایت شوند.
  ADR-010 این را از پیش تصویب کرده بود؛ این ADR فقط لحظه‌اش را ثبت می‌کند.
- سرویس بدون Temporal کار می‌کند اما سفارش پیش نمی‌رود. با
  `MARKETPLACE_TEMPORAL_ENABLED=false` این حالت **صریح** است، نه یک شکست خاموش.
- Workflow و پایگاه داده دو منبع وضعیت‌اند. با «HTTP اول، سیگنال بعد» پایگاه داده
  همیشه جلوتر یا برابر است، هرگز عقب‌تر.

## Compliance

- **A-11** — گردش‌کار چندمرحله‌ای در Temporal.
- **A-09** — هر Activity مالی Idempotent با کلید قطعی.
- **`Date.now()` در Workflow ممنوع** (AGENTS.md § ۳) — با `workflow.now()` و
  `sleep()` جایگزین شده و تست بازپخش آن را می‌آزماید.
- **ADR-036** — رویدادهای سفارش با `orderId` پارتیشن می‌شوند.
