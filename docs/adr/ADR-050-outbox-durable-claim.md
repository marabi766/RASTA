# ADR-050: Claim بادوام برای Outbox Relay

- **وضعیت:** Proposed
- **تاریخ:** 2026-09-02
- **اهمیت:** انتشار تکراری رویداد در هر هشت سرویس — D-026
- **پیاده‌سازی نشده.** این ADR فقط تصمیم را پیشنهاد می‌کند؛ فاز اجرا جداست.

## Context

### آنچه امروز هست

هر هشت Outbox Store پیاده‌شده یک `claimPending` یکسان دارند:

```sql
SELECT id, aggregate_type, ...
  FROM outbox_message
 WHERE published_at IS NULL
 ORDER BY created_at
 LIMIT $limit
 FOR UPDATE SKIP LOCKED
```

و `OutboxRelay` در `packages/nest-common/src/outbox/outbox.ts` این توالی را اجرا
می‌کند:

```ts
const batch = await store.claimPending(batchSize); // ← تراکنش اینجا تمام می‌شود
await publisher.publish(batch); // ← I/O شبکه، بدون قفل
await store.markPublished(batch.map((r) => r.id)); // ← عملیات جدا
```

`FOR UPDATE` قفل سطری می‌گیرد، اما قفل سطری در PostgreSQL **فقط تا پایان تراکنشِ
نگهدارنده‌اش** زنده است. `claimPending` یک `$queryRaw` مستقل است؛ با بازگشتش
تراکنش بسته شده و همه قفل‌ها آزادند. از آن لحظه تا نوشته‌شدن `published_at`،
ردیف‌ها **با هیچ سازوکار بادواری رزرو نشده‌اند**.

`this.running` در رله فقط Tickهای هم‌پوشان **درون یک پروسه** را مهار می‌کند و
درباره Replicaها چیزی نمی‌گوید.

### شواهد اندازه‌گیری‌شده

دو `PrismaService` مستقل (دو اتصال، مثل دو Replica) روی پایگاه داده واقعی
`rasta_document`. ترتیب قطعی — بدون Sleep، بدون Timing، بدون Kafka:

| #   | سناریو                                                      | نتیجه                             |
| --- | ----------------------------------------------------------- | --------------------------------- |
| M1  | A `claimPending(50)` سپس B `claimPending(50)`، پیش از Mark  | A=۱۰، B=۱۰، **اشتراک = ۱۰ از ۱۰** |
| M2  | پس از `markPublished` توسط A                                | B = **۰**                         |
| M3  | A Claim می‌کند، سپس اتصالش بسته می‌شود (Crash) بدون Publish | B = **۱۰** (بازیابی می‌شود)       |
| M4  | Publish موفق، `markPublished` شکست می‌خورد                  | B = **۱۰** قابل انتشار مجدد       |

M1 نشان می‌دهد هر دو رله همان ده رویداد را به Kafka می‌دادند.

M3 مهم‌تر از آن است که به‌نظر می‌رسد: بازیابی پس از Crash امروز **رایگان** است،
اما دقیقاً به این دلیل که هیچ رزروی وجود ندارد. همان خاصیتی که M3 را حل می‌کند،
M1 را می‌سازد. هر طراحی Claim بادوام، M1 را می‌بندد و در عوض **موظف** می‌شود
برای M3 پاسخی صریح داشته باشد — این‌جاست که Expiry از یک جزئیات به یک الزام
تبدیل می‌شود.

M4 با هیچ طراحی Claimی حل نمی‌شود؛ ذاتیِ At-Least-Once است.

### تفکیک تضمین‌ها

این ADR این شش را جدا نگه می‌دارد، چون خلط‌شان همان چیزی است که به ادعای نادرست
«SKIP LOCKED مانع انتشار تکراری است» انجامید:

| #   | تضمین                                              | امروز                     | با Option A              |
| --- | -------------------------------------------------- | ------------------------- | ------------------------ |
| G1  | نبودِ Claim تکراری هم‌زمان در طول یک Lease زنده    | ❌                        | ✅                       |
| G2  | بازیابی پس از Crash مدعی                           | ✅ (چون رزروی نیست)       | ✅ (با Expiry)           |
| G3  | تحویل حداقل‌یک‌بار پس از Crash میان Publish و Mark | ذاتی                      | **ذاتی — تغییر نمی‌کند** |
| G4  | ایدمپوتنسی مصرف‌کننده (A-09)                       | لازم                      | **همچنان لازم**          |
| G5  | ترتیب Kafka به‌ازای هر Aggregate                   | ❌ در برابری `created_at` | مشروط — بخش Ordering     |
| G6  | ترتیب قطعی انتخاب در پایگاه داده                   | ❌                        | ✅ با `created_at, id`   |

**هیچ گزینه‌ای Exactly-Once نمی‌دهد و این ADR چنین ادعایی نمی‌کند.** G3 با
At-Least-Once زندگی می‌کند؛ کاری که می‌شود کرد کوچک‌کردن پنجره است، نه صفرکردنش.

### چرا ایدمپوتنسی مصرف‌کننده کافی نیست

A-09 مصرف‌کننده ایدمپوتنت می‌خواهد و آن **اثر تجاری** تکراری را مهار می‌کند. اما
حذف نمی‌کند:

- انتشار تکراری در Kafka و مصرف پهنای‌باند و Retention؛
- بار روی Broker و روی همه مصرف‌کننده‌ها؛
- **ریسک ترتیب**: دو رله که یک Batch را هم‌زمان منتشر می‌کنند می‌توانند دو رویداد
  یک Aggregate را با ترتیب درهم به یک Partition برسانند. ایدمپوتنسی این را
  درست نمی‌کند، چون هر دو رویداد معتبرند و ترتیبشان معنا دارد.

## Decision

**Option A — Claim بادوام با Lease دارای انقضا.**

الگو تازه نیست: `document-service` همین را برای اسکن بدافزار دارد
(`scan_lease_owner` و `scan_lease_expires_at`، ADR-049). همان کد، همان پایگاه
داده، همان ORM — یعنی این تصمیم یک الگوی اثبات‌شده در همین Repository را به
Outbox تعمیم می‌دهد، نه یک اختراع تازه.

### شکل SQL اتمیک

```sql
UPDATE outbox_message AS o
   SET claim_owner      = $owner,
       claim_expires_at = now() + make_interval(secs => $leaseSeconds::double precision),
       claim_count      = o.claim_count + 1
  FROM (
    SELECT id
      FROM outbox_message
     WHERE published_at IS NULL
       AND (claim_expires_at IS NULL OR claim_expires_at <= now())
     ORDER BY created_at, id
     LIMIT $limit
     FOR UPDATE SKIP LOCKED
  ) AS due
 WHERE o.id = due.id
RETURNING o.id, o.aggregate_type, ..., o.claim_owner, o.claim_expires_at;
```

یک جمله. انتخاب و رزرو در یک تراکنش ضمنی اتفاق می‌افتند، پس بین آن دو پنجره‌ای
نیست. `FOR UPDATE SKIP LOCKED` در زیرپرسش باقی می‌ماند — نه به‌عنوان رزرو، بلکه
برای اینکه دو Claimکننده هم‌زمان روی یک ردیف سریالی نشوند.

### مالکیت Lease

- `claim_owner`: شناسه یکتای هر پروسه رله، ساخته‌شده هنگام Boot
  (`${SERVICE_NAME}:${hostname}:${ULID}`). در حافظه می‌ماند و با Restart عوض
  می‌شود — که عمدی است: پروسه تازه وارث Leaseهای پروسه مرده نیست.
- `claim_expires_at`: تنها مرجع «هنوز رزرو است یا نه». **Owner به‌تنهایی هرگز
  ملاک نیست**، چون یک Owner مرده تا ابد Owner می‌ماند.
- `claim_count`: چند بار این ردیف Claim شده. برای رصد؛ یک ردیف با
  `claim_count` بالا و `published_at` تهی یعنی چیزی مدام Claim می‌شود و
  هرگز موفق نمی‌شود.

### تأیید موفقیت — Mark مشروط بر Lease

```sql
UPDATE outbox_message
   SET published_at = now(), claim_owner = NULL, claim_expires_at = NULL
 WHERE id = ANY($ids)
   AND published_at IS NULL
   AND claim_owner = $owner
   AND claim_expires_at > now();
```

`markPublished` تعداد ردیف‌های تغییریافته را برمی‌گرداند. اگر کمتر از اندازه
Batch باشد، یعنی Lease برای بعضی ردیف‌ها منقضی شده و شخص دیگری آن‌ها را گرفته —
که **باید Log و Metric شود**، چون همان لحظه‌ای است که یک انتشار تکراری رخ داده.

**`published_at IS NULL` در شرط عمدی است.** حتی اگر Lease معتبر باشد، ردیفی که
قبلاً منتشر شده دوباره Mark نمی‌شود.

### شکست، آزادسازی و Backoff

```sql
UPDATE outbox_message
   SET attempts = attempts + 1,
       last_error = $error,
       claim_owner = NULL,
       claim_expires_at = NULL
 WHERE id = $id AND claim_owner = $owner;
```

آزادسازی صریح، تا ردیف تا انقضای Lease معطل نماند. Backoff از `attempts`
محاسبه می‌شود.

### محافظت در برابر مدعی کهنه

سه لایه، و هر سه لازم‌اند:

1. Claim فقط ردیف‌های `claim_expires_at IS NULL OR <= now()` را می‌گیرد.
2. `markPublished` مشروط بر `claim_owner` **و** `claim_expires_at > now()` است.
3. رله پیش از `publish`، اگر `claim_expires_at` گذشته باشد، Batch را دور
   می‌ریزد و Tick را بی‌اثر تمام می‌کند.

لایه ۳ پنجره را کوچک می‌کند اما نمی‌بندد: میان بررسی و رسیدن پیام به Broker
همچنان زمان می‌گذرد. این محدودیت باید صریح بماند.

### مالکیت Batch

Lease به‌ازای **ردیف** است، نه Batch. مسیر `publishIndividually` در رله همین
حالا ردیف‌به‌ردیف Mark و Fail می‌کند؛ Lease سطری با آن هم‌خوان است. Batch فقط
واحد Claim است.

### پیکربندی و پیش‌فرض‌های امن

| متغیر                        | پیش‌فرض | چرا                                                                                                                                                            |
| ---------------------------- | ------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `OUTBOX_CLAIM_LEASE_SECONDS` | `30`    | باید از بدترین زمان `publish` بیشتر باشد. با `OUTBOX_POLL_INTERVAL_MS=500` و Batch ۱۰۰، انتشار در حد میلی‌ثانیه است؛ ۳۰ ثانیه حاشیه‌ای است برای یک Broker کند. |
| `OUTBOX_CLAIM_MAX_ATTEMPTS`  | `—`     | **افزوده نمی‌شود.** `attempts` هست و Backoff از آن می‌آید.                                                                                                     |

Lease خیلی کوتاه: انتشار تکراری. خیلی بلند: ردیف پس از Crash تا انقضا معطل
می‌ماند. ۳۰ ثانیه سمت دوم را انتخاب می‌کند — تأخیر بهتر از تکرار است.

همه با `booleanEnv`/`z.coerce.number` در `@rasta/config` خوانده می‌شوند و
مقادیر نامعتبر سرویس را در Boot متوقف می‌کنند (D-020).

### Metric و Alert

| نام                                 | نوع     | چرا                                                                                                                |
| ----------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------ |
| `rasta_outbox_claim_conflict_total` | Counter | `markPublished` کمتر از Batch را تغییر داد — یعنی انتشار تکراری قطعی رخ داده. **هر مقدار غیرصفر باید Alert بدهد.** |
| `rasta_outbox_lease_expired_total`  | Counter | Claim یک ردیف با Lease منقضی — یعنی مدعی قبلی مرده یا کند بوده.                                                    |
| `rasta_outbox_claimed_total`        | Gauge   | ردیف‌های دارای Lease زنده. رشد پایدارش یعنی رله Claim می‌کند و Mark نمی‌کند.                                       |

`rasta_outbox_pending_total` معنایش عوض **نمی‌شود**: همچنان
`published_at IS NULL` سراسری، شامل ردیف‌های Claimشده — چون یک ردیف Claimشده
هنوز منتشر نشده و Backlog است.

### سازگاری با Rolling Deployment

ستون‌ها Nullable و بدون Default اضافه می‌شوند. در پنجره‌ای که نسخه قدیم و جدید
هم‌زمان اجرا می‌شوند:

- نسخه **قدیم** `claim_*` را نمی‌بیند و مثل امروز Claim می‌کند — ردیف‌های
  Claimشده توسط نسخه جدید را هم می‌گیرد.
- نسخه **جدید** ردیف Leaseدار را رد می‌کند اما ردیف‌های نسخه قدیم را می‌گیرد.

یعنی **در طول Rollout، تضمین G1 برقرار نیست** — رفتار به بدترین حالتِ امروز
برمی‌گردد، نه بدتر از آن. این پذیرفتنی است چون امروز هم همان است؛ اما باید
نوشته و پذیرفته شود، نه کشف.

| ------------------------------- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------- |
| **B — قفل نگه‌داشته در تراکنش** | ساده‌ترین از نظر مفهومی؛ G1 دقیق | تراکنش و اتصال در طول I/O شبکه Kafka باز می‌ماند؛ یک Broker کند Connection Pool را می‌خورد و به کل سرویس سرایت می‌کند؛ `idle_in_transaction` طولانی مانع Vacuum می‌شود                | هزینه‌اش روی مسیر داغِ یک سرویس مالی غیرقابل قبول است                |

## Ordering

### وضعیت امروز، اثبات‌شده

`created_at` از نوع `timestamp(3)` است — دقت **میلی‌ثانیه**. `ORDER BY created_at`
برای ردیف‌های هم‌میلی‌ثانیه ترتیب دلخواه می‌دهد.

`id` هم نجات نمی‌دهد. ULID با `ulid()` ساده تولید می‌شود و
**`monotonicFactory` هیچ‌جا استفاده نشده**. اندازه‌گیری روی همین Repository:

```
same-ms ULIDs generated in sorted order? false
inversions among 12 same-ms ULIDs: 6
cross-ms a<b (timestamp prefix dominates)? true
```

پس: ULID **میان** میلی‌ثانیه‌ها ترتیب ساخت را حفظ می‌کند، اما **درون** یک
میلی‌ثانیه تصادفی است. این با فرض «ULID یعنی ترتیب ساخت» فرق دارد و نباید فرض
شود.

### تصمیم

**`ORDER BY created_at, id`.**

چه می‌دهد: ترتیب **کلی و قطعی و پایدار**. دو Claim پیاپی همان پیشوند را
برمی‌گردانند؛ صفحه‌بندی معنا پیدا می‌کند؛ آزمون‌ها قابل نوشتن می‌شوند.

چه **نمی‌دهد**: ترتیب ساخت درون یک میلی‌ثانیه. `id` آنجا تصادفی است، پس ترتیب
قطعی است اما دلخواه.

### آیا Sequence به‌ازای Aggregate لازم است؟

برای G5 (ترتیب Kafka به‌ازای Aggregate) بله، **در اصول**. دو رویداد یک Aggregate
که در یک میلی‌ثانیه نوشته شده‌اند می‌توانند با ترتیب معکوس به Partition برسند،
و چون `partitionKey` همان Aggregate است هر دو به یک Partition می‌روند — یعنی
ترتیب اشتباه دیده می‌شود.

سه راه، و این ADR **تصمیم نمی‌گیرد**، فقط دامنه را روشن می‌کند:

1. **`BIGSERIAL`/Identity** — ترتیب درج یکنواخت. ساده و ارزان. اما Sequence
   ممکن است خارج از ترتیب Commit تخصیص یابد؛ برای ترتیب **درج** درست است، نه
   لزوماً برای ترتیب **Commit**.
2. **`aggregate_sequence`** به‌ازای هر Aggregate — دقیق‌ترین، اما نیازمند
   شمارنده در مسیر نوشتن دامنه و لمس هر Producer.
3. **پذیرش وضع موجود** با ثبت صریح محدودیت.

انتخاب میان این سه، **خودش یک ADR جداست** و نباید داخل تصمیم Claim پنهان شود.
`ORDER BY created_at, id` در این ADR G6 را می‌دهد و G5 را باز می‌گذارد.

## Consequences

**مثبت:** G1 برقرار می‌شود؛ انتشار تکراری میان Replicaها از «همیشه ممکن» به
«فقط در پنجره انقضای Lease» می‌رسد؛ G6 برقرار می‌شود؛ الگو با ADR-049 یکی
می‌شود؛ سه Metric تازه چیزی را قابل دیدن می‌کنند که امروز نامرئی است.

**منفی:**

- سه ستون و دو Index تازه در **هشت** پایگاه داده — هشت Migration، هشت Rollback.
- G3 حل نمی‌شود. At-Least-Once باقی می‌ماند و A-09 همچنان الزامی است.
- G5 حل نمی‌شود؛ به ADR بعدی موکول می‌شود.
- در طول Rolling Deployment، G1 برقرار نیست.
- Claim از `SELECT` به `UPDATE` تبدیل می‌شود: نوشتن روی هر Poll، حتی وقتی
  چیزی برای انتشار نیست… مگر اینکه زیرپرسش خالی برگردد، که آن‌وقت `UPDATE`
  صفر ردیف را لمس می‌کند. بار WAL افزایش می‌یابد و باید سنجیده شود.
- یک ردیف که مدعی‌اش مرده، تا `OUTBOX_CLAIM_LEASE_SECONDS` معطل می‌ماند —
  تأخیری که امروز وجود ندارد.

**خنثی:** `pendingCount()` و `rasta_outbox_pending_total` بدون تغییر می‌مانند.
`purgePublished` بدون تغییر می‌ماند.

## Compliance

- آزمون‌های مشخص‌شده در بخش «Required tests» فاز اجرا.
- `rasta_outbox_claim_conflict_total > 0` یعنی نقض G1 — Alert.
- بازبینی: هیچ Comment یا سندی نباید ادعا کند `SKIP LOCKED` به‌تنهایی مانع
  انتشار تکراری است.
