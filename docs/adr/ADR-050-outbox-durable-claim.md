# ADR-050: Claim بادوام برای Outbox Relay

- **وضعیت:** Proposed
- **تاریخ:** 2026-09-02
- **اهمیت:** انتشار تکراری رویداد در هر هشت سرویس — D-026
- **پیاده‌سازی نشده.** این ADR فقط تصمیم را پیشنهاد می‌کند؛ فاز اجرا جداست.

## Context

### آنچه امروز هست

هر هشت Outbox Store پیاده‌شده یک `claimPending` یکسان دارند:

```sql
SELECT id, aggregate_type, ...
  FROM outbox_message
 WHERE published_at IS NULL
 ORDER BY created_at
 LIMIT $limit
 FOR UPDATE SKIP LOCKED
```

و `OutboxRelay` در `packages/nest-common/src/outbox/outbox.ts` این توالی را اجرا
می‌کند:

```ts
const batch = await store.claimPending(batchSize); // ← تراکنش اینجا تمام می‌شود
await publisher.publish(batch); // ← I/O شبکه، بدون قفل
await store.markPublished(batch.map((r) => r.id)); // ← عملیات جدا
```

`FOR UPDATE` قفل سطری می‌گیرد، اما قفل سطری در PostgreSQL **فقط تا پایان تراکنشِ
نگهدارنده‌اش** زنده است. `claimPending` یک `$queryRaw` مستقل است؛ با بازگشتش
تراکنش بسته شده و همه قفل‌ها آزادند. از آن لحظه تا نوشته‌شدن `published_at`،
ردیف‌ها **با هیچ سازوکار بادواری رزرو نشده‌اند**.

`this.running` در رله فقط Tickهای هم‌پوشان **درون یک پروسه** را مهار می‌کند و
درباره Replicaها چیزی نمی‌گوید.

### شواهد اندازه‌گیری‌شده

دو `PrismaService` مستقل (دو اتصال، مثل دو Replica) روی پایگاه داده واقعی
`rasta_document`. ترتیب قطعی — بدون Sleep، بدون Timing، بدون Kafka:

| #   | سناریو                                                      | نتیجه                             |
| --- | ----------------------------------------------------------- | --------------------------------- |
| M1  | A `claimPending(50)` سپس B `claimPending(50)`، پیش از Mark  | A=۱۰، B=۱۰، **اشتراک = ۱۰ از ۱۰** |
| M2  | پس از `markPublished` توسط A                                | B = **۰**                         |
| M3  | A Claim می‌کند، سپس اتصالش بسته می‌شود (Crash) بدون Publish | B = **۱۰** (بازیابی می‌شود)       |
| M4  | Publish موفق، `markPublished` شکست می‌خورد                  | B = **۱۰** قابل انتشار مجدد       |

M1 نشان می‌دهد هر دو رله همان ده رویداد را به Kafka می‌دادند.

M3 مهم‌تر از آن است که به‌نظر می‌رسد: بازیابی پس از Crash امروز **رایگان** است،
اما دقیقاً به این دلیل که هیچ رزروی وجود ندارد. همان خاصیتی که M3 را حل می‌کند،
M1 را می‌سازد. هر طراحی Claim بادوام، M1 را می‌بندد و در عوض **موظف** می‌شود
برای M3 پاسخی صریح داشته باشد — این‌جاست که Expiry از یک جزئیات به یک الزام
تبدیل می‌شود.

M4 با هیچ طراحی Claimی حل نمی‌شود؛ ذاتیِ At-Least-Once است.

### تفکیک تضمین‌ها

این ADR این شش را جدا نگه می‌دارد، چون خلط‌شان همان چیزی است که به ادعای نادرست
«SKIP LOCKED مانع انتشار تکراری است» انجامید:

| #   | تضمین                                              | امروز                     | با Option A              |
| --- | -------------------------------------------------- | ------------------------- | ------------------------ |
| G1  | نبودِ Claim تکراری هم‌زمان در طول یک Lease زنده    | ❌                        | ✅                       |
| G2  | بازیابی پس از Crash مدعی                           | ✅ (چون رزروی نیست)       | ✅ (با Expiry)           |
| G3  | تحویل حداقل‌یک‌بار پس از Crash میان Publish و Mark | ذاتی                      | **ذاتی — تغییر نمی‌کند** |
| G4  | ایدمپوتنسی مصرف‌کننده (A-09)                       | لازم                      | **همچنان لازم**          |
| G5  | ترتیب Kafka به‌ازای هر Aggregate                   | ❌ در برابری `created_at` | مشروط — بخش Ordering     |
| G6  | ترتیب قطعی انتخاب در پایگاه داده                   | ❌                        | ✅ با `created_at, id`   |

**هیچ گزینه‌ای Exactly-Once نمی‌دهد و این ADR چنین ادعایی نمی‌کند.** G3 با
At-Least-Once زندگی می‌کند؛ کاری که می‌شود کرد کوچک‌کردن پنجره است، نه صفرکردنش.

### چرا ایدمپوتنسی مصرف‌کننده کافی نیست

A-09 مصرف‌کننده ایدمپوتنت می‌خواهد و آن **اثر تجاری** تکراری را مهار می‌کند. اما
حذف نمی‌کند:

- انتشار تکراری در Kafka و مصرف پهنای‌باند و Retention؛
- بار روی Broker و روی همه مصرف‌کننده‌ها؛
- **ریسک ترتیب**: دو رله که یک Batch را هم‌زمان منتشر می‌کنند می‌توانند دو رویداد
  یک Aggregate را با ترتیب درهم به یک Partition برسانند. ایدمپوتنسی این را
  درست نمی‌کند، چون هر دو رویداد معتبرند و ترتیبشان معنا دارد.

## Decision

**Option A — Claim بادوام با Fencing Token و تمدید Lease.**

الگو تازه نیست: `document-service` همین را برای اسکن بدافزار دارد
(`scan_lease_owner` و `scan_lease_expires_at`، ADR-049). اما آن الگو **عیناً**
کافی نیست و بازبینی محصول دو نقص را در نسخهٔ اول همین ADR گرفت که هر دو اینجا
اصلاح شده‌اند: Fencing و تمدید.

### Fencing — چه چیزی مالکیت را تعیین می‌کند

**نسخهٔ اول این ADR غلط بود.** پیشنهاد کرده بود مالکیت با `claim_owner`
(شناسهٔ پروسه) و شرط `claim_expires_at > now()` تعیین شود. هر دو نادرست‌اند:

- `claim_owner` **در سطح پروسه** است. یک پروسه که دو بار پیاپی Claim می‌کند،
  هر دو بار همان Owner را دارد؛ پس Owner نمی‌تواند Claim اول را از Claim دوم
  تشخیص دهد. Fence نیست، برچسب است.
- `claim_expires_at > now()` به‌عنوان شرط Ack **دو خطا** دارد. مالک قانونی‌ای
  که Lease‌اش منقضی شده اما **هیچ‌کس** ردیف را پس نگرفته، حق دارد Ack کند —
  رویداد را منتشر کرده و اگر Ack نکند دوباره منتشر می‌شود. و بالعکس، انقضا
  به‌تنهایی جلوی مدعی کهنه را نمی‌گیرد اگر ساعت‌ها یا مرزها لغزش داشته باشند.

**تصمیم:** هر تلاش Claim یک **Token یکتا و غیرقابل‌حدس** تولید می‌کند
(`claim_token`, UUIDv4). Token **تنها مرجع مالکیت** است.

| ستون               | نقش                                                            |
| ------------------ | -------------------------------------------------------------- |
| `claim_token`      | **Fence معتبر.** هر Mutation مشروط به تطابق دقیق آن است.       |
| `claim_owner`      | فقط **فراداده تشخیصی** — «کدام پروسه». هیچ تصمیمی روی آن نیست. |
| `claim_expires_at` | فقط **شرط واجد شرایط بودن برای پس‌گرفتن**. شرط Ack نیست.       |
| `claim_count`      | چند بار این ردیف Claim شده. رصدی.                              |

قاعدهٔ دقیق:

- **انقضا** ردیف را برای Claim مجدد **واجد شرایط** می‌کند.
- انقضا به‌تنهایی حق Ack دارندهٔ فعلی Token را **سلب نمی‌کند**.
- به‌محض اینکه مدعی دیگری ردیف را پس بگیرد، `claim_token` عوض می‌شود و از آن
  لحظه هر Mutation مدعی قبلی **صفر ردیف** را لمس می‌کند.

توالی‌ای که باید آزمون شود:

| گام | سناریو ۱ (مجاز)                       | سناریو ۲ (Fence می‌شود)               |
| --- | ------------------------------------- | ------------------------------------- |
| ۱   | A با Token A ردیف را Claim می‌کند     | A با Token A ردیف را Claim می‌کند     |
| ۲   | Lease منقضی می‌شود                    | Lease منقضی می‌شود                    |
| ۳   | کسی پس نمی‌گیرد؛ Token هنوز A است     | B با Token B پس می‌گیرد               |
| ۴   | A با Token A، Ack می‌کند → **۱ ردیف** | A با Token A، Ack می‌کند → **۰ ردیف** |

### شکل SQL اتمیک — Claim

```sql
UPDATE outbox_message AS o
   SET claim_token      = $token,
       claim_owner      = $owner,
       claim_expires_at = now() + make_interval(secs => $leaseSeconds::double precision),
       claim_count      = o.claim_count + 1
  FROM (
    SELECT id
      FROM outbox_message
     WHERE published_at IS NULL
       AND (claim_expires_at IS NULL OR claim_expires_at <= now())
       AND (next_attempt_at IS NULL OR next_attempt_at <= now())
     ORDER BY created_at, id
     LIMIT $limit
     FOR UPDATE SKIP LOCKED
  ) AS due
 WHERE o.id = due.id
RETURNING o.id, o.aggregate_type, ..., o.claim_token;
```

یک جمله؛ انتخاب و رزرو در یک تراکنش ضمنی. `claim_token` در `RETURNING` است، پس
رله دقیقاً همان Fenceای را در دست دارد که پایگاه داده نوشت — نه چیزی که خودش
تولید و امیدوار بوده بنشیند.

`FOR UPDATE SKIP LOCKED` در زیرپرسش می‌ماند، اما **نه به‌عنوان رزرو** — فقط
برای اینکه دو Claimکننده هم‌زمان روی یک ردیف سریالی نشوند. رزرو کار Token است.

### Ack، شکست، آزادسازی و تمدید — همه مشروط بر Token

```sql
-- Ack. هیچ شرط زمانی ندارد: Token تنها Fence است.
UPDATE outbox_message
   SET published_at = now(), claim_token = NULL, claim_owner = NULL,
       claim_expires_at = NULL, next_attempt_at = NULL
 WHERE id = ANY($ids) AND claim_token = $token AND published_at IS NULL;

-- شکست: آزادسازی + زمان‌بندی تلاش بعدی، با ساعت پایگاه داده.
UPDATE outbox_message
   SET attempts = attempts + 1,
       last_error = $error,
       next_attempt_at = now() + make_interval(secs =>
         least(power(2, least(attempts, 10)) * $baseSeconds, $maxBackoffSeconds)::double precision),
       claim_token = NULL, claim_owner = NULL, claim_expires_at = NULL
 WHERE id = $id AND claim_token = $token;

-- آزادسازی بدون شمردن شکست (خاموشی تمیز).
UPDATE outbox_message
   SET claim_token = NULL, claim_owner = NULL, claim_expires_at = NULL
 WHERE id = ANY($ids) AND claim_token = $token;

-- تمدید.
UPDATE outbox_message
   SET claim_expires_at = now() + make_interval(secs => $leaseSeconds::double precision)
 WHERE id = ANY($ids) AND claim_token = $token AND published_at IS NULL;
```

هر چهار مورد `claim_token = $token` دارند و **هیچ‌کدام** `claim_expires_at`
را شرط نمی‌کنند. مدعی کهنه‌ای که Token‌اش عوض شده، هیچ‌یک از این چهار را نمی‌تواند
اجرا کند — نه Ack، نه Fail، نه Release، نه Renew.

### تمدید Lease — چرا اجباری است

**نسخهٔ اول ادعا کرده بود «انتشار در حد میلی‌ثانیه است». این ادعا اندازه‌گیری
نشده بود و غلط است.**

پیکربندی واقعی KafkaJS در این Repository (`kafka.publisher.ts`، هشت سرویس یکسان):

| تنظیم                   | مقدار                        | منبع                      |
| ----------------------- | ---------------------------- | ------------------------- |
| `retries`               | **۸**                        | `new Kafka({ retry: … })` |
| `initialRetryTime`      | ۳۰۰ms                        | همان                      |
| `maxRetryTime`          | ۳۰٬۰۰۰ms                     | پیش‌فرض kafkajs@2.2.4     |
| `factor` / `multiplier` | ۰٫۲ / ۲                      | پیش‌فرض                   |
| `requestTimeout`        | **۳۰٬۰۰۰ms**                 | پیش‌فرض                   |
| `acks`                  | `-1` (همه)                   | `sendBatch`               |
| `maxInFlightRequests`   | ۱                            | Producer                  |
| `OUTBOX_BATCH_SIZE`     | پیش‌فرض ۱۰۰، حداکثر **۱۰۰۰** | `kafkaEnvSchema`          |

کران بالای محاسبه‌شده از همین اعداد:

| مسیر                                         | بدترین حالت     |
| -------------------------------------------- | --------------- |
| یک `sendBatch` (۹ تلاش × ۳۰s + ۱۰۹s Backoff) | **۳۷۹ ثانیه**   |
| `publishIndividually` با Batch ۱۰۰           | **≈ ۱۰٫۵ ساعت** |
| `publishIndividually` با Batch ۱۰۰۰          | **≈ ۱۰۵ ساعت**  |

مسیر Fallback ردیف‌به‌ردیف `publish([row])` صدا می‌زند و هر کدام یک `sendBatch`
کامل با همان Retry است. یعنی **زمان انتشار به‌هیچ‌وجه به‌طور مفید کران‌دار نیست**
و هیچ عدد ثابتی برای Lease نمی‌تواند هم‌زمان «بلندتر از بدترین انتشار» و «کوتاه
به‌اندازهٔ یک بازیابی معقول» باشد.

**پس تمدید اجباری است.** بررسی انقضا پیش از Publish کافی نیست، چون انقضا
می‌تواند **در حین** I/O کافکا رخ دهد.

### چهار راه، و انتخاب

| راه                                          | چرا رد/انتخاب                                                                                                                                    |
| -------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------ |
| **تمدید دوره‌ای در حین Batch** ✅ **انتخاب** | تنها راهی که هر دو مسیر (Batch و Fallback) را یکنواخت پوشش می‌دهد و به کران‌دار بودن Kafka وابسته نیست                                           |
| تمدید پیش از هر Publish تکی                  | فقط مسیر Fallback را می‌پوشاند؛ یک `sendBatch` ۳۷۹ ثانیه‌ای همچنان Lease را رد می‌کند                                                            |
| مهلت کل انتشار کوتاه‌تر از Lease             | نیازمند پایین‌آوردن `requestTimeout` و `retries` است — یعنی معاوضهٔ دوام با تأخیر، و رها کردن یک Broker کند. تصمیم محصولی است، نه جزئیات این ADR |
| آزادسازی و Claim تکی                         | تعداد Round-trip پایگاه داده را برابر اندازهٔ Batch می‌کند و مسئلهٔ ردیف تکیِ کند را حل نمی‌کند                                                  |

### قرارداد تمدید — مالکیت جزئی

تمدید **شناسه‌های تمدیدشده را برمی‌گرداند**، نه فقط تعدادشان:

```sql
UPDATE outbox_message
   SET claim_expires_at = now() + make_interval(secs => $leaseSeconds::double precision)
 WHERE id = ANY($ids) AND claim_token = $token AND published_at IS NULL
RETURNING id;
```

رله یک مجموعهٔ `ownedUnacknowledgedIds` نگه می‌دارد که با Claim پر می‌شود.

**اصلاح یک نقص در نسخهٔ قبلی همین ADR.** نسخهٔ قبل می‌گفت اگر تمدید کمتر از
انتظار برگرداند، رله «Heartbeat را متوقف می‌کند و هیچ Mutation دیگری روی
**هیچ** ردیفی نمی‌زند». این غلط است: اگر از صد ردیف، نود ردیف هنوز با Token
تطبیق دارند، آن نود **قانوناً مال ما هستند**. Ack نکردنشان پس از انتشار موفق،
آن‌ها را منتشرنشده رها می‌کند و یک بازپخش کاملاً غیرلازم را **تضمین** می‌کند.

قاعدهٔ درست، در هر Tick تمدید:

1. `renewed` = مجموعهٔ شناسه‌های برگشتی.
2. `lost` = `ownedUnacknowledgedIds − renewed`.
3. برای `lost`: `ack_fenced_total` به اندازهٔ `|lost|` بالا می‌رود و از
   `ownedUnacknowledgedIds` **حذف** می‌شوند. هیچ Mutation بعدی روی آن‌ها زده
   نمی‌شود.
4. برای `renewed`: Heartbeat **ادامه می‌یابد**.
5. هر شناسهٔ `renewed` که انتشارش موفق بوده، **Ack می‌شود**.
6. Heartbeat فقط وقتی متوقف می‌شود که `ownedUnacknowledgedIds` تهی شود.

Fencing در SQL از خرابی داده جلوگیری می‌کند؛ این قاعده از **کارِ دورریخته**
جلوگیری می‌کند. آن دو یکی نیستند.

### پروتکل خاموشی — سه حالت

نسخهٔ قبل می‌گفت `stop()` منتظر Batch می‌ماند و ردیف‌های Ackنشده را Release
می‌کند. این هم ناکافی است: یک درخواست Kafka می‌تواند **ساعت‌ها** در پرواز
بماند و نتیجه‌اش **نامعلوم** باشد. Release کردن ردیفی که شاید همین حالا منتشر
شده، یک بازپخش قطعی می‌سازد.

برای هر ردیف در `ownedUnacknowledgedIds`، دقیقاً یکی از سه حالت:

| حالت                         | اقدام                                                                                                           |
| ---------------------------- | --------------------------------------------------------------------------------------------------------------- |
| **هنوز فرستاده نشده**        | Release مشروط بر Token — امن است، چون هیچ‌چیز به Broker نرفته                                                   |
| **تمام‌شده با نتیجهٔ معلوم** | Ack یا Fail مشروط بر Token، طبق همان نتیجه                                                                      |
| **در پرواز / نتیجه نامعلوم** | **Release نکن.** مالکیت را در پنجرهٔ مهلت‌دار نگه دار؛ سپس تمدید را قطع کن و بگذار Lease به‌طور طبیعی منقضی شود |

حالت سوم دلیل دارد: تنها چیزی که می‌دانیم «نمی‌دانیم» است. Release یعنی ردیف
بلافاصله دوباره منتشر می‌شود حتی اگر بار اول رسیده باشد؛ انتظار تا انقضای
طبیعی یعنی همان تکرار **فقط اگر** واقعاً لازم باشد و پس از تأخیری که در آن
درخواست در پرواز فرصت تمام‌شدن داشته است.

- **مهلت خاموشی:** `OUTBOX_SHUTDOWN_GRACE_SECONDS`، پیش‌فرض ۳۰، بازهٔ
  `int, min(0), max(300)`. تا این مدت، Heartbeat برای ردیف‌های در پرواز ادامه
  می‌یابد تا مالکیت حفظ شود.
- **خاموشی هرگز بی‌نهایت منتظر نمی‌ماند:** با پایان مهلت، رله تمدید را قطع
  می‌کند، آنچه را که هنوز نامعلوم است **رها می‌کند بدون Release**، و پروسه
  خارج می‌شود. Lease خودش منقضی می‌شود و مدعی بعدی ردیف را برمی‌دارد.
- **درخواست در پرواز پس از ازدست‌رفتن مالکیت:** KafkaJS راهی برای لغو یک
  `sendBatch` ندارد. درخواست ممکن است کامل شود و رویداد **به Kafka برسد**. رله
  آن را Ack نمی‌کند (دیگر مالک نیست)، مدعی جدید دوباره منتشر می‌کند، و نتیجه
  **تحویل تکراری** است — همان At-Least-Once که G3 توصیفش می‌کند.

### زمان‌بندی Heartbeat — با عدد، نه ادعا

نسخهٔ قبل می‌گفت فاصله `Lease/3` با کف ۵ ثانیه و کمینهٔ Lease ده ثانیه، و ادعا
می‌کرد «یک تمدید ازدست‌رفته کشنده نیست». **این ادعا با آن اعداد برقرار نبود:**
با Lease ده ثانیه، فاصله `max(10/3, 5) = 5` می‌شد، تلاش‌ها در ۵ و ۱۰ ثانیه —
و تلاش دوم دقیقاً روی لحظهٔ انقضا می‌افتاد. یعنی تحمل صفر.

**فرمول اصلاح‌شده:**

```
interval          = leaseSeconds / 4
renewalDeadline   = min(interval / 2, 30s)      -- statement_timeout همان فراخوان
ownershipUnknownAt = lastSuccessfulRenewAt + leaseSeconds - renewalDeadline
```

کمینهٔ Lease از ۱۰ به **۲۰ ثانیه** بالا می‌رود تا فاصله زیر پنج ثانیه نرود.

| Lease          | فاصله | تلاش‌ها در      | مهلت هر فراخوان | حاشیه پس از آخرین تلاش | تحمل تمدید ازدست‌رفته |
| -------------- | ----- | --------------- | --------------- | ---------------------- | --------------------- |
| ۲۰s (کمینه)    | ۵s    | ۵، ۱۰، ۱۵       | ۲٫۵s            | ۵s                     | **۲**                 |
| ۶۰s (پیش‌فرض)  | ۱۵s   | ۱۵، ۳۰، ۴۵      | ۷٫۵s            | ۱۵s                    | **۲**                 |
| ۳۶۰۰s (بیشینه) | ۹۰۰s  | ۹۰۰، ۱۸۰۰، ۲۷۰۰ | ۳۰s (سقف)       | ۹۰۰s                   | **۲**                 |

سه تلاش پیش از انقضا در هر پیکربندی، یعنی **دو تمدید ازدست‌رفته قابل تحمل
است** — این بار واقعاً.

- **مهلت فراخوان تمدید:** با `statement_timeout` روی همان فراخوان اعمال می‌شود،
  نه با Timer برنامه. یک تمدید معلق نباید بی‌صدا حاشیه را بخورد.
- **خطای گذرا در تمدید:** یک‌بار بلافاصله دوباره تلاش می‌شود؛ اگر آن هم شکست
  خورد، به Tick بعدی موکول می‌شود. هیچ Mutation دیگری در این فاصله زده نمی‌شود.
- **نقطه‌ای که مالکیت «نامعلوم» می‌شود:** وقتی `now() > ownershipUnknownAt`.
  از آن لحظه رله هیچ Ack و هیچ Fail نمی‌زند — نه چون Fencing کافی نیست (هست)،
  بلکه چون نتیجه‌اش دیگر قابل پیش‌بینی نیست و باید در Metric دیده شود.

### پیکربندی

| متغیر                              | پیش‌فرض | اعتبارسنجی                    |
| ---------------------------------- | ------- | ----------------------------- |
| `OUTBOX_CLAIM_LEASE_SECONDS`       | `60`    | `int`، `min(20)`، `max(3600)` |
| `OUTBOX_CLAIM_BACKOFF_SECONDS`     | `5`     | `int`، `min(1)`، `max(3600)`  |
| `OUTBOX_CLAIM_BACKOFF_MAX_SECONDS` | `3600`  | `int`، `min(1)`، `max(86400)` |
| `OUTBOX_SHUTDOWN_GRACE_SECONDS`    | `30`    | `int`، `min(0)`، `max(300)`   |

۶۰ ثانیه **پس از** تحلیل بالا انتخاب شد، نه پیش از آن: با تمدید، Lease دیگر
لازم نیست از بدترین انتشار بلندتر باشد — فقط باید سه فاصلهٔ تمدید در آن جا شود
و از تأخیر بازیابی قابل‌قبول کوتاه‌تر بماند. کف از ۱۰ به **۲۰** ثانیه بالا رفت
تا `interval = Lease/4` زیر پنج ثانیه نرود؛ جدول زمان‌بندی بالا نشان می‌دهد چرا
کف ۱۰ ثانیه تحمل ادعاشده را نمی‌داد.

### Backoff — تناقض نسخهٔ اول

نسخهٔ اول می‌گفت «Backoff از `attempts` می‌آید»، اما شرط Claim هیچ فیلد زمانی
نداشت. یعنی ردیف مسموم بلافاصله در Poll بعدی (۵۰۰ms) دوباره Claim می‌شد و
Batch را تا ابد اشغال می‌کرد. **ادعایی بود که Schema پیشنهادی پیاده نمی‌کرد.**

**Option 1 انتخاب شد:** ستون `next_attempt_at` اضافه می‌شود و شرط Claim
`next_attempt_at IS NULL OR next_attempt_at <= now()` را دارد.

- **محاسبه:** تماماً با `now()` پایگاه داده — هیچ `Date.now()` جاوااسکریپتی، تا
  Skew میان Replicaها بی‌اثر باشد.
- **فرمول:** `min(2^min(attempts,10) × base, max)` — نمایی و سقف‌دار.
- **Reset:** Ack موفق `next_attempt_at` را `NULL` می‌کند.
- **انقضای Lease** `next_attempt_at` را **تغییر نمی‌دهد**: انقضا شکست نیست.
- **Index:** در Index جزئی Claim گنجانده می‌شود.

| گزینه                           | مزیت                  | عیب                                                                                                                                | چرا رد شد                                            |
| ------------------------------- | --------------------- | ---------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------- |
| **B — قفل نگه‌داشته در تراکنش** | ساده‌ترین؛ G1 دقیق    | تراکنش و اتصال در طول I/O کافکا باز می‌ماند. با کران ۳۷۹ ثانیه‌ای که اندازه‌گیری شد، یعنی یک اتصال تا ۶ دقیقه اشغال و Vacuum مسدود | روی مسیر داغ یک سرویس مالی غیرقابل قبول              |

## Ordering

### وضعیت امروز، اثبات‌شده

`created_at` از نوع `timestamp(3)` است — دقت میلی‌ثانیه. ULID با `ulid()` ساده
تولید می‌شود و `monotonicFactory` هیچ‌جا استفاده نشده. اندازه‌گیری:

```
same-ms ULIDs generated in sorted order? false
inversions among 12 same-ms ULIDs: 6
cross-ms a<b (timestamp prefix dominates)? true
```

ULID **میان** میلی‌ثانیه‌ها ترتیب ساخت را حفظ می‌کند، **درون** یک میلی‌ثانیه
تصادفی است.

### تصمیم

**`ORDER BY created_at, id`** — ترتیب کلی، قطعی و پایدار برای انتخاب از پایگاه
داده (G6).

**آنچه تضمین نمی‌کند:** ترتیب معنایی رویدادهای یک Aggregate (G5). دو رویداد یک
Aggregate در یک میلی‌ثانیه می‌توانند وارونه به Partition برسند. G5 **با D-026
حل نمی‌شود** و به‌عنوان **D-027** جداگانه ثبت شده است؛ گزینه‌هایش
(`BIGSERIAL`، `aggregate_sequence`، پذیرش محدودیت) ADR خودشان را می‌خواهند.

## Consequences

**مثبت:** G1 با Fencing واقعی برقرار می‌شود؛ G6 برقرار می‌شود؛ ردیف مسموم دیگر
Batch را اشغال نمی‌کند؛ الگو با ADR-049 هم‌خانواده می‌ماند اما Fence دارد.

**منفی:**

- پنج ستون، سه Index و پنج CHECK در **هشت** پایگاه داده.
- G3 حل نمی‌شود و ادعا هم نمی‌شود. At-Least-Once باقی است؛ A-09 الزامی است.
- G5 حل نمی‌شود (D-027).
- در طول Rolling Deployment، G1 برقرار نیست.
- Heartbeat تمدید یعنی نوشتن اضافه روی پایگاه داده در طول هر انتشار.
- Claim از `SELECT` به `UPDATE` تبدیل می‌شود؛ بار WAL بالا می‌رود.
- ردیفی که مدعی‌اش مرده تا انقضای Lease معطل می‌ماند.
- تحویل تکراری هنگام ازدست‌رفتن مالکیت با درخواست در پرواز، **باقی می‌ماند**.

**خنثی:** `pendingCount()`، `rasta_outbox_pending_total` و `purgePublished`
بدون تغییر.

## Compliance

- **بیست‌وچهار** آزمون قطعی در طرح اجرا.
- هیچ Comment یا سندی نباید ادعا کند `SKIP LOCKED` به‌تنهایی مانع انتشار
  تکراری است، و هیچ‌کدام نباید Exactly-Once ادعا کند.
- بازبینی: هیچ Mutation ردیف Outbox بدون شرط `claim_token` نوشته نشود.
