## ۳ — فازهای اتمیک

هر فاز به‌تنهایی Build و Deploy می‌شود و به‌تنهایی برگشت‌پذیر است.

### B1 — Schema، افزایشی و بی‌اثر

سه Migration به‌ازای هر سرویس (۲۴ عدد)، هرکدام با `down.sql`:

| Migration                     | محتوا                                                                                       |
| ----------------------------- | ------------------------------------------------------------------------------------------- |
| `_outbox_stream_sequence`     | جدول `outbox_stream_sequence`                                                               |
| `_outbox_stream_seq_columns`  | `stream_seq BIGINT NULL`, `is_stream_head BOOLEAN NOT NULL DEFAULT false`, Index یکتای جزئی |
| `_outbox_stream_head_indexes` | چهار Index سرصف                                                                             |

قواعد الزامی، از درس‌های ADR-050:

- `SET LOCAL lock_timeout = '3s'` در سر هر Migration؛
- **بدون** `CREATE INDEX CONCURRENTLY` (Prisma هر فایل را در تراکنش می‌پیچد ⇒
  SQLSTATE 25001)؛ همه با `IF NOT EXISTS` تا مسیر دستی برای صف بزرگ باز بماند؛
- هر `down.sql` باید در `pnpm test:migration` (چرخهٔ up → down → up روی هر هشت
  پایگاه داده) سبز شود.

**پس از B1 هیچ رفتاری عوض نشده.** Relay قدیمی بدون تغییر کار می‌کند.

### B2 — Backfill، دسته‌ای

R7 اندازه گرفت که یک `UPDATE` درجا جدول را ~۲ برابر می‌کند. پس:

- دسته‌های ۵٬۰۰۰ ردیفی بر اساس `(topic, partition_key)`، با `VACUUM` میانی؛
- ترتیب تخصیص همان ترتیب قطعی Claim: `row_number() OVER (PARTITION BY topic,
partition_key ORDER BY created_at, id)` — پس تکرارپذیر است؛
- پر کردن `outbox_stream_sequence` از `max(stream_seq)`؛
- `is_stream_head` فقط برای پایین‌ترین `stream_seq` منتشرنشدهٔ هر جریان.

**ردیف‌های قدیمی بدون توالی:** پس از Backfill هیچ ردیف منتشرنشده‌ای بدون توالی
نمی‌ماند. ردیف‌های منتشرشده دست‌نخورده می‌مانند (`purgePublished` هفت‌روزه
پاکشان می‌کند). Index یکتا `WHERE stream_seq IS NOT NULL` است تا در پنجرهٔ
Backfill معتبر بماند.

### B3 — تخصیص در سمت تولیدکننده

`buildOutboxRow` توالی می‌گیرد و `streamSeq`/`streamKey` را در Envelope
می‌گذارد. تخصیص **درون همان تراکنش دامنه** و پیش از درج ردیف Outbox.

هنوز هیچ مصرف‌کننده‌ای چیزی اجبار نمی‌کند و Claim تغییر نکرده. اثر بیرونی: دو
فیلد اختیاری تازه در Envelope.

### B4 — Claim با مسدودسازی سرصف، فقط STRICT

`is_stream_head` به چهار جریان واجد شرایط ADR-050 اضافه می‌شود؛ `markPublished`
داخل تراکنش خودش `published_seq` را جلو می‌برد و سرصف بعدی را علامت می‌زند.

**Feature Flag به‌ازای سرویس**، پیش‌فرض خاموش، تا انتشار مرحله‌ای ممکن باشد.

**ماتریس کلاس — هر هشت سرویس، پس از بسته شدن Q-36:**

| سرویس             | جریان (`topic + partitionKey`)                        | کلاس       | Flag لازم؟ |
| ----------------- | ----------------------------------------------------- | ---------- | ---------- |
| `document`        | `rasta.document.v1 + documentId`                      | STRICT     | بله        |
| `marketplace`     | `rasta.marketplace.v1 + orderId`                      | STRICT     | بله        |
| `marketplace`     | سایر کلیدها                                           | DETECT     | خیر        |
| `economic`        | `rasta.economic.v1 + transactionId`                   | STRICT     | بله        |
| `economic`        | `walletId`, `journalId`, `paymentIntentId`, `reward*` | DETECT     | خیر        |
| **`fleet`**       | **`rasta.fleet.v1 + assetId`**                        | **STRICT** | **بله**    |
| **`fleet`**       | رویدادهای راننده (کلید `driverId`)                    | DETECT     | خیر        |
| **`maintenance`** | **`rasta.maintenance.v1 + assetId`**                  | **STRICT** | **بله**    |
| `asset`           | `rasta.asset.v1`, `rasta.insurance.v1`                | DETECT     | خیر        |
| `identity`        | `rasta.identity.v1`                                   | DETECT     | خیر        |
| `organization`    | `rasta.organization.v1`                               | DETECT     | خیر        |

**نکتهٔ الزامی دربارهٔ `fleet` و `maintenance` — بدون آن، B4 روی این دو غلط
پیاده می‌شود.** R4 اندازه گرفت که این دو دامنه — برخلاف `economic` و
`marketplace` — **هیچ قفل دامنه‌ای روی مرز `assetId` ندارند**: قفل موجود
`maintenance` روی `repair_order` است و در `fleet` قفل صریحی روی `asset` یافت
نشد. پس این طرح **ادعا نمی‌کند** قفل‌های موجود کافی‌اند. نقطهٔ سریالایز شدن،
**قفل ردیف `outbox_stream_sequence` برای `(topic, assetId)`** است که در B3
گرفته می‌شود و تا Commit نگه داشته می‌شود. اگر آن قفل نباشد، دو تراکنش هم‌زمان
روی یک دستگاه می‌توانند با ترتیب Commit وارونه شماره بگیرند و STRICT بی‌اثر
می‌شود.

### B5 — تشخیص سمت مصرف‌کننده

`EventConsumer` جدول `stream_progress` به‌ازای `(streamKey, consumerName)`
نگه می‌دارد: `seq = last + 1` بپذیر · `≤ last` کهنه، رد کن و بشمار ·
`> last + 1` شکاف، تا Timeout مرزدار نگه دار سپس هشدار.

Envelope بدون `streamSeq` (تولیدکنندهٔ قدیمی در انتشار مرحله‌ای) مثل امروز
پردازش می‌شود — بدون تشخیص، بدون خطا.

### B6 — رصدپذیری و Runbook

متریک‌ها: `outbox_stream_head_age_seconds` · `outbox_blocked_streams` ·
`consumer_stream_gap_total` · `consumer_stale_event_total` ·
`consumer_reorder_buffer_size` · `outbox_stream_seq_allocation_wait_seconds`.

هشدارها: جریان مسدود بیش از آستانه؛ شکاف حل‌نشده بیش از Timeout.

**Runbook تازه** برای «جریان مسدود بر اثر رویداد مسموم» با دستور صریح «رد کردن
با ثبت شکاف» — که هرگز خودکار نیست. بدون این، B4 نباید روشن شود.

## ۴ — ترتیب استقرار

`B1 → B2` روی هر هشت پایگاه داده · `B3` روی همهٔ تولیدکنندگان · `B5` روی همهٔ
مصرف‌کنندگان **پیش از** `B4` · سپس `B4` سرویس‌به‌سرویس با Flag، به این ترتیب:

`document` (چهار رویداد، یک کلید، کم‌ریسک‌ترین) → **`fleet`** → **`maintenance`**
→ `marketplace` → `economic` (مالی، آخر).

`fleet` و `maintenance` عمداً زود می‌آیند و نه آخر: هر دو STRICT تازه‌اند، هیچ
قفل دامنه‌ای پشتیبانشان نیست (§ B4)، و `assetId` یک دستگاه پرکار داغ‌ترین کلید
این طرح است. بهتر است رفتار سریالایز شدن و سرصف مسموم روی این دو زودتر و با
بار کمتر دیده شود تا روی جریان مالی.

**رفتار نسخهٔ مخلوط.** تولیدکنندهٔ قدیمی + مصرف‌کنندهٔ جدید ⇒ بدون `streamSeq`،
بدون تشخیص. تولیدکنندهٔ جدید + مصرف‌کنندهٔ قدیمی ⇒ فیلد اختیاری نادیده. Relay
قدیمی + Schema جدید ⇒ `is_stream_head` را نمی‌بیند، مثل امروز رفتار می‌کند.
هیچ ترکیبی خطا نمی‌دهد.

**Rollback.** هر فاز مستقل: Flag را ببند (B4) · نسخهٔ مصرف‌کننده را برگردان
(B5) · نسخهٔ تولیدکننده را برگردان (B3) · `down.sql` ها (B1). ستون‌های
Backfillشده بی‌ضررند.

## ۵ — ماتریس آزمون قطعی

بدون `sleep`، بدون حلقهٔ Retry، بدون سوئیچ Planner — همان قواعد ADR-050. هر
مورد با PostgreSQL واقعی؛ موارد Broker با Kafka واقعی و Topic/Group یکتا.

| #   | آزمون                             | سناریو                                    | انتظار                                       |
| --- | --------------------------------- | ----------------------------------------- | -------------------------------------------- |
| ۱   | رویداد هم‌میلی‌ثانیه              | ۱۲ رویداد یک جریان، یک `created_at`       | `streamSeq` اکیداً افزایشی                   |
| ۲   | تخصیص = ترتیب Commit              | بازتولید R4 با تخصیص                      | تراکنش دوم تا Commit اولی بلوکه              |
| ۳   | Rollback بدون شکاف                | تخصیص، سپس Rollback                       | شمارنده برگردد؛ بدون شکاف                    |
| ۴   | سبقت Retry (بازتولید R2)          | سرصف در Backoff، بعدی تازه                | STRICT: هیچ‌کدام · DETECT: بعدی + شکاف       |
| ۵   | دو Relay (بازتولید R3، ≥۲۰ تکرار) | Claim هم‌زمان یک جریان                    | STRICT: **۰ وارونگی** روی Broker             |

| ۱۳  | هم‌ارزی                           | خروجی Claim جدید = قدیم وقتی همه سرصف‌اند | ردیف‌به‌ردیف یکسان                           |

**ماتریس دوم — جریان‌های دارایی STRICT (Q-36).** موارد ۱ تا ۱۴ عمومی‌اند؛ این
هفت مورد **به‌ازای هر یک از دو جریان** `rasta.fleet.v1 + assetId` و
`rasta.maintenance.v1 + assetId` جداگانه اجرا می‌شوند، چون هیچ قفل دامنه‌ای
پشتیبانشان نیست و تنها نقطهٔ سریالایز، قفل ردیف شمارنده است.

| #   | آزمون                                  | سناریو                                                          | انتظار                                                                 |

| A۳  | Lease زنده / Crash / بازپس‌گیری        | سرصف زیر Lease زندهٔ Relay مرده (بازتولید R5)                   | رویداد بعدی همان دستگاه Claim **نشود**                                 |
| A۴  | دو Relay                               | دو Relay مستقل، یک `assetId`، ≥۲۰ تکرار (بازتولید R3)           | **صفر وارونگی** روی Broker                                             |
| A۵  | سرصف مسموم + بازیابی اپراتور           | سرصف به سقف تلاش برسد                                           | جریان همان دستگاه مسدود؛ متریک و هشدار؛ رفع فقط با دستور صریح اپراتور  |

| A۷  | **نبود ترتیب میان‌Topic — آزمون منفی** | یک رویداد `fleet` و یک رویداد `maintenance` با **یک `assetId`** | آزمون **تأیید کند هیچ ترتیبی میانشان ادعا نمی‌شود**؛ هر شکل رسیدن مجاز |

A۷ عمداً یک آزمون **منفی** است: وجودش مانع می‌شود کسی بعداً از STRICT بودن هر دو
نتیجه بگیرد که میانشان ترتیبی هست. دو Topic، دو پایگاه داده، دو شمارندهٔ مستقل.

## ۶ — Fixture کارایی و آستانه‌های پذیرش

آستانه‌ها از اندازه‌گیری R7–R10 می‌آیند، نه از عدد اختراعی.

| Fixture | شکل                                                    | چرا                                                                 |
| ------- | ------------------------------------------------------ | ------------------------------------------------------------------- |
| F1      | ۲۰۰٬۰۰۰ ردیف / ۲۰٬۰۰۰ جریان، هم‌شکل ADR-050            | مقایسه‌پذیری با پایهٔ موجود                                         |
| F2      | ۲۰۰٬۰۰۰ ردیف / ۲٬۰۰۰ جریان، **سرصف هرکدام در Backoff** | حالت متخاصم R9 — همان که شکل بدیهی را شکست                          |
| F3      | مثل F2 ولی سرصف‌ها **سررسیدشده**                       | چون R10 مسیر `retry` سرصف را اجرا **نکرد**                          |
| F4      | یک جریان داغ با ۵۰٬۰۰۰ ردیف — **کلید `assetId`**       | سریالایز شدن D-2 و توان عملیاتی؛ پس از Q-36 واقعی‌ترین کلید داغ طرح |

| آستانه                                      | مقدار                               | مبنا                                         |
| ------------------------------------------- | ----------------------------------- | -------------------------------------------- |
| ردیف حذف‌شده با Filter، هر جریان واجد شرایط | **≤ `۱۰ × LIMIT`**                  | سقف موجود ADR-050                            |
| زمان Claim، F2                              | **≤ ۵ ms** (اندازه‌گیری R10: ۰٫۰۱۲) | R10 با فاصلهٔ ایمنی بزرگ                     |
| رشد Index روی F1                            | **≤ +۶۵٪**                          | R7 اندازه گرفت +۵۹٫۲٪                        |
| رشد جدول روی F1                             | **≤ +۸٪**                           | R7 اندازه گرفت +۵٫۸٪                         |
| اوج Backfill                                | **< ۱٫۳ برابر**                     | R7 با یک `UPDATE`: ~۲ برابر ⇒ دسته‌ای الزامی |
| تقویت قفل                                   | **بدتر از `۴ × limit` نشود**        | ADR-050 § Consequences                       |
| EXPLAIN، هر چهار جریان × هر چهار Fixture    | `Limit → LockRows → Index Scan`     | همان شکل نقشهٔ ADR-050                       |

هر عدد باید با `EXPLAIN (ANALYZE, BUFFERS)` روی PostgreSQL واقعی ثبت شود، بدون
`enable_seqscan = off` یا هر سوئیچ دیگر Planner.

## ۷ — امنیت و جداسازی مستأجر

`streamSeq` عدد و `streamKey` همان `partitionKey` امروز است ⇒ **بدون داده
حساس تازه** روی سیم. `outbox_stream_sequence` داده مستأجر ندارد؛ ولی
`partition_key` می‌تواند شناسهٔ متعلق به یک سازمان باشد، پس هر Query روی آن
باید در محدودهٔ پایگاه دادهٔ همان سرویس بماند (A-01) و آزمون ۱۲ الزامی است.
مجوزدهی تغییر نمی‌کند: هیچ Endpoint تازه‌ای اضافه نمی‌شود.

## ۸ — دروازه‌های پذیرش

Phase B وقتی «تمام» است که همهٔ این‌ها هم‌زمان برقرار باشند:

1. `pnpm verify` سبز؛
2. ۱۴ آزمون عمومی § ۵ سبز، بدون Flaky — هر ناپایداری صادقانه گزارش شود؛
3. **هفت آزمون A۱–A۷ به‌ازای هر دو جریان دارایی** (`fleet` و `maintenance`)
   سبز — یعنی ۱۴ اجرا، شامل آزمون منفی A۷ که تأیید می‌کند هیچ ترتیب
   میان‌Topicی ادعا نمی‌شود؛
4. `pnpm test:migration` روی هر هشت پایگاه داده سبز؛
5. شواهد EXPLAIN برای چهار جریان × چهار Fixture، درون آستانه‌های § ۶؛
6. R2، R3، R4، R5 و R6 روی **هر** جریان STRICT — از جمله دو جریان دارایی — **بازتولید نشوند**؛
7. آزمون جداسازی مستأجر سبز؛
8. Runbook «جریان مسدود» موجود و ارجاع‌شده از هشدار — **پیش‌شرط روشن کردن Flag روی `fleet` و `maintenance`**، چون این دو اولین STRICTهای بدون قفل دامنه‌ای‌اند؛
9. CI کامل `main` سبز، شامل هر هشت جفت Build/Trivy.

**پذیرش محصول جداست.** سبز شدن Phase B، D-027 را نمی‌بندد و ADR-051 را
`Accepted` نمی‌کند؛ آن یک تصمیم صریح صاحب محصول روی همین شواهد است — همان
تفکیکی که برای ADR-050 رعایت شد.
