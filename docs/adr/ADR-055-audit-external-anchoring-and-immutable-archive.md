# ADR-055: لنگرگذاری خارجی و بایگانی تغییرناپذیر شواهد حسابرسی

- **وضعیت:** Proposed
- **تاریخ:** 2026-09-12
- **مربوط به:** ADR-053 · `COM-009`
- **زمان هدف:** سخت‌سازی پس از MVP، پیش از استقرار Production با سطح اطمینان بالا
- **تصمیم‌های باز:** Q-44

## Context

ADR-053 زنجیرهٔ Hash را برای آشکارکردن تغییر رکوردهای `audit_event` و Head هر زنجیره تعریف می‌کند. این کنترل درون همان مرز
اعتماد پایگاه داده است: مهاجمی که اختیار کافی برای بازنویسی هم‌زمان رکوردها و Head داشته باشد می‌تواند زنجیره‌ای سازگار ولی جعلی
بسازد. بنابراین وضع موجود **Tamper-Evident در برابر تغییر عادی** است، نه Tamper-Proof و نه مستقل از مدیر پایگاه داده.

هدف این ADR «امنیت مطلق» نیست—چنین تضمینی وجود ندارد و `AGENTS.md` S-10 نیز ادعایش را ممنوع می‌کند. هدف، تبدیل دست‌کاری
موفق به حمله‌ای چندمرزی، پرهزینه و قابل‌کشف است: کنترل هم‌زمان برنامه، پایگاه داده، سامانهٔ مدیریت کلید و مخزن تغییرناپذیر.

## Decision

پس از تثبیت MVP، رستا یک قابلیت مستقل با عنوان **External Audit Anchoring and Immutable Archive** می‌سازد:

1. **Checkpoint دوره‌ای.** برای هر زنجیرهٔ `(organizationId, UTC month)`، Head و محدودهٔ Sequence در یک Canonical Manifest
   ثبت می‌شود. Manifest شامل Payload حسابرسی یا دادهٔ شخصی نیست؛ فقط شناسه‌های حداقلی، Digest، بازه، نسخهٔ الگوریتم و زمان است.
2. **امضای نامتقارن خارج از Process.** Digest با API امضای KMS یا HSM امضا می‌شود. سرویس فقط مجوز `Sign` و خواندن Public Key
   دارد؛ کلید خصوصی Export، Mount یا ذخیره نمی‌شود. شناسه و نسخهٔ کلید همراه Checkpoint ثبت می‌شود تا Rotation قابل‌بررسی باشد.
3. **مرز اعتماد مستقل.** Manifest امضاشده در Object Storage با قابلیت WORM/Object Lock و Retention قفل‌شده، ترجیحاً در
   Account/Project و نقش مدیریتی جدا از Runtime و DBA، ذخیره می‌شود. تغییر Retention، Legal Hold و حذف کلید نیز Audit و Alert دارد.
4. **اعتبارسنجی مستقل.** ابزار Verify با Public Key، نسخهٔ الگوریتم و نسخهٔ کلید، زنجیرهٔ پایگاه داده را به Checkpoint خارجی
   پیوند می‌دهد. نتیجه‌ها `VERIFIED`، `DIVERGED`، `UNANCHORED` یا `UNAVAILABLE` هستند؛ نبود لنگر هرگز به‌عنوان صحت گزارش نمی‌شود.
5. **عدم وابستگی مسیر کسب‌وکار.** ثبت رویداد و پاسخ HTTP منتظر KMS/HSM یا WORM نمی‌ماند. درخواست لنگرگذاری بادوام و قابل‌تکرار
   است؛ اختلال، Lag و وضعیت `UNANCHORED` می‌سازد و Alert می‌دهد، اما Auth یا عملیات دامنه را Fail-Open یا متوقف نمی‌کند.
6. **عدم امضای هر رکورد.** امضا بر Checkpoint دسته‌ای انجام می‌شود تا هزینه، Latency و وابستگی Availability به KMS/HSM در
   مسیر داغ قرار نگیرد. فاصلهٔ Checkpoint، سقف پنجرهٔ دست‌کاری کشف‌نشده است و در Q-44 تعیین می‌شود.
7. **قابلیت تعویض ارائه‌دهنده.** دامنه فقط Portهای `CheckpointSigner` و `ImmutableArchive` را می‌شناسد. انتخاب AWS، Azure،
   Google Cloud یا HSM خودمیزبان یک تصمیم استقرار است و نباید منطق دامنه یا Format شواهد را تغییر دهد.

## کنترل‌های اجباری استقرار

- جداسازی وظایف: هیچ هویت انسانی یا Workload واحدی هم‌زمان اختیار نوشتن Audit DB، مدیریت کلید و کاهش/حذف Retention ندارد.
- MFA مقاوم در برابر Phishing برای مدیران امنیتی، Credential کوتاه‌عمر و Least Privilege.
- Key Rotation بدون از دست‌دادن قابلیت Verify تاریخی؛ Public Key و Metadata نسخه‌ها باید فراتر از عمر کلید امضاکننده نگه داشته شود.
- Backup تغییرناپذیر و آزمون دوره‌ای Restore؛ WORM جای Backup و Disaster Recovery را نمی‌گیرد.
- Alert برای عقب‌افتادن Checkpoint، شکست امضا، Divergence، تغییر Policy/Retention، تلاش حذف و Key Disable/Scheduled Deletion.
- آزمون حمله: DBA مخرب، Credential سرویس سرقت‌شده، Replay، حذف/جابه‌جایی Manifest، Rotation و بازیابی پس از قطعی.

## پیامدها و محدودیت‌ها

| پیامد                                | نحوهٔ کنترل                                                              |
| ------------------------------------ | ------------------------------------------------------------------------ |
| هزینه KMS/HSM و WORM                 | امضای دسته‌ای؛ HSM اختصاصی فقط اگر مدل تهدید یا الزام قراردادی ایجاب کند |
| وابستگی به ارائه‌دهنده               | Port مستقل و Format استاندارد/نسخه‌دار؛ Adapter استقراری                 |
| عدم امکان حذف پیش از پایان Retention | سیاست Retention و Legal Hold پیش از فعال‌سازی Production تصویب شود       |
| پنجرهٔ بین دو Checkpoint             | SLO و Alert برای Anchor Lag؛ مقدار نهایی در Q-44                         |
| رشد داده و الزامات حریم خصوصی        | ذخیرهٔ Hash و Metadata حداقلی خارج از DB، نه Payload حساس                |
| اختلال KMS/WORM                      | Queue بادوام، Retry محدود و وضعیت صریح `UNANCHORED`؛ بدون جعل `VERIFIED` |

این معماری دست‌کاری را **بسیار مقاوم‌تر و مستقلاً قابل‌اثبات** می‌کند، اما حقیقت داده‌ای را که از ابتدا دروغ ثبت شده تضمین نمی‌کند و
در برابر مهاجمی که همهٔ مرزهای مستقل و فرایندهای انسانی را هم‌زمان تصاحب کرده باشد تضمین مطلق نمی‌دهد.

## Alternatives

1. **ادامهٔ Hash Chain داخلی:** کم‌هزینه، اما در برابر DBA/Superuser مستقل نیست — رد شد برای Production با اطمینان بالا.
2. **امضای هر رکورد:** هزینه و Latency زیاد و وابستگی مسیر داغ به KMS/HSM — رد شد.
3. **فقط WORM بدون امضا:** تغییرپذیری Storage را محدود می‌کند، ولی منشأ و اصالت Cryptographic Manifest را ثابت نمی‌کند — ناکافی.
4. **فقط KMS/HSM بدون WORM:** اصالت Checkpoint را می‌دهد، ولی حذف کامل Checkpointها و شواهد را به‌اندازهٔ کافی سخت نمی‌کند — ناکافی.

## Rollout و معیار پذیرش

این ADR عمداً Implementation یا Story Point اعطا نمی‌کند. پس از پاسخ Q-44، کار باید به Storyهای مستقل برای Format/Verifier،
Signer، Archive، IAM/Separation of Duties، عملیات/Restore و آزمون امنیتی شکسته شود. فعال‌سازی به‌ترتیب Shadow Checkpoint،
اعتبارسنجی Read-only، WORM Retention و در پایان Alert اجباری انجام می‌شود؛ Rollback هرگز Object قفل‌شده را حذف نمی‌کند.

قابلیت زمانی Done است که آزمون واقعی نشان دهد مهاجم دارای اختیار Audit DB نمی‌تواند تاریخ را بدون Divergence نسبت به یک
Checkpoint امضاشده و قفل‌شده بازنویسی کند، و اختلال KMS/WORM نیز دادهٔ Audit را از بین نمی‌برد یا به‌دروغ `VERIFIED` نمی‌سازد.
