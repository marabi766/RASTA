# ADR-059: نگهداشت توکن در پورتال — نشست سمت سرور، نه توکن در مرورگر

- **وضعیت:** Accepted
- **تاریخ:** 2026-09-21
- **تصمیم‌گیرنده:** معماری پلتفرم (C0)، زیر اختیار صریح مدیر پروژه برای تصمیم‌های امنیت و کیفیت
- **اهمیت:** سطح حملهٔ نشست کاربر، مسیر هر درخواست مرورگر، و اینکه XSS چه چیزی را می‌تواند بدزدد
- **مرتبط:** ADR-009 (API Gateway)، ADR-020 (توکن داخلی)، ADR-035 (مستأجر داخل امضا)، ADR-058 (جای پورتال)،
  `docs/16-ui-architecture.md § ۱۶٫۱` و `§ ۱۶٫۱۱`، `docs/09-security-architecture.md`
- **Story:** `EXP-002`

---

## Context

### سند معماری در این نقطه با خودش نمی‌خواند

دو بند، هر دو الزام‌آور، و با هم شدنی نیستند:

| بند       | چه می‌گوید                                                                                           |
| --------- | ---------------------------------------------------------------------------------------------------- |
| `§ ۱۶٫۱`  | احراز هویت با `oidc-client-ts` — یعنی کتابخانه‌ای که **در مرورگر** اجرا می‌شود                       |
| `§ ۱۶٫۱۱` | «Access Token فقط در حافظه» و «Refresh Token در Cookie با `HttpOnly` + `Secure` + `SameSite=Strict`» |

**یک کتابخانهٔ جاوااسکریپتِ مرورگر نمی‌تواند `HttpOnly` Cookie بنویسد.** معنای `HttpOnly` دقیقاً همین است: جاوااسکریپت
آن را نمی‌بیند و نمی‌نویسد. فقط سرور، با سرتیتر `Set-Cookie`، می‌تواند. پس اگر `oidc-client-ts` در مرورگر جریان را
اجرا کند، Refresh Token ناگزیر جایی می‌نشیند که جاوااسکریپت می‌بیند — `sessionStorage`، `localStorage` یا یک Cookie
معمولی — و آن دقیقاً همان چیزی است که بند دوم منع کرده.

این تناقض باید یک‌بار و با دلیل بسته شود، نه با انتخاب ضمنی اولین چیزی که کار کند. سابقهٔ این کار در همین مخزن هست:
`ADR-054` هم یک تناقض در سند معماری پیدا کرد و با ADR حلش کرد، نه با حدس.

### آنچه از قبل هست و این تصمیم نباید خرابش کند

- `ADR-058 § ۳`: **مرورگر فقط با API Gateway حرف می‌زند.** هر کنترل عرضی — تأیید JWT، حل مستأجر، Rate Limit،
  Correlation، Circuit Breaker — آن‌جا زندگی می‌کند.
- Keycloak در Realm توسعه یک Client عمومی به نام `rasta-web` دارد، با Standard Flow و `redirectUris` روی
  `http://localhost:3200/*`.
- `tests/e2e` از همان Client با Direct Access Grant توکن می‌گیرد. آن مسیر نباید بشکند.

### تهدید واقعی، نه تهدید تئوریک

یک آسیب‌پذیری XSS در پورتال — یک وابستگی آلوده، یک `dangerouslySetInnerHTML` فراموش‌شده، یک نام دارایی که جایی
Escape نشده — در مدل «توکن در مرورگر» یعنی مهاجم **توکن را برمی‌دارد و می‌برد**. با Refresh Token، آن دسترسی روزها
زنده می‌ماند و از هر دستگاهی قابل استفاده است. این پلتفرم چندمستأجری است و همان توکن، کلید دادهٔ یک سازمان کامل است.

## Decision

### ۱. نشست سمت سرور است؛ مرورگر هیچ توکنی نمی‌بیند

جریان `Authorization Code + PKCE` را **Route Handler های Next.js** اجرا می‌کنند، نه کد مرورگر:

```
مرورگر → /auth/login      → ریدایرکت به Keycloak (PKCE، state، nonce)
مرورگر → /auth/callback   → سرور کد را با Keycloak تعویض می‌کند
سرور   → Set-Cookie       → نشست مهرشده: HttpOnly + Secure + SameSite=Strict
مرورگر → صفحه/اکشن        → سرور توکن را از نشست برمی‌دارد و به Gateway می‌زند
```

هیچ Access Token و هیچ Refresh Token ای به جاوااسکریپت مرورگر نمی‌رسد. یک XSS در پورتال می‌تواند از طرف کاربرِ
حاضر درخواست بزند — که با هر مدلی می‌تواند — ولی **چیزی برای بردن ندارد**: نه توکنی برای استفاده از دستگاه دیگر، نه
دسترسی‌ای که پس از بستن مرورگر زنده بماند.

این هر دو بند `§ ۱۶٫۱۱` را واقعاً برآورده می‌کند، به‌جای برآورده‌کردن نیمی از آن‌ها.

### ۲. انحراف صریح از `§ ۱۶٫۱`: `oidc-client-ts` استفاده نمی‌شود

آن کتابخانه برای جریان در مرورگر است و اینجا جریانی در مرورگر وجود ندارد.

جریان سمت سرور هم با یک کتابخانهٔ تازه پیاده نمی‌شود. چهار قدمِ لازم — ساخت URL مجوز با PKCE، تعویض کد در
Endpoint توکن، تأیید ID Token با JWKS، و تمدید با Refresh Token — با `fetch` و `jose` نوشته می‌شوند. `jose`
از قبل در `@rasta/nest-common` هست و همان چیزی است که Gateway با آن JWT را تأیید می‌کند، پس وابستگی تازه‌ای به
مخزن اضافه نمی‌شود. هر چهار قدم تست خودش را دارد.

**این انحراف از یک ردیف جدول است، نه از یک قاعدهٔ امنیتی.** جدول `§ ۱۶٫۱` یک انتخاب ابزار را ثبت می‌کند؛
`§ ۱۶٫۱۱` یک قاعده را. وقتی این دو با هم نمی‌خوانند، قاعده می‌ماند و ابزار عوض می‌شود.

### ۳. مرورگر همچنان فقط با Gateway حرف می‌زند — از راه سروری که پشتش ایستاده

`ADR-058 § ۳` دست‌نخورده می‌ماند، و این بند مهم‌ترین قید این تصمیم است:

- **هیچ کد مرورگری به هیچ پورت سرویسی وصل نمی‌شود.** همچنان.
- کد سمت سرور پورتال **فقط** به `NEXT_SERVER_API_GATEWAY_URL` می‌زند و به هیچ آدرس دیگری. یک تست این را نگه می‌دارد،
  نه یک جملهٔ README.
- پورتال **هیچ منطق دامنه‌ای ندارد**: نه مجوزدهی، نه قاعدهٔ کسب‌وکار، نه دسترسی مستقیم به پایگاه داده. کاری که
  می‌کند حمل نشست و فراخوانی Gateway است. هر تصمیم مجوزدهی همان‌جا و در سرویس مقصد گرفته می‌شود
  (`docs/16 § ۱۶٫۱۱`: «پنهان کردن یک دکمه در UI کنترل امنیتی نیست»).

### ۴. Cookie نشست: چه داخلش است و چه نیست

یک Cookie، مهرشده با `AES-256-GCM` و کلیدی که فقط از محیط می‌آید:

| داخلش هست                      | چرا                                                   |
| ------------------------------ | ----------------------------------------------------- |
| Refresh Token                  | تنها راه تمدید بدون فرستادن دوبارهٔ کاربر به Keycloak |
| Access Token و زمان انقضایش    | تا هر درخواست یک رفت‌وبرگشت تازه به Keycloak نباشد    |
| `sub`، نام کاربری، سازمان فعال | برای نمایش، و برای اینکه سرور بداند نشست کیست         |

| داخلش نیست                   | چرا                                                                                                                                   |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------- |
| نقش‌ها به‌عنوان مرجع مجوزدهی | نقش‌ها داخل خود JWT هستند و Gateway و سرویس آن‌ها را می‌خواند؛ یک کپی در Cookie، نسخهٔ دومی است که می‌تواند با واقعیت اختلاف پیدا کند |
| هر دادهٔ دامنه‌ای            | Cookie روی هر درخواست حمل می‌شود؛ اندازه و نشت، هر دو                                                                                 |

**رمزگذاری، نه فقط امضا.** یک Cookie صرفاً امضاشده، Refresh Token را برای هر کسی که فایل Cookie را ببیند خواناست.

### ۵. CSRF: `SameSite=Strict` به‌علاوهٔ یک توکن

`SameSite=Strict` تقریباً همه‌چیز را می‌گیرد، ولی «تقریباً» برای نوشتن کافی نیست. هر Route Handler ای که وضعیت را
عوض می‌کند، یک توکن CSRF می‌خواهد که در همان نشست نشسته و فرم آن را پس می‌دهد. خواندن‌ها لازمش ندارند.

### ۶. نقش در UI فقط تجربهٔ کاربری است

Route Guard و پنهان‌کردن دکمه، فقط برای این است که کاربر به صفحه‌ای نرود که برایش خطا می‌گیرد. **هیچ‌کدام کنترل
امنیتی نیستند** و هیچ‌جا به‌عنوان کنترل شمرده نمی‌شوند. سرور مستقلاً و همیشه دوباره تصمیم می‌گیرد.

## Alternatives

**`oidc-client-ts` در مرورگر، توکن در حافظهٔ جاوااسکریپت.** همان چیزی که `§ ۱۶٫۱` نام می‌برد. رد شد: نیمهٔ دوم
`§ ۱۶٫۱۱` را نمی‌تواند برآورده کند — Refresh Token ناگزیر جایی می‌نشیند که جاوااسکریپت می‌بیند. به‌علاوه، «توکن فقط
در حافظه» با Server Component های Next.js نمی‌خواند: صفحه‌ای که روی سرور Render می‌شود به توکنی که در حافظهٔ مرورگر
است دسترسی ندارد، و نتیجه‌اش این است که هر صفحه عملاً سمت کلاینت Fetch کند و SSR — یعنی دلیل انتخاب Next.js در
`§ ۱۶٫۱` — از دست برود.

**Cookie نشست با Session Store سمت سرور (Redis).** رد شد **برای امروز**، نه برای همیشه: یک وابستگی حالت‌دار تازه به
مسیر ورود اضافه می‌کند و Redis روی این پلتفرم هنوز برای Rate Limit است. Cookie مهرشده همان تضمین‌ها را بدون آن
وابستگی می‌دهد. اگر ابطال فوری نشست لازم شود (`Q-21` درباره تفکیک نقش‌های مرکز مدیریت باز است)، این تصمیم همان‌جا
بازبینی می‌شود؛ مسیر مهاجرتش این است که محتوای Cookie با یک شناسهٔ نشست جایگزین شود و بقیهٔ این ADR دست نخورد.

**افزودن جریان OIDC به خود Gateway.** رد شد: Gateway امروز یک مسیریاب بدون حالت است و افزودن Cookie، نشست و
ریدایرکت به آن، یک مؤلفهٔ بی‌حالت را حالت‌دار می‌کند — و همان کنترلی که همهٔ سرویس‌ها به آن تکیه دارند.

## Consequences

### مثبت

- XSS در پورتال دیگر «سرقت نشست» نیست. چیزی برای بردن وجود ندارد.
- Server Component واقعاً کار می‌کند: سرور توکن دارد، پس صفحه می‌تواند داده‌اش را روی سرور بگیرد.
- هیچ توکنی در `localStorage` یا `sessionStorage` نیست — قابل اثبات با یک تست، نه با یک قول.

### منفی — و هیچ‌کدام کوچک نیست

- **پورتال حالا یک مؤلفهٔ سمت سرور است، نه یک Bundle ایستا.** استقرارش سرور Node می‌خواهد و `apps/web` باید
  روزی Dockerfile بگیرد. امروز ندارد (`ADR-058`).
- **یک کلید تازه در محیط.** `WEB_SESSION_SECRET` باید وجود داشته باشد و امن بماند؛ نبودنش **Boot را رد می‌کند**،
  چون نشستِ رمزنشده بدتر از نشستِ نبوده است.
- **ابطال فوری ممکن نیست.** یک نشست مهرشده تا انقضای خودش معتبر است. بالادست این را با عمر کوتاه Access Token
  محدود می‌کنیم، ولی «خروج از همه‌جا» امروز فوری نیست.
- **یک پرش شبکه بیشتر.** مرورگر → Next → Gateway → سرویس. در ازای آن، هیچ توکنی از مرورگر عبور نمی‌کند.
- **تمدید میان Replica ها هماهنگ می‌شود (افزودهٔ 2026-09-26، بازبینی Codex #113).** Realm چرخش Refresh Token را بدون
  استفادهٔ دوباره اجرا می‌کند (`revokeRefreshToken: true`، `refreshTokenMaxReuse: 0`) و پورتال دو Replica دارد
  (`docs/12` § ۱۲٫۴)؛ پس دو درخواست با یک Cookie نباید هر دو توکن را خرج کنند. هماهنگی از راه Redis پلتفرم است
  (`WEB_REDIS_URL`، `apps/web/src/server/refresh-coordinator.ts`): قفل با کلیدِ Hash توکن، برنده نتیجه را **مهرشده با
  `WEB_SESSION_SECRET`** و گره‌خورده به همان کلید برای مدتی کوتاه نگه می‌دارد، بقیه همان را می‌خوانند. Redis هرگز
  توکنی خوانا نگه نمی‌دارد. **ردِ تمدید هرگز Cookie را پاک نمی‌کند** — ممکن است Replica دیگری همین لحظه Cookie
  چرخیده را برگرداند؛ تنها Cookie ای که باز نشود یا از عمر مطلق گذشته باشد پاک می‌شود. بی‌Redis یا هنگام قطعی‌اش،
  تمدید بی‌هماهنگی پیش می‌رود و بدترین پیامد یک درخواستِ «خارج‌شده» است، نه خروج کاربر. `refreshTokenMaxReuse`
  دست‌نخورده ماند. **`WEB_REDIS_URL` در production الزامی است** (تصمیم PM، 2026-09-26): توپولوژی مستند دو Replica است و
  هماهنگی درون‌فرایندی آنجا جایگزین امنی نیست، پس سرور بی آن هنگام شروع با وضعیت ۱ خارج می‌شود
  (`apps/web/src/instrumentation.ts`)؛ در development و test اختیاری است، با هشدار.

## Compliance

- `docs/16 § ۱۶٫۱۱` — هر دو بند نگهداشت توکن، واقعاً برآورده.
- `docs/16 § ۱۶٫۱` — **انحراف ثبت‌شده**: جریان سمت سرور با `fetch` و `jose` به‌جای `oidc-client-ts` در مرورگر، با دلیل بالا.
- `ADR-058 § ۳` — دست‌نخورده، و برای نخستین بار با تست بسته شده.
- `AGENTS.md` S-09 — هیچ Secret و هیچ توکنی در Log، و هیچ‌کدام در `NEXT_PUBLIC_*`.
