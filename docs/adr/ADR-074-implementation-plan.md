# ADR-074 implementation plan — Staging روی rasta-dev

- **ADR:** [ADR-074](ADR-074-staging-on-a-single-host.md) · **Backlog:** RUN-002 (سپس RUN-003، RUN-004)
- **وضعیت:** طرح؛ هیچ PR ـِ این فهرست جز S0 شروع نشده است. دور ۲ (2026-10-27): گراف بسته شد، چرخه‌ی O-3 ↔ M-1 شکست، و
  S4، S6، S7، S8، S9 و S10 تقسیم شدند (نگاشت در ADR § «تغییرات r2»). دور ۳ (2026-10-28): پیکربندی پیش از اندازه‌گیری
  (O-8، S8p)، S7c برای فرمان‌های کپی‌پذیر، و جدول تولید/مصرف پارامترها که وارسی گراف آن را هم می‌سنجد (ADR § «تغییرات r3»).
- **قاعده‌ی اندازه** (`~/pm-board/pre-review-checklist.md`، «Size and stacking»): آن قاعده برای صفحه و فرمان نوشته شده است؛
  اینجا به این معنا خوانده می‌شود: **هر PR یک دغدغه‌ی استقرار، با حداکثر دو فرمان یا Artifact ـِ تازه**. PRی که بیشتر بخواهد،
  پیش از شروع تقسیم می‌شود. ماژول کتابخانه‌ای که فقط همان دو فرمان از آن می‌خوانند جدا شمرده نمی‌شود.
- **وابستگی بیرونی:** کار W#8 828 (ساخت و Scan ـِ تصویر روی Train و `main`) پیش از S3 ادغام شده باشد.

## ترتیب

چهار گام، به این ترتیب و نه جز آن:

1. **فاز ساخت (S1 تا S8b):** هیچ چیز روی میزبان اجرا نمی‌شود جز آزمون‌های یک‌بارمصرف.
2. **پیکربندی پیش از اندازه‌گیری (O-8 ← S8p):** مالک **همه‌ی** ورودی‌های نخستین `up` را با مقدار محافظه‌کارانه و کران‌دار
   تأیید می‌کند (ADR § ۳، جدول «پیکربندی پیش از اندازه‌گیری»: `R_host_0`، سقف‌های موقت و `H_max_0`، `k_0`، `R_max_0`،
   `G_window_0`، `grace_0`، زمان‌های Watchdog، `D_meta_0`) و S8p آن‌ها را در `bootstrap-params.json` ثبت می‌کند؛ `up` و Watchdog
   بی هر کدام رد می‌کنند. r2 فقط سقف‌های حافظه را پیش از فاز M داشت و بقیه را از خروجی خود فاز M می‌خواست.
3. **فاز M — اندازه‌گیری محدود:** نخستین `up` روی میزبان، فقط در پنجره‌ی انحصاری، زیر قفل و Watchdog، فقط با ورودی‌های S8p.
   خروجی: عددهای M-1 تا M-3، M-5، M-6 (و M-4 فقط اگر گزینه‌ی هم‌زمان خواسته شود). فاز M به O-3 نیاز **ندارد**: پیش‌فرض ADR
   (پنجره‌ی انحصاری) را اجرا می‌کند.
4. **S8m، تأیید O-3، سپس استقرار عادی (S8c به بعد).** O-3 روی عددهای فاز M (S8m) تصمیم می‌گیرد و فقط می‌تواند کران‌های O-8 را
   تنگ‌تر کند؛ هیچ استقرار عادی پیش از آن نیست.

```
فاز ساخت:  S0 → { S1, S1b, S2a → S2b → S3, S4a → { S4b, S5b, S6a, S6b }, S5a, S7a → S7c, S7b } → S8a → S8b
پیکربندی:  S8b + O-8 → S8p
فاز M:     S8p → [اندازه‌گیری] → S8m → O-3
استقرار:   S8m + O-3 → S8c → S9a؛  S8b → S8d؛  { S9a، S8d، O-1 } → S9b → S9c → { O-6 } → S10b؛  { S8c، S8d } → S10a
پذیرش:     { S9b، S9c، S10a، S10b، O-1، O-6 } → RUN-002
```

جدول «پیش‌نیاز» پایین منبع است و نمودار فقط خلاصه‌ی آن. **S1 و S1b پیش‌نیاز S8a اند**، پس هیچ `up` ـِ Staging — حتی در فاز M —
بی پیکربندی هم‌شکل Production و Listener ـِ مقید اجرا نمی‌شود؛ و **S8p (O-8) پیش‌نیاز فاز M است**، پس فاز M هیچ ورودی‌ای را
از خروجی خودش نمی‌خواهد.

## وارسی گراف (r2، گسترده در r3)

پیش از هر بازنگری این برنامه، جدول «PRها»، جدول «پارامترها» و جدول «گام‌هایی که مالک باید بردارد» با این قاعده‌ها وارسی
می‌شوند (اسکریپت خصوصی روی همین سه جدول، نتیجه و Mutantها در STATUS):

1. **بی چرخه:** ترتیب توپولوژیک وجود دارد.
2. **بسته:** هر گره جز S0 دست‌کم یک پیش‌نیاز دارد، و هر گره به «پذیرش RUN-002» می‌رسد (هیچ PR ـِ آویزان، مثل S1 ـِ دور ۱).
3. **پیش‌نیاز امنیتی پیش از اجرا:** هر PR که روی میزبان چیزی اجرا می‌کند (S8a به بعد و فاز M) به‌طور تراگذر به S1، S1b، S4b،
   S5b، S7a، S7b و S7c وابسته است.
4. **تصمیم مالک پیش از مصرف (r3: اجرایی):** هر سطر جدول «گام‌هایی که مالک باید بردارد» یک گره‌ی O-n با پیش‌نیازهای ستون «پس از»
   است؛ هر گره‌ی ستون «پیش از» باید O-n را **نیای تراگذر** داشته باشد. این ستون مستقل از ستون «پیش‌نیاز» ـِ جدول PRها خوانده
   می‌شود؛ پس حذف `O-4` از پیش‌نیاز S3 (Mutant ـِ بازبین) شکست می‌دهد.
5. **پارامتر پیش از مصرف (r3):** برای هر سطر جدول «پارامترها»، هر مصرف‌کننده باید تولیدکننده را نیای تراگذر داشته باشد؛ و
   هیچ گره‌ای پارامتری را مصرف نمی‌کند که تولیدکننده‌اش نوادگانِ خودش است (چرخه‌ی r2: فاز M ← `k`، `R_max` و مهلت‌ها از S8m).
6. **ورودی کامل فاز M:** هر ورودی ADR § ۳ که نخستین `up` می‌خواند (`R_host`، سقف‌ها و `H_max`، `k`، `R_max`، `G_window`،
   مهلت‌ها، زمان‌های Watchdog، `D_meta`) در جدول «پارامترها» سطری دارد که فاز M مصرف‌کننده‌اش است؛ نبود هر کدام = شکست.
