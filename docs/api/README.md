## فایل‌های OpenAPI

هر سرویس مشخصات OpenAPI خودش را تولید می‌کند و فایل تولیدشده **در Repository Commit
می‌شود**. CI بررسی می‌کند فایل Commit‌شده با کد همگام است — **انحراف = شکست Build**.

```
docs/api/
├── api-gateway.openapi.json      (تجمیع همه)
├── identity-service.openapi.json
├── organization-service.openapi.json
├── asset-service.openapi.json
└── ...
```

**چرا Commit می‌شوند؟** تا تغییر شکننده در Diff یک PR دیده شود، نه پس از استقرار در Production.

**استثنا — قرارداد طرح‌شده.** `construction-service.tender.planned.openapi.json` (CON-002) قرارداد **طراحی** است، نه رفتار امروز: با
کنترلر تولید نمی‌شود و آزمون همگامی (`document.spec.ts`، `openapi.int-spec.ts`) آن را نمی‌خواند. هر ردیف `x-step` دارد؛ وقتی PR آن گام
پیاده شد، همان مسیرها به `construction-service.openapi.json` تولیدشده منتقل و از فایل طرح حذف می‌شوند؛ با پایان CON-002 این فایل حذف می‌شود.
`procurement-service.planned.openapi.json` (COM-007، [ADR-070](../adr/ADR-070-procurement-service-boundary-and-lifecycle.md)) همین قاعده را دارد: سرویس هنوز
وجود ندارد، `x-step` شمارهٔ برش [برنامهٔ اجرا](../adr/ADR-070-implementation-plan.md) است و هر برش مسیرهایش را به فایل تولیدشدهٔ سرویس منتقل می‌کند.

## تولید

```bash
pnpm --filter @rasta/identity-service openapi:generate
pnpm --filter @rasta/organization-service openapi:generate
```

Identity publishes its complete document; organization's committed document stays scoped to
the procurement-thresholds read. Their `src/openapi/document.spec.ts` tests check generated bytes.
Asset and API gateway publish their documents at runtime only.

Error responses use the shared strict `ApiError` envelope. D-121 retains six explicit exceptions:
`GET /health/ready` and `GET /health/startup`, status **503**, in each of asset-service,
identity-service and organization-service. These orchestrator probes retain their health-status
bodies for tooling compatibility. Each 503 schema explicitly describes that body and also the
envelope a thrown exception can produce. Liveness failures use the envelope. Conformance tests
enumerate the six exceptions by service, path and status and validate real HTTP probe bodies.

The publisher supplies the envelope only where a route declares no error body: a typed refusal a
route declares (`publishedApiErrorSchema.extend({ details: … })`) is published unchanged, and a
declared error body that is not one resolvable JSON schema stops generation. `routeErrorProblems`
(FU-031) reads the routes the application really serves — not only the document: every real route
must be published (the gateway's proxy catch-all is the one listed exclusion), every published
operation must be served, every declared error body must survive publication, and each route is
sent one real request whose error answer is validated against that route's published schema.

## منبع Schema

همه Schemaها از Zod در `@rasta/contracts` می‌آیند و با `nestjs-zod` به OpenAPI تبدیل
می‌شوند. **یک تعریف، چهار مصرف:**

```
Zod Schema ──┬──► اعتبارسنجی زمان اجرا (Backend)
             ├──► نوع TypeScript (Backend + Frontend)
             ├──► مستند OpenAPI
             └──► اعتبارسنجی فرم (Frontend)
```

اگر فرم Frontend و API واگرا شوند، Build می‌شکند.

## قواعد تغییر

| تغییر                       | شکننده؟ | اقدام                                             |
| --------------------------- | ------- | ------------------------------------------------- |
| افزودن فیلد اختیاری به پاسخ | ❌      | همان نسخه                                         |
| افزودن Endpoint             | ❌      | همان نسخه                                         |
| افزودن مقدار Enum           | ⚠️      | همان نسخه؛ کلاینت باید مقدار ناشناخته را تحمل کند |
| حذف یا تغییر نام فیلد       | ✅      | نسخه جدید                                         |
| اجباری کردن فیلد اختیاری    | ✅      | نسخه جدید                                         |
| **تغییر معنای فیلد**        | ✅      | نسخه جدید — **خطرناک‌ترین نوع**                   |

نسخه `n-1` حداقل **۶ ماه** پس از انتشار `n` پشتیبانی می‌شود.
منسوخ‌سازی با Header `Deprecation` و `Sunset` (RFC 8594).

FU-120: shared Zod conversion publishes only string constraints checked before a value-changing step.
For example, `z.string().max(200).trim().min(1)` publishes `maxLength: 200`, with this description:
“Constraints after a value-changing step are omitted; validation applies them to the transformed value.”
Post-step lengths, patterns and formats remain enforced by the server. Overwrites (including trim,
lowercase and normalization), arbitrary transforms, preprocessors and unrecognized checks are barriers.
The registered `codePointLength` check is known to preserve its input. Opaque preprocessors publish an
open schema with the marker, including numeric preprocessors; their output type is not a raw-input
contract. Query-object preprocessors are refused rather than publishing their output fields.
The marker survives optional/nullable wrappers, descriptions and pipes. This intentionally describes
less than all validation; it never presents a post-transform check as a raw-input check.
