# حالت ارائه — اجرای نمایش روی یک لپ‌تاپ، بدون هیچ Backend

> شاخه: `demo/investor-preview`. این شاخه به `main` merge نمی‌شود — جهت Merge
> فقط از `main` به این شاخه است (آخرین بار: `main@d183ff3` با یک Merge Commit
> دوپرنتی، بدون Rebase و بدون بازنویسی تاریخچه)، که AUD-001 تا AUD-003 را وارد
> این شاخه کرد. سند خواهرِ این متن، [`investor-preview.md`](investor-preview.md)،
> اجرای **زنده** را پوشش می‌دهد. این یکی فقط حالت داده‌های نمایشی را پوشش می‌دهد.

این سند برای یک وضعیت مشخص نوشته شده است: شما یک لپ‌تاپ ویندوزی دارید، Node
نصب است، و **هیچ‌چیز دیگری در دسترس نیست** — نه Docker، نه پایگاه داده، نه
Keycloak، نه اینترنتِ قابل اتکا. در این حالت هم باید بتوانید محصول را نشان
دهید.

## ۰. دو حالت، و تفاوت واقعی‌شان

| حالت                           | داده از کجا می‌آید           | چه چیزی لازم است          | چه کسی مسئول است        |
| ------------------------------ | ---------------------------- | ------------------------- | ----------------------- |
| **الف — ارائه (`fixture`)**    | یک مجموعهٔ ثابتِ درون‌برنامه | فقط Node و pnpm           | خودِ ارائه‌دهنده        |
| **ب — زنده (`live`، پیش‌فرض)** | درگاه API واقعی              | تمام Stack، مهاجرت و Seed | مالکِ محیط یکپارچه‌سازی |

تفاوت، «داده‌ی بهتر» یا «داده‌ی بدتر» نیست. تفاوت این است که در حالت الف
**هیچ درخواستی از مرورگر خارج نمی‌شود**؛ آنچه روی صفحه است ساختگی است و صفحه
خودش، بالای هر نما، همین را می‌گوید.

> **حالت پیش‌فرض، «زنده» است.** حالت ارائه فقط با یک متغیر صریح روشن می‌شود و
> **هرگز** به‌دنبال یک خطای شبکه به‌طور خودکار فعال نمی‌شود. اگر درگاه پاسخ
> ندهد، صفحه خطا را نشان می‌دهد — نه دادهٔ ساختگی. این قاعده، آزمون دارد
> (`apps/web/src/lib/demo/demo-mode.spec.ts`).

## ۳. اجرا

یک دستور:

```bash
pnpm demo:web:fixture
```

سپس `http://localhost:3200/demo` را باز کنید.

**فایل `.env` لازم نیست.** اسکریپت، مقادیر عمومیِ لازم را خودش با نشانی‌های
`.invalid` پر می‌کند — دامنه‌ای که RFC 2606 رزرو کرده تا هرگز به هیچ میزبانی
resolve نشود. این مقادیر خوانده نمی‌شوند؛ فقط وجود دارند تا بررسی پیکربندی
چیزی معتبر برای تأیید داشته باشد.

### چرا یک اسکریپت، و نه یک متغیر درون‌خطی

`NEXT_PUBLIC_DEMO_DATA_MODE=fixture next dev` نحو bash است. روی ویندوز،
`cmd.exe` آن را نام یک فرمان می‌خواند و شکست می‌خورد و PowerShell آن را خطای
تجزیه می‌داند. اسکریپت (`scripts/run-demo-web.mjs`) متغیر را خودش تنظیم و
فرایند فرزند را اجرا می‌کند، پس در هر Shell کار می‌کند.

اسکریپت **فقط یک سرور توسعه را بالا می‌آورد**. هیچ Container، پایگاه داده،
مهاجرت یا Seed را لمس نمی‌کند، هیچ فرایندی را نمی‌کشد و هیچ پورتی را آزاد
نمی‌کند.

### ساخت نسخهٔ Production در همین حالت

```bash
node scripts/run-demo-web.mjs --mode fixture --command build
```

```bash
node scripts/run-demo-web.mjs --mode fixture --command start
```

مهم: `NEXT_PUBLIC_*` در زمان **Build** درون Bundle نوشته می‌شود. یعنی حالت
داده، خاصیتِ همان Build است، نه خاصیتِ اجرا. یک Build که در حالت `fixture`
ساخته شده، همیشه `fixture` می‌ماند — و برعکس.

## ۴. مسیر ارائه

| گام | چه چیزی                   | نشانی              |
| --- | ------------------------- | ------------------ |
| ۰   | نقطهٔ شروع ارائه          | `/demo`            |
| ۱   | روایت هدایت‌شده           | دکمهٔ «شروع روایت» |
| —   | متن ارائه به‌صورت یک صفحه | `/present`         |

`/demo` عمداً هیچ نگهبان نشستی ندارد: این نخستین چیزی است که ارائه‌دهنده باز
می‌کند و یک دیوار ورود در آنجا، هدف را از بین می‌برد.

روایت، دوازده ایستگاه دارد و ایستگاه آخر عمداً یک قابلیت **ساخته‌نشده** است.
عنوان، مقصد و نشان وضعیت هر ایستگاه از دفتر قابلیت‌ها
(`apps/web/src/lib/capabilities.ts`) خوانده می‌شود، نه از متن روایت — پس روایت
نمی‌تواند چیزی بگوید که داشبورد آن را انکار کند.

کلیدها:

| کلید            | کار                                 |
| --------------- | ----------------------------------- |
| `Esc`           | پایان روایت                         |
| `Tab` / `Enter` | حرکت میان کنترل‌ها                  |
| کلیدهای جهت     | **به صفحه تعلق دارند**، نه به روایت |

در هر گام، تمرکز (focus) روی عنوان همان گام قرار می‌گیرد؛ بدون این کار، پس از
تغییر مسیر هیچ اعلانی به کاربرِ صفحه‌خوان داده نمی‌شد.

اگر وسط ارائه صفحه را Reload کنید، روایت در همان گام می‌ماند (در
`sessionStorage`، فقط یک شمارهٔ گام — نه هیچ اعتبارنامه‌ای).

## ۵. آنچه در این حالت روی صفحه است

- یک نوار دائمی و **غیرقابل‌بستن** بالای هر صفحه:
  «حالت نمایشی — داده‌های این صفحه ساختگی‌اند و از سرویس‌های واقعی خوانده
  نمی‌شوند».
- یک نشان `FIXTURE` در ابزار ارائه.
- یک هویتِ **شبیه‌سازی‌شده**: نامش «کاربر نمایشی (شبیه‌سازی‌شده)» است، نشانی
  رایانامه‌اش روی `example.invalid` است و **هیچ Token ای ندارد** — چون هیچ
  درخواستی نمی‌فرستد، چیزی برای نگه‌داشتن، تازه‌کردن یا افشا شدن ندارد.
- داده‌های به‌هم‌پیوسته: همان گریدری که در پروندهٔ الکترونیکی «در تعمیر» است،
  در تابلوی ناوگان هم «غیرقابل اعزام» است، چون هر دو صفحه از یک مجموعه
  می‌خوانند.

## ۶. آنچه در این حالت **ممکن نیست**

- **هیچ نوشتنی.** منبع دادهٔ نمایشی هر روشی جز `GET` را — پیش از آنکه اصلاً
  مسیر را جست‌وجو کند — رد می‌کند.
- **هیچ درخواست شبکه‌ای.** کلاسِ منبع داده، هیچ ارجاعی به `fetch` ندارد؛ پس
  حتی به اشتباه هم نمی‌تواند به Backend برسد.
- **هیچ ورودی به Keycloak.** حالت نمایشی هرگز `oidc-client-ts` را بارگذاری
  نمی‌کند، پس نه iframe تمدید خاموش دارد و نه پرسش SSO. مسیر احراز هویت
  Production دست‌نخورده باقی می‌ماند.

## ۷. موتور سناریوی تعاملی (فقط حالت نمایشی)

یک ماشین‌حالت کوچک و قطعی، درون همین تب مرورگر، که می‌گذارد ارائه‌دهنده
بخش‌هایی از داستان — درخواست تعمیر، تأیید برآورد، انتخاب پیشنهاد تأمین‌کننده،
سفارش، اثر آن روی کیف پول، پیوست سند و اسکن آن — را **شبیه‌سازی** کند، بدون
اینکه هیچ‌کدام از آن‌ها واقعاً اتفاق بیفتد.

### این موتور چیست

- در `apps/web/src/lib/demo/scenario/` زندگی می‌کند: مدل وضعیت، Reducer،
  Invariant‌ها، ماندگاری در `sessionStorage`، و یک لایهٔ «مدل خواندنی» که
  `FixtureGatewayClient` از آن برای پاسخ‌دادن به `GET` استفاده می‌کند.
- کاملاً **فقط حالت نمایشی** است. در حالت زنده نه بار می‌شود، نه نمونه‌سازی.
  بسته‌بندی آن با `next/dynamic` از بقیهٔ برنامه جداست؛ تست
  `lib/demo/scenario/fixture-integration.spec.ts` ثابت می‌کند که هیچ فایل
  دیگری جز سه ماژول مجاز (خود `fixture-client.ts` و دو جزیرهٔ رابط کاربری) به
  آن دسترسی ندارد، و Build حالت زنده اصلاً هیچ Chunk ای با این کد تولید
  نمی‌کند.
- هیچ‌کدام از فرمان‌های آن (`MAINTENANCE_REQUEST_CREATED`،
  `PAYMENT_CAPTURED` و مانند آن‌ها) یک HTTP Method نیست. این‌ها رویدادهای
  شبیه‌سازی درونی‌اند؛ هرگز `fetch`، `GatewayClient` یا OIDC را فرا نمی‌خوانند.

### چه چیزی روی صفحه دیده می‌شود

روی `/demo`، در حالت نمایشی: نام سناریو، ایستگاه فعلی («سازمان انتخاب شد»، …)
و شمارهٔ بازبینی (Revision). هیچ JSON خامی نمایش داده نمی‌شود. دکمهٔ
«بازنشانی سناریوی نمایشی» در ابزار ارائه، پیش از بازنشانی واقعی یک گام تأیید
می‌خواهد و پس از آن یک پیام موفقیت با `aria-live="polite"` نشان می‌دهد.

### ماندگاری و بازنشانی

- در یک کلید مجزا و نسخه‌دار از `sessionStorage` ذخیره می‌شود
  (`rasta.demo.scenario.v1`) — هرگز در `localStorage`.
- بستن تب، آن را فراموش می‌کند؛ ناوبری و تازه‌سازی صفحه در همان تب آن را نگه
  می‌دارد.
- هر مقدار ذخیره‌شده پیش از استفاده در برابر همان Invariant‌های Reducer
  بررسی می‌شود. نسخهٔ طرحواره ناشناخته، حجم بیش از حد، JSON نامعتبر یا
  مقداری که یک Invariant را نقض کند — همگی بی‌صدا و امن به وضعیت اولیهٔ
  تازه برمی‌گردند؛ هیچ‌کدام خطایی روی صفحه نشان نمی‌دهند یا برنامه را
  می‌شکنند.
- دکمهٔ بازنشانی، وضعیت را دقیقاً به همان عکس فوری اولیه برمی‌گرداند و به
  `rasta.tour.state` (وضعیت روایت هدایت‌شده) **دست نمی‌زند** — دو کلید کاملاً
  مجزا در `sessionStorage`اند.

### این موتور چه چیزی اثبات **نمی‌کند**

هیچ تراکنش Backend ای رخ نمی‌دهد. وضعیت کیف پول، سفارش و سند، همگی درون
حافظهٔ مرورگر شبیه‌سازی می‌شوند؛ دفتر کل واقعی، سرویس بازار واقعی و سرویس سند
واقعی هیچ‌کدام فراخوانی نمی‌شوند. آنچه این موتور اثبات می‌کند، صحت خودِ
ماشین‌حالت است — نه اینکه Backend واقعی همین رفتار را دارد.

### دکمه‌های واقعی کنش (Roadmap Phase C)

فاز بعدی از فاز قبل، همین موتور را به یک داستان کامل و قابل‌اجرا برای
ارائه‌دهنده تبدیل کرد — بدون دست‌زدن به `lib/demo/scenario/` (جز یک رفع‌نقص
کوچک در خود لایهٔ «مدل خواندنی»، پایین‌تر توضیح داده شده). ده دکمهٔ واقعی،
روی شش صفحهٔ واقعی، همان ده فرمان بسته را صدا می‌زنند:

| گام | صفحه                 | دکمه                     | فرمان                           |
| --- | -------------------- | ------------------------ | ------------------------------- |
| ۱   | `/demo` (پانل مرکزی) | انتخاب نقش ارائه         | `PERSONA_SELECTED`              |
| ۲–۳ | `/assets/{id}`       | ثبت درخواست تعمیر        | `MAINTENANCE_REQUEST_CREATED`   |
| ۴   | `/maintenance/{id}`  | تأیید برآورد هزینه       | `MAINTENANCE_ESTIMATE_APPROVED` |
| ۵   | `/marketplace/{id}`  | انتخاب این پیشنهاد       | `SUPPLIER_OFFER_SELECTED`       |
| ۶   | `/marketplace/{id}`  | ثبت سفارش                | `ORDER_PLACED`                  |
| ۷   | `/orders/{id}`       | ثبت پرداخت شبیه‌سازی‌شده | `PAYMENT_CAPTURED`              |
| ۸   | `/documents`         | پیوست سند                | `DOCUMENT_ATTACHED`             |
| ۹   | `/documents`         | تکمیل اسکن سند           | `DOCUMENT_SCAN_COMPLETED`       |
| ۱۰  | `/audit`             | افزودن یادداشت بازرسی    | `AUDIT_RECORD_APPENDED`         |

هر دکمه در یک جزیرهٔ `next/dynamic` مستقل، پشت همان گیت `isFixtureMode`
زندگی می‌کند — دقیقاً الگوی کارت وضعیت و دکمهٔ بازنشانی در فاز قبل. هر
جزیره فقط برای شناسهٔ ثابت سناریو (دارایی، درخواست، کالا، سفارش) رندر
می‌شود، نه برای هر رکورد مشابه در مجموعهٔ نمایشی.

**قفل و توضیح پیش‌نیاز.** هر کنشی که پیش از موعدش در UI قابل‌کلیک باشد،
همان کنشی است که Reducer آن را `INVALID_TRANSITION` رد می‌کرد — پس هر
دکمه تا برآورده‌شدن پیش‌نیازش غیرفعال است و متن کوتاهی می‌گوید چرا («ابتدا
باید درخواست تعمیر … ثبت شود»). این یعنی یک کاربر عادی هرگز از راه کلیک
به یک رد شدن واقعی نمی‌رسد؛ مسیر پیام رد شدن (ترجمهٔ فارسی هر یک از شش
دلیل بستهٔ Reducer، نه متن انگلیسی توسعه‌دهندهٔ خودش) در
`ScenarioActionButton` به‌طور مستقل تست شده است.

**خواندن از مسیر واقعی.** هیچ دکمه‌ای وضعیت یک کامپوننت را مستقیماً
پچ نمی‌کند. صفحه‌هایی که بعد از یک کنش همان داده را دوباره نشان می‌دهند
(تأیید برآورد، سفارش، پرداخت، سند) با فراخوانی `resource.reload()` همان
صفحه، از همان مسیر `FixtureGatewayClient` → «مدل خواندنی» دوباره می‌خوانند
— نه از یک شیٔ محلی ساختگی.

**برچسب کنش، جدای برچسب صفحه.** نوار دائمی «حالت نمایشی» (بخش ۵) دربارهٔ
_داده_ است. هر پانل کنش، جدا از آن، برچسب «سناریوی نمایشی — این کنش فقط
داده‌های شبیه‌سازی‌شده را تغییر می‌دهد، نه Backend واقعی» را هم دارد — چون
یک دکمهٔ «ثبت سفارش» می‌تواند با نوار بالای صفحه اشتباه گرفته نشود، اما
هنوز شبیه یک کنش واقعی به نظر برسد.

**اسکن شبیه‌سازی‌شده، نتیجهٔ قطعی.** دکمهٔ تکمیل اسکن همیشه به نتیجهٔ
«پاک» می‌رسد — نه یک موتور ClamAV واقعی، نه یک تصادف. دیگر نتیجه‌های اسکن
(`INFECTED`, `FAILED`) فقط از راه Reducer و تست‌های آن اثبات‌شده‌اند، نه از
این UI.

**یادداشت حسابرسی، تکرارپذیر.** برخلاف بقیهٔ فرمان‌ها، `AUDIT_RECORD_APPENDED`
هیچ بررسی وضعیتی در Reducer ندارد — هر کلیک یک ردیف تازه به خط زمانی
حسابرسی همین سناریو اضافه می‌کند، زنده جلوی ارائه‌دهنده. این رکورد فقط
درون همین سناریوی نمایشی می‌ماند؛ هیچ پایگاه‌دادهٔ واقعی حسابرسی را
نمی‌نویسد و زنجیرهٔ Hash واقعی را تغییر نمی‌دهد — همان ادعای «مشهودِ
دست‌کاری، نه غیرقابل‌دست‌کاری» که بخش حسابرسی از پیش دارد.

**یک رفع‌نقص در لایهٔ مدل خواندنی.** `projectOrder` پیش از این فاز، یک
سفارش ثبت‌شده و پرداخت‌نشده را با مقدار لفظی `'CREATED'` نشان می‌داد —
مقداری که اصلاً عضو `ORDER_STATUSES` سرویس بازار نیست و باعث می‌شد نمودار
مسیر سفارش هشدار «خارج از مسیر عادی» نشان دهد. این مقدار به `'PENDING'`
(عضو واقعی `ORDER_HAPPY_PATH`) اصلاح شد — تنها تغییری که این فاز در خود
فایل‌های موتور (`lib/demo/scenario/`) ایجاد کرد.

### فازهای بعدی

این فاز عمداً به سمت صفحهٔ مدیریت اقدامات (Bulk)، یک ماشین‌حالت تازه یا
مجموعهٔ دادهٔ دوم نرفته — فقط UI روی همان ده فرمان، با همان شناسه‌های
سناریوی فاز قبل. فاز بعدی می‌تواند ظاهر این پانل‌ها را به سمت روایت
هدایت‌شده (Tour) متصل کند، یا مرحله‌های جدیدی (مثل لغو سفارش) به همان
Reducer اضافه کند — که در آن صورت، طبق قاعدهٔ «هرگز واقعیت کسب‌وکاری
اختراع نکن»، باید اول از سند محصول یا `docs/24-open-questions.md` تأیید
گرفت.

### اگر سناریو یک‌دفعه به ابتدا برگشت

یعنی مقدار ذخیره‌شده یکی از Invariant‌های بالا را نقض کرده یا نسخهٔ طرحوارهٔ
آن منطبق نبوده — رفتار عمدی است، نه یک خطا. وضعیت قبلی قابل بازیابی نیست
(چون هرگز معتبر نبوده)، اما خودِ ارائه از کار نمی‌افتد.

---

## ۸. بررسی پیش از ارائه

برای این حالت، بررسی زیرساخت بی‌معناست — زیرساختی در کار نیست. آنچه معنا دارد
این است که خودِ Build سالم باشد:

```bash
pnpm --filter @rasta/web test
```

```bash
pnpm demo:web:verify
```

دستور دوم، نسخهٔ Production را در حالت `fixture` می‌سازد و آن را در مرورگر
واقعی، روی سه اندازهٔ ۳۹۰ و ۷۶۸ و ۱۴۴۰ می‌آزماید: دیده‌شدن نوار افشا روی هر
صفحه، رفتار صفحه‌کلید و تمرکزِ روایت، و اینکه **هیچ درخواستی به هیچ میزبان
دیگری خارج نمی‌شود**.

> `pnpm demo:preflight` مربوط به حالت **زنده** است، نه این حالت. آن اسکریپت
> اتصال به درگاه و Keycloak را می‌سنجد و در اینجا به‌درستی شکست می‌خورد.

---

## ۹. حالت ب — اجرای زنده

اجرای زنده، **مالک** دارد: کسی که محیط یکپارچه‌سازی را می‌گرداند. این سند آن
را بالا نمی‌آورد و اسکریپت‌های اینجا هم هیچ‌کدام Docker یا پایگاه داده را لمس
نمی‌کنند.

آنچه سمت رابط کاربری لازم است:

```bash
cp .env.demo.example .env
```

سپس در `.env`:

| متغیر                            | مقدار                                           |
| -------------------------------- | ----------------------------------------------- |
| `NEXT_PUBLIC_DEMO_DATA_MODE`     | `live`                                          |
| `NEXT_PUBLIC_API_BASE_URL`       | نشانی درگاه API — مثلاً `http://localhost:3000` |
| `NEXT_PUBLIC_KEYCLOAK_URL`       | نشانی Keycloak — مثلاً `http://localhost:8080`  |
| `NEXT_PUBLIC_KEYCLOAK_REALM`     | `rasta`                                         |
| `NEXT_PUBLIC_KEYCLOAK_CLIENT_ID` | `rasta-web`                                     |

هر پنج متغیر `NEXT_PUBLIC_` هستند، یعنی به مرورگر فرستاده می‌شوند و **هیچ‌کدام
راز نیستند و نباید بشوند**. `.env.demo.example` عمداً فقط همین‌ها را دارد.

```bash
pnpm demo:web:live
```

اگر متغیرها تنظیم نشده باشند، اسکریپت با پیامی که دقیقاً می‌گوید کدام‌یک کم
است متوقف می‌شود — به‌جای آنکه بالا بیاید و به محیط اشتباهی وصل شود.

برای بالا آوردن Stack، مهاجرت، Seed و عیب‌یابی ویندوز:
[`investor-preview.md`](investor-preview.md).

## ۱۰. اگر چیزی درست نبود

### صفحه بالا می‌آید ولی نوار «حالت نمایشی» نیست

یعنی Build در حالت زنده ساخته شده است. متغیر در زمان Build خوانده می‌شود؛
سرور را متوقف کنید و دوباره با `pnpm demo:web:fixture` اجرا کنید.

### روی یک صفحه، خطای «برای این مسیر دادهٔ نمایشی تعریف نشده است»

یک مسیر واقعی که مجموعهٔ نمایشی پوشش نمی‌دهد. این عمداً یک خطای صریح است و نه
یک فهرست خالی: فهرست خالی از «سرویس واقعاً چیزی ندارد» قابل تشخیص نیست.
مسیر را به `apps/web/src/lib/demo/fixtures.ts` اضافه کنید.

### پورت ۳۲۰۰ اشغال است

یک نسخهٔ دیگر از همین پورتال در حال اجراست. آن را ببندید؛ اسکریپت عمداً هیچ
فرایندی را نمی‌کشد.

---

## ۱۱. آنچه این حالت **ادعا نمی‌کند**

- این حالت **هیچ چیزی را دربارهٔ Backend اثبات نمی‌کند**. داده‌ها ساختگی‌اند.
  آنچه اثبات می‌شود، رابط کاربری و قراردادهای آن است — و چون همان Schema های
  `@rasta/contracts` روی دادهٔ نمایشی هم اجرا می‌شوند، هر انحراف از قرارداد
  سرویس، همان‌جا شکست می‌خورد.
- هیچ عددی در این حالت، سنجه یا KPI واقعی نیست.
- هیچ نامی در این حالت به هیچ سازمان یا شخص واقعی اشاره ندارد.
