# حالت ارائه — اجرای نمایش روی یک لپ‌تاپ، بدون هیچ Backend

> شاخه: `demo/investor-preview`. این شاخه به `main` merge نمی‌شود — جهت Merge
> فقط از `main` به این شاخه است (آخرین بار: `main@d183ff3` با یک Merge Commit
> دوپرنتی، بدون Rebase و بدون بازنویسی تاریخچه)، که AUD-001 تا AUD-003 را وارد
> این شاخه کرد. سند خواهرِ این متن، [`investor-preview.md`](investor-preview.md)،
> اجرای **زنده** را پوشش می‌دهد. این یکی فقط حالت داده‌های نمایشی را پوشش می‌دهد.

این سند برای یک وضعیت مشخص نوشته شده است: شما یک لپ‌تاپ ویندوزی دارید، Node
نصب است، و **هیچ‌چیز دیگری در دسترس نیست** — نه Docker، نه پایگاه داده، نه
Keycloak، نه اینترنتِ قابل اتکا. در این حالت هم باید بتوانید محصول را نشان
دهید.

---

## ۰. دو حالت، و تفاوت واقعی‌شان

| حالت                           | داده از کجا می‌آید           | چه چیزی لازم است          | چه کسی مسئول است        |
| ------------------------------ | ---------------------------- | ------------------------- | ----------------------- |
| **الف — ارائه (`fixture`)**    | یک مجموعهٔ ثابتِ درون‌برنامه | فقط Node و pnpm           | خودِ ارائه‌دهنده        |
| **ب — زنده (`live`، پیش‌فرض)** | درگاه API واقعی              | تمام Stack، مهاجرت و Seed | مالکِ محیط یکپارچه‌سازی |

تفاوت، «داده‌ی بهتر» یا «داده‌ی بدتر» نیست. تفاوت این است که در حالت الف
**هیچ درخواستی از مرورگر خارج نمی‌شود**؛ آنچه روی صفحه است ساختگی است و صفحه
خودش، بالای هر نما، همین را می‌گوید.

> **حالت پیش‌فرض، «زنده» است.** حالت ارائه فقط با یک متغیر صریح روشن می‌شود و
> **هرگز** به‌دنبال یک خطای شبکه به‌طور خودکار فعال نمی‌شود. اگر درگاه پاسخ
> ندهد، صفحه خطا را نشان می‌دهد — نه دادهٔ ساختگی. این قاعده، آزمون دارد
> (`apps/web/src/lib/demo/demo-mode.spec.ts`).

## ۳. اجرا

یک دستور:

```bash
pnpm demo:web:fixture
```

سپس `http://localhost:3200/demo` را باز کنید.

**فایل `.env` لازم نیست.** اسکریپت، مقادیر عمومیِ لازم را خودش با نشانی‌های
`.invalid` پر می‌کند — دامنه‌ای که RFC 2606 رزرو کرده تا هرگز به هیچ میزبانی
resolve نشود. این مقادیر خوانده نمی‌شوند؛ فقط وجود دارند تا بررسی پیکربندی
چیزی معتبر برای تأیید داشته باشد.

### چرا یک اسکریپت، و نه یک متغیر درون‌خطی

`NEXT_PUBLIC_DEMO_DATA_MODE=fixture next dev` نحو bash است. روی ویندوز،
`cmd.exe` آن را نام یک فرمان می‌خواند و شکست می‌خورد و PowerShell آن را خطای
تجزیه می‌داند. اسکریپت (`scripts/run-demo-web.mjs`) متغیر را خودش تنظیم و
فرایند فرزند را اجرا می‌کند، پس در هر Shell کار می‌کند.

اسکریپت **فقط یک سرور توسعه را بالا می‌آورد**. هیچ Container، پایگاه داده،
مهاجرت یا Seed را لمس نمی‌کند، هیچ فرایندی را نمی‌کشد و هیچ پورتی را آزاد
نمی‌کند.

### ساخت نسخهٔ Production در همین حالت

```bash
node scripts/run-demo-web.mjs --mode fixture --command build
```

```bash
node scripts/run-demo-web.mjs --mode fixture --command start
```

مهم: `NEXT_PUBLIC_*` در زمان **Build** درون Bundle نوشته می‌شود. یعنی حالت
داده، خاصیتِ همان Build است، نه خاصیتِ اجرا. یک Build که در حالت `fixture`
ساخته شده، همیشه `fixture` می‌ماند — و برعکس.

## ۴. مسیر ارائه

| گام | چه چیزی                   | نشانی              |
| --- | ------------------------- | ------------------ |
| ۰   | نقطهٔ شروع ارائه          | `/demo`            |
| ۱   | روایت هدایت‌شده           | دکمهٔ «شروع روایت» |
| —   | متن ارائه به‌صورت یک صفحه | `/present`         |

`/demo` عمداً هیچ نگهبان نشستی ندارد: این نخستین چیزی است که ارائه‌دهنده باز
می‌کند و یک دیوار ورود در آنجا، هدف را از بین می‌برد.

روایت، دوازده ایستگاه دارد و ایستگاه آخر عمداً یک قابلیت **ساخته‌نشده** است.
عنوان، مقصد و نشان وضعیت هر ایستگاه از دفتر قابلیت‌ها
(`apps/web/src/lib/capabilities.ts`) خوانده می‌شود، نه از متن روایت — پس روایت
نمی‌تواند چیزی بگوید که داشبورد آن را انکار کند.

کلیدها:

| کلید            | کار                                 |
| --------------- | ----------------------------------- |
| `Esc`           | پایان روایت                         |
| `Tab` / `Enter` | حرکت میان کنترل‌ها                  |
| کلیدهای جهت     | **به صفحه تعلق دارند**، نه به روایت |

در هر گام، تمرکز (focus) روی عنوان همان گام قرار می‌گیرد؛ بدون این کار، پس از
تغییر مسیر هیچ اعلانی به کاربرِ صفحه‌خوان داده نمی‌شد.

اگر وسط ارائه صفحه را Reload کنید، روایت در همان گام می‌ماند (در
`sessionStorage`، فقط یک شمارهٔ گام — نه هیچ اعتبارنامه‌ای).

## ۵. آنچه در این حالت روی صفحه است

- یک نوار دائمی و **غیرقابل‌بستن** بالای هر صفحه:
  «حالت نمایشی — داده‌های این صفحه ساختگی‌اند و از سرویس‌های واقعی خوانده
  نمی‌شوند».
- یک نشان `FIXTURE` در ابزار ارائه.
- یک هویتِ **شبیه‌سازی‌شده**: نامش «کاربر نمایشی (شبیه‌سازی‌شده)» است، نشانی
  رایانامه‌اش روی `example.invalid` است و **هیچ Token ای ندارد** — چون هیچ
  درخواستی نمی‌فرستد، چیزی برای نگه‌داشتن، تازه‌کردن یا افشا شدن ندارد.
- داده‌های به‌هم‌پیوسته: همان گریدری که در پروندهٔ الکترونیکی «در تعمیر» است،
  در تابلوی ناوگان هم «غیرقابل اعزام» است، چون هر دو صفحه از یک مجموعه
  می‌خوانند.

## ۶. آنچه در این حالت **ممکن نیست**

- **هیچ نوشتنی.** منبع دادهٔ نمایشی هر روشی جز `GET` را — پیش از آنکه اصلاً
  مسیر را جست‌وجو کند — رد می‌کند.
- **هیچ درخواست شبکه‌ای.** کلاسِ منبع داده، هیچ ارجاعی به `fetch` ندارد؛ پس
  حتی به اشتباه هم نمی‌تواند به Backend برسد.
- **هیچ ورودی به Keycloak.** حالت نمایشی هرگز `oidc-client-ts` را بارگذاری
  نمی‌کند، پس نه iframe تمدید خاموش دارد و نه پرسش SSO. مسیر احراز هویت
  Production دست‌نخورده باقی می‌ماند.

## ۷. بررسی پیش از ارائه

برای این حالت، بررسی زیرساخت بی‌معناست — زیرساختی در کار نیست. آنچه معنا دارد
این است که خودِ Build سالم باشد:

```bash
pnpm --filter @rasta/web test
```

```bash
pnpm demo:web:verify
```

دستور دوم، نسخهٔ Production را در حالت `fixture` می‌سازد و آن را در مرورگر
واقعی، روی سه اندازهٔ ۳۹۰ و ۷۶۸ و ۱۴۴۰ می‌آزماید: دیده‌شدن نوار افشا روی هر
صفحه، رفتار صفحه‌کلید و تمرکزِ روایت، و اینکه **هیچ درخواستی به هیچ میزبان
دیگری خارج نمی‌شود**.

> `pnpm demo:preflight` مربوط به حالت **زنده** است، نه این حالت. آن اسکریپت
> اتصال به درگاه و Keycloak را می‌سنجد و در اینجا به‌درستی شکست می‌خورد.

## ۸. حالت ب — اجرای زنده

اجرای زنده، **مالک** دارد: کسی که محیط یکپارچه‌سازی را می‌گرداند. این سند آن
را بالا نمی‌آورد و اسکریپت‌های اینجا هم هیچ‌کدام Docker یا پایگاه داده را لمس
نمی‌کنند.

آنچه سمت رابط کاربری لازم است:

```bash
cp .env.demo.example .env
```

سپس در `.env`:

| متغیر                            | مقدار                                           |
| -------------------------------- | ----------------------------------------------- |
| `NEXT_PUBLIC_DEMO_DATA_MODE`     | `live`                                          |
| `NEXT_PUBLIC_API_BASE_URL`       | نشانی درگاه API — مثلاً `http://localhost:3000` |
| `NEXT_PUBLIC_KEYCLOAK_URL`       | نشانی Keycloak — مثلاً `http://localhost:8080`  |
| `NEXT_PUBLIC_KEYCLOAK_REALM`     | `rasta`                                         |
| `NEXT_PUBLIC_KEYCLOAK_CLIENT_ID` | `rasta-web`                                     |

هر پنج متغیر `NEXT_PUBLIC_` هستند، یعنی به مرورگر فرستاده می‌شوند و **هیچ‌کدام
راز نیستند و نباید بشوند**. `.env.demo.example` عمداً فقط همین‌ها را دارد.

```bash
pnpm demo:web:live
```

اگر متغیرها تنظیم نشده باشند، اسکریپت با پیامی که دقیقاً می‌گوید کدام‌یک کم
است متوقف می‌شود — به‌جای آنکه بالا بیاید و به محیط اشتباهی وصل شود.

برای بالا آوردن Stack، مهاجرت، Seed و عیب‌یابی ویندوز:
[`investor-preview.md`](investor-preview.md).

## ۹. اگر چیزی درست نبود

### صفحه بالا می‌آید ولی نوار «حالت نمایشی» نیست

یعنی Build در حالت زنده ساخته شده است. متغیر در زمان Build خوانده می‌شود؛
سرور را متوقف کنید و دوباره با `pnpm demo:web:fixture` اجرا کنید.

### روی یک صفحه، خطای «برای این مسیر دادهٔ نمایشی تعریف نشده است»

یک مسیر واقعی که مجموعهٔ نمایشی پوشش نمی‌دهد. این عمداً یک خطای صریح است و نه
یک فهرست خالی: فهرست خالی از «سرویس واقعاً چیزی ندارد» قابل تشخیص نیست.
مسیر را به `apps/web/src/lib/demo/fixtures.ts` اضافه کنید.

### پورت ۳۲۰۰ اشغال است

یک نسخهٔ دیگر از همین پورتال در حال اجراست. آن را ببندید؛ اسکریپت عمداً هیچ
فرایندی را نمی‌کشد.

## ۱۰. آنچه این حالت **ادعا نمی‌کند**

- این حالت **هیچ چیزی را دربارهٔ Backend اثبات نمی‌کند**. داده‌ها ساختگی‌اند.
  آنچه اثبات می‌شود، رابط کاربری و قراردادهای آن است — و چون همان Schema های
  `@rasta/contracts` روی دادهٔ نمایشی هم اجرا می‌شوند، هر انحراف از قرارداد
  سرویس، همان‌جا شکست می‌خورد.
- هیچ عددی در این حالت، سنجه یا KPI واقعی نیست.
- هیچ نامی در این حالت به هیچ سازمان یا شخص واقعی اشاره ندارد.
